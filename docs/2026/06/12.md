## [CloudWatch] Amazon CloudWatch Application Signals now supports infrastructure, logs, and traces context for faster troubleshooting

- **公開日**: 2026-06-12 (JST)
- **カテゴリ**: CloudWatch
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/cloudwatch-application-signals-supports infrastructure-logs-traces-context-for-faster troubleshooting/

### 概要

Amazon CloudWatch Application Signalsがアプリケーションマップにサービスのヘルスランキングとランタイムインジケータを追加し、サービス概要にインフラ、ログ、トレースのタブを導入しました。これにより、EKS/ECS/Lambda/EC2上の分散アプリケーションを1つの画面で迅速にトリアージして根本原因を特定できます。

### 変更内容・新機能の詳細

新機能は主に2点です。1) アプリケーションマップ上のサービスヘルスランキング：サービスノードが健康度順に並び、最も劣化したサービスをすばやく特定できます。ノード上にはAmazon EKS、Amazon ECS、AWS Lambda、Amazon EC2に対するランタイム指標（CPU、メモリ、コンテナ/インスタンス状態など）を示す可視化が表示されます。2) サービス概要ページの新タブ（Infrastructure、Logs、Traces）：Infrastructureタブは該当サービスの基盤となるコンピュート/ランタイム環境（クラスタ、タスク/ポッド、インスタンス、Lambda関数など）とその構成要素を列挙し、デフォルトでキュレーションされた監視指標（例：CPU、メモリ、ネットワーク、スケジューリング失敗など）への深いリンクを提供します。Logsタブはエラーを含むログスニペットをコンテキスト付きで表示し、Tracesタブは遅延や失敗トランザクションのトレース詳細にドリルダウンできます。これらにより、従来別ツールで行っていたインフラ・ログ・トレースの相関をApplication Signals内部で完結して実行できるようになります。機能はApplication Signalsがサポートされる全リージョンで利用可能です。詳細はCloudWatch Application SignalsのドキュメントおよびCloudWatchの料金ページを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: SRE、プラットフォーム/インフラエンジニア、アプリケーション開発者、オブザーバビリティ/運用チーム
- **利用シーン**: 異常なサービスの早期検出とトリアージ（例：本番でのレスポンス低下、エラー増加、デプロイ後の異常確認）
- **運用効果**: ツール間のコンテキスト切替を減らし、症状から根本原因解析までの時間を数時間から数分へ短縮
- **対応ワークロード**: Amazon EKS、Amazon ECS、AWS Lambda、Amazon EC2上で稼働するサービスに適用可能
- **可観測性向上**: インフラ指標、ログスニペット、トレースを同一画面で確認できるため、問題発見→切り分け→修復のフローが容易に

### 技術的な注意点

- **IAM権限**: Application Signalsおよび関連リソース（CloudWatch Logs、X-Ray、Container Insights、EC2/Lambda/ECS/EKSメトリクス）への読み取りアクセス権が必要。必要に応じて専用のIAMロール/ポリシーを用意してください。
- **リージョン制限**: Application SignalsがサポートされるAWSリージョンで利用可能。利用前に対象リージョンでのサポート状況を確認してください。
- **コスト**: ログ受信、トレース（X-Ray）利用、追加メトリクスやダッシュボード表示にはCloudWatchの通常料金が発生します。深いログ保持や高頻度メトリクス収集を行うとコストが増加します。
- **前提設定**: ランタイム指標やログ/トレースを表示するには、対象リソースでCloudWatchメトリクスの有効化、CloudWatch Logsの送信設定、トレース収集（X-Rayなど）の有効化が必要です。コンテナ環境ではContainer Insightsやメトリクスエージェントの導入が必要になる場合があります。
- **データ遅延/サンプリング**: メトリクス/ログ/トレースの収集・表示には遅延がある場合があります。トレースはサンプリングされることがあるため、完全な全件トレースではない点に留意してください。
- **連携リンク**: Infrastructureタブから他のCloudWatchコンソール（ダッシュボード、アラーム、ロググループ、X-Rayコンソール等）へ深いリンクが張られます。該当コンソールへの権限がないと遷移先で表示が制限されます。

## [Govcloud Us] Amazon Aurora now supports PostgreSQL major version 18

- **公開日**: 2026-06-12 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-aurora-postgresql-major-version-18/

### 概要

Amazon AuroraのPostgreSQL互換エディションがPostgreSQLメジャーバージョン18（開始は18.3）をサポートしました。クエリ性能改善や新拡張 pg_roaringbitmap のサポート、レプリケーションとアップグレードの運用改善が含まれます。

### 変更内容・新機能の詳細

主な変更点:
- サポートバージョン: Aurora PostgreSQL 18.3 を提供開始（商用リージョンおよびAWS GovCloud (US)にて利用可能）。
- pg_roaringbitmap拡張: 大規模な整数集合に対してメモリ効率が高く高速な集合演算（AND/OR/存在確認など）を提供。受信者セグメント抽出、タグベースフィルタ、権限制御のDB内処理が可能になり、アプリケーション側での追加処理を減らせます。CREATE EXTENSIONで有効化して使用します。
- B-tree skip scans: B-treeインデックスに対するスキップスキャンが導入され、一部のクエリでスキャン効率が向上し、インデックスのストレージおよびメンテナンス負荷を低減します。
- オプティマイザ統計の保持: メジャーアップグレード時にオプティマイザ統計が保持されるようになり、アップグレード直後から安定したクエリプランが得られやすくなります（統計再生成を待つ必要が減少）。
- 論理レプリケーションの並列大トランザクションストリーミング: 大きなトランザクションを並列でストリーム可能になり、レプリケーション遅延が低減、ダウンストリームの最新性が向上します。
- アップグレード手段: RDS Blue/Greenデプロイ、インプレースアップグレード、スナップショットからの復元など複数のパスをサポート。運用要件に合わせてダウンタイムとリスクを最小化できます。
- その他: Auroraの既存機能（自動バックアップ、最大15のリードレプリカ、サーバーレスオプション、マルチリージョン複製、AWSサービス連携等）との互換性は維持されています。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、DBチューニング担当者、アプリケーション開発者、SRE/運用チーム
- **利用シーン**: 大規模オーディエンスセグメンテーション、タグ/属性ベースの高速フィルタリング、権限判定をDB内で完結させたいアプリケーション、レプリケーション遅延を低減したいシステム
- **運用効果**: アップグレード直後からの安定したクエリ性能、インデックス管理コストの低減、レプリケーション遅延の改善により運用負荷とアプリケーションレイヤーの処理を削減可能

### 技術的な注意点

- **IAM権限**: CREATE EXTENSION や拡張機能の管理には適切なDB/OS権限が必要。RDSではDBクラスタ上の拡張許可とRDS管理ポリシーを確認してください。
- **リージョン制限**: Aurora PostgreSQL 18.3 は商用リージョンおよび AWS GovCloud (US) で提供。特定リージョンのロールアウト状況はドキュメントで要確認。
- **コスト**: バージョン変更自体に直接料金はないが、アップグレード作業（Blue/Greenデプロイでの追加リソース、スナップショット復元、一時的なリードレプリカ作成等）で追加コストが発生する可能性があります。
- **アップグレード影響**: インプレースアップグレードはダウンタイムが発生する場合あり。Blue/Greenはダウンタイムを最小化できるが追加リソースを要します。ロールバック手順（スナップショットや旧クラスタ保管）を準備してください。
- **拡張機能(pg_roaringbitmap)**: 拡張は手動で有効化（CREATE EXTENSION pg_roaringbitmap）が必要。機能やパフォーマンスの特性を事前に検証し、データ型や期待するワークロードでベンチマークを行ってください。
- **オプティマイザ統計**: メジャーアップグレードで統計が保持されるが、長期間のデータ分布変化や特定クエリについてはANALYZEの明示実行やpg_statisticの確認を推奨します。
- **論理レプリケーション**: 並列ストリーミングは遅延低減に寄与しますが、受信側の適切な設定（ワーカー数、applyプロセス）やネットワーク帯域の確認が必要です。
- **互換性テスト**: メジャーバージョンアップは拡張互換性やPostgres内部の挙動変化があるため、本番移行前にステージング環境でアプリケーションレベルの回帰テストを必ず行ってください。
- **バックアップ/スナップショット**: アップグレード前に完全なスナップショットを取得し、想定外の事象に備えて復元手順を検証してください。

## [Elastic Beanstalk] AWS Elastic Beanstalk console now integrates CloudWatch Logs in the Logs tab

- **公開日**: 2026-06-12 (JST)
- **カテゴリ**: Elastic Beanstalk
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/elastic-beanstalk-cloudwatch-logs/

### 概要

AWS Elastic Beanstalk コンソールの「Logs」タブに CloudWatch Logs の統合表示が追加され、環境に紐づくロググループやログストリームをコンソールから離れることなく参照・フィルタできるようになりました。

### 変更内容・新機能の詳細

Elastic Beanstalk の環境ページ内「Logs」タブで、環境がストリームしている CloudWatch Logs のロググループと、プレフィックス aws/elasticbeanstalk/* に一致するロググループを一覧表示します。ロググループを選択すると対応するログストリームを表示し、もっとも最近アクティブなストリームがデフォルトで選択されます。ログストリームのドロップダウンから別ストリームへの切替やフィルタリングが可能で、さらに「View in CloudWatch」ドロップダウンで該当ロググループ／ログストリーム／CloudWatch Logs Insights への直接リンクを開けます。これにより、ログの確認 → 詳細解析（Logs Insights）への遷移がスムーズになり、トラブルシューティングや運用上のログ確認手順が簡素化されます。機能はすべての Elastic Beanstalk プラットフォームブランチで、Elastic Beanstalk が利用可能な AWS 商用リージョンおよび AWS GovCloud (US) リージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: Elastic Beanstalk を利用する開発者、SRE、運用チーム
- **利用シーン**: デプロイ後のログ確認、異常検知時の初動調査、ログレベルの切替やフィルタでの問題切り分け
- **運用効果**: コンソール間の移動が不要になり調査時間を短縮。Logs Insights への遷移が容易なため、問題の深掘りやクエリ実行が速く行える

### 技術的な注意点

- **IAM権限**: CloudWatch Logs の参照に必要な権限（例: logs:DescribeLogGroups, logs:DescribeLogStreams, logs:GetLogEvents、Logs Insights を利用する場合は logs:StartQuery, logs:GetQueryResults）および Elastic Beanstalk 環境の閲覧権限が必要です
- **リージョン制限**: Elastic Beanstalk が提供されている AWS 商用リージョンおよび AWS GovCloud (US) で利用可能。詳細はリージョン一覧を確認してください
- **コスト**: 表示自体は追加料金を伴わないが、CloudWatch Logs のデータ取り込み・保管、Logs Insights のクエリ実行には通常の CloudWatch Logs 課金が発生します
- **ログの出所**: コンソールに表示されるのは環境からストリーミングされているロググループと aws/elasticbeanstalk/* プレフィックスに一致するグループのみで、環境で CloudWatch Logs へのストリーミング設定がされていないログは表示されません
- **暗号化/保持設定**: CloudWatch Logs 側のログ保持期間や暗号化設定は引き続き適用されます。必要に応じてロググループ設定を確認してください
- **UI挙動**: 最も最近アクティブなログストリームがデフォルト選択されるため、過去ログを遡る場合は手動でストリーム選択やフィルタが必要です

## [Mwaa] Amazon MWAA Serverless now supports Amazon EventBridge notifications

- **公開日**: 2026-06-12 (JST)
- **カテゴリ**: Mwaa
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-mwaa-serverless-eventbridge/

### 概要

Amazon MWAA Serverless がワークフローとタスクの状態変更イベントを Amazon EventBridge に送信できるようになり、Airflow ワークフローをトリガーにしたイベント駆動の自動化が容易になりました。

### 変更内容・新機能の詳細

本リリースにより、MWAA Serverless はワークフローと個別タスクの状態遷移（例: ワークフローの started, running, succeeded, failed／タスクの scheduled, succeeded, failed, up_for_retry など）を EventBridge に送出できるようになりました。従来は実行状況の監視にカスタムのポーリングや手動確認が必要でしたが、EventBridge によりルールでイベントをフィルタして Lambda、SNS、SQS、Step Functions、S3 などをターゲットに自動化や通知、監査ログ保存を実装できます。これにより、失敗時のアラートや上流ワークフロー成功時の下流パイプライン自動再起動、状態遷移のS3保存によるコンプライアンス対応などが容易になります。機能は Amazon MWAA Serverless が利用可能なすべてのリージョンで提供されます（対応リージョンはユーザーガイド参照）。詳細なイベントスキーマやサンプルは EventBridge のイベントリファレンスおよび MWAA Serverless の監視ドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: データエンジニア、プラットフォーム/SRE、運用チーム、Airflow を使う開発チーム
- **利用シーン**: 実行失敗時の即時アラート送信、上流ジョブ成功をトリガーにした下流ワークフロー起動、状態遷移の監査ログ保存、自動リトライ/自動修復ワークフローの開始
- **運用効果**: ポーリング不要でリアルタイムに状態変化を検知できるため、MTTR（復旧時間）の短縮、監査/コンプライアンス要件の自動化、運用負荷の低減が期待できる
- **開発効果**: イベントを契機にサーバーレス関数やワークフローを組み合わせることで設計が単純化され、依存関係の自動連携が容易になる

### 技術的な注意点

- **IAM権限**: EventBridge ルール作成やターゲット（Lambda/SNS/SQS/Step Functions/S3 等）に対する実行権限を適切に付与してください。イベントを受け取る側のリソースに必要な IAM ポリシー（Lambda 実行、SQS 送信など）を設定する必要があります。
- **イベントスキーマ**: 送信されるイベントのフィールド（ワークフロー名、実行ID、状態、タイムスタンプ、タスク名など）を事前に確認し、EventBridge ルールのパターンを作成してください。リファレンスのスキーマを参照してフィルタリングを設計します。
- **リージョン制限**: 機能は "Amazon MWAA Serverless が利用可能なリージョン" で提供されます。利用前に対象リージョンで MWAA Serverless の対応を確認してください（ドキュメント参照）。
- **コスト**: EventBridge のイベント受信・取り扱いに対する課金（PutEvents 等）およびルール数やターゲット実行（Lambda 呼び出し、S3 PUT、Step Functions 実行など）に伴うコストが発生します。大量イベント発生時のコスト影響を見積もってください。
- **運用注意**: 高頻度のイベント発行があるワークフローではルール設計やターゲットのスケーリング設計（Lambda 同時実行制限や SQS バックプレッシャー等）を検討してください。
