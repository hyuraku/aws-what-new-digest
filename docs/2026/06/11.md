## [General] Amazon Managed Service for Prometheus now supports Native Histograms

- **公開日**: 2026-06-11 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-managed-service-prometheus-native-histograms/

### 概要

Amazon Managed Service for Prometheus (AMP) が Prometheus ネイティブヒストグラムの取り込み、保存、クエリをサポートしました。これにより高解像度な分布計測を低い時系列カーディナリティで正確に取得できます。

### 変更内容・新機能の詳細

AMPはPrometheusネイティブヒストグラムをネイティブに受け入れ、保存、クエリできるようになりました。ネイティブヒストグラムは指数的（exponential）バケットを用いてデータに自動適応することで、事前にバケット境界を定義する必要を減らし、分布全体を単一の時系列で表現します（従来のクラシックヒストグラムで必要だった「バケットごとの時系列」を不要にする設計）。これによりアクティブ時系列数が大幅に削減され（記事の例：クラシックで20バケット＝22時系列必要だったものがネイティブヒストグラムでは1時系列に）、histogram_quantile() 等でのパーセンタイル（特にテールレイテンシ）の算出精度が向上します。導入は既存のクラシックヒストグラムと共存させて段階的に移行可能で、現在のモニタリングを中断することなく移行できます。課金は観測値がある「populated buckets」分のみをメーターするため、スパースな分布で空のバケット分を払う必要がなくなりコスト効率が改善します。機能はAMPが提供されているすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: DevOps、SRE、プラットフォーム/監視チーム、アプリ開発者
- **利用シーン**: レイテンシ／リクエスト時間などの分布計測、パーセンタイル（p50/p95/p99）算出、テールレイテンシ監視
- **運用効果**: 時系列カーディナリティ削減によるストレージ・クエリ負荷の低減とコスト最適化、より高精度なパーセンタイル算出による問題検出の向上

### 技術的な注意点

- **IAM権限**: AMP ワークスペースへの書き込みやクエリには該当ワークスペースへのアクセス権（workspace:Query/Put）やSigV4認証設定が必要です。Grafana/Prometheus 連携時のIAMロール設定を確認してください。
- **クライアント互換性**: ネイティブヒストグラムをエクスポートするには、使用するPrometheusクライアントライブラリや収集経路がネイティブヒストグラムのエクスポート（OpenMetrics/remote_writeでのネイティブ形式）をサポートしている必要があります。既存のクラシックヒストグラムとは互換性がありますが、クライアント側の対応が必要な場合があります。
- **リージョン制限**: AMPが提供されている全リージョンで利用可能とされていますが、リージョンごとのサービス可用性はAWSの最新情報を確認してください。
- **コスト**: 課金は「populated buckets（実際に観測値があるバケット）」のみに基づくため、スパース分布ではコスト削減が期待できます。ただし高頻度で大量データを記録する場合は従来と同様にストレージ/クエリ費用が発生します。詳細は料金ページで確認してください。
- **マイグレーション**: クラシックヒストグラムと共存可能なため段階的移行が可能ですが、ダッシュボードやアラート（ヒストグラムに依存するクエリ）を移行後に見直す必要があります。

## [General] Amazon Managed Service for Prometheus now supports out of order sample ingestion

- **公開日**: 2026-06-11 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/amazon-managed-service-prometheus-outoforder-ingestion/

### 概要

Amazon Managed Service for Prometheus (AMP) が時系列順序外（out-of-order）のサンプル受信をサポートし、ワークスペース単位でルール評価のオフセット時間を設定できるようになりました。これにより遅延到着のサンプルを取りこぼさず取り込み、アラート精度が向上します。

### 変更内容・新機能の詳細

主な変更点は以下です。
- out-of-order sample ingestion: ワークスペースごとにデフォルトで1分の時刻ずれ許容ウィンドウを持ち、到着順が前後するメトリクスサンプルを指定時間内であれば受け入れて取り込むようになりました。ウィンドウはワークスペース設定で変更可能（0に設定すると機能無効化して時系列順序外サンプルは破棄）です。
- workspace-level rule query offset: ルール（Ruler/Alerting）評価を実行する前に意図的な遅延（オフセット）を入れることで、遅れて到着するサンプルが取り込まれる時間を確保できます。即時評価だと評価時点でサンプルが未到着で正しい結果が得られない可能性があります。
- 可視化用メトリクス: CloudWatch に OutOfOrderIngestionRate と OutOfOrderSampleAge の2つの vended metrics が追加され、受信パターンや遅延の度合いを観測してウィンドウ／オフセット値のチューニングに利用できます。
- 利用可能リージョン: AMP が一般提供（GA）されているすべてのリージョンで利用可能。
- 設定方法: AWS 管理コンソール、API、CLI からワークスペースの out-of-order time window と ruler/rule query offset を設定可能。
技術的な背景: 分散コレクタ、バッチエクスポート、ネットワーク遅延がある環境では、メトリクスが厳密な時間順に到着しないことがあり、従来は遅れて到着したサンプルが破棄されることでメトリクスの欠損やアラート誤検知を招くことがありました。本機能により、所定の許容時間内の後着サンプルを取り込み、ルール評価側でオフセットを与えることでアラート結果の安定化が図れます。

### 影響範囲・利用シーン

- **対象ユーザー**: Prometheus/AMP を利用するアプリケーション運用者、SRE、監視担当者
- **利用シーン**: 分散エージェント（例: 多数のノードからのプル/プッシュ）、バッチでメトリクスをエクスポートするワークロード、ネットワーク遅延や再送が発生しやすい環境でのメトリクス収集
- **運用効果**: 遅延到着サンプルの取りこぼしが減少しメトリクスの完全性が向上、ルール評価／アラートの誤検出・漏れが減り信頼性が上がる
- **導入時の注意点**: out-of-order ウィンドウやルールオフセットの値によってアラート遅延（検知までの時間）が発生するため、検知遅延とデータ完全性のトレードオフを設計段階で評価する必要がある
- **運用監視**: OutOfOrderIngestionRate と OutOfOrderSampleAge を監視してウィンドウ／オフセットの最適化が可能

### 技術的な注意点

- **IAM権限**: ワークスペース設定を変更する権限（AMP ワークスペースの更新権限）を持つ IAM ポリシーが必要です。具体的なアクションは管理コンソール／API 操作に対応する権限を確認してください
- **リージョン制限**: AMP が GA のリージョンでは利用可能です。未対応リージョンでは利用不可です（該当リージョンの AMP サービス可否を事前確認）
- **コスト**: 新機能自体に直接の追加料金は明記されていませんが、CloudWatch の vended metrics を追加で取得・保存・アラーム化する場合は CloudWatch の課金対象になる可能性があります。取り込み増加に伴うストレージ/クエリ量の増加もコスト影響となり得ます
- **デフォルト設定**: out-of-order time window のデフォルトは 1 分。0 に設定すると時系列順序外サンプルは破棄される（機能無効）
- **設定方法**: AWS コンソール、AWS CLI、または AMP API を用いてワークスペース単位で out-of-order window と rule query offset を設定可能
- **メトリクス**: CloudWatch vended metrics は OutOfOrderIngestionRate（割合/率）と OutOfOrderSampleAge（サンプル遅延時間）で、これらを基にチューニングすることが推奨される
- **ルール運用**: ルールの query offset は評価遅延を導入するため、即時性を求めるアラートでは適切な妥協が必要。一般的には offset &gt;= out-of-order window を検討してください
- **互換性**: 既存の Prometheus クライアントやリモート書き込みフローには変更不要ですが、バッチ送信のタイミングやラベル付けポリシーは従来通り考慮してください

- https://docs.aws.amazon.com/prometheus/latest/userguide/

## [General] AWS announces AWS Workload Credentials Provider

- **公開日**: 2026-06-11 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/aws-workload-credentials-provider/

### 概要

AWS Workload Credentials Providerは、ACMからのエクスポート証明書とSecrets Managerのシークレットをクライアント側で自動配布・ローカルキャッシュする軽量プロバイダーです。Windows/Linux上で動作し、Apache/NGINXを含むAWS／非AWSワークロードへ自動展開を可能にします。

### 変更内容・新機能の詳細

このプロバイダーは、ACMでエクスポート可能な証明書のエクスポート、配備、サーバーの再読み込み挙動までを自動化する機能を提供します。従来はEventBridge等を使ったカスタム自動化が必要だった証明書更新の検出と展開を一本化し、CA/Bフォーラムによる公開証明書の寿命短縮に伴う頻繁なローテーション問題を緩和します。Secrets Managerのローカルキャッシュ機能は既存のAWS Secrets Manager Agentと後方互換性があり、同一プロバイダーでアプリケーションのシークレットを安全にキャッシュできます。設定は証明書ARNや出力ファイルパス、サーバーのリロード動作などを指定するだけで、プロバイダーがエクスポート／配置／更新を自動で行います。対応環境はWindowsおよびLinux、対応ウェブサーバーはApacheとNGINXです。プロジェクトはオープンソースとしてGitHubで公開されており、エクスポート可能なACM証明書とSecrets ManagerはすべてのAWSリージョンで利用可能とされています。

### 影響範囲・利用シーン

- **対象ユーザー**: TLS証明書を自動配布・更新したいアプリケーション開発者、SRE、運用チーム
- **利用シーン**: ACMで管理するエクスポート可能な証明書をサーバーに自動配備して証明書期限切れ障害を防止する場面
- **運用効果**: EventBridge等のカスタムスクリプトを減らし、renewal検知〜デプロイ〜サーバ再読込の一連処理を標準化することで運用負荷とヒューマンエラーを低減
- **対象ユーザー（Secrets）**: Secrets Managerでシークレットを配布・キャッシュしたいアプリケーション開発者、オンプレ／マルチクラウド環境の運用者
- **利用シーン（Secrets）**: アプリケーション側でSecrets Managerの値をローカルに安全にキャッシュし、API呼び出し頻度削減やレスポンスタイム改善を図る場面

### 技術的な注意点

- **必要IAM権限**: ACMのエクスポート（acm:ExportCertificate 等）とSecrets Managerの取得（secretsmanager:GetSecretValue 等）、および関連するKMS復号 (kms:Decrypt) 権限が必要です。EC2/ECSではインスタンスプロファイルやタスクロールの利用を推奨します。
- **証明書の種類**: ACMの "エクスポート可能" な証明書のみ対応します。パブリックに発行されたACMの証明書は通常エクスポート不可のため対象外です（プライベートCAで発行した証明書やインポート済み証明書が該当）。
- **OS/サーバー対応**: WindowsおよびLinuxで動作し、Apache・NGINXの自動リロード動作をサポートします。その他のサーバーはカスタムコマンドで対応可能か確認が必要です。
- **リージョン制限**: 記載された範囲では "全リージョンで利用可能" とされていますが、利用前に対象リージョンでACMのエクスポート機能およびSecrets Managerが利用可能か確認してください。
- **セキュリティ注意**: ローカルに配置される秘密鍵／シークレットのファイル保護（適切なファイル権限、OSレベルのアクセス制御）と監査が必要です。非AWS環境で利用する場合、AWS認証情報の保護方法（短期クレデンシャルやプロキシ経由の認証）を検討してください。
- **互換性/移行**: Secrets Manager Agentとの後方互換性があるため、既存のAgentからの移行が容易ですが、設定オプション（ファイルパス、更新ポリシー、リロード動作）を事前に検証してください。
- **コスト**: プロバイダー自体の追加料金は公表されていませんが、実行環境（EC2、オンプレのホスト）コスト、Secrets Manager / ACM API呼び出しやKMS利用による通常の課金が発生します。
- **ライセンス/OSS**: プロジェクトはオープンソースとしてGitHubで公開されています。利用前にリポジトリのライセンスとセキュリティガイドラインを確認してください。

## [ECS] Amazon ECS Managed Daemons now support inter-task visibility and communication

- **公開日**: 2026-06-11 (JST)
- **カテゴリ**: ECS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/ecs-managed-daemons-pid-ipc-modes/

### 概要

Amazon ECS の Managed Daemons がタスク間のプロセス可視化（PID 名前空間）と IPC 名称空間の共有をサポートしました。これにより、トレーシング／プロファイリング／セキュリティエージェント等をアプリケーションのサイドカーではなくデーモンタスクとして安全に展開できます。

### 変更内容・新機能の詳細

今回の更新で、ECS のデーモンタスク定義に pidMode と ipcMode の2つの設定が追加されました。各設定は既定値 "none"（分離）と "shared"（共有）を取り、pidMode を "shared" にするとデーモンタスクはインスタンス上の全プロセスを参照できるようになり、ipcMode を "shared" にすると他のコンテナと IPC 名前空間（例：System V IPC、POSIX メッセージキュー、ソケットペア等）を共有します。ECS の Managed Daemons は各 Managed Instance に対してちょうど1つ配置され、アプリケーションタスクより先に起動するため、プラットフォームチームがエージェントを独立して配備・更新して全ワークロードに一貫して適用できます。デーモンタスクはコンソール、AWS CLI、CloudFormation、SDK で登録可能で、対象のクラスターに ECS Managed Instances 用のキャパシティプロバイダーを関連付けてデーモンを作成／更新します。本機能は全リージョンで利用可能で、追加料金は発生しません。

### 影響範囲・利用シーン

- **対象ユーザー**: プラットフォーム／SRE チーム、セキュリティチーム、APM（アプリ性能管理）/トレーシング/プロファイリング担当者
- **利用シーン**: アプリケーションプロセスのトレース（例: eBPFベースのプロファイラ）、セキュリティエージェント（ランタイム監視、プロセス検査）、IPC を利用するメトリクス収集やロギングエージェントのデプロイ
- **運用効果**: サイドカー化によるタスク定義の分散管理を避け、エージェントの一元的な配備と更新が可能になり、全インスタンスに一貫して適用されるため運用負荷が低減される
- **コスト**: サービス自体に追加料金は無いが、エージェントのリソース使用（CPU/RAM/ディスク）によるインスタンスサイズや数の見直しが必要になる場合がある

### 技術的な注意点

- **対応環境**: 本機能は ECS Managed Instances（EC2 ベースのマネージドインスタンス）向けで、Fargate ではサポートされません
- **IAM権限**: デーモンタスクの登録・更新やキャパシティプロバイダーの関連付けには通常の ECS 操作権限が必要です。エージェントが AWS API を呼ぶ場合は追加の IAM ロール/ポリシーが必要です
- **セキュリティ**: pidMode/ipcMode を "shared" にするとデーモンタスクはインスタンス上の他プロセスや IPC リソースへアクセスできるため、最小権限の原則、コンテナの実行ユーザー、Linux セキュリティ機能（seccomp、capabilities、SELinux/AppArmor など）を活用してリスクを軽減してください
- **互換性**: 共有 PID/IPC 名称空間はカーネルとコンテナランタイムの機能に依存します。ECS 最適化 AMI や利用しているコンテナランタイムのバージョンで動作確認を行ってください
- **構成手順**: デーモンタスク定義で pidMode または ipcMode を "shared" に設定し、該当タスク定義でデーモンを登録、クラスタに ECS Managed Instances 用キャパシティプロバイダーを関連付けてデーモンを作成/更新します（Console/CLI/CloudFormation/SDK 利用可）
- **リージョン制限**: 記事によると全リージョンで利用可能です
- **コスト注意点**: 機能自体に追加料金はありませんが、エージェントが消費するリソースによりインスタンス構成の見直しが必要になる場合があります

- https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-managed-daemons.html

## [Ec2] Amazon EC2 M9g and M9gd general purpose instances are now available

- **公開日**: 2026-06-11 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/06/ec2-m9g-m9gd-instances-graviton5-processors-available

### 概要

Amazon EC2のM9gおよびM9gdインスタンス（AWS Graviton5搭載）が一般提供開始されました。汎用ワークロード向けに最大25%の計算性能向上を実現し、M9gdはローカルNVMeベースのSSDを提供します。

### 変更内容・新機能の詳細

M9g/M9gdはAWSがカスタム設計した第5世代プロセッサ「AWS Graviton5」を採用した汎用インスタンスで、アプリケーションサーバ、マイクロサービス、ゲーム、キャッシュ、コンテナに加え、リアルタイム推論やコード生成、マルチステップオーケストレーションなどのエージェント型AIユースケースにも適した性能を提供します。M9gdはインスタンスストアとしてNVMeベースのローカルSSDを備え、メディア処理、バッチ／ログ処理、一時的なキャッシュやスクラッチ領域が必要なアプリケーション向けに低レイテンシかつ高スループットのローカルストレージを提供します。性能面ではM8g（Graviton4）比で最大25%のコンピュート性能向上、データベースで最大30%高速化、Webアプリで最大35%高速化、機械学習で最大35%高速化が公称されています。基盤は第6世代AWS Nitro Systemで、今回から「Nitro Isolation Engine」による形式手法（formal verification）を用いた数学的保証により、顧客ワークロードと他テナントおよびAWSオペレータ間の分離を強化しています。提供リージョンは US East (N. Virginia, Ohio)、US West (Oregon)、EU (Frankfurt)で、購入方法はSavings Plans、On‑Demand、Spot、Dedicated Instances、Dedicated Hostsが利用可能です。なお、M9g/M9gdはARM64アーキテクチャ（AArch64）を採るため、OS/AMIやバイナリの互換性確認（ARM版AMIかマルチアーキテクチャコンテナの利用、ネイティブビルドや再コンパイル）が必要です。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドエンジニア、SRE、アプリケーション開発者、データベース運用者、機械学習エンジニア
- **利用シーン**: 一般的なアプリケーションサーバやマイクロサービス、コンテナ基盤、ゲームサーバ、キャッシュ、メディア処理やバッチ処理、エージェント型AI（リアルタイム推論・コード生成・マルチステップオーケストレーション）
- **運用効果**: 同世代（M8g/Graviton4）から移行することで計算性能とスループットが向上しコスト効率が改善される可能性が高い。M9gdを使うことでローカルNVMeの低遅延I/Oが活かせるワークロードで処理時間短縮やI/Oボトルネックの解消が期待できる

### 技術的な注意点

- **アーキテクチャ互換性**: Graviton5はARM64（AArch64）なので、使用するOS/AMI、ネイティブバイナリ、カスタムカーネルモジュールはARM対応である必要があります。x86バイナリは動作しません。
- **インスタンスストア（M9gd）**: M9gdのNVMeはインスタンスストア（エフェメラル）です。停止・終了でデータは消失するため永続化はEBSやS3を使用してください。
- **Nitro/セキュリティ**: 第6世代Nitro SystemとNitro Isolation Engineにより形式手法での分離保証が提供されますが、顧客側のセキュリティ対策（IAM・ネットワーク設計・暗号化）は引き続き必要です。
- **リージョン制限**: 現時点での公開リージョンは US East (N. Virginia, Ohio)、US West (Oregon)、EU (Frankfurt) のみ。日本（ap-northeast-1）などでは未対応のためリージョン制限に注意してください。
- **コスト**: 公称の性能向上はコスト効率改善につながりますが、実運用でのTCOはワークロード特性とスポット/Savings Plansなどの購入形態に依存します。価格差を確認のうえ性能あたりコストを評価してください。
- **購入方法**: On‑Demand、Savings Plans、Spot、Dedicated Instances、Dedicated Hostsで利用可能です。スポットや専用ホストの在庫/価格はリージョンや時期で変動します。
- **互換性検証**: 既存のアプリケーションは実運用前にARM向けビルドやマルチアーキコンテナで十分な動作検証（性能・依存ライブラリ・ネイティブ拡張）を行ってください。
- **インスタンスタイプ詳細**: 各インスタンスサイズごとのvCPU、メモリ、ローカルSSD容量、ネットワーク帯域はタイプ毎に異なります。移行時は用途に合わせてサイズを選定し、ベンチマークで確認してください。
- **サポートツール**: 多くのAWSの監視/プロファイリングツール（CloudWatch、X‑Rayなど）は対応しますが、パフォーマンスチューニング時はARM向けプロファイラやライブラリの互換性を確認する必要があります。
