## [RDS] Amazon RDS now supports backup configuration when restoring snapshots

- **公開日**: 2026-02-13 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/02/rds-aurora-backup-configuration-restoring-snapshots/

### 概要

Amazon RDS と Amazon Aurora のスナップショット復元時に、復元前および復元処理中にバックアップ保持期間（Backup retention period）と推奨バックアップウィンドウ（Preferred backup window）を確認・変更できるようになりました。復元後に個別に設定変更する必要がなくなります。

### 変更内容・新機能の詳細

従来、スナップショットから復元した DB インスタンス／クラスターはスナップショットに保存されたバックアップ設定（自動バックアップの保持日数や推奨バックアップウィンドウ）を継承し、これらを変更するには復元完了後に別途 Modify 操作が必要でした。本リリースでは次の機能が追加されています：
- スナップショットや自動バックアップのメタデータとして保存されている「バックアップ保持期間」と「推奨バックアップウィンドウ」を復元画面（および API/CLI）で事前に閲覧可能。
- 復元操作中に Backup retention period と Preferred backup window を指定・変更でき、復元完了後に追加で設定を変更する手間を排除。
これらは Amazon RDS（MySQL、PostgreSQL、MariaDB、Oracle、SQL Server、DB2）と Amazon Aurora（MySQL/PostgreSQL 互換）のすべてのサポートリージョン（商用リージョンおよび AWS GovCloud (US)）で利用可能で、AWS マネジメントコンソール、AWS CLI、AWS SDK から操作できます。追加料金は発生しません。設定変更により自動バックアップの保持日数が増えれば、保存されるバックアップデータ量（増分ストレージ）に応じたストレージ料金に影響する点に注意してください。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、クラウド運用チーム、SRE、DevOps
- **利用シーン**: スナップショットからの復元時に即座にバックアップポリシー（保持日数／バックアップ時間帯）を適用したい場合、例えば復元先の運用ポリシーや規制要件に合わせて復元と同時にバックアップ設定を整えたいシナリオ
- **運用効果**: 復元後に追加で Modify 操作を行う手間と誤設定リスクを削減。バックアップウィンドウを復元時に設定できるため、復元直後から望ましい時間帯に自動バックアップが実行されるようにできる
- **対象DBエンジン**: MySQL、PostgreSQL、MariaDB、Oracle、SQL Server、DB2、Aurora MySQL-Compatible、Aurora PostgreSQL-Compatible
- **可用性**: 全 AWS 商用リージョンおよび AWS GovCloud (US)（RDS/Aurora と各 DB エンジンがサポートされているリージョン）

### 技術的な注意点

- **IAM権限**: スナップショットの復元を実行するための権限（例: rds:RestoreDBInstanceFromDBSnapshot、rds:RestoreDBClusterFromSnapshot）およびスナップショット／インスタンス情報参照用の権限（rds:DescribeDBSnapshots、rds:DescribeDBInstances 等）が必要です。必要に応じて Modify 操作権限も検討してください。
- **リージョン制限**: 発表によれば全商用リージョンと AWS GovCloud (US) で利用可能ですが、リージョンごとの DB エンジン提供状況に依存します。対象リージョンで機能が有効か事前に確認してください。
- **コスト**: 機能自体の追加料金はありませんが、Backup retention period を増やすと自動バックアップの保存期間が延び、保存される増分データ量に応じたストレージ料金が増加する可能性があります。
- **対応方法**: AWS マネジメントコンソール、AWS CLI、AWS SDK から復元時にパラメータを指定して利用可能です。自動化する場合は使用する SDK/CLI の復元 API のパラメータを確認してください。
- **バックアップウィンドウ仕様**: RDS の推奨バックアップウィンドウは通常 30 分の時間帯で指定します。復元時に設定した時間帯がそのまま適用されます。
- **既存スナップショットのメタデータ**: スナップショットに保存されているバックアップ設定を表示できるため、復元前に現在の設定を確認して適切な値に変更できます。

## [General] Amazon Aurora DSQL adds support for identity columns and sequence objects 

- **公開日**: 2026-02-13 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-aurora-dsql-adds-identity-columns-sequence/

### 概要

Amazon Aurora DSQLがIDENTITY列とSEQUENCEオブジェクトのサポートを追加しました。これにより、データベース側で自動インクリメントの整数IDをネイティブに生成でき、PostgreSQLからの移行や新規ワークロードの開発が容易になります。

### 変更内容・新機能の詳細

今回の追加により、Aurora DSQL上でSQL標準のIDENTITY列（例: GENERATED {ALWAYS | BY DEFAULT} AS IDENTITY）やPostgreSQL互換のSEQUENCEオブジェクト（CREATE SEQUENCE、nextval(), currval(), setval()など）が利用可能になりました。開発者はテーブル定義に対してIDENTITYを設定したり、独立したシーケンスを作成してDEFAULT nextval('seq')を割り当てることで、自動採番の整数型ID（SMALLINT、INTEGER、BIGINT）を生成できます。シーケンスにはSTART、INCREMENT、MINVALUE、MAXVALUE、CACHE、CYCLEなどのパラメータを指定可能です。

技術的挙動として、IDENTITYは内部的にシーケンスを利用する点、シーケンス呼び出し（nextval）はトランザクションのロールバックで値が戻らない（値のギャップが発生する可能性がある）点、CACHE設定による性能向上とクラッシュ時のギャップ発生トレードオフがある点に注意が必要です。また、既存のPostgreSQLアプリケーションで使用されているSERIALや明示的なシーケンスは互換性の高い移行パスが用意されているため、ORMや既存SQLの変更を最小限に抑えられます。UUIDなど文字列ベースIDと比べて、整数IDはストレージ効率・インデックス効率に優れるため、注文番号やアカウントIDなど人間可読性のある短い識別子に適しています。

### 影響範囲・利用シーン

- **対象ユーザー**: PostgreSQLからAurora DSQLへ移行を検討している開発者／DBA、アプリでデータベース側の自動採番を使いたい開発チーム
- **利用シーン**: 注文番号、アカウントID、運用参照番号などのコンパクトな整数ID生成、既存アプリケーションのPostgreSQL互換機能の移行
- **運用効果**: アプリケーションやミドルウェアでのカスタムID生成ロジックを削減し、パフォーマンスとインデックス効率が向上。移行工数の削減と運用負荷の低減が期待できる

### 技術的な注意点

- **IAM権限**: データベース内のCREATE TABLE、CREATE SEQUENCE、ALTER TABLE、USAGE権限など、適切なDB権限が必要です（RDS/Auroraの管理IAMとは別のDBユーザー権限）。
- **リージョン制限**: 公開記事に特定リージョン制限の記載はありません。利用予定のリージョンで機能提供されているかAWSコンソール／リージョンのWhat's Newを確認してください。
- **コスト**: 機能自体で直接の追加料金は想定されませんが、シーケンスや追加カラムに伴うストレージ増加は発生します。高スループット設計ではインスタンスやストレージ要件が変わる可能性があります。
- **互換性**: PostgreSQLのSERIALや既存シーケンスからの移行が容易ですが、アプリケーションやORMの設定（IDENTITY対応、DDL生成ポリシー）を確認してください。
- **挙動注意点**: nextval()はトランザクションロールバックで戻らないため、ギャップが発生する可能性があります。CACHE設定は性能に寄与する一方でクラッシュ後のギャップリスクを高めます。
- **型設計**: 将来のID上限を考慮してINTEGERとBIGINTを適切に選定してください（BIGINTは64ビット）。
- **マイグレーション**: SERIALカラムをIDENTITYに置き換える場合、既存のシーケンス状態（last_valueやownership）を移行・同期する手順を踏む必要があります。

### 参考情報

- https://www.postgresql.org/docs/current/sql-createsequence.html
- https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-IDENTITY

## [Govcloud Us] Amazon Bedrock increases default quotas for Anthropic’s Claude Sonnet 4.5 model in AWS GovCloud (US)

- **公開日**: 2026-02-13 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.comabout-aws/whats-new/2026/02/amazon-bedrock-increases-default-sonnet-4.5-quotas-aws-govcloud-us

### 概要

Amazon Bedrockは、AWS GovCloud (US-West) と AWS GovCloud (US-East) におけるAnthropicのClaude Sonnet 4.5のデフォルトクォータを引き上げ、1分あたり5,000,000トークンおよび1分あたり1,000リクエストに変更しました。これにより商用リージョンと同等のスループットが規制環境でも利用可能になります。

### 変更内容・新機能の詳細

今回の変更でデフォルトのスロットル値が従来から25倍に増加しました（tokens/min: 5,000,000、requests/min: 1,000）。対象はAmazon Bedrock上のAnthropic Claude Sonnet 4.5で、対象リージョンはAWS GovCloud (US-West) と AWS GovCloud (US-East)です。Claude Sonnet 4.5は複雑なエージェント構築、コード生成、長期的なコンテキストを要するタスクに強みを持ち、レイテンシとコストのバランスを取りながら高スループット運用を想定したモデルです。トークン/分はモデル入力＋出力の合計トークン量に基づくレート制限であるため、長いコンテキストや大きなバッチはトークン消費が増えます。高負荷運用ではリクエストのバッチ化、ストリーミング出力（対応する場合）、ワーカーによる水平スケーリング、適切なリトライ／バックオフ実装、およびCloudWatch等による監視が推奨されます。なお、本設定はデフォルトのソフトクォータであり、更なる増枠が必要な場合はService QuotasまたはAWSサポート経由で申請可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: 政府機関・規制産業のクラウド開発者、MLエンジニア、SRE/運用チーム
- **利用シーン**: 高スループットが必要なAIエージェント、バッチコード生成、大規模ドキュメント要約や長期コンテキストを要する推論処理
- **運用効果**: デフォルトでのスループット増加によりスロットリングが減少し、スケール性能が向上。商用リージョンと同等の運用設計がGovCloudでも可能になるため、規制対応ワークロードの移行・本番運用が容易に
- **注意点（運用面）**: トークン消費量に応じたコスト増加と、リクエスト設計（バッチ化/ストリーミング/並列度）の見直しが必要

### 技術的な注意点

- **IAM権限**: BedrockやAnthropicモデル呼び出しに必要なIAMポリシー（bedrock:InvokeModel等）を確認してください。GovCloudは専用アカウントでの管理が必要です
- **リージョン制限**: 対象はAWS GovCloud (US-West) と AWS GovCloud (US-East) のみ。商用リージョンとはアカウント/コンプライアンスが分離されています
- **コスト**: トークンベースの課金によりスループット増加はコスト増を伴います。モデルごとの料金を確認し、コスト試算を実施してください
- **モニタリング/スロットリング**: CloudWatchでレイテンシ・エラー・スロットル指標を監視し、スロットリング時は指数バックオフとリトライを実装してください
- **トークン計算**: 1リクエストあたりの入力＋出力トークン合計がtokens/minに影響します。長文や大きなバッチはトークン制限を先に消費します
- **クォータ変更方法**: さらに高い上限が必要な場合はService QuotasコンソールまたはAWSサポートにて増枠申請を行ってください
- **互換性/性能**: 高並列実行時はネットワーク帯域やクライアント側リソース（接続数、スレッド数）がボトルネックになる可能性があるため負荷試験を推奨

## [RDS] Amazon RDS for PostgreSQL supports minor versions  18.2, 17.8, 16.12, 15.16 and 14.21

- **公開日**: 2026-02-13 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/02/rds-minor-version-18-2-17-8-16-12-15-16-14-21

### 概要

Amazon RDS for PostgreSQL が PostgreSQL の最新マイナーバージョン 18.2、17.8、16.12、15.16、14.21 をサポートしました。セキュリティ修正やバグフィックスに加え、クエリ性能を統合的に可視化する拡張 pg_stat_monitor が利用可能になっています。

### 変更内容・新機能の詳細

今回の更新で RDS for PostgreSQL は PostgreSQL の各メジャー系列に対して最新のマイナーバージョン（18.2、17.8、16.12、15.16、14.21）をサポートします。これらのマイナーバージョンには既知のセキュリティ脆弱性の修正やコミュニティによるバグフィックスが含まれており、アップグレードが推奨されています。新たに利用可能になった拡張 pg_stat_monitor により、クエリ実行のメトリクスを収集してクエリ性能の洞察を統一ビューで評価できます。アップグレードはスケジュール済みメンテナンスウィンドウ中に自動マイナーアップグレードで実行可能です。大量の DB を段階的に運用移行するには AWS Organizations の Upgrade Rollout Policy を使ってまず開発環境へ、その後本番へとフェーズ化する運用が推奨されます。ダウンタイムを最小化したい場合は Amazon RDS Blue/Green デプロイメント（物理レプリケーション利用）を利用してマイナーバージョンアップグレードを行えます。アップグレードや拡張の有効化は RDS 管理コンソール、AWS CLI から実施できます。詳細はリージョン毎の提供状況や料金ページを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: PostgreSQL を RDS 上で運用するデータベース管理者、SRE、アプリケーション開発チーム
- **利用シーン**: セキュリティ脆弱性の修正適用、バグ修正適用による安定性向上、クエリ性能の可視化・調査（pg_stat_monitor を用いたクエリ分析）
- **運用効果**: 自動マイナーアップグレードと Organizations のロールアウトで大規模環境の段階的な更新が可能。Blue/Green によりダウンタイムを抑えつつバージョン移行ができるため本番移行リスクを低減できる

### 技術的な注意点

- **IAM権限**: DB インスタンスの変更や Blue/Green の作成には rds:ModifyDBInstance や rds:CreateBlueGreenDeployment などの IAM 権限が必要になる場合があります。事前に権限を確認してください。
- **リージョン制限**: 新バージョンや拡張の提供状況はリージョン毎に異なるため、東京リージョン等での対応状況は事前に確認してください。
- **コスト**: Blue/Green デプロイメントや追加のリードレプリカの作成、pg_stat_monitor による追加ログ/メトリクス保存は一時的に追加料金やストレージ/IO 負荷を発生させる可能性があります。
- **互換性と事前検証**: マイナーバージョンでも拡張やアプリケーションの挙動が変わる場合があるため、まず開発/ステージ環境で検証し、自動ロールアウトやメンテナンス期間で段階的に適用してください。
- **pg_stat_monitor の注意**: pg_stat_monitor はメトリクス収集により追加の CPU/ストレージコストやパフォーマンス負荷が発生する可能性があります。RDS 上では使用可能な拡張の一覧に基づき有効化が必要で、RDS の権限モデル（rds_superuser 相当）により利用可能かを事前に確認してください。
- **アップグレード手順**: 自動マイナーアップグレードはメンテナンスウィンドウで実行され、即時アップグレードや手動アップグレードも可能です。ダウンタイムや再起動が発生するケースを想定し、バックアップやスナップショットを事前に取得してください。

## [Ec2] Announcing new Amazon EC2 general purpose M8azn instances

- **公開日**: 2026-02-13 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/02/aws-m8azn-instances-generally-available

### 概要

Amazon EC2の新しいM8aznインスタンスタイプが一般提供開始になりました。第5世代AMD EPYC（Turin）プロセッサによりクラウドで最大5GHzの高クロックを実現し、汎用かつ高周波・高ネットワーク性能を提供します。

### 変更内容・新機能の詳細

M8aznは第5世代AMD EPYC（コード名: Turin）を搭載した汎用の高周波・高ネットワーク性能インスタンスです。主な特長は、クラウドで最大5.0GHzのCPU周波数を実現する点で、前世代のM5znに対して最大で2倍の計算性能、M8aに対して最大約24%の性能向上を謳っています。メモリ帯域はM5zn比で最大4.3倍、L3キャッシュは最大10倍に拡大しており、レイテンシ敏感で計算集約的なワークロードの単スレッド／低レイテンシ性能を押し上げます。ネットワークスループットは最大2倍、EBSスループットは最大3倍（M5zn比）を提供します。Nitro System上に構築され、第6世代Nitroカードを採用。メモリ対vCPU比は4:1で、2〜96 vCPU（最大384 GiBメモリ）の9サイズを用意し、うち2つはベアメタルバリアントです。利用可能リージョンは US East (N. Virginia), US West (Oregon), Asia Pacific (Tokyo), Europe (Frankfurt) で、Savings Plans、オンデマンド、Spotで購入可能です。推奨利用例はリアルタイム金融分析、HPC、高頻度取引（HFT）、CI/CD、重負荷ゲーム、車載/航空/エネルギー/通信分野のシミュレーションなどです。

### 影響範囲・利用シーン

- **対象ユーザー**: ハイパフォーマンスコンピューティング（HPC）エンジニア、金融機関のリアルタイム分析/HFTチーム、ゲーム/シミュレーション開発者、SRE/プラットフォーム運用者
- **利用シーン**: 単一スレッド性能や低レイテンシが重要なワークロード（リアルタイム分析、トレーディング、CI/CDビルド、物理シミュレーション、低遅延ゲームバックエンド）
- **運用効果**: 同一コア数での処理時間短縮・スループット向上により、ジョブ完了時間の短縮や処理密度の向上が期待できる。ネットワーク・EBS性能向上はデータ移送・I/O集約処理の効率改善につながる

### 技術的な注意点

- **アーキテクチャ**: x86_64（AMD EPYC）ベース。Graviton（ARM）とは互換性がありません
- **AMI互換性**: ENA/NVMeドライバや最新カーネルを含むAMI（Amazon Linux 2、主要なLinuxディストロ）を使用してください。HVM仮想化対応が必要です
- **リージョン制限**: 公開時点では us-east-1, us-west-2, ap-northeast-1 (Tokyo), eu-central-1 (Frankfurt) のみ利用可能です
- **IAM権限**: インスタンス起動・EBS作成・ネットワーク設定に必要なec2:RunInstances等の権限を事前に確認してください
- **EBS/ネットワーク設定**: 公称スループットは向上しますが、実効性能は選択するボリュームタイプ（gp3/io1等）やネットワーク設定に依存します。必要に応じてI/O/スループットのプロビジョニングを行ってください
- **EFA/アクセラレータ**: EFAや特定のネットワーク機能のサポートはインスタンスタイプ依存です。EFAやSR-IOV等が必要な場合は事前に互換性を確認してください
- **ベアメタル注意点**: ベアメタルは専用ハードウェア上で実行されるためライセンスや管理面（BIOS設定やAMTなど）が異なります。ライセンス要件や運用手順を確認してください
- **コスト**: 高周波・高ネットワーク性能により単価は高めの可能性があります。長期/継続的運用はSavings PlansやReserved Instances/Spotの活用でコスト最適化を検討してください
- **移行/検証**: ワークロードにより性能改善の度合いが異なるため、実運用移行前にベンチマーク・負荷試験を実施してパフォーマンスとコスト効果を検証してください
