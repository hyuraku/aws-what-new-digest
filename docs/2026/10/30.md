## [CloudWatch] Managed Prometheus collectors now support Amazon MSK consumer-group metrics

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: CloudWatch
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/prometheus-collectors-msk-metrics/

### 概要

Managed Prometheus のマネージドコレクタが Amazon MSK の consumer-group メトリクスを収集できるようになりました。Kafka エクスポータとコンシューマグループのラグを自動で取得し、Amazon Managed Service for Prometheus（AMP）または Amazon CloudWatch に取り込めます。

### 変更内容・新機能の詳細

今回の対応により、Managed Prometheus のマネージドコレクタは MSK クラスター上で公開されている Prometheus 形式の Kafka エクスポータメトリクスとコンシューマグループの lag メトリクスを発見（service discovery）し、スクレイプして取得します。収集したメトリクスは AMP ワークスペースまたは CloudWatch の Prometheus 互換取り込み経路に送られ、クエリや可視化が可能です。これにより、アプリケーションのストリーム処理におけるコンシューマの遅延やスループット問題、処理ボトルネックを可視化でき、個別にエージェントをデプロイして運用する必要がなくなります。機能は Managed Prometheus collectors が一般提供されている全リージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon MSK を使用する開発者、データエンジニア、SRE/運用チーム
- **利用シーン**: コンシューマグループの lag 監視、Kafka ストリーム処理の健全性チェック、スケーリング判断や障害切り分け
- **運用効果**: エージェント運用負荷の軽減、リアルタイムな消費遅延検知による迅速な対応、Prometheus 互換のクエリで詳細な分析が可能

### 技術的な注意点

- **IAM権限**: マネージドコレクタの設定に必要な IAM 権限や AMP / CloudWatch への書き込み権限を確認してください（ワークスペースや PutMetricData 権限等）。
- **ネットワーク/VPC**: コレクタが MSK ブローカーや Kafka エクスポータのエンドポイントへ到達可能であること（VPC、サブネット、セキュリティグループ、VPC エンドポイント等のネットワーク設定を確認）。マネージドコレクタの配置方法に応じてプライベート接続が必要になる場合があります。
- **メトリクス供給元設定**: Kafka エクスポータまたは JMX エクスポータ等が Prometheus 形式でメトリクスを公開している必要があります。コンシューマグループ lag を提供するエクスポータの導入／設定を行ってください。
- **リージョン制限**: 「Managed Prometheus collectors が一般提供されているリージョン」で利用可能です。利用前に対象リージョンでサポート状況を確認してください。
- **コスト**: AMP へのメトリクス取り込み、ストレージ、CloudWatch への取り込みによる料金が発生します。メトリクスの発行頻度やカーディナリティが高いとコスト増加およびクエリ性能に影響します。
- **性能注意**: 高いメトリクスカーディナリティや短いスクレイプ間隔はコストとクエリ遅延の要因になります。必要なメトリクスのみを公開・収集する設計を推奨します。

## [Glue] AWS Glue Data Catalog now supports Apache Iceberg table optimization in the US West (N. California) Region

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: Glue
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/glue-data-catalog-optimizers-us-west-1/

### 概要

AWS Glue Data Catalogが米国西部（北カリフォルニア）リージョンでApache Icebergテーブルの自動最適化（table optimization）に対応しました。Icebergテーブルの小ファイルや古いスナップショット、未参照ファイルを自動的に整理してクエリ性能とストレージ効率を改善します。

### 変更内容・新機能の詳細

この機能はGlue Data Catalogに登録されたApache Icebergテーブルに対して、継続的に監視を行いバックグラウンドで次の最適化操作を実行します：小ファイルのコンパクション、保持期限を過ぎたスナップショットの削除、参照されなくなったファイルの削除。最適化は個別テーブル単位またはData Catalog内の全テーブルに対して有効化可能で、AWS Glueコンソール、AWS CLI、AWS SDKから設定できます。各実行はGlueコンソールのジョブログ、Amazon CloudWatchのメトリクスとログで監視でき、最適化の成功/失敗や処理時間・対象ファイル数などを確認できます。なお、サポートされるリージョン一覧は別途ドキュメントで提供されており、本リリースでは米国西部（北カリフォルニア）リージョンでの利用開始が告知されています。

### 影響範囲・利用シーン

- **対象ユーザー**: データプラットフォームエンジニア、データエンジニア、SRE/運用チーム
- **利用シーンまたは効果**: 大量の書き込みやストリーミング取り込みで小ファイルが増えるIcebergベースのデータレイクにおいて、クエリ遅延の低減・ストレージコスト削減・メタデータ肥大化の抑制を実現
- **運用効果**: 手動によるファイル管理や定期バッチの実装が不要になり、運用工数削減とクエリ安定化が期待できる

### 技術的な注意点

- **IAM権限**: Glue Data Catalogの読み書き、および最適化ジョブの開始/管理に必要なGlue関連権限と、最適化中にS3オブジェクトを削除/読み書きするためのS3アクセス権限（Glueサービスロールや実行ロール）を事前に確認してください
- **リージョン制限**: 本発表は米国西部（北カリフォルニア／us-west-1）リージョンでの対応開始を示しています。利用前に「Supported Regions for table optimizers」を確認してください
- **コスト**: 最適化はGlue側の処理（コンピューティング）、S3のリクエスト/削除、およびCloudWatchメトリクス/ログのコストを発生させます。頻度や対象データ量に応じたコスト見積もりが必要です
- **データ保護/保持**: スナップショットや未参照ファイルの削除を行うため、タイムトラベルやリカバリ要件（スナップショット保持期間）は事前にポリシー設計してください。バックアップやクロスリージョン複製との整合性にも注意が必要ですn・対象フォーマット: 本機能はApache Icebergテーブル専用です。Parquet/ORC等ファイル形式自体は問いませんが、テーブルがIcebergフォーマットでGlueに登録されていることが前提です

## [SageMaker] Amazon SageMaker AI inference now supports GPU partitioning for real-time endpoints

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: SageMaker
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/sagemaker-gpu-partitioning/

### 概要

Amazon SageMaker AI inferenceがGPUパーティショニングをサポートしました。NVIDIA Multi-Instance GPU (MIG) を用いて1つのGPUを最大7つの独立したパーティションに分割し、複数モデルを単一GPU上で安全に並列実行できます。

### 変更内容・新機能の詳細

SageMaker AIのリアルタイムエンドポイントでGPUパーティショニングを利用可能になりました。NVIDIAのMIG技術により、GPUを最大7つのハードウェア分離されたパーティション（各パーティションに専有のメモリと計算リソース）に分割できます。これにより、従来は1モデルにつき1アクセラレータを割り当てる必要があった小〜中規模のモデル（ファインチューニング済みバリアント、埋め込みモデル、リランキング、分類器など）を、適切なサイズのパーティションに配置して1台のGPUで複数ホスト可能となります。パーティション間はハードウェアで隔離されるため、あるモデルがメモリやスループットを奪うことはありません。エンドポイント作成時にGPUの分割方法を指定し、各モデルは従来どおり名前で呼び出せるため、アプリケーション側の呼び出しコードは変更不要です。サポートインスタンスは P4d、P5、G7、G7e、利用可能リージョンは US East (N. Virginia)、US East (Ohio)、US West (Oregon)、Asia Pacific (Singapore)、Asia Pacific (Tokyo)、Europe (Frankfurt)、Europe (Ireland) です。パーティション化により、より新しく大容量のインスタンス世代を1モデル用に使う必要がなくなり、リソース利用率とコスト効率が向上します。

### 影響範囲・利用シーン

- **対象ユーザー**: 機械学習エンジニア、モデル運用チーム、SRE/クラウドアーキテクト
- **利用シーン**: 小〜中規模モデル（埋め込み、再ランキング、軽量分類器、ファインチューニング済みモデル）を複数同一エンドポイント／同一GPU上でホストするケース
- **運用効果**: GPUリソースの有効利用によるコスト削減、インスタンス当たりのホスト可能モデル数増加、ハードウェア側のメモリ/スループット隔離による安定性向上
- **コスト影響**: インスタンス課金は継続するが、モデルあたりのGPU浪費が減り総コスト削減につながる可能性が高い
- **開発影響**: 既存のモデル呼び出し（モデル名でのinvoke）は変更不要で移行コストが小さい

### 技術的な注意点

- **IAM権限**: エンドポイント作成・更新に必要なSageMaker権限（例: sagemaker:CreateEndpointConfig, sagemaker:CreateEndpoint, sagemaker:UpdateEndpoint）を確認してください
- **リージョン制限**: 現時点での対応リージョンは US East (N. Virginia), US East (Ohio), US West (Oregon), Asia Pacific (Singapore), Asia Pacific (Tokyo), Europe (Frankfurt), Europe (Ireland) のみです
- **インスタンスタイプ**: P4d, P5, G7, G7e がサポートされています（これ以外のGPUインスタンスでは利用不可）
- **パーティション制限**: 1GPUを最大7つのMIGパーティションに分割可能。各パーティションはメモリと演算を共有せずハードウェア隔離されますが、パーティションを細かく分けると各パーティションの利用可能リソースが小さくなるため、モデルのサイズと推論要求に合わせて試験検証が必要です
- **互換性**: SageMakerの推論コンテナ・フレームワーク（コンテナベースのモデルサービング）と互換で、モデル呼び出しAPIは変更不要。ただしコンテナやドライバの要件により追加の検証が必要な場合があります
- **エンドポイント設定**: GPUパーティショニングはエンドポイント作成時に指定します。既存のエンドポイントに対する変更はエンドポイントの再作成または更新で対応する必要があります
- **スケーリング/モニタリング**: パーティション化した環境でもオートスケーリングやCloudWatchによるメトリクス収集は必要です。レイテンシやスループットの特性が変わるため、負荷試験でスケーリングポリシーを調整してください
- **コスト**: GPU利用の効率化で総コスト削減が期待できますが、インスタンス選定（より新しい世代を使うかどうか）やパーティション数によるスループット変化で運用コストが変動します。事前に負荷テストでTCOを評価してください

### 参考情報

- https://aws.amazon.com/sagemaker/ai-deployment/
- https://docs.aws.amazon.com/sagemaker/latest/dg/

## [General] AWS Marketplace now enables partners to list once and sell through multiple subsidiary accounts

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-marketplace-subsidiary-account-authorization

### 概要

AWS Marketplaceは、複数の法的事業体（子会社）を持つパートナーが、プライマリアカウントに一度出品すれば、その出品を各子会社が直接プライベートオファーで販売できる機能を発表しました。重複した出品管理が不要になり、販売・請求のローカル運用が可能になります。

### 変更内容・新機能の詳細

技術的には、パートナーのプライマリアカウントが出品の所有権を保持したまま、どの製品をどの子会社が販売できるか、およびその子会社がどの購買国に対してプライベートオファーを出せるかを承認します。子会社側は自身の税務IDで取引を行い、対応通貨の選択、支払振込先口座や分配（disbursement）設定を個別に管理できます。プライマリアカウントには、接続された全子会社アカウントに跨るオファー、契約、更新の統合的なMarketplace Insightsレポートが提供されます。パートナは子会社の承認や接続をいつでも取り消せますが、取り消しは新規オファー作成の停止に即時反映され、既存の契約や既にバイヤーに提示されたオファーには影響を与えません。この機能は追加料金なしで、AWS Marketplaceが利用可能なすべてのリージョンで利用可能です。開始手順や詳細は「Managing subsidiary account connections」「Creating private offers as a subsidiary account」のドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: SaaS/IaaSベンダーやソフトウェア販売パートナーで、複数の法的エンティティ（子会社／地域法人）を持つ事業者
- **利用シーン**: 単一の出品をグローバルに管理しつつ、各子会社が自社の税務・銀行口座・通貨でローカル販売（プライベートオファー）を行う場合
- **運用効果**: 出品の重複作成・同期コストを削減し、地域ごとの請求・税務処理の分離とローカルキャッシュフロー管理を実現
- **ガバナンス**: プライマリアカウントが出品所有を保持するため、中央管理とローカル販売のバランスを取りやすく、必要に応じて子会社権限を即時取り消し可能
- **コンプライアンス/税務**: 各子会社がローカル税IDで取引するため、現地の税務・請求要件に合わせた運用が可能（ただし適用法令は各社で確認が必要）

### 技術的な注意点

- **IAM権限**: プライマリアカウント側／子会社側それぞれでMarketplace関連のアカウント接続・承認操作を行う権限が必要。具体的な権限はドキュメントを確認してください。
- **リージョン制限**: 発表によればAWS Marketplaceが利用可能なすべてのリージョンで提供されていますが、リージョンごとの支払い処理や通貨サポートは異なる場合があるため事前確認を推奨します。
- **コスト**: この新機能自体に追加費用は発生しません。ただしMarketplaceの通常の手数料、決済手数料、為替変換コスト等は別途適用されます。
- **税務/請求**: 子会社はローカル税IDでの取引・請求を行うため、現地の消費税／付加価値税（VAT）や源泉税等の扱いについて自社の税務担当と確認してください。
- **オファー／契約の扱い**: 子会社接続の取り消しは新規オファー作成を即時停止しますが、既存に締結済みの契約や既に提示済みのオファーには影響しません。撤回後の既存契約の管理（更新・解約等）は事前に運用ルールを設けてください。
- **制限事項**: 本機能は「直接プライベートオファー（direct private offers）」を対象とする運用を前提としており、公開マーケットプレイス上の出品編集権限はプライマリアカウントに残ります。

## [RDS] Amazon RDS for Oracle and SQL Server now support storage autoscaling on additional storage volumes

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-rds-oracle-sqlserver-autoscaling-additional-storage-volumes

### 概要

Amazon RDS for Oracle と Amazon RDS for SQL Server が、追加ストレージボリュームに対する RDS ストレージ自動スケーリングをサポートしました。最大 3 つの追加ボリュームを使ってストレージ容量を自動で拡張でき、最大合計容量は 256 TiB です。

### 変更内容・新機能の詳細

これまで追加ストレージボリュームは手動で容量を見積もり・プロビジョニングする必要があり、過小/過大プロビジョニングによるダウンタイムやコスト増のリスクがありました。今回の拡張により、各追加ボリュームごとに最大ストレージ上限を設定すると、RDS のストレージ自動スケーリングが実際の利用状況を継続監視して上限に近づくと自動的に容量を拡張します（ダウンタイムなし）。新規／既存のインスタンス両方に適用可能で、追加課金はなく、増加した分のプロビジョンドストレージ分のみ課金されます。設定は AWS マネジメントコンソール、AWS CLI、または Amazon RDS API から行えます。対応リージョンは全商用リージョンおよび AWS GovCloud (US) です。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、SRE、運用チーム、Oracle/SQL Server を利用するアプリケーション所有者
- **利用シーン**: 急激なデータ増加が発生するトランザクション系/ログ格納系データベース、容量予測が難しい環境でのストレージ拡張の自動化
- **運用効果**: ダウンタイムや手動オペレーションを抑えつつ、ストレージ不足によるサービス障害のリスクを低減。過剰プロビジョニングの抑制でコスト効率が向上

### 技術的な注意点

- **IAM権限**: ストレージ自動スケーリングを有効化/変更するには rds:ModifyDBInstance / rds:ModifyDBCluster 等の適切な RDS 修正権限が必要です
- **リージョン制限**: 全商用リージョンおよび AWS GovCloud (US) で利用可能（ただし利用前に対象リージョンでのサポート状況を公式ドキュメントで確認してください）
- **コスト**: 自動スケーリング自体に追加料金は無し。増加したプロビジョンドストレージ分のみ課金されるため、最大上限値の設定によりコスト上昇が発生する可能性があります
- **ダウンスケール**: 通常、ストレージの自動縮小（自動で容量を減らす）はサポートされていないため、縮小は手動での再設計やリサイズが必要です
- **サポート対象エンジン/バージョン**: 本機能は Amazon RDS for Oracle と Amazon RDS for SQL Server 向け。インスタンスタイプや特定エンジンバージョンによる制約がある可能性があるため、適用前に公式ドキュメントで対象バージョン・制限を確認してください
- **ストレージタイプ/IOPS**: ストレージタイプ（汎用 SSD、プロビジョンド IOPS など）や IOPS の設定と自動スケーリングの挙動（IOPS の増減やパフォーマンス影響）を事前に確認してください
- **運用上の注意**: 各追加ボリュームごとに最大上限を設定する必要があります。監視とアラート（CloudWatch）を併用し、上限に達する前の運用対応方針を定めてください

- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_Storage.AutoScaling.html

## [Aurora] Amazon Aurora now supports post-quantum TLS key exchange

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: Aurora
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aurora-postgresql-post-quantum-tls-key-exchange/

### 概要

Amazon Aurora PostgreSQL互換エディションがポスト量子（PQ）耐性を考慮したTLS鍵交換（PQ-TLS）をサポートしました。バージョン18以降でssl_groupsパラメータを変更して、Auroraの許可リストにある暗号グループを選択できます。

### 変更内容・新機能の詳細

本アップデートにより、Aurora PostgreSQL（バージョン18以上）でTLSの鍵交換にポスト量子暗号オプションを利用できるようになりました。具体的にはDBのssl_groupsパラメータを更新して、Auroraが提供する許可済みの暗号グループ（ポスト量子のグループや組合せグループ）を選択できます。これによりネットワーク経路上の機密データに対して、将来の量子コンピュータによる解読リスクを低減する設計が可能です。実装はサーバー側のTLSネゴシエーションで行われるため、クライアント側（接続元のドライバ・ライブラリ・プロキシ・ロードバランサ等）が該当するグループをサポートしている必要があります。PQ-TLSの採用は「データの暗号化方式（in transit）」に関する変更であり、暗号化の対象は通信経路で、保存データ（at rest）の暗号化設定には影響しません。また、PQアルゴリズムは計算コストが高くなる場合があるため、レイテンシやCPU使用率の影響を事前に評価することを推奨します。導入手順や詳細は公式の「Getting started」ドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: Aurora PostgreSQL（v18以上）を利用するアプリケーション開発者、セキュリティおよびコンプライアンス担当者、SRE/運用チーム
- **利用シーンまたは効果**: 量子耐性を強化したい通信経路の保護（機密データのトランスポート保護、長期保管データの将来リスク低減）
- **運用効果**: 将来の量子攻撃に備えた暗号強度向上により規制要件やベンダー方針への適合性を高められる。検証により本番切替時のリスクを管理できる

### 技術的な注意点

- **IAM権限**: DBパラメータグループの変更やクラスタ管理に必要なRDS/Aurora関連権限（例: rds:ModifyDBClusterParameterGroup / rds:ModifyDBParameterGroup、必要に応じて再起動操作権限）を付与してください
- **リージョン制限**: 公開発表では特定リージョンの限定は明示されていませんが、導入前に対象リージョンでのサポート状況を公式ドキュメントで確認してください
- **コスト**: 機能自体に追加料金は通常発生しませんが、ポスト量子鍵交換は計算負荷が高くなる可能性があり、CPU使用率増加によるインスタンスサイズやスケール要件、結果的なコスト増加が発生する場合があります
- **クライアント互換性**: 接続元のTLSスタック（アプリケーションライブラリ、OSのOpenSSL/BoringSSL、JavaのTLS実装、プロキシ/ロードバランサ等）が選択したPQグループをサポートしている必要があります。TLS終端を別レイヤで行っている場合は、その層でPQ-TLSがサポートされているか確認してください
- **パラメータ適用**: ssl_groupsはDBのパラメータグループで管理します。パラメータ変更の適用に再起動が必要かどうかは設定項目に依存するため、変更はメンテナンスウィンドウでの適用や事前検証を推奨します
- **監査・運用**: 新しい暗号グループ採用後は接続ログ／TLSネゴシエーション情報をモニタリングして接続失敗や予期せぬフォールバックが発生していないか確認してください

## [Msk] Amazon MSK Connect now supports updating connector plugins and worker configurations

- **公開日**: 2026-10-30 (JST)
- **カテゴリ**: Msk
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-msk-connect-update-plugin-worker-configurations

### 概要

Amazon MSK Connectで既存コネクタのカスタムプラグインおよびワーカー設定をインプレースで更新できるようになりました。従来の「削除して再作成する」手順を不要にし、コミット済みオフセットを保持して更新後に処理を継続できます。

### 変更内容・新機能の詳細

今回の機能追加により、既存のコネクタについてカスタムプラグイン（コネクタ実装や依存ライブラリを含む）とワーカー構成（キー/バリューコンバータ、producer/consumerプロパティ等）をその場で更新できます。想定ユースケースは、コネクタ実装の新バージョンへの差し替え（依存関係の更新など）や、レイテンシ／スループットチューニングのためのワーカー設定変更、コンバータの切り替えなどです。これまではプラグインやワーカー設定の変更が必要な場合、コネクタを削除して再作成する必要があり、オフセットや処理の中断、運用コストが発生していました。本アップデートではコネクタはインプレースで更新され、コネクタが保持しているコミット済みオフセットに基づいて更新後に処理を再開します。追加料金はなく、Amazon MSK Connectがサポートされている全リージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: Kafka Connectを運用するプラットフォーム/データエンジニア、SRE、運用チーム
- **利用シーン**: コネクタ実装のバージョンアップ（依存ライブラリの更新）、キー/バリューコンバータの切替、producer/consumer設定のチューニング
- **運用効果**: コネクタの削除・再作成によるダウンタイムや運用リスクを削減し、オフセットの維持により処理継続が容易になる

### 技術的な注意点

- **IAM権限**: MSK Connectのコネクタ更新を行うための適切な権限（UpdateConnector 相当や関連のIAMポリシー）が必要です
- **オフセットとタスク挙動**: コネクタはコミット済みオフセットを保持しますが、更新中にタスクの再起動や一時的な処理停止が発生する可能性があるため短時間の処理遅延を想定してください
- **互換性・テスト**: プラグインの新バージョンやコンバータ変更はスキーマ互換性や依存関係の問題を引き起こす可能性があるため、本番へ適用する前にステージングで検証してください
- **リージョン制限**: 本機能はAmazon MSK Connectがサポートされている全リージョンで利用可能と明記されていますが、利用予定リージョンでの展開状況はドキュメントで再確認してください
- **コスト**: 本機能自体に追加料金は発生しませんが、更新に伴う一時的なリソース（再起動時のスループット変動等）やテスト環境での実行はコストに影響する可能性があります
- **Infrastructure as Code / 自動化**: CloudFormationやTerraformでのサポート状況は確認が必要です。既存のCI/CDパイプラインでの更新フロー（ロールバック手順を含む）を整備してください
- **ログ・モニタリング**: 更新時の失敗や再起動を検知できるよう、CloudWatch Logs/メトリクスを監視対象に含め、アラートを設定してください
