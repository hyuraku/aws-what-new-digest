## [General] Amazon Connect Customer now lets you view metrics by customer lifetime value and repeat-caller status

- **公開日**: 2026-10-26 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/connect-customer-boma-segment/

### 概要

Amazon Connect Customerで、顧客ライフタイムバリュー（LTV）とリピートコーラー（再発信者）を軸にメトリクスをセグメント表示できるようになりました。特定の顧客グループごとの傾向を早期に把握して、ルーティングやセルフサービス、エージェント指示の改善につなげられます。

### 変更内容・新機能の詳細

今回の機能強化により、Amazon Connectのダッシュボードや分析画面で標準メトリクス（通話件数、平均応答時間、平均処理時間、解決率、顧客満足度など）を「LTVが高い顧客」と「リピートコーラー」などのセグメント別に比較・表示できます。LTVセグメントは、外部CRMや顧客プロファイル（Amazon Connect Customer ProfilesやCustomer Profiles連携）から投入した顧客属性（LTV値）を基に集計され、リピートコーラーは過去のコンタクト履歴（Contact Trace Recordsなど）から所定期間内に複数回接触した顧客を自動判定してセグメント化します。表示はセグメント間の差分比較や時系列トレンドで確認でき、セグメントごとの低下が確認された場合は以下のような対処が可能です：高LTV顧客を優先ルーティング（ルーティングプロファイルやコンタクトフローの調整）で特定の熟練エージェントへ振り分け、リピートコーラーが離脱しているセルフサービスフローやナレッジベース（Amazon Connect Wisdom）を改善、エージェント向けスクリプト/ガイダンスをセグメントに応じて最適化。これにより、集計値に現れる前に問題の発生している顧客層を特定し早期対応が可能になります。

### 影響範囲・利用シーン

- **対象ユーザー**: カスタマーサポートチーム、コンタクトセンターの運用・分析担当（SRE/運用）、カスタマーサクセス、CRM担当者
- **利用シーンまたは効果**: 高LTV顧客への優先対応や、繰り返し問い合わせる顧客が離脱するセルフサービス箇所の特定と改善
- **運用効果**: セグメント単位での問題検出により顧客離脱・不満の早期抑止、優先顧客のLTV保持とオペレーション効率化が期待できる
- **期待される改善**: 平均処理時間や満足度の向上、再発信率の低下、重要顧客の解約抑止やアップセル機会の向上

### 技術的な注意点

- **IAM権限**: 分析・ダッシュボード閲覧やCustomer Profiles、Contact Lens等の機能を利用するための適切なIAMポリシーが必要です（analyticsやprofiles関連の権限を確認してください）
- **データ準備**: LTVは外部CRMやCustomer Profiles経由での属性取り込みが必要です。リピートコーラー判定は過去のコンタクト履歴に基づくため、CTR（Contact Trace Record）や通話ログの保持が前提になります
- **関連機能**: 検出・改善のためにはAmazon Connect Customer Profiles、Contact Lens、Amazon Connect Wisdom、ルーティングプロファイル／コンタクトフローの設定などと連携して使うと効果的です
- **データ遅延**: セグメント集計・メトリクスの更新には一定の遅延が発生する場合があります。リアルタイム性が必要なシナリオは仕様を確認してください
- **リージョン制限**: 新機能の提供状況はリージョンによって異なる可能性があります。利用前に対象リージョンでの提供可否を確認してください
- **コスト**: Customer Profiles、Contact Lens、追加のストレージやデータ取り込み（例: S3、Kinesis）などを利用する場合は別途料金が発生します。ダッシュボードや高度な分析利用時のコスト影響を事前に評価してください

## [General] Amazon Connect Customer now measures the outcomes that drive retention and revenue

- **公開日**: 2026-10-26 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/connect-customer-boma-metrics/

### 概要

Amazon Connect Customerが各顧客対応の「成果（outcome）」をスコア化できるようになりました。満足・解約リスク・購入・セルフサービス解決など、効率ではなく「やり遂げたか」を可視化します。

### 変更内容・新機能の詳細

本アップデートでは、各インタラクション（通話／チャット等）に対して成果を判定する複数のメトリクスが提供されます。標準で用意されるメトリクス例は「顧客満足」「解約リスク」「購入検知」「セルフサービスでの解決」などで、各メトリクスにはデフォルトの定義（判定ルール／閾値）があり、業務要件に応じてカスタマイズ可能です。これらのスコアはAmazon Connectの分析ダッシュボード上で可視化できるほか、API経由で個別インタラクションのスコアや集計データを取得できます。実装面では、連絡履歴・コンタクト属性・会話のトランスクリプト・外部CRM／購買イベントなどを活用して判定ロジックを組み立てられるため、既存のイベントストリームやデータレイクに取り込み、BIや機械学習パイプラインと組み合わせることが可能です。これにより従来の運用KPI（待ち時間・通話時間・解決率）に加えて、顧客維持・売上に直結する成果指標での評価・改善が行えるようになります。

### 影響範囲・利用シーン

- **対象ユーザー**: コンタクトセンター管理者、CX（顧客体験）分析担当者、データアナリスト、マーケティングおよびプロダクトオーナー
- **利用シーン**: 解約リスクの早期検知と介入、セルフサービス（IVR/FAQ/チャットボット）の改善、キャンペーンやプロモーションによる購入誘導の効果測定、A/Bテストによる対応方針の最適化
- **運用効果**: 成果ベースの指標で優先対応や人員配置が可能になり、顧客維持率と売上向上につながる意思決定が行える
- **レポーティング**: ダッシュボード／API経由で定量的な成果指標が取得でき、経営指標（KPI/OKR）との紐付けや自動レポート化が容易になる

### 技術的な注意点

- **IAM権限**: 分析ダッシュボードの閲覧・編集、メトリクス定義の変更、API呼び出しにはAmazon Connect関連の適切なIAM権限が必要です。CloudWatch、Kinesis、S3等へ出力する場合はそれらのサービス権限も確認してください
- **リージョン制限**: 新機能はリージョンごとに段階的に提供される可能性があります。利用前に該当リージョンで提供済みか公式ページで確認してください
- **データとプライバシー**: 会話トランスクリプトや外部イベントを判定に使う場合、個人情報（PII）取り扱いの方針、保持期間、暗号化（KMS）の設定を確認してください
- **コスト**: メトリクス計測・保存、API呼び出し、追加の分析ストレージやML評価によって追加料金が発生する可能性があります。既存のConnect使用料に加算される点に注意してください
- **互換性・統合**: 判定ロジックはContact Attributesや外部CRMイベントと組み合わせる想定です。既存のイベントストリーム/Kinesisやデータレイクとの連携設計を見直してください
- **注意点**: デフォルト定義は業種・ビジネスモデルによって合わない場合があるため、本番運用前にサンプル期間で定義を調整・検証することを推奨します

## [Iam Identity Center] AWS IAM Identity Center now supports cross-Region trusted identity propagation

- **公開日**: 2026-10-26 (JST)
- **カテゴリ**: Iam Identity Center
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-iam-identity-center-cross-region-tip/

### 概要

AWS IAM Identity Center（旧AWS SSO）が、ユーザーの識別情報（trusted identity propagation）をリージョンを跨いで伝搬できるようになりました。これにより、複数リージョンに分散したサービスでも個々のユーザー／グループに基づく細かいアクセス制御と監査が可能になります（追加料金なし）。

### 変更内容・新機能の詳細

従来は「trusted identity propagation（TIP）」を利用する場合、同一リージョン内のサービス間でのみユーザーの識別コンテキストを伝搬できました。今回のアップデートで、IAM Identity Centerが発行する認証情報に含まれるユーザーIDやグループ情報などのアイデンティティコンテキストが、リクエストとともに自動的に他リージョンのAWSサービスへ伝搬されるようになりました。これにより、以下が可能になります：
- 各ユーザーや所属グループに基づく細粒度なアクセス制御（広域的なロールの付与ではなく個別ユーザー識別）
- 異なるリージョンにあるリソースに対するアクセスの正確な監査（どのユーザーがどのリソースへアクセスしたかの記録）
- ワークロードをリージョン分散（データとコンピュートの分離、容量または災害対策の理由）した設計を維持しつつ、セキュアなアクセス管理を実現
実装面では、サービス側がIAM Identity Centerからのアイデンティティコンテキストを受け取り、それに基づいてアクセス判断やログ出力を行える必要があります。クロスリージョンTIPは、IAM Identity Centerが利用可能な全リージョンで追加料金なく利用できますが、各AWSサービスや統合先のサポート状況は個別に確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドエンジニア、IAM管理者、SRE/運用チーム、セキュリティチーム
- **利用シーン**: 複数リージョンにまたがるアプリケーションでのユーザー単位のアクセス制御と監査（例：東京リージョンのデータに米国リージョンの分析ジョブがアクセスするケース）
- **運用効果**: リージョン分散アーキテクチャでも個別ユーザーに基づく最小権限ポリシーと監査が可能になり、広域ロールに頼る必要が減ることでセキュリティが向上
- **コスト影響**: 機能自体に追加料金はないが、クロスリージョン通信やログ出力（CloudTrail／ログ保存）の増加はネットワーク／ストレージコストに影響する可能性あり
- **リージョン可用性**: IAM Identity Centerが利用可能なリージョンで利用可能。対象リージョンの可用性は公式のリージョン一覧で要確認

### 技術的な注意点

- **IAM権限**: IAM Identity Centerの設定や対象リソースで必要なIAM/IAM Identity Center権限を適切に付与してください。サービス側が受け取るアイデンティティ情報でアクセス制御する場合、関連するポリシーや信頼ポリシーの確認が必要です
- **リージョン制限**: クロスリージョンTIPはIAM Identity Centerが利用可能なリージョンで提供されますが、すべてのAWSサービスやサードパーティが同機能をサポートするわけではありません。各サービスのドキュメントでTIPサポート状況を確認してください
- **サービス対応**: TIPの利用には、対象サービスがリクエストに含まれるアイデンティティコンテキスト（例：フェデレーテッドプリンシパルやセッション情報）を解釈できることが前提です。サービス固有の制約（セッションタグの伝搬、STSの利用可否等）を確認してください
- **監査/ログ**: クロスリージョンでのアクセス記録はCloudTrailやサービス固有のアクセスログに反映されますが、ログの出力先リージョンや保存ポリシーを確認し、必要に応じて集中ログ収集/分析の設計を行ってください
- **パフォーマンス/レイテンシ**: リージョン間通信に伴う遅延や復旧要件があるため、設計時にレイテンシやフェイルオーバー挙動を評価してください
- **コスト**: 機能自体は無料ですが、クロスリージョンデータ転送、CloudTrail/ログ保存/分析などの関連コストは発生する可能性があります

## [KMS] AWS Key Management Service now supports ML-KEM for post-quantum key encapsulation

- **公開日**: 2026-10-26 (JST)
- **カテゴリ**: KMS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/kms-ml-kem-post-quantum/

### 概要

AWS KMSがNIST FIPS 203で規定されたポスト量子鍵カプセル化方式 ML-KEM をサポートしました。これにより、量子耐性を持つ鍵確立（shared secret）の生成と復号がKMS内で可能になります。

### 変更内容・新機能の詳細

ML-KEM（Module-Lattice-Based Key-Encapsulation Mechanism）は、DH/ECDHやRSAベースの鍵確立を置き換えることを想定したNISTのポスト量子KEM標準です。AWS KMSはFIPS 203で定義された3つのキー仕様（ML-KEM-512、ML-KEM-768、ML-KEM-1024）をサポートしています。Encapsulate APIは公開鍵を使ってランダムな32バイトの共有シークレットとその暗号文を生成し、Decapsulate APIは対応する秘密鍵で暗号文から共有シークレットを復元します。ML-KEM鍵ペアの秘密鍵はFIPS 140-3 レベル3 検証済みのHSM内で保護されます。GetPublicKey APIで公開鍵をエクスポートしてパートナーやクライアントに配布し、AWS-LC、OpenSSL、Bouncy Castle等の暗号ライブラリでローカルにEncapsulateを実行できます。ML-KEMはKMSが利用可能なほとんどのリージョンで利用可能ですが、中東（UAE）、中東（バーレーン）および中国リージョンは除きます。実装にあたっては生成される32バイト共有シークレットをそのまま鍵として使うのではなく、必要に応じてKDFで鍵派生（AESキーやHMACキー等）を行う設計が推奨されます。

### 影響範囲・利用シーン

- **対象ユーザー**: セキュリティ/暗号実装エンジニア、クラウドアーキテクト、SRE/運用チーム
- **利用シーン**: 長期間機密性を保持する必要がある通信や鍵配布（ハイブリッド鍵交換、エンベロープ暗号化、パートナー間の安全な鍵共有）
- **運用効果**: "ハーベストして後で復号（harvest now, decrypt later）" の脅威に対する耐性が向上し、将来の量子攻撃に備えた鍵確立が可能になる
- **互換性効果**: クライアント側で対応ライブラリがあれば既存のワークフロー（公開鍵配布＋ローカルEncapsulate／KMSでDecapsulate）へ比較的容易に組み込み可能

### 技術的な注意点

- **IAM権限**: Encapsulate/Decapsulate/GetPublicKey等のKMS API呼び出し権限（kms:Encapsulate、kms:Decapsulate、kms:GetPublicKey等）を適切に付与してください
- **リージョン制限**: ほとんどのAWSリージョンで利用可能ですが、中東（UAE）、中東（バーレーン）、中国リージョンでは未提供です
- **コスト**: API呼び出し数やカスタマー管理キーの保持等に基づくKMSの通常料金が発生する可能性があります。利用前にKMSの料金ページで確認してください
- **暗号ライブラリ互換性**: AWS-LC、OpenSSL、Bouncy Castle等でML-KEMを利用するには、該当ライブラリがFIPS 203の各スペック（512/768/1024）をサポートするバージョンであることを確認してください
- **鍵管理**: 秘密鍵はFIPS 140-3 レベル3 検証済みHSMで保護されますが、公開鍵を配布する際の信頼チェーン／配布方法（改竄防止、期限管理）を設計してください
- **運用上の注意**: Encapsulateが返す32バイトの共有シークレットはそのまま暗号鍵として使わず、KDF（例: HKDF）で適切な鍵長に派生することを推奨します
- **監査/ログ**: Encapsulate/Decapsulate操作の監査やアクセスログ（CloudTrail等）を有効にして操作履歴を記録してください

## [Ec2] AWS EC2 Auto Scaling now supports Launch Before Terminate at account-level to replace instances

- **公開日**: 2026-10-26 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/ec2-auto-scaling-launch-before-terminate/

### 概要

EC2 Auto Scalingで、アカウント単位で「Launch Before Terminate（置換時に先に新しいインスタンスを起動してヘルスチェックが通ってから古いインスタンスを終了する）」をデフォルト動作として有効化できるようになりました。これにより、インスタンス置換時の容量喪失やサービス停止を抑制できます。

### 変更内容・新機能の詳細

今回の追加により、アカウント設定で Launch Before Terminate を有効にすると、そのアカウント内の全ての Auto Scaling グループに対して置換時の既定の振る舞いが「先に置換インスタンスを起動し、ヘルスチェック合格後に置換元を終了する」になるよう設定できます。該当する置換イベントはインスタンスリフレッシュ、リバランス、ヘルスチェックによる置換、最長インスタンス寿命に伴う置換などが含まれます。設定は AWS マネジメントコンソール、AWS CLI、AWS SDK 経由で行え、API は PutAccountSetting と DescribeAccountSettings を使用します。新しい動作は全リージョンで利用可能で、AWS側の追加料金はありません（ただし置換期間中は一時的に追加インスタンス分の料金が発生します）。具体的には、Auto Scaling は新しいインスタンスを起動し、当該 Auto Scaling グループで設定されたヘルスチェック（EC2 インスタンスステータスチェックやロードバランサ／ターゲットグループのヘルスチェック等）が合格するのを待ってから古いインスタンスを終了します。アカウント設定により一括で既定動作を変更できるため、大規模環境での個別グループ設定の手間を削減できます。

### 影響範囲・利用シーン

- **対象ユーザー**: SRE／プラットフォームエンジニア、DevOps、アプリケーションオーナー
- **利用シーン**: インスタンスリフレッシュやローリングアップデート、ヘルスチェックに伴う置換、スポット回避やAZリバランス時の置換でダウンタイムを抑えたい場合
- **運用効果**: 置換中のキャパシティ低下や接続切断を低減し、可用性を維持しやすくなる（メンテナンスや自動置換の影響を緩和）
- **コスト影響**: 置換完了までの短時間、同時に稼働するインスタンスが増えるため追加のインスタンス時間分の費用が発生する可能性あり
- **運用負荷**: アカウント単位での一括設定により、ASGごとの個別設定作業を削減可能

### 技術的な注意点

- **IAM権限**: PutAccountSetting と DescribeAccountSettings を実行できる autoscaling 権限（例: autoscaling:PutAccountSetting, autoscaling:DescribeAccountSettings）が必要。コンソール／CLI操作には追加の IAM 権限（console access）が必要な場合あり
- **リージョン制限**: 記事によれば全リージョンで利用可能
- **既存のASG設定との関係**: アカウント既定を設定しても、ASG レベルで明示的に別の置換動作が設定されている場合はその設定が優先される運用パターンが一般的（事前にグループ単位設定の挙動を確認してください）
- **ヘルスチェックの考慮**: 新インスタンスの健全性判定は当該ASGで設定されているヘルスチェック（EC2ステータス、ELB/ターゲットグループ等）に従うため、適切なヘルスチェックとヘルス判定しきい値を設定すること
- **コスト**: AWS側の追加費用はないが、置換期間中の追加インスタンス分の料金は発生する点に注意
- **API/CLI**: 設定は PutAccountSetting（名前: LaunchBeforeTerminate などのキー）と DescribeAccountSettings で管理可能。操作前にAPIリファレンスでパラメータとフォーマットを確認すること

## [Govcloud Us] Amazon RDS now supports the latest Cumulative Update and GDR updates for Microsoft SQL Server

- **公開日**: 2026-10-26 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-rds-supports-latest-cumulative-update-gdr-microsoft-sql-server/

### 概要

Amazon RDS for SQL Server が Microsoft SQL Server の最新 Cumulative Update(CU) と General Distribution Release(GDR) をサポートしました。複数の SQL Server バージョン向けに RDS エンジンの新しいバージョンが提供されています。

### 変更内容・新機能の詳細

今回のリリースでは以下の SQL Server 更新が RDS 上で利用可能になりました。各更新は Microsoft の KB に記載された修正・改善を含みます。

- SQL Server 2017: CU31 + GDR KB5122774 (RDS エンジン 14.00.3550.4.v1)
- SQL Server 2019: CU32 + GDR KB5122772 (RDS エンジン 15.00.4490.9.v1)
- SQL Server 2022: CU27 KB5104824 (RDS エンジン 16.00.4295.3.v1)
- SQL Server 2025: CU9 KB5122048 (RDS エンジン 17.00.5005.3.v1)

GDR(General Distribution Release) は主にセキュリティ修正や緊急パッチを含み、CU はそれまでの累積的な修正と改良を含む更新です。RDS ではこれらの更新を適用するために、AWS マネジメントコンソール、AWS CLI、または SDK を使って DB インスタンスのアップグレードを行います。アップグレード前にスナップショット取得やステージングでの互換性検証を行うことを推奨します。アップグレードにはインスタンスの再起動や短時間の接続中断が伴う場合があります。詳細は各 KB と Amazon RDS SQL Server のアップグレード手順を参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: DB 管理者、アプリ開発者、SRE/運用チーム
- **利用シーン**: セキュリティ修正の適用、既知バグやパフォーマンス修正の反映、準拠要件対応
- **運用効果**: セキュリティリスク低減と安定性向上により障害やインシデントの抑止が期待できる
- **注意点**: アップグレードに伴う再起動・短時間のダウンタイムと互換性確認が必要

### 技術的な注意点

- **IAM権限**: rds:ModifyDBInstance、rds:RebootDBInstance、rds:CreateDBSnapshot 等の権限を持つことを確認してください
- **バックアップ/テスト**: 本番適用前にスナップショットを取得し、ステージング環境でアプリ互換性とクエリ動作を検証してください
- **ダウンタイム**: バージョン適用で再起動が発生する可能性があり、メンテナンスウィンドウの調整が必要です
- **リージョン制限**: 記事は GovCloud (US) カテゴリで公開されています。各リージョンでの提供状況はコンソールまたはドキュメントで確認してください
- **互換性**: 新しい CU/GDR でデータベース互換レベルや非推奨機能の振る舞いが変わる可能性があるため、アプリ側の互換性検証を行ってください
- **コスト**: RDS 側の追加料金は通常発生しませんが、ダウンタイムによる業務影響や検証コスト、必要に応じたインスタンス変更による料金変動は考慮してください
