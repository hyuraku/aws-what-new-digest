## [RDS] Amazon RDS for Oracle now supports September 2026 Monthly Recommended Patch

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-rds-oracle-september-mrp

### 概要

Amazon RDS for Oracle が Oracle Database の September 2026 Monthly Recommended Patch (MRP) をサポートしました。19c および 26ai 向けのこの MRP は 2026 年 7 月の RU の上に適用され、Oracle の 2026 年 9 月 CSPU と更新されたタイムゾーンファイル（DST v46）を含みます。

### 変更内容・新機能の詳細

MRP（Monthly Recommended Patch）は四半期ごとの Release Update (RU) をベースに、Oracle の Critical Security Patch Update (CSPU) と Oracle 推奨の追加修正をまとめたマイナーエンジンバージョンです。今回の September 2026 MRP は 2026-07 RU の上に適用される形で提供され、Oracle の 2026 年 9 月 CSPU を含んでいます。加えてタイムゾーンファイル DST version 46 を含み、ブリティッシュコロンビア州・アルバータ州（カナダ、2026-11-01 発効）やモロッコ／西サハラ（2026-09-20 発効）などの夏時間／UTCオフセットの変更を反映します。RDS 上では新規インスタンス作成時にこの MRP を選択するか、既存インスタンスをエンジンバージョン 19.0.0.0.ru-2026-07.mrp-2026-09.r2 または 26.0.0.0.ru-2026-07.mrp-2026-09.r2 にアップグレードできます。適用は Amazon RDS コンソール、AWS CLI、または SDK から実行可能です。セキュリティ修正が含まれるため適用を推奨します。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for Oracle（Oracle Database 19c または 26ai）を利用している DB 管理者、SRE、アプリケーション開発者
- **利用シーンまたは効果**: セキュリティパッチ（CSPU）の適用およびOracle推奨の修正を迅速に反映することで既知脆弱性を解消し、タイムゾーン規則変更を反映してタイムスタンプデータの整合性を保つ
- **運用効果**: セキュリティリスク低減、法令や地域ルールによる時刻ズレの防止、ダウンタイムを計画して適用すれば安定した運用維持が可能

### 技術的な注意点

- **IAM権限**: ModifyDBInstance、DescribeDBInstances、CreateDBSnapshot などの RDS 操作権限が必要です
- **ダウンタイム/再起動**: エンジンバージョンのアップグレード適用時は DB インスタンスの再起動が発生し、短時間のダウンタイムが必要になります（即時適用またはメンテナンスウィンドウでの適用を選択可能）
- **バックアップ**: アップグレード前にスナップショットやバックアップの取得を推奨します（ロールバック手順の準備）
- **パラメータ/互換性**: カスタム DB パラメータグループや拡張機能（互換性パラメータ）が影響を受ける可能性があるため事前に検証・テストしてください
- **リージョン制限**: 新しい MRP はリージョン毎のリリースタイミングが異なる場合があります。適用可否は Amazon RDS for Oracle のリリースノートで確認してください
- **コスト**: MRP 適用自体に追加課金は通常発生しませんが、新規インスタンス作成やテスト環境の利用は通常の RDS 課金が適用されます
- **タイムゾーン影響**: DST v46 の適用により対象地域のタイムゾーンが恒久的にUTCオフセットに移行します。TZ付きタイムスタンプを保存・表示するアプリケーションは動作確認と表示ロジックの見直しを行ってください

### 参考情報

- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_Oracle.html

## [Bedrock] Amazon Bedrock AgentCore CLI version 1.0 is now available

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-bedrock-agentcore-cli-version-1-0-available/

### 概要

Amazon Bedrock の AgentCore CLI がバージョン 1.0（@aws/agentcore 1.0.0）で一般提供開始されました。起動高速化、コマンド構造の一貫化、およびより多くの AgentCore リソース直接操作のサポートが追加されています。

### 変更内容・新機能の詳細

AgentCore CLI v1.0 は再設計され、ターミナルから AI エージェントおよびその周辺リソース（ハーネス、ランタイム、メモリ、アイデンティティ、ゲートウェイ、支払い設定など） を作成・開発・デプロイ・運用できるツール群を一貫した操作性で提供します。主な技術的変更点は以下の通りです。
- 起動速度改善: CLI の起動時間が短縮され、インタラクティブ操作の待ち時間が減少します。これにより反復的な開発フローが高速化されます。
- 一貫したコマンド構造: グローバルフラグ（--region、--output json、--debug、--version 等）が全コマンドで統一され、スクリプト化や自動化が容易になっています。
- プロジェクトに依存しないリソース操作: 従来はプロジェクトに追加する必要があったハーネスやランタイム等を、事前にプロジェクト化せずに ID/ARN 指定で直接操作・呼び出し可能になりました。
- インタラクティブ機能の強化: 既存リソースを ID/ARN で呼び出す、対話シェルの起動、ハーネスのエクスポート、検索可能なメニュー／リソースピッカー、ガイド付きワークフローが利用可能です。
- 移行サポート: 既存の AgentCore プロジェクトは agentcore migrate コマンドで v1 へ移行できます（移行ルールに従って自動・半自動変換）。
- 入手経路: npm（@aws/agentcore 1.0.0）からインストール可能で、ソースは GitHub で公開されています。
これらにより、開発者はローカル端末から迅速にエージェント開発パイプラインを回せるようになり、スクリプトや CI/CD に組み込みやすい一貫性のある CLI 操作が可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: AI エージェント開発者、プラットフォームエンジニア、SRE、DevOps チーム
- **利用シーンまたは効果**: ターミナルから直接ハーネスやランタイム等の構成管理・デプロイを行うことで、プロトタイピングや本番デプロイの速度が向上。既存リソースの ID/ARN 指定や対話シェルで運用タスクが簡素化される
- **運用効果**: 起動高速化と統一フラグによりスクリプトや CI/CD の信頼性が上がり、手動運用コストとヒューマンエラーが低減される
- **移行影響**: 既存プロジェクトは agentcore migrate で移行可能だが、移行前に設定のバックアップや互換性チェックが必要

### 技術的な注意点

- **IAM権限**: AgentCore が操作する Bedrock/関連リソースに対する適切な IAM 権限（作成/更新/参照/削除）が必要です。CLI 自体は権限チェックを行いますが、事前にポリシーを確認してください
- **インストール要件**: Node.js と npm が必要です（@aws/agentcore パッケージをインストールして使用します）。グローバルインストールやプロジェクト依存のインストール方法を検討してください
- **リージョン制限**: Bedrock および AgentCore の一部機能は利用可能リージョンが限られる可能性があります。使用予定リージョンでの対応状況を確認してください
- **コスト**: CLI 自体はオープンソース/無償ですが、CLI 経由で作成・操作する Bedrock のモデル実行・ストレージ・ネットワーク等は通常の AWS 課金対象です。リソース作成時の料金に注意してください
- **移行手順**: agentcore migrate コマンドで自動移行をサポートしますが、移行前にプロジェクトのバックアップを取り、移行後のテストを必ず行ってください。破壊的変更がある可能性に備えてステージングで検証することを推奨します
- **セキュリティ注意**: --output json や --debug フラグで機密情報（ARN、トークン等）が表示される可能性があります。ログ保管や CI 環境での扱いに注意してください
- **互換性**: v1.0 でコマンド名やオプションに変更がある場合があります。既存自動化スクリプトは移行後に動作確認・修正が必要です

## [Lambda] AWS Lambda supports Seekable OCI (SOCI) lazy loading for Lambda Managed Instances 

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-lambda-seekable-oci-soci/

### 概要

AWS Lambda が Lambda Managed Instances 上で実行する OCI イメージ（Event Functions）に対して、Seekable OCI (SOCI) による遅延ロード（lazy loading）をサポートしました。これにより、実行環境の起動時に必要なファイルのみをオンデマンドで取得でき、コンテナの起動時間を最大で約70%短縮できます。

### 変更内容・新機能の詳細

SOCI は OCI イメージ層内のファイル配置を示す索引（テーブル・オブ・コンテンツ）を作成し、ランタイムがイメージ全体をダウンロードする代わりにファイル単位で必要なデータをストリーミング取得できる仕組みです。Lambda Managed Instances 上で SOCI を使用するには、コンテナイメージに対して SOCI インデックスを作成し、そのタグ（例: my-function:v1-soci）を Amazon ECR にプッシュします。関数を作成・更新して SOCI インデックス付きのイメージ URI を指定してバージョンを公開すると、Lambda が自動で SOCI を検出して遅延ロードを有効化します。結果として、特に数GBにおよぶ大きなコンテナイメージを使うデータ処理パイプライン、高スループット API、バッチ計算などのスケール時に、新規実行環境プロビジョニングの待ち時間が大幅に短縮されます。Agent Toolkit 経由で Kiro、Claude Code、Codex 等のコーディングアシスタントを使う場合は、Lambda Managed Instances のスキルをインストールしてエージェントから設定・デプロイできます。対応はすべての商用リージョン（Lambda Managed Instances 提供リージョン）で利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発者、SRE/運用チーム、データエンジニア（大規模コンテナイメージを使う Lambda 関数を運用する組織）
- **利用シーン**: 大容量イメージを用いるデータ処理パイプライン、高スループット・低レイテンシ API バックエンド、バッチ計算ワークロードのスケールアウト時の起動最適化
- **運用効果**: 実行環境の起動時間を最大約70%短縮し、スケール時のウォームアップ時間・コールドスタートの影響を低減。イメージ全体のダウンロードを避けることでネットワーク帯域とプロビジョニング時間を削減し、オートスケール応答性が向上します。

### 技術的な注意点

- **IAM権限**: ECR へ SOCI インデックスとイメージを push する権限（ECR への書き込み）や、デプロイ時の Lambda 関数作成/更新に必要な IAM 権限を事前に用意してください
- **リージョン制限**: Lambda Managed Instances が提供されている商用リージョンで利用可能です。該当リージョンで Lambda Managed Instances がサポートされていることを確認してください
- **コスト**: SOCI インデックス自体のストレージは小さく追加コストは限定的ですが、ECR ストレージやデータ転送量が発生します。起動時間短縮は間接的にオペレーショナルコスト削減につながる場合があります
- **イメージ互換性**: SOCI は OCI 形式イメージに対する索引化が前提です。既存の Docker レジストリイメージをそのまま使う場合は OCI 形式への変換や SOCI インデックス作成が必要です
- **導入手順の注意**: SOCI インデックスを作成して ECR に push した後、関数のイメージ URI を SOCI 対応のタグ（例: my-function:v1-soci）に設定して関数バージョンを公開する必要があります。Lambda は自動検出しますが、タグ付けミスに注意してください
- **ツールチェーン**: SOCI インデックス作成ツールや ECR の手順に慣れておくと導入がスムーズです。Agent Toolkit 経由の自動化を使う場合は、Lambda Managed Instances スキルをエージェントにインストールしてください
- **デバッグ/運用**: 遅延ロードにより起動シーケンスが変更されるため、起動時に参照されるファイルが正しく索引化されているか（必要なファイルのパス／バイト範囲が正確か）を検証してください

- https://docs.aws.amazon.com/lambda/latest/dg/lambda-managed-instances.html

## [Opensearch Service] Introducing time series collections for the next generation of Amazon OpenSearch Serverless

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Opensearch Service
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/time-series-collection-next-generation-opensearch-serverless/

### 概要

Amazon OpenSearch Serverlessの次世代で「time series collections」が利用可能になりました。ログ／メトリクス／トレース／イベントを単一コレクションでサーバーレスに取り込み・保存・検索でき、ホット／ウォームのストレージ階層、アラートや異常検知機能が追加されています。

### 変更内容・新機能の詳細

time series collectionsは、プロビジョニング不要のサーバーレス環境で時系列データ（ログ、メトリクス、トレース、イベント）を取り込み、短期は高速にクエリできるホット層、長期は低コストで保存するウォーム層を同一コレクション内で運用できる機能です。特徴的な技術点は次の通りです。
- 自動スケーリングによるインジェストスパイク吸収: クラスタ管理やノード調整なしに大量一時流入を処理します。
- ホット／ウォーム階層: ホットストレージは高パフォーマンスで、コレクションあたり最大100 TBまで利用可能。ウォームは低コストな長期保存層で、データをホットに保持する期間をユーザが設定し、その後自動で移行します。
- 単一コレクションでの混在保存: 最近のデータを高速にクエリしつつ、数ヶ月〜数年の履歴を低コストで保持・検索可能です。
- 組み込みアラートと異常検知: 外部ツール不要で、データ変化に対する通知やパターン検出が可能になります。
- 利用可能リージョン: OpenSearch Serverlessが提供されているすべてのAWSリージョンで利用可能。
運用上は、保持期間（ホット→ウォームの遷移ポリシー）、コスト最適化（ウォームの利用比率）、およびアラート/検知ルールの設計が重要になります。料金や細かい制限はOpenSearch Serverlessの料金ページとドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: SRE/運用チーム、プラットフォーム/インフラエンジニア、セキュリティアナリスト、IoT/観測データを扱うプロダクトチーム
- **利用シーン**: アプリケーション監視、セキュリティログ分析、IoTテレメトリ集約、長期ログ保持と検索、イベントドリブンのアラート発行
- **運用効果**: クラスタ管理負荷の削減とスパイク耐性の向上、ホットストレージコストの削減（ウォーム層への自動移行による）、アラートと異常検知を統合することでツールチェーンを簡素化

### 技術的な注意点

- **IAM権限**: OpenSearch Serverlessのコレクション作成/管理、アラート・異常検知の設定に必要なIAM権限を設定してください（細かい権限は公式ドキュメントを参照）。
- **リージョン制限**: OpenSearch Serverlessが提供されているリージョンでは利用可能ですが、利用前に対象リージョンでの提供状況を確認してください。
- **コスト**: ウォームストレージはホットより低コストですが、保存容量とデータ転送・クエリに対する課金が発生します。ホット保有期間の設定によりコスト最適化が可能なので料金ページで単価を確認してください。
- **ストレージ制限**: ホットストレージはコレクションあたり最大100 TBが上限として明示されています。超過するワークロードは設計を見直すか複数コレクションで分割する必要があります。
- **データライフサイクル**: ホット→ウォームへの移行ポリシーを必ず設計・テストしてください。移行のタイミングはクエリ遅延やコストに影響します。
- **互換性/移行**: 既存のOpenSearch/OpenSearch Serverless構成からの移行時はインデックスマッピングやクエリの挙動差分を確認してください。
- **監視とクォータ**: 自動スケーリングはあるものの、アカウント/リージョンのクォータやAPI制限に注意し、必要に応じてクォータ引き上げ申請を行ってください。
- **アラート/異常検知**: 検知ルールや通知チャネル（SNSなど）の設定が別途必要になる場合があります。特になしではありません—設定と権限を確認してください。

## [Aiml] Quick now supports smart approvals for agentic actions

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Aiml
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/quick-smart-approvals-agentic-actions/

### 概要

Amazon Quickにスマート承認（smart approvals）が追加され、エージェントが行う定型的な操作を自動承認しつつ、重要な操作はユーザーにレビューさせることで承認疲労を低減しつつ人的監督を維持します。

### 変更内容・新機能の詳細

スマート承認は、エージェントがユーザーに代わって行う候補アクションを別のレビュー用モデル（classifier）で評価し、ルーチンな操作は自動で承認、影響の大きい操作はユーザーへ振り分けてレビューを要求します。既存のポリシーが常に優先され、スマート承認はユーザー設定が「毎回確認（ask）」になっているアクションのみを評価します。拒否されたアクションは引き続き拒否されたままであり、スマート承認が新しいアクセス権を付与することはありません。classifierは外部送信（組織外へのコンテンツ送信）、権限変更、コンテンツ削除、支払い実行、ユーザー要求の範囲を超える操作などを高影響アクションとしてユーザーに回します。自動承認が適用される場合でも、その承認はレビューされた「その特定のアクション」にのみ有効です。レビューが失敗するかタイムアウトした場合、アクションはユーザーの確認にフォールバックします。スマート承認は全ユーザーでデフォルトONですが、管理者はカスタム権限で利用可能者を制御でき、ユーザーはチャットのオプションから会話やスケジュール実行に対してオフにできます。AWS CloudTrailはスマート承認を経由した各アクションレビューおよびユーザーのスマート承認設定変更を記録します。スマート承認は、Amazon Quickのエージェンティック機能がサポートされるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: プロダクト開発者、AI/エージェント利用者、SRE/運用チーム、セキュリティ管理者
- **利用シーンまたは効果**: 定型的なメール送信、レコード更新、チケット作成などを自動承認してヒューマンレビューの負荷を下げる。重要操作（権限変更、削除、支払い、組織外送信など）は都度ユーザーレビューに回されるため誤操作のリスクを低減
- **運用効果**: 承認フローの効率化（承認待ちボトルネックの削減）と、重要操作への監視強化でコンプライアンス維持を両立
- **管理者への影響**: 管理者はカスタム権限で誰がスマート承認を使えるか制御でき、設定のデフォルトはONのためポリシー設計と権限管理を早急に見直す必要がある
- **監査・コンプライアンス**: CloudTrailにレビュー履歴と設定変更が記録されるため監査証跡を確保できる

### 技術的な注意点

- **IAM権限**: 管理者はスマート承認の利用を制御するためのカスタム権限ポリシーを設定可能。ユーザーがオフにできる点も考慮して権限設計を行ってください

- **セキュリティ**: スマート承認は新たなアクセス権を付与しないため、権限昇格のリスクはない設計ですが、権限変更や外部送信といった高影響操作は必ずユーザーの確認が必要です
- **コスト**: 発表時点でスマート承認自体の追加料金は明示されていません。ただし、Amazon Quickやエージェント機能の利用に伴う通常の料金は発生します。CloudTrailログ保存等の関連コストも考慮してください

### 変更内容・新機能の詳細

Amazon EKS Dashboardは、AWS Organizationsを通じて複数アカウント・リージョンのクラスタ情報を集約して表示します。本アップデートにより各EKSクラスタのCAローテーションステータス（CAの有効期限、期限切れが近いクラスタ、自動ローテーション予定イベントなど）をフリート単位で可視化可能になりました。EKSクラスタは各々固有のCAを持ち、2018年以降に作成されたクラスタのCAは10年の有効期間を持つため、ローテーション開始時期が近づいているクラスタがあることが多く、プラットフォームチームはダッシュボードで優先度を付けて対応できます。ダッシュボードは管理アカウントでAWS Organizationsの「trusted access」を有効化することでデータを集約し、表示はus-east-1(米国東部)から行います。CAローテーションの可視化自体は追加料金なしで提供され、CAローテーションのステータス表示は全ての商用リージョンを対象にしています。なお、ダッシュボードは状況の可視化を行うもので、実際のローテーション作業（必要に応じたクラスタ側の操作やクライアント設定更新など）は別途実施または確認が必要です。

- **セキュリティ効果**: CAの期限切れによる証明書信頼障害や接続断を未然に防止し、コンプライアンス基準の維持に寄与

- **IAM権限**: AWS Organizationsの管理アカウントでtrusted accessを有効にするための権限（Organizationsの設定権限）およびダッシュボード閲覧用のEKS関連権限が必要です
- **リージョン制限**: ダッシュボードはus-east-1から表示しますが、CAローテーションのステータス集約は全ての商用リージョンを対象としています

## [ECS] Amazon ECS Managed Instances adds cross-instance and Spot consolidation

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: ECS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/ecs-managed-instances-consolidation/

### 概要

Amazon ECS Managed Instancesにクロスインスタンス（cross-instance）とSpot統合（Spot consolidation）の最適化機能が追加され、複数インスタンスに分散する未活用リソースを横断的に再配置して利用率を高め、コスト削減を図れるようになりました。Spot容量にも同様の統合が適用されます（置換容量の確認後）。

### 変更内容・新機能の詳細

従来のECS Managed Instancesのインフラ最適化は「各インスタンスを個別に評価」して未利用インスタンスを統合していましたが、今回の更新で「複数インスタンスを同時に評価してタスクを詰め直す」クロスインスタンス統合が可能になりました。これにより、インスタンスタイプの選択肢が狭いCapacity Provider環境でも、複数の小さな未利用インスタンスをまとめて少数のインスタンスへリパッキングでき、全体のCPU/メモリ利用率を向上させます。Spot統合は同じ手法をSpotインスタンスに適用しますが、実行前に置換用のキャパシティ（同等のSpot/オンデマンド容量）が利用可能かを確認してから統合を実行することで、意図しないタスクの停止やキャパシティ不足を回避します。ECS Managed Instancesの既存の「start-before-stop」によるタスク置換フローは引き続き用いられ、ダウンタイムを最小化します。記事のテスト例では、c9gのCapacity Provider（最小サイズ: 4xlarge）で261タスク（各1 vCPU、1.94 GiB）を稼働させた場合、インスタンス数を19台から13台に削減し、CPU利用率を42%→91%、メモリ利用率を41%→88%に改善しています。新機能は追加料金なしで全リージョンに展開され、既存・新規のECS Managed InstancesのCapacity Providerに自動適用されます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon ECS Managed Instancesを利用しているクラウド運用者、SRE、コスト最適化担当者
- **利用シーンまたは効果**: 未利用/低利用のEC2インスタンスが多いワークロードの統合によるコスト削減（オンデマンドおよびSpot双方）とリソース利用率向上
- **運用効果**: インスタンス台数削減によるEC2コスト低減、CPU/メモリ利用率向上でリソース効率が改善される。Spotでは置換容量がある場合にのみ安全に統合され、予期せぬタスク停止を抑制可能
- **適用範囲**: ECS Managed Instances（AWSがプロビジョニング／運用するEC2ベースのCapacity Provider）に自動適用。セルフマネージドのEC2クラスターやFargateには影響しない

### 技術的な注意点

- **IAM権限**: 追加のIAM権限をユーザー側で付与する必要は基本的にありませんが、Capacity ProviderやECSの既存スケーリング/配置ポリシーが統合動作に影響する可能性があるため設定を確認してください
- **リージョン制限**: 記事の通り「全AWSリージョンで利用可能」とされています
- **コスト**: 機能自体に追加料金は発生しませんが、実際のコスト影響はインスタンス台数・Spot利用割合の変化によります。統合によりオンデマンド/Spotの利用比率が変わる可能性があります
- **Spot固有注意点**: Spot統合は置換用キャパシティの確認後に実行されるため、Spot供給が逼迫していると統合が保留される場合があります。急激なSpot市場変動時は期待する削減が得られないことがあります
- **タスク配置制約**: 特定のインスタンスタイプやアーキテクチャ（GPU、特殊ハードウェア）、タスク配置制約（インスタンスラベルやアフィニティ）を使用している場合、統合の効果が限定されることがあります
- **運用監視**: 統合アクションは自動実行されるため、CloudWatchメトリクスやイベント、ECSのアクティビティログで置換/スケール操作を監視してください
- **既存環境への影響**: 自動適用されるため、Capacity Providerの構成が特に制限的な環境では計画的な検証を推奨します

## [Lambda] AWS Lambda durable functions now exports live telemetry for execution insights 

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/lambda-durable-telemetry/

### 概要

AWS LambdaのDurable Execution Telemetry Exporterは、Lambda Durable Functionsの実行履歴（ステップ入力/出力、実行状態、タイミング、エラー等）をリアルタイムで外部宛先へエクスポートし、長期保存やAIエージェントによる自然言語クエリを可能にする観測プラグインです。

### 変更内容・新機能の詳細

本プラグインはLambda Durable Functions向けの観測（telemetry）エクスポーターで、各実行のステップ単位の履歴（実行ステータス、各オペレーションの開始/終了時刻、ステップの入力と出力、発生したエラーなど）を取得して、あらかじめ設定した1つ以上の出力先に送信します。出力先は13の組み込みデスティネーションに対応しており、例としてAmazon CloudWatch Logs、Amazon S3（Athenaでのクエリ用）、Amazon DynamoDB、Amazon Aurora、Amazon OpenSearch Serviceなどが含まれます。エクスポート前に機密フィールドのマスキング（redact）を行うオプションや、送信データ量を制御するサンプリング率の指定が可能です。さらに、Model Context Protocol（MCP）サーバーが提供され、これをAIエージェント（記事例: Kiro）に組み込むことで、自然言語でエクスポート済みのテレメトリを検索・解析できます。エクスポーターはTypeScript、Python、Java、Goの各ランタイムをサポートしています。導入は、エクスポーターのインストール、関数ハンドラへのプラグイン登録、必要に応じてMCPサーバーをエージェントに追加する、という流れです。この記事時点では、追加料金は発生せず、Lambda durable functionsをサポートする全リージョンで利用可能とされています（ただし各出力先の通常のストレージ／利用料金は別途発生）。

### 影響範囲・利用シーン

- **対象ユーザー**: サーバレス/クラウドエンジニア、SRE、開発者、AIワークフロー設計者、ビジネスアナリスト
- **利用シーン**: マルチステップの耐久処理（Durable Functions）の詳細な実行トレース保存や長期保持、障害解析、KPIやビジネスイベントの抽出、AIエージェントによる自然言語クエリによるオペレーショナル検索
- **運用効果**: ステップ単位の履歴により障害原因の迅速特定や再現性の向上が可能。S3/Athenaなどへエクスポートすれば長期保存と大規模分析が可能になり、オンコール対応の効率化やビジネス分析への活用が容易になる

### 技術的な注意点

- **IAM権限**: 出力先への書き込み権限（例: s3:PutObject、logs:PutLogEvents、dynamodb:PutItem、rds/Aurora接続権限、es:ESHttpPut 等）が必要です。MCPサーバー経由でのクエリにも適切な認可を設定してください。
- **リージョン制限**: 本機能は「Lambda durable functions」をサポートするリージョンで利用可能です。利用前に対象リージョンでのサポート状況を確認してください。
- **コスト**: エクスポーター自体に追加料金はありませんが、エクスポート先（S3、CloudWatch Logs、DynamoDB、Aurora、OpenSearchなど）のストレージ、クエリ（Athena等）やリクエストに対する通常料金が発生します。高頻度や詳細トレースはコスト増に繋がるため、サンプリングやフィルタリングの設定で制御してください。
- **データ量とサンプリング**: ステップ単位の詳細データは高いボリュームになるため、サンプリング率設定や重要なフィールドのみエクスポートする設定で運用負荷を抑制してください。
- **機密情報**: フィールドのマスキング（redaction）機能を利用してPII/機密データを除外してください。出力先の暗号化（S3のSSE、RDS/Auroraの暗号化等）とアクセス制御を併せて設定することを推奨します。
- **デスティネーション固有の注意**: 各デスティネーションはスキーマやレコードサイズ、スループット制限が異なります。例えばS3→Athenaを想定する場合はクエリ効率を考えたファイル形式（Parquet/JSON）設計、OpenSearchはシャード/インデックス設計に注意してください。
- **言語/導入手順**: TypeScript、Python、Java、Goをサポート。導入は(1)エクスポーターをインストール、(2)関数ハンドラにプラグイン登録、(3)必要に応じてMCPサーバーをエージェントに追加する流れです。
- **セキュリティ/アクセス制御**: MCPサーバー経由での自然言語クエリは強力ですが、テレメトリへのアクセス範囲とログの可視化権限を厳密に管理してください。ネットワーク配置（VPCエンドポイント、プライベート接続）や認証・監査の設計が重要です。
- **互換性/保持期間**: エクスポートにより標準のLambdaログ保持期間の制限を超えて歴史を保持できます。既存のログ・監視構成との整合性を確認してください。
