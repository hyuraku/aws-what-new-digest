## [Step Functions] AWS Step Functions workflows now available as AI agent tools

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Step Functions
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/step-functions-workflows-ai-agent-tools/

### 概要

Amazon BedrockのAgentCore Gatewayを通じて、既存のAWS Step Functions（Standard/Express）ワークフローをAIエージェントの「ツール」として利用できるようになりました。エージェントが実行タイミングと入力を決め、Step Functionsは定義どおりに各ステップを実行します。

### 変更内容・新機能の詳細

AgentCore GatewayはModel Context Protocol（MCP）を介してAIエージェントと外部ツールを接続します。本アップデートにより、エージェントはStep Functionsコネクタを呼び出してマルチステップの業務プロセス（例：返金フロー、承認ワークフロー、障害対応の診断手順など）を順序どおりに実行できます。対象は既存のStandardおよびExpressワークフローで、Step Functionsは220以上のAWSサービスと連携して分散アプリケーションをオーケストレーションします。エージェントはワークフロー実行の開始だけでなく、実行履歴の照会（失敗したランや該当ステップの特定）も可能なため、オンコール対応や運用調査を自動化・支援できます。本機能はAgentCore Gatewayが利用可能なすべてのAWSリージョンで有効で、課金はStep FunctionsとAgentCore Gatewayの標準料金が適用されます。導入はStep Functions開発者ガイドのチュートリアルおよびAgentCore Gatewayのコネクタ設定を参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: AIエージェントを運用・開発するSRE、機械学習エンジニア、アプリ開発者、運用チーム
- **利用シーン**: 自動化されたカスタマーサポート（返金・エスカレーション）、運用エージェントによる障害箇所の特定、AIによる業務フロー起動と監査トレース
- **運用効果**: 手順の一貫性確保（定義どおりに毎回実行）、オンコール対応時間短縮（失敗ステップの直接特定）、既存ワークフロー資産の再利用による開発コスト削減

### 技術的な注意点

- **IAM権限**: エージェントがStep Functionsを起動・照会できるよう、適切なIAMロール/ポリシー（states:StartExecution, DescribeExecution, ListExecutionsなど）を付与してください
- **リージョン制限**: 本機能はAgentCore Gatewayが利用可能なリージョンで有効です。AgentCore Gateway非対応リージョンでは利用できません
- **コスト**: Step Functions（Standard/Express）とAgentCore Gatewayの標準課金が適用されます。ワークフロー実行数や実行時間、AgentCore Gatewayの料金を想定してコスト見積りを行ってください
- **Step Functionsタイプ**: StandardおよびExpressワークフローがサポートされています。要件に応じたタイプ選択（耐久性、実行時間、コスト特性）を行ってください
- **接続方式/MCP**: AgentCore GatewayはModel Context Protocolを使ってエージェントと連携します。コネクタの設定でエージェントが渡す入力フォーマットと結果の扱いを定義してください
- **実行保証/順序**: Step Functionsはワークフロー定義どおりに各ステップを実行しますが、エージェントが渡す入力次第で挙動が変わる点に注意してください
- **監査/ログ**: 実行履歴、CloudWatch Logs/Events、X-Ray（必要に応じて）を有効化して監査・デバッグに備えてください
- **設定手順**: AgentCore Gateway側のStep Functionsコネクタ設定とワークフローARNの提供が必要です。サポートされる操作やセットアップ詳細はコネクタドキュメントを参照してください

## [DynamoDB] Amazon DynamoDB Accelerator (DAX) is now available in additional Regions

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: DynamoDB
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/dax-additional-regions/

### 概要

Amazon DynamoDB Accelerator (DAX) がカナダ（Central）とアフリカ（Cape Town）リージョンでも利用可能になりました。DAX は DynamoDB 向けのフルマネージドなインメモリキャッシュで、読み取り性能を最大10倍（ミリ秒→マイクロ秒レベル）向上させます。

### 変更内容・新機能の詳細

DAX は DynamoDB と API 互換のフルマネージド、マルチノードのインメモリキャッシュサービスで、読み取り集中型およびバースト型ワークロード（リアルタイム入札、ゲームのランキング、商品カタログなど）でのレイテンシを単桁ミリ秒からマイクロ秒に改善します。今回の更新で Canada (Central) と Africa (Cape Town) リージョンでも DAX クラスターを作成できるようになり、リージョン内にキャッシュを保持して低レイテンシ要件を満たすことが可能です。DAX はフルマネージドで自動パッチ適用や障害時のフェイルオーバーを提供し、既存の DynamoDB アプリケーションへは最小限のコード変更（DAX エンドポイントへの接続に置き換える等）で導入できます。大規模スループット（百万リクエスト/秒規模）にも対応する設計で、DAX クラスターは複数のノードで構成し可用性向上のためにAZにまたがって配置できます。

### 影響範囲・利用シーン

- **対象ユーザー**: DynamoDB を使用するアプリケーション開発者、SRE/運用チーム、ゲーム開発者、広告配信やEコマースなど低レイテンシ読み取りが重要なサービス運用者
- **利用シーン**: リアルタイム入札、ゲームのランキング表示、商品カタログ検索、読み取り負荷が高い API やピーク時トラフィックの吸収
- **運用効果**: 読み取り負荷を DynamoDB からオフロードしてレイテンシを大幅に低減し、スループット効率を改善。リージョン内にキャッシュを保持できるためデータ主権や低遅延要件を満たせる

### 技術的な注意点

- **IAM権限**: DAX クラスターの作成・管理には適切な IAM 権限（dax:* 系の権限や関連する EC2/VPC 権限）が必要です。アプリ側は DAX クライアントの実行に必要な権限を確認してください
- **リージョン制限**: 今回は Canada (Central) と Africa (Cape Town) が追加。全リージョンで利用可能ではないため、利用前に AWS Regional Services ページで対応リージョンを確認してください
- **コスト**: DAX ノード（インスタンスタイプ）に対する時間課金とデータ転送コストが発生します。読み取りオフロードによる DynamoDB 読み取り容量削減でトータルコストが下がる場合もありますが、事前に試算してください
- **ネットワーク/VPC**: DAX クラスターは VPC 内に配置されます。セキュリティグループ、サブネット設定とアプリケーションの接続経路（同一 VPC または VPC ピアリング/Transit Gateway 等）を確認してください
- **互換性・整合性**: DAX は DynamoDB API 互換ですが、キャッシュの整合性や TTL、キャッシュ無効化の挙動は DynamoDB 直接アクセスと異なる場合があります。強整合読み取りやトランザクションの扱いは確認・テストが必要です
- **運用/可用性**: DAX は自動フェイルオーバーとパッチ適用を提供しますが、クラスター設計（ノード数、AZ 配置）によって可用性挙動が変わるため運用要件に合わせた構成が必要です
- **移行作業**: 既存アプリは通常 DAX エンドポイントに接続先を切り替える程度で導入可能ですが、SDK の DAX クライアントの利用や接続設定の変更、性能テストを事前に行ってください

## [CloudWatch] Amazon Managed Grafana now supports in-place upgrade to Grafana version 13.2

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: CloudWatch
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/managed-grafana-upgrade-version-13-2/

### 概要

Amazon Managed Grafana (AMG) がワークスペースのインプレースアップグレードで Grafana 12.4 から 13.2 へ移行できるようになりました。Grafana 13 系で追加された Git Sync、動的ダッシュボード、CloudWatch データソースの PromQL サポートなどの機能を利用可能になります。

### 変更内容・新機能の詳細

今回のアップグレードはインプレース（既存ワークスペース上での直接更新）で行え、Grafana OSS の 13.0～13.2 で導入された機能を取り込みます。主な新機能は以下の通りです。
- Git Sync（ダッシュボードをコード化）: ワークスペースを Git リポジトリにリンクしてダッシュボードのバージョン管理・変更追跡・差分レビュー・ロールバックを行えます。CI/CD やプルリクエストを組み合わせた運用が可能です。
- 動的ダッシュボード: データや変数の状態に応じてレイアウトやパネルを動的に切り替える条件駆動のビューを作成でき、レスポンシブかつコンテキスト依存の可視化が容易になります。
- CloudWatch データソースの PromQL サポート: CloudWatch が OTLP（OpenTelemetry）経由で受け取ったメトリクスに対して Prometheus Query Language（PromQL）でクエリを実行できるようになり、既存の Metric Search や Metrics Insights と併用できます。
アップグレードは AMG が一般提供されている全リージョンでサポートされ、AWS コンソール、AWS SDK、AWS CLI から数クリック／API 呼び出しで実行できます。詳細は Amazon Managed Grafana ユーザーガイドの「Differences between Grafana versions」およびワークスペースのバージョン更新手順を参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: SRE、監視・可観測性チーム、ダッシュボード作成者（ダッシュボードをコード化したい開発チーム）
- **利用シーンまたは効果**: Git Sync によりダッシュボードの変更管理とレビューが可能になり、変更のトレーサビリティと共同作業が向上します。動的ダッシュボードにより状況依存の可視化が実現し、多様な環境・サービスの監視テンプレートを柔軟に構築できます。CloudWatch の PromQL サポートにより、OTLP 経由で取り込んだメトリクスに対して Prometheus 互換のクエリが使え、既存の PromQL ノウハウを活用して高度な分析が可能になります。

### 技術的な注意点

- **IAM権限**: ワークスペースのバージョン更新には該当する IAM 権限（例: grafana の更新操作権限）が必要です。Git Sync 用に外部 Git へのアクセス設定（トークンや認証情報）も必要になります。
- **リージョン制限**: 記事によれば AMG が一般提供されている全リージョンでサポートされていますが、実際に利用するリージョンで機能が有効か事前に確認してください。
- **コスト**: バージョンアップ自体に追加料金は通常発生しませんが、PromQL を通したクエリ実行や OTLP 経由のメトリクス取り込み、ダッシュボードの増加に伴うクエリ量・ストレージ増加により CloudWatch 側の課金やデータ転送コストが増える可能性があります。
- **互換性/ロールバック**: インプレースアップグレードではカスタムプラグインや既存ダッシュボードの動作が変わる可能性があります。アップグレード前にダッシュボードのエクスポート（JSON 保存）と設定のバックアップを取り、必要に応じてロールバック手順を確認してください。
- **Git Sync の注意点**: Git リポジトリのブランチ運用、アクセス権限、マージ/レビュー運用ルールを事前に設計してください。自動同期設定は意図しない上書きを招くことがあるため慎重に設定します。
- **CloudWatch PromQL の制約**: PromQL は CloudWatch が OTLP 経由で受け取ったメトリクスに対してサポートされます。標準的な CloudWatch ネイティブメトリクスや一部のデータ型では動作が異なる場合があるため、利用前に対象メトリクスの取り込み方法と互換性を確認してください。

## [Datasync] AWS DataSync Enhanced mode now supports Amazon FSx for Windows File Server, FSx for NetApp ONTAP, and Red Hat OpenShift Virtualization

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Datasync
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/datasync-enhanced-fsx-openshift/

### 概要

AWS DataSyncのEnhanced modeが、Amazon FSx for Windows File ServerとAmazon FSx for NetApp ONTAPをソース／デスティネーションとしてサポートし、さらにDataSyncエージェントがRed Hat OpenShift Virtualization (v4.20+) 上で動作可能になりました。これによりEnhanced modeでBasic modeと同等のロケーション選択肢が利用でき、高性能かつ大規模なファイル転送が容易になります。

### 変更内容・新機能の詳細

主な変更点は以下のとおりです。1) Amazon FSx for Windows File ServerおよびAmazon FSx for NetApp ONTAPをEnhanced modeのロケーションとして指定可能になりました。これによりオンプレのWindowsファイルサーバからFSx for WindowsへのWindows→Windows転送などがEnhanced modeで実行できます。2) Enhanced modeエージェントをRed Hat OpenShift Virtualization 4.20以降の環境で稼働できるようになり、エージェント展開オプションがVMware ESXi、KVM、Microsoft Hyper-V、Amazon EC2に加えてOpenShift Virtualizationで拡張されました。3) Enhanced mode自体はBasic modeと比べてデータを並列処理することでスループットを向上させ、ファイル数制限を撤廃し、転送に関する詳細メトリクスを提供します。利用開始はDataSyncコンソールでタスク作成時にEnhanced modeを選択するだけで、Enhanced modeがサポートされている全リージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: ファイルサーバ移行担当者、ストレージ管理者、クラウド移行チーム
- **利用シーン**: オンプレのWindowsファイルサーバをFSx for Windowsへ移行するWindows→Windows転送、またはON T A Pベースの共有をFSxに移行・同期するケース
- **運用効果**: 並列処理とファイル数制限撤廃により大規模データ移行のスループット向上と運用期間短縮が期待できる
- **展開柔軟性**: OpenShift Virtualization上でエージェントを動かせるため、既存のOpenShift基盤に組み込みやすく、仮想化プラットフォームに依存しない運用が可能

### 技術的な注意点

- **IAM権限**: DataSync用のIAMロール・ポリシー（タスク作成、エージェント登録、監視など）を適切に設定してください
- **エージェント要件**: OpenShift Virtualizationで動作させる場合はRed Hat OpenShift Virtualization 4.20以上が必要。エージェントのVMイメージ/設定は公式手順に従ってください
- **ネットワーク**: DataSyncエージェントからFSxやオンプレストレージへの接続に必要なポート（SMB/NFS等）とルーティング、セキュリティグループ／ファイアウォール設定を確認してください
- **プロトコル/マウント**: FSx for Windows File ServerはSMBを用いるのが一般的。FSx for NetApp ONTAPはNFS/SMB両対応のため、利用するプロトコルに応じたアクセス権とボリューム設定を確認してください
- **リージョン制限**: 記事では「Enhanced modeがサポートされているすべてのリージョンで利用可能」とありますが、実際の利用前に対象リージョンでEnhanced modeと各FSxサービスの対応状況を確認してください
- **コスト**: DataSyncの転送料金およびエージェントの実行に伴う基盤側（OpenShift/VMリソース、EC2等）のコスト発生があります。転送量と実行時間に基づく料金影響を見積もってください

## [Govcloud Us] ACM now supports ACME for public certificates in AWS GovCloud (US)

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/acm-acme-support-govcloud-us/

### 概要

AWS Certificate Manager (ACM) が AWS GovCloud (US-East) と AWS GovCloud (US-West) で ACME プロトコルをサポートしました。ACMEv2 対応クライアント（Certbot、cert-manager、acme.sh など）を使って、Amazon Trust Services 発行の公開 TLS 証明書を自動発行・自動更新できます。

### 変更内容・新機能の詳細

ACM のマネージド ACME サーバーエンドポイントが GovCloud（US-East / US-West）で利用可能になりました。ACMEv2 互換クライアントを使い、標準的な ACME チャレンジ（HTTP-01 / DNS-01 等、詳細はドキュメント参照）を経て Amazon Trust Services の公開証明書を取得できます。これにより、手動での証明書管理が困難になる（例：CA/Browser Forum による 2029 年までに有効期間が最大 47 日へ短縮される要件など）状況で、cert-manager を用いた Kubernetes クラスタや Certbot/ acme.sh を用いるサーバー環境での完全自動化が可能になります。対象は公開 TLS 証明書であり、ACM Private CA（PCA）で発行するプライベート証明書とは別扱いです。実運用では、ACM が提供する発行・更新ワークフローと既存の自動化ツールを組み合わせることで、稼働中のロードバランサーや API Gateway、CloudFront 等に対する証明書ローテーションの手間を大幅に削減できます。実装にあたっては、サポートされるチャレンジ種類・レート制限・クライアント設定方法・ドメイン検証の要件などを公式ドキュメントで確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: GovCloud 環境で公開 TLS 証明書を利用する開発者、SRE、セキュリティ運用チーム
- **利用シーン**: Kubernetes（cert-manager）やサーバー上の Certbot/ acme.sh による証明書の自動発行・自動更新
- **運用効果**: 証明書の手動更新作業削減、短い証明書有効期間への対応、運用ミスによるサービス停止リスクの低減

### 技術的な注意点

- **IAM権限**: ACM や関連サービス（Route 53 等）を操作する場合は適切な IAM ポリシーが必要。ACME クライアント側の設定や自動化用ロールを事前に確認してください
- **リージョン制限**: 現時点で AWS GovCloud (US-East) と AWS GovCloud (US-West) のみで提供。商用の通常リージョンとは別扱いとなるため利用可否を確認してください
- **証明書の種類**: 公開 TLS 証明書（Amazon Trust Services 発行）に限定。ACM Private CA（PCA）発行のプライベート証明書は対象外です
- **サポートチャレンジ**: 標準的な ACME チャレンジ（例：DNS-01 / HTTP-01）をサポートすると記載されていますが、実際に使用するチャレンジ種類や自動化の流れはドキュメントに従って確認してください
- **レート制限・運用制限**: ACME エンドポイントや ACM の発行レート制限、ドメイン検証要件があるため大量発行や短期間の連続試行はエラーや制限に注意が必要です
- **コスト**: ACM の公開証明書自体は通常の ACM の取り扱いに準じますが、関連する AWS サービス（ロードバランサー、CloudFront、API Gateway 等）や追加機能の利用による料金は別途発生する可能性があります。ACM の価格ページで確認してください

## [ECR] Amazon SageMaker AI now supports SOCI-indexed images to start training jobs in seconds

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: ECR
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/sagemaker-ai-soci-images-training/

### 概要

### 技術的な注意点

## [Lambda] AWS Lambda supports Seekable OCI (SOCI) lazy loading for Lambda Managed Instances

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-lambda-seekable-oci-soci/

### 概要

AWS Lambda が Lambda Managed Instances 上で実行する OCI イメージ（Event Functions）に対して、Seekable OCI (SOCI) による遅延ロード（lazy loading）をサポートしました。これにより、実行環境の起動時に必要なファイルのみをオンデマンドで取得でき、コンテナの起動時間を最大で約70%短縮できます。

### 変更内容・新機能の詳細

SOCI は OCI イメージ層内のファイル配置を示す索引（テーブル・オブ・コンテンツ）を作成し、ランタイムがイメージ全体をダウンロードする代わりにファイル単位で必要なデータをストリーミング取得できる仕組みです。Lambda Managed Instances 上で SOCI を使用するには、コンテナイメージに対して SOCI インデックスを作成し、そのタグ（例: my-function:v1-soci）を Amazon ECR にプッシュします。関数を作成・更新して SOCI インデックス付きのイメージ URI を指定してバージョンを公開すると、Lambda が自動で SOCI を検出して遅延ロードを有効化します。結果として、特に数GBにおよぶ大きなコンテナイメージを使うデータ処理パイプライン、高スループット API、バッチ計算などのスケール時に、新規実行環境プロビジョニングの待ち時間が大幅に短縮されます。Agent Toolkit 経由で Kiro、Claude Code、Codex 等のコーディングアシスタントを使う場合は、Lambda Managed Instances のスキルをインストールしてエージェントから設定・デプロイできます。対応はすべての商用リージョン（Lambda Managed Instances 提供リージョン）で利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発者、SRE/運用チーム、データエンジニア（大規模コンテナイメージを使う Lambda 関数を運用する組織）
- **利用シーン**: 大容量イメージを用いるデータ処理パイプライン、高スループット・低レイテンシ API バックエンド、バッチ計算ワークロードのスケールアウト時の起動最適化
- **運用効果**: 実行環境の起動時間を最大約70%短縮し、スケール時のウォームアップ時間・コールドスタートの影響を低減。イメージ全体のダウンロードを避けることでネットワーク帯域とプロビジョニング時間を削減し、オートスケール応答性が向上します。

### 技術的な注意点

- **IAM権限**: ECR へ SOCI インデックスとイメージを push する権限（ECR への書き込み）や、デプロイ時の Lambda 関数作成/更新に必要な IAM 権限を事前に用意してください
- **リージョン制限**: Lambda Managed Instances が提供されている商用リージョンで利用可能です。該当リージョンで Lambda Managed Instances がサポートされていることを確認してください
- **コスト**: SOCI インデックス自体のストレージは小さく追加コストは限定的ですが、ECR ストレージやデータ転送量が発生します。起動時間短縮は間接的にオペレーショナルコスト削減につながる場合があります
- **イメージ互換性**: SOCI は OCI 形式イメージに対する索引化が前提です。既存の Docker レジストリイメージをそのまま使う場合は OCI 形式への変換や SOCI インデックス作成が必要です
- **導入手順の注意**: SOCI インデックスを作成して ECR に push した後、関数のイメージ URI を SOCI 対応のタグ（例: my-function:v1-soci）に設定して関数バージョンを公開する必要があります。Lambda は自動検出しますが、タグ付けミスに注意してください
- **ツールチェーン**: SOCI インデックス作成ツールや ECR の手順に慣れておくと導入がスムーズです。Agent Toolkit 経由の自動化を使う場合は、Lambda Managed Instances スキルをエージェントにインストールしてください
- **デバッグ/運用**: 遅延ロードにより起動シーケンスが変更されるため、起動時に参照されるファイルが正しく索引化されているか（必要なファイルのパス／バイト範囲が正確か）を検証してください

### 変更内容・新機能の詳細

### 概要

Amazon Quickにスマート承認（smart approvals）が追加され、エージェントが行う定型的な操作を自動承認しつつ、重要な操作はユーザーにレビューさせることで承認疲労を低減しつつ人的監督を維持します。

### 変更内容・新機能の詳細

スマート承認は、エージェントがユーザーに代わって行う候補アクションを別のレビュー用モデル（classifier）で評価し、ルーチンな操作は自動で承認、影響の大きい操作はユーザーへ振り分けてレビューを要求します。既存のポリシーが常に優先され、スマート承認はユーザー設定が「毎回確認（ask）」になっているアクションのみを評価します。拒否されたアクションは引き続き拒否されたままであり、スマート承認が新しいアクセス権を付与することはありません。classifierは外部送信（組織外へのコンテンツ送信）、権限変更、コンテンツ削除、支払い実行、ユーザー要求の範囲を超える操作などを高影響アクションとしてユーザーに回します。自動承認が適用される場合でも、その承認はレビューされた「その特定のアクション」にのみ有効です。レビューが失敗するかタイムアウトした場合、アクションはユーザーの確認にフォールバックします。スマート承認は全ユーザーでデフォルトONですが、管理者はカスタム権限で利用可能者を制御でき、ユーザーはチャットのオプションから会話やスケジュール実行に対してオフにできます。AWS CloudTrailはスマート承認を経由した各アクションレビューおよびユーザーのスマート承認設定変更を記録します。スマート承認は、Amazon Quickのエージェンティック機能がサポートされるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: プロダクト開発者、AI/エージェント利用者、SRE/運用チーム、セキュリティ管理者
- **利用シーンまたは効果**: 定型的なメール送信、レコード更新、チケット作成などを自動承認してヒューマンレビューの負荷を下げる。重要操作（権限変更、削除、支払い、組織外送信など）は都度ユーザーレビューに回されるため誤操作のリスクを低減
- **運用効果**: 承認フローの効率化（承認待ちボトルネックの削減）と、重要操作への監視強化でコンプライアンス維持を両立
- **管理者への影響**: 管理者はカスタム権限で誰がスマート承認を使えるか制御でき、設定のデフォルトはONのためポリシー設計と権限管理を早急に見直す必要がある
- **監査・コンプライアンス**: CloudTrailにレビュー履歴と設定変更が記録されるため監査証跡を確保できる

### 技術的な注意点

- **IAM権限**: 管理者はスマート承認の利用を制御するためのカスタム権限ポリシーを設定可能。ユーザーがオフにできる点も考慮して権限設計を行ってください
- **リージョン制限**: Amazon Quickのエージェンティック機能をサポートするリージョンで利用可能。利用前にリージョン対応状況を確認してください（公式リージョン表参照）
- **ログ・監査**: すべてのスマート承認レビューとユーザー設定変更はAWS CloudTrailに記録されます。必要なCloudTrailの設定とログ保持ポリシーを確認してください
- **動作制約**: スマート承認はユーザー設定が「ask」のアクションのみを評価し、拒否済みのアクションに影響を与えません。自動承認はレビュー対象の「その特定のアクション」だけに適用され、タイムアウトやレビュー失敗時はユーザー確認にフォールバックします
- **セキュリティ**: スマート承認は新たなアクセス権を付与しないため、権限昇格のリスクはない設計ですが、権限変更や外部送信といった高影響操作は必ずユーザーの確認が必要です
- **コスト**: 発表時点でスマート承認自体の追加料金は明示されていません。ただし、Amazon Quickやエージェント機能の利用に伴う通常の料金は発生します。CloudTrailログ保存等の関連コストも考慮してください

- **運用監視**: 統合アクションは自動実行されるため、CloudWatchメトリクスやイベント、ECSのアクティビティログで置換/スケール操作を監視してください
- **既存環境への影響**: 自動適用されるため、Capacity Providerの構成が特に制限的な環境では計画的な検証を推奨します

### 影響範囲・利用シーン

- **対象ユーザー**: サーバレス/クラウドエンジニア、SRE、開発者、AIワークフロー設計者、ビジネスアナリスト
- **利用シーン**: マルチステップの耐久処理（Durable Functions）の詳細な実行トレース保存や長期保持、障害解析、KPIやビジネスイベントの抽出、AIエージェントによる自然言語クエリによるオペレーショナル検索
- **運用効果**: ステップ単位の履歴により障害原因の迅速特定や再現性の向上が可能。S3/Athenaなどへエクスポートすれば長期保存と大規模分析が可能になり、オンコール対応の効率化やビジネス分析への活用が容易になる

### 技術的な注意点

- **IAM権限**: 出力先への書き込み権限（例: s3:PutObject、logs:PutLogEvents、dynamodb:PutItem、rds/Aurora接続権限、es:ESHttpPut 等）が必要です。MCPサーバー経由でのクエリにも適切な認可を設定してください。
- **リージョン制限**: 本機能は「Lambda durable functions」をサポートするリージョンで利用可能です。利用前に対象リージョンでのサポート状況を確認してください。
- **コスト**: エクスポーター自体に追加料金はありませんが、エクスポート先（S3、CloudWatch Logs、DynamoDB、Aurora、OpenSearchなど）のストレージ、クエリ（Athena等）やリクエストに対する通常料金が発生します。高頻度や詳細トレースはコスト増に繋がるため、サンプリングやフィルタリングの設定で制御してください。
- **データ量とサンプリング**: ステップ単位の詳細データは高いボリュームになるため、サンプリング率設定や重要なフィールドのみエクスポートする設定で運用負荷を抑制してください。
- **機密情報**: フィールドのマスキング（redaction）機能を利用してPII/機密データを除外してください。出力先の暗号化（S3のSSE、RDS/Auroraの暗号化等）とアクセス制御を併せて設定することを推奨します。
- **デスティネーション固有の注意**: 各デスティネーションはスキーマやレコードサイズ、スループット制限が異なります。例えばS3→Athenaを想定する場合はクエリ効率を考えたファイル形式（Parquet/JSON）設計、OpenSearchはシャード/インデックス設計に注意してください。
- **言語/導入手順**: TypeScript、Python、Java、Goをサポート。導入は(1)エクスポーターをインストール、(2)関数ハンドラにプラグイン登録、(3)必要に応じてMCPサーバーをエージェントに追加する流れです。
- **セキュリティ/アクセス制御**: MCPサーバー経由での自然言語クエリは強力ですが、テレメトリへのアクセス範囲とログの可視化権限を厳密に管理してください。ネットワーク配置（VPCエンドポイント、プライベート接続）や認証・監査の設計が重要です。
- **互換性/保持期間**: エクスポートにより標準のLambdaログ保持期間の制限を超えて歴史を保持できます。既存のログ・監視構成との整合性を確認してください。

## [EKS] Amazon EKS Auto Mode now supports Kubernetes Gateway API

- **公開日**: 2026-10-29 (JST)
- **カテゴリ**: EKS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-eks-auto-mode-kubernetes-gateway-api/

### 概要

Amazon EKS Auto ModeがKubernetes Gateway APIをサポートしました。これにより、Gateway/HTTPRouteリソースでアプリケーショントラフィックのルーティングを定義すると、EKS Auto Modeが必要なAWSロードバランサーやTLS設定を自動でプロビジョニング・管理します。

### 変更内容・新機能の詳細

EKS Auto ModeはKubernetesの次世代トラフィック管理仕様であるGateway APIをネイティブにサポートします。ユーザーはGatewayおよびHTTPRouteリソースを使ってApplication Load Balancer等を介したHTTP/gRPCルーティングを定義でき、EKS Auto Modeが背後のAWSインフラ（ALB/NLB、ターゲットグループ、証明書等）を自動作成・管理します。主な機能にはHTTPおよびgRPCルーティング、クロスネームスペースルーティング（マルチチーム環境向け）、重み付けによるトラフィック分割、ヘッダベースルーティング、AWS Certificate Managerによる自動TLS証明書検出が含まれます。既存のIngressリソースは引き続き併用可能で、別途Gatewayコントローラをインストールする必要はありません。Gateway APIサポートはEKS Auto Modeに含まれ、EKS Auto Modeが提供されている全リージョンで利用可能です。なお、プロビジョニングされるAWSロードバランシングリソースには標準の課金が適用されます。

### 影響範囲・利用シーン

- **対象ユーザー**: Kubernetesアプリケーションの開発者、プラットフォームチーム、SRE/運用チーム
- **利用シーン**: マルチチーム環境でのクロスネームスペースルーティング、gRPC/HTTPサービスのルーティング定義、カナリア/ブルーグリーン等の重みづけリリースの実施、TLS管理の自動化
- **運用効果**: Gateway APIという標準仕様を追加設定なしで採用可能になり、ロードバランサーや証明書の手動セットアップが不要となるためインフラ運用負荷を低減し、一貫したトラフィック管理が実現できる
- **コスト影響**: 自動でプロビジョニングされるALB/NLB等に対して標準のAWS料金が発生します

### 技術的な注意点

- **IAM権限**: EKS Auto ModeがロードバランサーやACM証明書を作成・管理するためのサービスリンクドロールやIAM権限（またはIRSA設定）が必要になる可能性があるため事前に確認してください
- **リージョン制限**: EKS Auto ModeがサポートされているAWSリージョンで利用可能です。EKS Auto Mode自体が未対応のリージョンでは利用できません
- **互換性**: 既存のIngressリソースと共存可能です。Gateway APIを使用する際はクラスタやKubernetesのバージョン要件、EKS Auto Modeのドキュメントを確認してください
- **コントローラ**: Gateway APIサポートはEKS Auto Modeに組み込まれており、追加でコントローラをインストールする必要はありません
- **コスト**: AWSのロードバランサーや関連リソースに対する標準料金が適用されます
