## [General] OpenAI GPT-6.1 Sol now supports Ultrafast mode on Amazon Bedrock

- **公開日**: 2026-10-09 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/openai-gpt-sol-ultrafast-amazon/

### 概要

Amazon BedrockでOpenAIのGPT-6.1 SolがUltrafastモードに対応しました。低レイテンシが要求されるリアルタイム系アプリケーション向けに、より高速な推論を提供します。

### 変更内容・新機能の詳細

UltrafastモードはGPT-6.1 Solに対して低遅延の推論パスを提供する推論プロファイルです。Amazon Bedrockの推論エンジン上で動作し、本番環境向けの性能・セキュリティ・信頼性を確保しています。開発者はコンソールまたはBedrockのAPI/SDKを使ってUltrafastモードを選択し、リアルタイムコーディングアシスタント、対話型エージェント、カスタマーインタラクションなどレイテンシ敏感なユースケースで高速かつ高品質な応答を得られます。既存のAWSコントロール（IAM、VPCエンドポイント、暗号化、CloudTrailによる呼び出し監査など）を利用してアクセス制御や監査が可能です。利用可能なリージョン、エンドポイント、API、推論プロファイルや料金体系についてはAmazon Bedrockのドキュメントで確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: アプリケーション開発者、AI/MLエンジニア、SRE/運用チーム
- **利用シーン**: リアルタイムコーディング補助、対話型エージェント、顧客向けチャット/ボット、マルチステップのインタラクティブワークフロー
- **運用効果**: レイテンシ短縮によりユーザー体験が向上し、インタラクティブな操作感や即時フィードバックが必要な場面での応答性が改善される
- **導入効果**: 本番レベルの信頼性とAWSのセキュリティ統制下でOpenAIモデルを低遅延で利用可能になるため、サービス化（SaaS化）や顧客向け機能の高速化に貢献する

### 技術的な注意点

- **IAM権限**: Bedrockの呼び出しに必要なIAM権限（例: bedrock:InvokeModel 等）を付与してください
- **リージョン制限**: Ultrafastモードの提供リージョンは限定される可能性があるため、利用前にAmazon Bedrockドキュメントで対応リージョンとエンドポイントを確認してください
- **コスト**: Ultrafastは通常の推論プロファイルと異なる料金体系（または単価差）がある可能性があるため、事前にBedrockの料金ページで確認し、コスト試算/負荷試験を実施してください
- **運用/監査**: CloudTrailやBedrockのログ機能でモデル呼び出しを監査可能。ログ/監査要件に応じてログ保存先や保持期間を設計してください
- **ネットワーク/セキュリティ**: VPCエンドポイント（PrivateLink）や暗号化設定を用いてネットワーク経路とデータ保護を確保してください
- **互換性/API**: UltrafastはAmazon Bedrockの既存API/SDKから選択できる推論プロファイルの一つです。実際のリクエスト/レスポンス形状やストリーミング挙動はBedrockドキュメントで確認してください
- **品質/性能のバランス**: 低遅延化に伴う品質やスループットの変化がある可能性があるため、本番導入前に性能（レイテンシ、スループット）と出力品質のテストを行ってください
- **データ利用/コンプライアンス**: モデルプロバイダ（OpenAI）やデータ転送先に関わる取り扱い方針を確認し、データ保護要件やリージョン制約を満たす設計にしてください

## [Cost Explorer] AWS Cost Explorer, Budgets, and Dashboards now support Amazon Bedrock product attributes

- **公開日**: 2026-10-09 (JST)
- **カテゴリ**: Cost Explorer
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-bedrock-attributes-in-cost-explorer/

### 概要

AWS Cost Explorer、AWS Budgets、AWS Cost Management Dashboardsで、Amazon Bedrockのコストを「モデル」「モデルプロバイダー」「推論タイプ」「機能」といった製品属性（product attributes）で分解・集計できるようになりました。これにより、どのモデルやワークロードがBedrockコストを牽引しているかを既存の請求ツール上で直接把握できます。

### 変更内容・新機能の詳細

新たに追加されたAmazon Bedrock用の製品属性ディメンションは、Cost ExplorerおよびCost Management Dashboardsでのグループ化・フィルタリング、Budgetsでのフィルタリングに対応します。対象となる属性は主に以下の4種です：
- model: 例）Claude Sonnet 5、Claude Haiku 4.5など個々のモデル名
- model provider: 例）Anthropic、Cohereなどモデル提供者
- inference type: 例）input tokens、output tokensなどの推論トークン種別
- feature: 例）on-demand inference、rerankerなど実行機能
これらの製品属性は、アプリケーションの推論プロファイルやプロジェクト、ワークスペースに付与したコスト割当タグ（cost allocation tags）と組み合わせて使用できます。また、IAM principal tags と組み合わせることで、どのユーザー/ロールがどのモデルでコストを発生させているかの可視化も可能です。ユースケース例：月次のBedrock支出をモデル別にグルーピングして高コストモデルを特定、プロバイダー別のコスト推移をダッシュボードウィジェットで監視、特定モデルに対する予算（Budget）を作成して超過時にアラートを受け取る等。なお、本機能は追加料金なしで今日から利用可能（ただし AWS GovCloud (US)、中国（北京・寧夏）リージョンを除く）。詳細な操作手順や制約は各ユーザーガイドを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: 財務チーム、FinOps、クラウドプラットフォーム/インフラ運用チーム、SRE、AI/MLエンジニア
- **利用シーン**: モデル別・プロバイダー別・推論タイプ別のコスト分析、プロジェクト／アプリケーションごとのBedrock支出の内訳把握、特定モデルのコストに対する予算設定とアラート
- **運用効果**: 高コストモデルの早期検出、プロバイダーや機能単位でのコスト最適化、予算超過の事前通知によるコストコントロール
- **コスト管理**: 既存のコスト割当タグやIAM principal tagsと組み合わせて、組織・プロジェクト単位での課金責任や費用配分が明確になる

### 技術的な注意点

- **IAM権限**: Cost Explorer/Budgets/Dashboardsを表示・操作するための適切なIAM権限（Cost ExplorerやBudgetsの読み取り権限）を付与してください。詳細は各サービスのアクセス管理ポリシーを確認してください。
- **リージョン制限**: 全リージョンで利用可能だが、AWS GovCloud (US) と中国リージョン（北京・寧夏）は未対応です。
- **コスト**: 本機能自体に追加料金は発生しませんが、細かい分析のためにダッシュボードやアラートを増やすと運用工数が増える可能性があります。
- **タグ運用**: コスト割当タグやIAM principal tagsを組み合わせる場合は、タグ付けの一貫性と事前の有効化（Billingでのタグ有効化設定）が必要です。
- **データ反映遅延**: 製品属性を含む請求データは通常の請求集計遅延に従います。最新の利用状況が反映されるまで時間がかかる場合があるため、即時の精緻な計測は注意してください。
- **互換性/詳細**: 属性の割り当てや表現はBedrockの課金イベントに依存するため、モデル名やfeatureの表記がBedrock側の表記と一致することを前提にしてください。動作やフィルタリングの詳細は各ユーザーガイドを参照してください。

## [Rds For Oracle] Amazon RDS for Oracle now supports minor version upgrade prechecks and a new RDS event to help reduce patching downtime

- **公開日**: 2026-10-09 (JST)
- **カテゴリ**: Rds For Oracle
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-rds-oracle-minor-version-upgrade-precheck-new-patching-rds-event/

### 概要

Amazon RDS for Oracleでマイナー・バージョンアップの事前チェックを自分で実行できるようになり、パッチ適用中にDBが接続受付を再開したことを示す新しいRDSイベント（RDS-EVENT-0596）が追加され、メンテナンスによるダウンタイムを短縮できるようになりました。

### 変更内容・新機能の詳細

新機能として、rdsadmin.rdsadmin_precheck_tasks.precheck_minor_upgrade ストアドプロシージャにより、マイナー・バージョンアップ開始前にRDS for Oracleが実行するチェック（空きストレージ不足、Oracle管理オブジェクトの不整合、無効なトリガー等）を任意のタイミングで実行できます。プリチェックは読み取り専用でワークロードに影響を与えず、検出された全ての問題を単一のログで報告するため、問題を修正して合格するまで繰り返し実行できます。加えて、マイナー・バージョンアップやOSアップデート中に、DBインスタンスが接続を受け付けられるようになった時点で RDS-EVENT-0596 を発行するようになりました。このイベントをトリガーにして、RDSイベント通知やAmazon EventBridge経由でアプリケーションの再接続や運用通知を自動化でき、残りのメンテナンスタスクはデータベースがオンラインのまま続行されます。これらの機能は、Amazon RDS for Oracleが利用可能な全てのAWS商用リージョンおよびAWS GovCloud (US)で提供されます。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者（DBA）、SRE/運用チーム、アプリケーション開発者
- **利用シーン**: マイナー・バージョンアップ前の事前検査（問題の早期発見）およびパッチ適用中にアプリケーションを早期に復帰させたいケース
- **運用効果**: 事前に問題を修正することでアップグレード失敗や再スケジュールのリスクを低減し、RDS-EVENT-0596によりDBが接続可能になった時点でアプリケーションを復帰させられるため、実際のダウンタイムを短縮できる

### 技術的な注意点

- **DB実行権限**: rdsadminスキーマのプロシージャを実行するためにDBに接続できる権限（通常はマスターユーザーまたはAWSが許可する実行権限）が必要です
- **プリチェックの性質**: precheckは読み取り専用でワークロードに影響しないとされていますが、本番で実行する前にステージングでの動作確認を推奨します
- **イベント購読権限/IAM権限**: RDSイベント通知（SNS）やEventBridgeで自動化する場合は、SNS PublishやEventBridgeのルール作成等のIAM権限が必要です
- **リージョン制限**: Amazon RDS for Oracleが提供されている全ての商用リージョンおよびAWS GovCloud (US)で利用可能です（利用不可リージョンはなし）
- **コスト**: 事前チェックやイベント発行自体に追加料金は発生しませんが、EventBridgeやSNS等の通知サービス利用に伴う通常の課金が発生する可能性があります
- **運用上の注意**: RDS-EVENT-0596は「DBインスタンスが接続を受け付けている」ことを示すもので、残りのメンテナンス作業はバックグラウンドで続行されるため、アプリケーション再接続後に残タスクの影響を受けないか事前に確認してください

## [Network Firewall] AWS Network Firewall adds wildcard support for container attribute filters 

- **公開日**: 2026-10-09 (JST)
- **カテゴリ**: Network Firewall
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-network-firewall-container-attributes-wildcard

### 概要

AWS Network Firewallは、Amazon EKSおよびAmazon ECS向けのコンテナ属性ベース検査フィルタでワイルドカードマッチをサポートしました。これにより、単一ルールで複数のコンテナバリアントを一括でカバーでき、ファイアウォールルールの管理負荷が低減します。

### 変更内容・新機能の詳細

コンテナ属性ベースの検査フィルタでワイルドカード（例: app=payments-*）が利用可能になりました。ワイルドカードパターンはコンテナ属性（ラベルや属性キー/値）に対して複数のバリアントを一度にマッチさせるために使え、個別のコンテナ関連付け（container association）を各バリアント毎に作成する必要がなくなります。これにより、マイクロサービスや頻繁にデプロイされるアプリケーションの変種が増えても、Firewallポリシーの更新回数を減らして一貫したセキュリティ適用が可能です。本機能は、AWS Network Firewallの「コンテナ属性ベース検査」がサポートされているすべてのリージョンで利用可能です。ワイルドカードの具体的なパターン構文（例: '*' の取り扱い）や適用箇所は公式ドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドセキュリティエンジニア、SRE、プラットフォームチーム、EKS/ECSでコンテナ運用する開発チーム
- **利用シーン**: マイクロサービスの複数バリアント（例: payments-api／payments-worker／payments-cron）を単一ルールで制御したい場合
- **運用効果**: ルール作成・更新の工数低減、ポリシーの一貫性向上によりセキュリティカバレッジが安定化
- **導入メリット**: 新しいアプリケーションバリアントのデプロイ時にFirewall設定を都度変更する必要がなくなるため、デプロイ速度と運用効率が向上

### 技術的な注意点

- **IAM権限**: Firewallポリシーやルールグループを編集するための適切なIAM権限（Network Firewall関連APIの許可）が必要です
- **リージョン制限**: "コンテナ属性ベース検査" をサポートするリージョンで利用可能です。詳細はAWS Region Tableを確認してください
- **コスト**: Network Firewallの通常料金が適用されます。ルール数やトラフィック量に応じた課金が発生するため、広範囲マッチの適用で評価コスト/スループット要件に影響がないか確認してください
- **前提条件**: コンテナ属性（ラベル／タグ）がNetwork Firewall側に渡される設定が済んでいること（EKS/ECSの連携設定やエージェント側の属性送出設定など）
- **パターン仕様**: ワイルドカード（例: '*'）の具体的な動作・エスケープ規則はドキュメントで確認してください。誤ったパターンは過広なマッチを招く可能性があります
- **運用上の注意**: 本番適用前にステージング環境でワイルドカードルールを検証し、意図しないトラフィック遮断が発生しないか確認してください
- **監視/ロギング**: ルール適用結果とログ（Kinesis/S3/CloudWatch Logs等）を有効にして、マッチ状況と誤検出を定期的にレビューしてください
