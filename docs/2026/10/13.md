## [General] Bring deep SageMaker AI expertise to your coding agent with the AWS AI/ML skill in the Agent Toolkit for AWS

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/bring-sagemaker-ai-expertise-to-your-coding-agent/

### 概要

Agent Toolkit for AWS のコアスキルとして「AWS AI/ML skill」が提供され、コーディングエージェント（例: Kiro）から自然言語ワークフローで Amazon SageMaker のモデル選定、学習、最適化、デプロイを行えるようになりました。ツールキットは既存の AWS Labs スキル／プラグインに替わる公式の統合ポイントとして配布されます。

### 変更内容・新機能の詳細

新しい AWS AI/ML スキルは Agent Toolkit for AWS のコアスキルとなり、EC2 や Bedrock など他の AWS スキルと並列して動作します。主な機能拡張は以下の通りです。
- 推論最適化: デプロイ済みモデルのレイテンシ、スループット、コストのトレードオフを考慮した最適化（マルチモデルエンドポイント、サーバーレス推論やインスタンスタイプ切替などの SageMaker 機能と連携可能）。
- モデルカスタマイズ: ユースケース定義からデータ準備、ファインチューニング、評価、デプロイまでのガイド付きエンドツーエンドワークフローをサポート。生成系／従来型 ML の両方を対象としたチューニングを想定。
- サーバフルトレーニング: 管理されたコンピュート上でのトレーニング（従来型 ML と生成 AI の両方）をサポート。
- MLflow 統合: 実験トラッキングとモデルライフサイクル管理のための MLflow サポート（実験履歴／モデル登録と連携）。
- JumpStart: 事前構築モデルのデプロイ機能と、ユースケースに応じたモデル推奨機能。
- Processing jobs: データ準備／ETL を管理されたコンピュートで実行する処理ジョブの起動・管理。

また、AWS AI/ML スキルは追加料金なしで利用可能で、課金はエージェントが利用する AWS リソース（SageMaker インスタンス、S3、ECR など）に対してのみ発生します。スキルは Agent Toolkit for AWS の GitHub からインストールするか、SageMaker Studio の JupyterLab にプリインストールされた状態で利用できます。従来の AWS Labs スキル／プラグインはこのツールキットに置き換えられ、インストールと更新が一貫化されます。

### 影響範囲・利用シーン

- **対象ユーザー**: 機械学習エンジニア、データサイエンティスト、ML プラットフォーム/インフラ担当、SRE や開発者
- **利用シーン**: コーディングアシスタントにより自然言語でモデルの選定～学習～評価～本番デプロイを自動化したいワークフロー（例: プロトタイプの高速化、モデルの継続的改善、データ準備の自動化）
- **運用効果**: モデル開発→本番デプロイまでの手作業を削減し、反復サイクルを高速化。推論最適化や JumpStart による初期コスト削減、MLflow でのトラッキングによる再現性向上が期待できる

### 技術的な注意点

- **IAM権限**: SageMaker、S3、ECR、CloudWatch、EC2（必要な場合）、STS などの権限が必要。最小権限の IAM ロール/ポリシー設計を推奨。
- **リージョン制限**: SageMaker の機能（JumpStart、特定のインスタンスタイプ、サーバーレス推論等）はリージョン依存。利用前に対象リージョンでの対応状況を確認すること。
- **コスト**: スキル自体は無料だが、トレーニング/推論/処理ジョブなどで発生する AWS リソース利用料は別途発生する。大規模トレーニングや継続的推論はコストが増大するため見積もりを行うこと。
- **前提条件**: Agent Toolkit for AWS の導入（または SageMaker Studio JupyterLab のプリインストール環境）、SageMaker Studio ドメイン/ユーザープロファイルの準備が必要。
- **互換性**: Kiro などの対応エージェントと連携可能だが、利用するコーディングエージェント側でも Agent Toolkit のスキルを呼び出すための設定が必要。
- **セキュリティ**: エージェントが実行する操作は AWS リソースへのアクセスを伴うため、資格情報管理（短期トークン、ロール委任）と機密データの扱いルールを整備すること。
- **MLflow 注意点**: MLflow 統合を利用する場合、MLflow サーバやバックエンドストア（S3/Databases）などの構成が別途必要となる場合がある。
- **移行**: 既存の AWS Labs スキル／プラグインを利用している環境は、Agent Toolkit への移行手順を確認して互換性を検証すること。

## [Fsx For Openzfs] AWS DataSync Enhanced mode now supports FSx for OpenZFS, NFS 4.2, and object metadata controls

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: Fsx For Openzfs
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/datasync-enhanced-openzfs-nfs42-metadata/

### 概要

AWS DataSyncのEnhanced modeが、Amazon FSx for OpenZFSのソース/デスティネーション、NFSv4.2（オンプレNFSおよびFSx for OpenZFS）、およびオブジェクト転送時のユーザーメタデータ制御（ObjectMetadataオプション）をサポートするようになりました。

### 変更内容・新機能の詳細

今回の更新により、以下が可能になります：
- Amazon FSx for OpenZFSをDataSync Enhanced modeのソースまたはデスティネーションとして指定可能になりました（従来はBasic modeのみ対応）。
- NFSバージョン4.2をサポート。オンプレのNFSサーバーおよびFSx for OpenZFSファイルシステムと直接やり取りでき、サーバー側で古いプロトコルに落とす必要がなくなります。
- ObjectMetadataオプションを追加。オブジェクトストレージへ転送する際に、元オブジェクトのユーザーメタデータをコピーするかどうかを制御できます。これにより、転送先のメタデータを保持する必要があるケース（例：AWS Storage Gatewayが提供するバケット）や、ソースのメタデータキーが転送先と互換性がないケース（例：Azure Blob）での柔軟な制御が可能になります。
既存のタスクは影響を受けず継続して実行されます。この機能は、AWS DataSync Enhanced modeをサポートするすべてのリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: データ移行/レプリケーション担当者、ストレージ管理者、SRE
- **利用シーン**: FSx for OpenZFSを含むオンプレ⇄クラウド間やクラウド内のファイル移行、NFSv4.2を利用する最新NFSサーバーからのデータ転送、オブジェクト転送時のメタデータ保持・除外の制御
- **運用効果**: プロトコル互換性のためにサーバー設定をダウングレードする必要がなくなり移行工数が低減。メタデータの上書き/破壊を防げるため、互換性問題や運用ポリシーに沿った転送が行える

### 技術的な注意点

- **IAM権限**: DataSync用のサービスロール（AWSDataSyncRole等）や、転送先/転送元リソース（FSx、S3、NFSサーバー等）への適切なアクセス権が必要です。S3や他クラウドへの書き込みでは追加の認証情報や権限が必要になる場合があります。
- **リージョン制限**: 本機能は「Enhanced modeをサポートするリージョン」で利用可能です。FSx for OpenZFS自体の提供状況や一部リージョンの制約は別途確認してください。
- **コスト**: DataSyncの転送料金および転送先ストレージ（S3、FSx等）のストレージ料金、データ送信に伴うネットワーク転送料が発生します。大量データ移行ではコスト影響を事前に見積もってください。
- **NFSバージョン**: NFSv4.2を使うには、オンプレ/FSxのファイルサーバーがv4.2をサポートしている必要があります。互換性やマウントオプションの確認をお願いします。
- **ObjectMetadata**: ユーザーメタデータのコピー有無を選択可能ですが、転送先ストレージのメタデータ形式/制約（例：許容されるキー名や文字セット）を事前に確認してください。不一致がある場合はメタデータを除外するか変換処理を検討してください。
- **既存タスク**: 既存の（Basic/Enhanced）タスクは本変更によって停止・変更されません。新機能を利用するにはEnhanced modeのタスクで対象ロケーション/オプションを指定してタスクを作成または更新する必要があります。

## [Route 53] Amazon Route 53 now supports registrations, transfers, and renewals for Premium Domains

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: Route 53
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/route-53-premium-domains/

### 概要

Amazon Route 53 Domainsがプレミアムドメインに対応しました。検索、登録、移管、更新、復旧をRoute 53上で直接行え、プレミアム／通常ドメインを一元管理できます。

### 変更内容・新機能の詳細

Route 53 Domainsが“プレミアムドメイン”の検索・登録・移管・更新・復旧をサポートします。プレミアムドメインとは短く覚えやすい、需要が高いなどの理由でレジストリが特別価格を設定するドメイン名のことです。これまではRoute 53で扱えなかったため他レジストラに分散していた管理を、Route 53のドメイン検索結果にプレミアムドメインが自動的に表示され、価格が事前に提示される形でRoute 53の通常フロー（検索→確認→登録／移管）で取得・管理できるようになりました。対応TLDや各レジストリ固有のルール（価格、プライバシー対応、復旧手続きなど）は存在するため、登録前にTLDリストと詳細ドキュメントで確認する必要があります。なお、料金は登録時および更新時にプレミアム価格が適用され、復旧や移管に追加費用が発生する場合があります。コンソールでの操作が主導ですが、既存のRoute 53 Domainsの手続きフローに準じてAPI/CLIでの操作確認も推奨されます。

### 影響範囲・利用シーン

- **対象ユーザー**: ドメイン管理者、SRE/運用チーム、プロダクト/マーケティング担当者
- **利用シーン**: ブランド用の短く覚えやすいドメイン取得、既存プレミアムドメインのRoute 53への集約および一元管理
- **運用効果**: ドメインポートフォリオの集中管理による請求・アクセス権の簡素化、検索結果で価格を事前確認できるためコスト意識を持った取得が可能

### 技術的な注意点

- **IAM権限**: route53domainsに対するドメイン登録・移管・更新・復旧（例: RegisterDomain, TransferDomain, RenewDomain 等）を許可するIAMポリシーが必要です。具体的なアクションはドキュメントで確認してください。
- **リージョン制限**: Route 53はグローバルサービスですが、レジストリごとに利用可否や取り扱いが異なります。TLDごとの対応状況を確認してください。
- **対応TLD/レジストリ制約**: 全TLDがプレミアム対象ではありません。各TLD／レジストリ固有の価格・プライバシー可否・復旧ポリシーがあります。
- **コスト**: プレミアム価格は登録時・更新時に追加で課金されます。復旧（レストア）や移管時にも追加料金が発生する可能性があります。価格は検索時に表示されますが、請求影響を事前に確認してください。
- **移管/技術手続き**: 他レジストラからの移管は通常のAuth/EPPコードやロック解除などの手続きが必要です。移管料金や残存期間の扱いはレジストリに依存します。
- **プライバシー・WHOIS**: 一部のプレミアムドメインではドメインプライバシー（WHOISプライバシー）が制限される場合があります。レジストリポリシーを確認してください。
- **API/CLI/コンソール**: コンソールで検索・取得が可能で、既存のRoute 53 DomainsのAPI/CLIフローと統合される想定ですが、使用前にAPIリファレンスで対応状況を確認してください。

## [Govcloud Us] Amazon RDS now supports the latest CU for Microsoft SQL Server

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-rds-supports-latest-cu-microsoft-sql-server/

### 概要

Amazon RDS for Microsoft SQL Server が Microsoft SQL Server 2025 の最新 Cumulative Update (CU8、KB5104822) をサポートするようになりました。RDS エンジンバージョンは 17.00.4075.5.v1 です。

### 変更内容・新機能の詳細

今回のリリースにより、Amazon RDS for SQL Server は Microsoft が提供する SQL Server 2025 CU8 (KB5104822) をサポートします。RDS 側のエンジン識別子は 17.00.4075.5.v1 で、Microsoft の KB ドキュメントに記載されたバグ修正やセキュリティ/安定性向上が含まれます。ユーザーは AWS マネジメントコンソール、AWS CLI、または AWS SDK を使って対象の RDS インスタンスをアップグレードできます。アップグレード手順や互換性、事前チェックについては Amazon RDS SQL Server のユーザーガイド（アップグレード手順）を参照してください。アップグレードは既存インスタンスのエンジンパッチ適用（マイナー/パッチレベルの更新）であり、適用中はインスタンスの再起動や短時間のダウンタイムが発生する可能性があります。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for SQL Server を運用しているデータベース管理者、SRE、アプリケーション開発チーム
- **利用シーン**: セキュリティ修正や不具合修正を含む最新 CU を適用して本番／ステージング環境の安定性と安全性を維持する場面
- **運用効果**: 既知のバグ修正やパフォーマンス改善、セキュリティ向上により運用リスクの低減と障害対応コスト削減が期待できる
- **互換性影響**: 一部のアプリケーション依存機能（透過的データ暗号化、サードパーティ拡張、カスタム構成等）で互換性の確認が必要
- **リージョン影響**: GovCloud (US) 向けアナウンスだが、実際の提供リージョンはコンソールでの確認が必要（リージョン差異があり得る）

### 技術的な注意点

- **IAM権限**: DB インスタンスの変更・開始・停止・スナップショット作成に必要な IAM 権限が必要です（rds:ModifyDBInstance など）
- **リージョン制限**: 発表カテゴリは GovCloud (US) 向けだが、実際の提供状況はリージョンごとに差があるためコンソールまたは API で確認してください
- **コスト**: パッチ適用自体に追加料金は発生しないが、アップグレード作業中のスナップショット作成や追加の検証環境利用によるコストが発生する可能性があります
- **バックアップ/ロールバック**: アップグレード前に必ずスナップショットを取得してください。RDS のエンジンパッチは即時反映かメンテナンスウィンドウでの実行が選べますが、ロールバックは自動ではなく、必要なら新しいインスタンスを旧エンジンで再作成する等の手順が必要です
- **ダウンタイム**: 多くの場合インスタンスの再起動を伴うため短時間のダウンタイムまたは接続切れが発生します。業務影響を低くするためメンテナンスウィンドウの設定やフェイルオーバー試験を検討してください
- **互換性試験**: 本番適用前にステージング環境でアプリケーションの機能テストとパフォーマンステストを実施してください。特にサードパーティ製ドライバや拡張機能の互換性を確認すること
- **操作方法**: コンソール、AWS CLI (aws rds modify-db-instance --engine-version 17.00.4075.5.v1 等)、または SDK での実行が可能です。操作前にドキュメントの手順を確認してください

## [CloudFront] Amazon CloudFront now supports AWS Lambda Web Functions as an origin

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-lambda-web-functions-origin/

### 概要

Amazon CloudFrontがAWS Lambda Web Functionsをオリジンとして直接配信できるようになりました。エッジでのTLS終端、キャッシュ、カスタムドメイン（管理されたTLS証明書）などのCloudFront機能をそのまま利用できます。

### 変更内容・新機能の詳細

CloudFrontをLambda Web Functionsの前段に置くことで、以下が可能になります：エッジでのTLS終端によりレイテンシと接続確立が改善される点、CloudFrontキャッシュによる応答性能向上、カスタムドメインとマネージドTLS証明書の利用、既存アプリケーションコードの変更不要。CloudFront Origin Access Control（OAC）を使ってLambda Web Functionへの直接アクセスをブロックし、CloudFront経由のみ許可することで、オリジンへの意図しないアクセスを防ぎます。OACを使用すると、ネットワーク層のDDoSに対する保護（CloudFrontのグローバルエッジ＋Shieldの効果）を受けられ、さらにAWS WAFを組み合わせてアプリケーション層の防御を強化できます。独自にユーザー認証を行うアプリケーションでも、OACは元の認証情報を変更せずにオリジンへ渡すため、既存のサインインフローに影響を与えません。機能はCloudFrontの全リージョンで利用可能（CloudFront Chinaリージョンは除く）。設定はCloudFrontコンソール、SDK、CLI、CloudFormationで行えます。なお、本機能自体に追加料金はありません（ただしCloudFrontおよびLambdaの従来の課金は適用されます）。

### 影響範囲・利用シーン

- **対象ユーザー**: Webアプリ開発者、フロントエンドエンジニア、クラウドインフラ/運用チーム
- **利用シーン**: サーバーレスWebアプリのグローバル配信（低遅延接続、カスタムドメイン、エッジキャッシュ適用）
- **運用効果**: オリジンへの不要なトラフィックを防止しつつエッジでTLS終端・キャッシュを活用でき、応答性能とセキュリティ（DDoS軽減、WAF併用）が向上する

### 技術的な注意点

- **IAM権限**: CloudFrontディストリビューションの作成/更新、OACの管理、Lambda Web Functionの更新・設定に必要なIAM権限を事前に確認してください（例: cloudfront:CreateDistribution / UpdateDistribution、lambda:UpdateFunctionConfigurationなど）。
- **リージョン制限**: 全リージョンで利用可能ですが、CloudFront Chinaリージョンでは未対応です。Lambda Web Functionsのリージョン配置とCloudFrontのエッジ挙動を確認してください。
- **コスト**: 本機能に対する追加料金はありませんが、CloudFront（データ転送、リクエスト数、キャッシュミス時のオリジンフェッチ）とLambda Web Functions（実行時間・リクエスト数など）の通常の課金が適用されます。キャッシュ設定次第でオリジンコストに大きく影響します。
- **OAC/アクセスポリシー**: OACを設定してCloudFront経由のみアクセス可能にすることを推奨します。OACの設定とディストリビューションのオリジン設定（プロトコルポリシー等）を正しく組み合わせてください。
- **認証/ヘッダ保持**: 記事のとおり、OACを使っても元の認証情報はオリジンへ届きますが、CloudFrontのキャッシュポリシーやヘッダー転送設定（Cookie/Authorizationヘッダーの転送）を適切に構成しないと認証付きレスポンスがキャッシュされてしまう可能性があります。
- **キャッシュ設計**: 動的・ユーザー固有レスポンスを扱う場合はCache PolicyやOrigin Request Policyを使って、キャッシュキーやヘッダ/クエリ文字列の扱いを制御してください。誤ったキャッシュ設定は情報漏洩やセッション不整合を招きます。
- **WAF/Shield連携**: CloudFrontにアタッチすることでAWS WAFとShield（Standard）の保護が利用可能です。必要に応じてWAFルールやレートベースルールでアプリケーション層防御を強化してください。
- **設定手段**: CloudFrontコンソール、AWS CLI、SDK、CloudFormationでの設定が可能です。Infrastructure as Codeでの運用を検討してください。
- **既存コード変更**: 記事では「コード変更不要」とされていますが、キャッシュやヘッダー要件に応じてアプリケーション側でCache-ControlやCORS設定の調整が必要になる場合があります。

- **制限/注意点（影響）**: 現時点はNode.jsのみ対応のため他ランタイムは利用不可。リージョン対応状況により利用可能性が変動

## [General] Announcing consumption-based pricing for short-term memory in Amazon Bedrock AgentCore

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/agentcore-memory-consumption-based-pricing

### 概要

Amazon Bedrock AgentCoreの短期メモリ（STM）がイベントごとの定額課金から消費量ベース課金に変更されました。エージェントが取り込む・検索する・保存するデータ量に応じて課金されます。

### 変更内容・新機能の詳細

短期メモリ（STM）は、従来の「イベント単位のフラット料金」を廃止し、以下の3つの次元での消費量ベース課金に変更されました。
- 取り込み（ingestion）: $1.00／GB（イベント単位で課金）
- 検索／取得（retrieval）: $0.20／GB（イベント単位で課金）
- 保存（storage）: $0.10／GB‑month（各イベントの実サイズで課金）
取り込みと取得は「イベントごと」に課金され、課金対象サイズは最小12KB、最大64KBの範囲で評価されます（つまり各イベントの請求サイズは12KB未満なら12KB、64KB超なら64KBで換算されます）。保存（ストレージ）についてはイベントの実際のサイズがそのままGB‑monthに換算されて課金されます。長期メモリ（LTM）に関する料金は変更されていません。多くのワークロードではコスト低下が見込まれ、特に小さなペイロードを頻繁に扱うケースで削減効果が大きくなります。保管コストを抑えるために、メモリリソースのTTL（有効期間）を短めに設定することでストレージ使用量を制御できます。消費ベース課金はAgentCore Memoryが提供されるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: エージェント開発者、AI/チャットボット実装者、SRE/クラウド運用チーム
- **利用シーン**: セッション内コンテキスト保持（短期メモリ）を多用するエージェント、頻繁に小さなイベントを取り扱うリアルタイム会話システム
- **運用効果**: 小ペイロードを多数扱うワークロードでコスト削減が期待でき、TTL調整によりストレージ費用を運用で抑制可能
- **コスト影響**: 大容量の取り込みや頻繁な取得が多い場合は従来より費用が増える可能性があるため見積りが必要
- **可用性**: AgentCore Memoryが提供されるすべてのリージョンで利用可能（リージョンによる限定はなし）

### 技術的な注意点

- **IAM権限**: AgentCoreのメモリ設定（TTL等）やメモリ操作を行うためのBedrock/AgentCore関連の権限と、請求/コスト閲覧のためのCost Explorer/Billing権限を確認してください
- **リージョン制限**: 消費ベース課金はAgentCore Memoryが提供されるすべてのAWSリージョンで有効です（リージョン未提供の場所では利用不可）
- **コスト**: 取り込み($1/GB)と取得($0.20/GB)はイベント単位で請求され、請求サイズは12KB最小・64KB最大で評価されます。保存は実サイズでGB‑month換算され$0.10/GB‑monthで請求されます。高頻度・大容量の読み書きがあるワークロードはコスト増となるため事前に試算してください
- **運用上の注意**: 小さいペイロード（&lt;12KB）は取り込み／取得で最小課金単位の12KBで請求されるため、頻度とサイズのバランスを検討してください。ストレージ削減にはTTLを短くする運用が有効です
- **監視／予算**: CloudWatchやCost Explorer、Budgetsでメモリ取り込み／取得量と保存量を監視し、アラートや予算閾値を設定することを推奨します
