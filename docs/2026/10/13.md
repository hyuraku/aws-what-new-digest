## [CloudFront] Amazon CloudFront now supports AWS Lambda Web Functions as an origin

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-lambda-web-functions-origin/

### 概要

Amazon CloudFrontがAWS Lambda Web Functionsをオリジンとして直接配信できるようになりました。エッジでのTLS終端、キャッシュ、カスタムドメイン（管理されたTLS証明書）などのCloudFront機能をそのまま利用できます。

### 変更内容・新機能の詳細

CloudFrontをLambda Web Functionsの前段に置くことで、以下が可能になります：エッジでのTLS終端によりレイテンシと接続確立が改善される点、CloudFrontキャッシュによる応答性能向上、カスタムドメインとマネージドTLS証明書の利用、既存アプリケーションコードの変更不要。CloudFront Origin Access Control（OAC）を使ってLambda Web Functionへの直接アクセスをブロックし、CloudFront経由のみ許可することで、オリジンへの意図しないアクセスを防ぎます。OACを使用すると、ネットワーク層のDDoSに対する保護（CloudFrontのグローバルエッジ＋Shieldの効果）を受けられ、さらにAWS WAFを組み合わせてアプリケーション層の防御を強化できます。独自にユーザー認証を行うアプリケーションでも、OACは元の認証情報を変更せずにオリジンへ渡すため、既存のサインインフローに影響を与えません。機能はCloudFrontの全リージョンで利用可能（CloudFront Chinaリージョンは除く）。設定はCloudFrontコンソール、SDK、CLI、CloudFormationで行えます。なお、本機能自体に追加料金はありません（ただしCloudFrontおよびLambdaの従来の課金は適用されます）。

### 影響範囲・利用シーン

- **対象ユーザー**: Webアプリ開発者、フロントエンドエンジニア、クラウドインフラ/運用チーム
- **利用シーン**: サーバーレスWebアプリのグローバル配信（低遅延接続、カスタムドメイン、エッジキャッシュ適用）
- **運用効果**: オリジンへの不要なトラフィックを防止しつつエッジでTLS終端・キャッシュを活用でき、応答性能とセキュリティ（DDoS軽減、WAF併用）が向上する

### 技術的な注意点

- **IAM権限**: CloudFrontディストリビューションの作成/更新、OACの管理、Lambda Web Functionの更新・設定に必要なIAM権限を事前に確認してください（例: cloudfront:CreateDistribution / UpdateDistribution、lambda:UpdateFunctionConfigurationなど）。
- **リージョン制限**: 全リージョンで利用可能ですが、CloudFront Chinaリージョンでは未対応です。Lambda Web Functionsのリージョン配置とCloudFrontのエッジ挙動を確認してください。
- **コスト**: 本機能に対する追加料金はありませんが、CloudFront（データ転送、リクエスト数、キャッシュミス時のオリジンフェッチ）とLambda Web Functions（実行時間・リクエスト数など）の通常の課金が適用されます。キャッシュ設定次第でオリジンコストに大きく影響します。
- **OAC/アクセスポリシー**: OACを設定してCloudFront経由のみアクセス可能にすることを推奨します。OACの設定とディストリビューションのオリジン設定（プロトコルポリシー等）を正しく組み合わせてください。
- **認証/ヘッダ保持**: 記事のとおり、OACを使っても元の認証情報はオリジンへ届きますが、CloudFrontのキャッシュポリシーやヘッダー転送設定（Cookie/Authorizationヘッダーの転送）を適切に構成しないと認証付きレスポンスがキャッシュされてしまう可能性があります。
- **キャッシュ設計**: 動的・ユーザー固有レスポンスを扱う場合はCache PolicyやOrigin Request Policyを使って、キャッシュキーやヘッダ/クエリ文字列の扱いを制御してください。誤ったキャッシュ設定は情報漏洩やセッション不整合を招きます。
- **WAF/Shield連携**: CloudFrontにアタッチすることでAWS WAFとShield（Standard）の保護が利用可能です。必要に応じてWAFルールやレートベースルールでアプリケーション層防御を強化してください。
- **設定手段**: CloudFrontコンソール、AWS CLI、SDK、CloudFormationでの設定が可能です。Infrastructure as Codeでの運用を検討してください。
- **既存コード変更**: 記事では「コード変更不要」とされていますが、キャッシュやヘッダー要件に応じてアプリケーション側でCache-ControlやCORS設定の調整が必要になる場合があります。

- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/

Amazon EC2のG7インスタンス（NVIDIA RTX PRO 4500 Blackwell Server Edition搭載）がEurope (Frankfurt) と Europe (Stockholm) リージョンで利用可能になりました。高性能GPUによりAI推論、グラフィックス、GPU加速データ分析等のワークロードを大幅に高速化します。

- **リージョン影響**: 欧州（フランクフルト／ストックホルム）が新たに利用可能となり、データ主権やレイテンシ要件を満たす選択肢が拡大する

### 技術的な注意点

- **ネットワーク/EFA**: 分散トレーニングや低レイテンシ通信ではEFAの利用を検討してください。EFAの構成やOSレベルの設定（ドライバ/ライブラリ）が必要です
- **ローカルストレージ**: 高速NVMeローカルストレージを持ちますが、インスタンス停止/終了時のデータ保持に注意してください
- **互換性**: 一般的な深層学習フレームワーク（TensorFlow、PyTorch等）やGPUアクセラレーションライブラリと互換ですが、特定のバージョン間の互換性は事前に検証してください

## [General] Amazon Connect Customer now prefills step-by-step guides for after contact work 

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/connect-customer-prefills-guides-acw

### 概要

Amazon Connect Customerの「ステップバイステップガイド」に通話内容から抽出した情報を自動で事前入力できる機能が追加され、エージェントのアフターコンタクトワーク（ACW）を短縮し、入力ミスを減らします。

### 変更内容・新機能の詳細

管理者が会話から抽出する情報（予約ID、請求番号、通話サマリなど）とガイド内の各フォームフィールドのマッピングルールを定義できます。通話内容は自動的に解析・抽出され、該当フィールドに事前入力されるため、エージェントは手入力する代わりに内容をレビューして必要があれば修正して送信できます。機能は既存のステップバイステップガイド機能に統合され、テキスト抽出や要約は会話の音声→文字起こし→情報抽出のパイプライン（会話インテリジェンス）を用いて行われます。これによりACWの時間短縮、データ品質向上、処理効率の改善が期待できます。

### 影響範囲・利用シーン

- **対象ユーザー**: コンタクトセンターのマネージャー、スーパーバイザー、およびエージェント
- **利用シーン**: 保険のクレーム処理、予約受付、顧客情報の記録など、通話後に定型情報をフォームに入力する業務
- **運用効果**: ACW時間の短縮、手入力によるヒューマンエラーの低減、ワークフローの標準化による報告・監査対応の効率化

### 技術的な注意点

- **IAM権限**: ステップバイステップガイドの設定や情報抽出ルールの管理には管理者権限が必要。エージェントはガイドの閲覧・編集・送信権限が必要になります。
- **リージョン制限**: 機能は次のリージョンで利用可能です：US East (N. Virginia), US West (Oregon), Asia Pacific (Seoul), Asia Pacific (Singapore), Asia Pacific (Sydney), Asia Pacific (Tokyo), Canada (Central), Europe (Frankfurt), Europe (London)。コンタクトサマリは Africa (Cape Town) でも利用可能です。
- **コスト**: 会話の文字起こしや要約、情報抽出に関連する会話インテリジェンス（例: Contact Lens相当）の処理は追加課金対象となる可能性があるため、利用前に料金を確認してください。
- **プライバシー/コンプライアンス**: 会話内容から個人識別情報（PII）を抽出するため、データ保持ポリシー、アクセス制御、マスク処理の要件を確認し、必要に応じて同意・監査対応を実装してください。
- **精度と運用**: 事前入力の正確性は音声品質やモデルの抽出精度に依存します。重要フィールドはエージェントによる検証フローを維持してください。
- **設定/運用**: 管理画面でフィールドと抽出ルールのマッピングを定義する必要があります。既存のステップバイステップガイドを有効化して設定を行ってください。

## [General] AWS Lambda announces Lambda Web Functions

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-lambda-web-functions/

### 概要

AWS Lambdaに新しく「Lambda Web Functions」が追加されました。これはコードが直接HTTPサーバとしてポートで待ち受け、既存のWebフレームワークをそのまま使ってリクエストを処理できるサーバーレス実行プリミティブです。

### 変更内容・新機能の詳細

主な特徴と技術的仕様:
- HTTPサーバモデル: 関数コードがポートでリッスンし、ExpressやHonoなど既存のWebフレームワークをアダプタ不要で利用可能。従来のLambdaハンドラモデルとは異なり、コードは通常のHTTPサーバと同様にリクエスト/レスポンスを直接扱います。
- ランタイムと同時実行: 発表時点ではNode.jsランタイムをサポート。1つの“ウォーム”実行環境が複数の同時リクエストを処理できるため、コールドスタートを大幅に削減できます。
- ネイティブHTTPストリーミング: クライアントへ逐次的に結果をストリーム送信することが可能で、ストリーミングAPIや長時間レスポンスに適します。
- 請求モデル: アイドル時に待機しているCPU時間ではなく、「アクティブなCPU時間」と実行環境が保持するメモリ量に対して課金されるモデル。I/O待ちが多い（DBや外部サービス待ち）処理ではコスト改善が期待できます。
- ネットワークと運用: Amazon VPC接続をサポートし、VPC内のリソースへアクセス可能。マルチリージョンルーティングにより一度デプロイして各リクエストを最寄りリージョンで応答できます。
- デプロイと互換性: AWS Lambda API、Agent Toolkit for AWS、マネジメントコンソール、AWS CLI、CloudFormation、SAM、CDK、各種SDKから作成・設定可能。既存のLambda関数は“Lambda Event Functions”へ名称変更されますが、コード変更や再デプロイは不要の名称変更のみです。
- 用途例: AI推論エンドポイント、サーバーサイドレンダリング(SSR)、ストリーミングAPI、マイクロサービス、Webhookなど低レイテンシでHTTP応答が必要なワークロードに向きます。

### 影響範囲・利用シーン

- **対象ユーザー**: Webアプリ開発者、バックエンドエンジニア、AI推論サービス開発者、SRE/運用チーム
- **利用シーン**: SSRやAI推論の低遅延エンドポイント、ストリーミングAPI、Webhook受信、マイクロサービスのHTTPエンドポイント
- **運用効果**: コールドスタートの頻度削減によるレイテンシ改善、IO待ちでの無駄なCPU課金削減によるコスト最適化
- **開発効果**: Express/Honoなど既存フレームワークをそのまま利用できるためローカル開発から本番デプロイまでの障壁が低下
- **制限/注意点（影響）**: 現時点はNode.jsのみ対応のため他ランタイムは利用不可。リージョン対応状況により利用可能性が変動

### 技術的な注意点

- **IAM権限**: 関数の作成/更新には標準的なLambda権限が必要（例: lambda:CreateFunction, lambda:UpdateFunctionConfiguration）。VPC接続を使う場合はENI作成のためのEC2権限（ec2:CreateNetworkInterface等）が必要になる点に注意。
- **リージョン制限**: 発表時点で利用可能なリージョンは US East (N. Virginia), US East (Ohio), US West (Oregon), Asia Pacific (Tokyo), Europe (Ireland)。利用前に「AWS Capabilities by Region」ページで最新状況を確認してください。
- **コスト**: 「アクティブなCPU時間」と実行環境のメモリ保持量に基づく課金モデル。I/O待ちが多い処理ではコスト削減が見込める一方、CPU集約型処理や長時間実行のワークロードでは従来のモデルより高くなる可能性があるため事前に料金ページで試算してください。
- **ランタイム制限**: 初期提供はNode.jsのみ。将来的に他ランタイムが追加される可能性はあるが、現状は対応言語に制約あり。
- **互換性**: 従来のLambdaハンドラモデル（Event Functions）とはライフサイクルや並列処理モデルが異なるため、ライブラリやミドルウェアが期待する初期化/クリーンアップタイミングに注意が必要です。
- **ネットワーク/VPC**: VPC接続をサポートするが、VPC内リソースへのアクセスやセキュリティグループの設定、ENI関連の起動遅延・制限を考慮してください。
- **デプロイ/運用ツール**: CloudFormation/SAM/CDK/CLIなど既存ツールで管理可能。既存関数は“Lambda Event Functions”へ名前変更されるのみでコード変更不要。
- **特になし**: 特になし

## [General] Announcing consumption-based pricing for short-term memory in Amazon Bedrock AgentCore

- **公開日**: 2026-10-13 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/agentcore-memory-consumption-based-pricing

### 概要

Amazon Bedrock AgentCoreの短期メモリ（STM）がイベントごとの定額課金から消費量ベース課金に変更されました。エージェントが取り込む・検索する・保存するデータ量に応じて課金されます。

### 変更内容・新機能の詳細

短期メモリ（STM）は、従来の「イベント単位のフラット料金」を廃止し、以下の3つの次元での消費量ベース課金に変更されました。
- 取り込み（ingestion）: $1.00／GB（イベント単位で課金）
- 検索／取得（retrieval）: $0.20／GB（イベント単位で課金）
- 保存（storage）: $0.10／GB‑month（各イベントの実サイズで課金）
取り込みと取得は「イベントごと」に課金され、課金対象サイズは最小12KB、最大64KBの範囲で評価されます（つまり各イベントの請求サイズは12KB未満なら12KB、64KB超なら64KBで換算されます）。保存（ストレージ）についてはイベントの実際のサイズがそのままGB‑monthに換算されて課金されます。長期メモリ（LTM）に関する料金は変更されていません。多くのワークロードではコスト低下が見込まれ、特に小さなペイロードを頻繁に扱うケースで削減効果が大きくなります。保管コストを抑えるために、メモリリソースのTTL（有効期間）を短めに設定することでストレージ使用量を制御できます。消費ベース課金はAgentCore Memoryが提供されるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: エージェント開発者、AI/チャットボット実装者、SRE/クラウド運用チーム
- **利用シーン**: セッション内コンテキスト保持（短期メモリ）を多用するエージェント、頻繁に小さなイベントを取り扱うリアルタイム会話システム
- **運用効果**: 小ペイロードを多数扱うワークロードでコスト削減が期待でき、TTL調整によりストレージ費用を運用で抑制可能
- **コスト影響**: 大容量の取り込みや頻繁な取得が多い場合は従来より費用が増える可能性があるため見積りが必要
- **可用性**: AgentCore Memoryが提供されるすべてのリージョンで利用可能（リージョンによる限定はなし）

### 技術的な注意点

- **IAM権限**: AgentCoreのメモリ設定（TTL等）やメモリ操作を行うためのBedrock/AgentCore関連の権限と、請求/コスト閲覧のためのCost Explorer/Billing権限を確認してください
- **リージョン制限**: 消費ベース課金はAgentCore Memoryが提供されるすべてのAWSリージョンで有効です（リージョン未提供の場所では利用不可）
- **コスト**: 取り込み($1/GB)と取得($0.20/GB)はイベント単位で請求され、請求サイズは12KB最小・64KB最大で評価されます。保存は実サイズでGB‑month換算され$0.10/GB‑monthで請求されます。高頻度・大容量の読み書きがあるワークロードはコスト増となるため事前に試算してください
- **運用上の注意**: 小さいペイロード（&lt;12KB）は取り込み／取得で最小課金単位の12KBで請求されるため、頻度とサイズのバランスを検討してください。ストレージ削減にはTTLを短くする運用が有効です
- **監視／予算**: CloudWatchやCost Explorer、Budgetsでメモリ取り込み／取得量と保存量を監視し、アラートや予算閾値を設定することを推奨します
