## [General] AWS Transform announces Azure-to-AWS cloud-native code conversion

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-transform-azure-to-aws-code-conversion/

### 概要

AWS TransformがAzure SDKからAWS SDKへのアプリケーションコード変換機能をGAで提供開始しました。Azureネイティブな.NETアプリケーションの移行を自動化・加速するための変換エージェントが利用可能です。

### 変更内容・新機能の詳細

AWS Transformの.NETモダナイゼーションエージェントが、提出されたソースコードを解析してAzure SDKの呼び出しを検出し、対応するAWS SDK呼び出しへコード変換します。変換対象例としては、Azure Functions → AWS Lambda、Azure Blob Storage → Amazon S3、Azure Queue Storage → Amazon SQSが正式サポートされ、Azure Cosmos DB → Amazon DynamoDBはプレビュー提供されています。Transformはソースコードの評価レポートとモダナイゼーションプランで変換候補を提示し、ユーザーは提示されたオプションをそのまま受け入れるか、調整してから変換を実行できます。変換実行後は、該当箇所が変換済みであることを検証するプロセスが行われます。なお本機能はコードレベル（SDK呼び出し）の変換にフォーカスしており、アプリケーション固有のビジネスロジックやインフラ構成（例：IaC、ネットワーク設定、ランタイム環境の差異）については追加対応や手作業による調整が必要になる場合があります。利用可能リージョンは、米国東部（バージニア北部）、アジアパシフィック（ムンバイ、東京、ソウル、シドニー）、カナダ（中部）、欧州（フランクフルト、ロンドン）の8リージョンです。

### 影響範囲・利用シーン

- **対象ユーザー**: Azure上のクラウドネイティブな.NETアプリケーションをAWSへ移行したい開発者・クラウドエンジニア・SRE
- **利用シーン**: Azure FunctionsやAzure Blob/Queue を用いたアプリケーションをAWS Lambda/S3/SQSへ移行するコード変換作業の自動化
- **運用効果**: 手動変換工数を削減し移行期間を短縮、初期変換提案に基づく移行プランニングが容易になる（ただし変換後のテストと設定調整は必要）

### 技術的な注意点

- **IAM権限**: Transformの操作やソースコードの読み取り・書き込みに必要なAWS IAM権限を事前に用意してください（例: Transformサービス実行権限、S3/CodeCommitアクセス権などが想定されます）。
- **リージョン制限**: 本機能は指定の8リージョンで利用可能です。その他リージョンでは未提供のため、リージョンの確認が必要です。
- **対応サービス**: 正式サポートは Azure Functions→Lambda、Blob→S3、Queue→SQS。Cosmos DB→DynamoDBはプレビューです。その他Azure特有のバインディングやマネージドサービスは変換対象外または部分的サポートの可能性があります。
- **互換性・追加作業**: SDK呼び出しの置換は自動化されますが、環境変数、シークレット管理、認証（Azure AD→IAMロール）、ランタイム設定、ネットワーク（VPC）や監視・ロギングの差異、データモデルやクエリ特性（Cosmos DBとDynamoDBの違い等）については手動での調整・検証が必要です。
- **テスト**: 変換後は単体テスト・統合テスト・負荷試験を実施して機能・パフォーマンス・一貫性（整合性モデル）の違いを検証してください。
- **コスト**: Transformの利用や追加で発生するリソース（Lambda、DynamoDB、S3等）には料金が発生します。変換に伴うリファクタやテスト実行の工数コストも考慮してください。
- **サポート状況**: 一部変換（例: Cosmos DB→DynamoDB）はプレビューのため、商用移行前に制限事項や既知の問題を確認してください。

## [Outposts] Second-generation AWS Outposts racks now supported in the AWS Mexico (Central) Region

- **カテゴリ**: Outposts
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-outposts-racks-mexico-central/

### 概要

AWS Outpostsの第2世代ラックが、AWSメキシコ（Central）リージョンでサポートされるようになりました。これにより、同リージョンに接続するOutpostsラックを注文して、レイテンシやデータ駐在要件に合わせたハイブリッド構成が可能になります。

### 変更内容・新機能の詳細

第2世代のAWS Outpostsラックは、AWSのインフラ、サービス、API、およびツールをオンプレミスやコロケーションスペースに拡張し、クラウドと一貫したハイブリッド環境を提供します。今回の拡張により、メキシコ（Central）リージョンをOutpostsラックの接続先として選択できるようになり、レイテンシ最適化やデータ主権（データ駐在）要件への対応が容易になります。加えて、顧客はOutpostsが接続できるAWSリージョンの選択肢が増えるため、設計上の柔軟性が向上します。詳細な運用手順や技術仕様（設置要件、ネットワーク接続、電源・ラック要件など）はOutpostsユーザーガイドおよびFAQを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: ハイブリッド構成を必要とするエンタープライズ、公共機関、スタートアップ、コロケーション事業者
- **利用シーンまたは効果**: レイテンシに敏感なアプリケーションやデータ駐在規制のあるワークロードを、メキシコ地域に近い場所で実行可能にすることで応答性向上と法令順守を支援

### 技術的な注意点

- **IAM権限**: Outpostsの作成・管理には専用のIAM権限が必要です。プロビジョニングや管理APIの実行権限を事前に確認してください。
- **リージョン制限**: 第2世代Outpostsラックは今回メキシコ（Central）でサポートされますが、すべてのリージョン/国で利用可能というわけではありません。対応リージョン・国の最新一覧はOutpostsラックのFAQを確認してください。
- **ネットワーク接続**: Outpostsは管理プレーンやサービス接続のためにAWSリージョンとのネットワーク接続が必要です。帯域・回線冗長化、VPN/Direct Connectの要件、IPアドレッシング設計を事前に計画してください。
- **物理要件**: ラックの設置スペース、電源容量、冷却、搬入経路など物理要件の確認と現地調整が必要です。設置には事前のサイト調査が求められます。
- **コスト**: ラック本体の購入/レンタル、運用料金、ネットワーク接続費用、設置・保守費などが発生します。見積もりは導入前に確認してください。
- **プロビジョニング時間**: ラックの注文〜設置〜稼働までにリードタイムが発生します。導入スケジュールに余裕を持って計画してください。

## [General] AWS End User Messaging adds registration improvements for faster, higher-quality submissions

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-end-user-messaging-adds-registration-improvements-for-faster-higher-quality-submissions

### 概要

AWS End User Messagingの登録フローが改善され、米国の10DLC/ショートコード/トールフリーおよびRCS向けに準拠サンプルや条件付き必須フィールドの明示、RCS用の動画録画ガイドが追加され、初回で正しく・高速に申請できるようになりました。

### 変更内容・新機能の詳細

主な変更点は次の3点です。
1) 準拠サンプルの追加: US 10DLC、USショートコード、USトールフリー、RCS登録に対して、準拠したオプトインのモックアップおよびサンプルメッセージを示す例が登録フローに追加されました。これにより、どのような証拠（オプトインの記録やサンプルメッセージ）が受理されやすいかを事前に確認できます。
2) 登録APIレスポンスでの条件付き必須フィールドの明示: 登録APIのレスポンスに「条件付きロジック」が含まれるようになり、あるフィールドの値に応じてどのフィールドが必須になるかを明示的に返します。これにより、AIエージェントや自動化スクリプトが“推測”する必要がなく、申請に必要なフィールドを正確に埋められます。
3) RCS向けのエージェント登録用動画ガイド: RCS（Rich Communication Services）で要求されるエージェント登録用の準拠ビデオ（録画）について、記録手順のウォークスルーが追加され、要件を満たす動画を正しく用意できるようになりました。
これらの改善は、AWS End User Messagingの登録が提供されている全リージョンで利用可能です。技術的には、申請時に提出する証拠（オプトイン証拠、サンプルメッセージ、場合によってはエージェント動画）をあらかじめ模倣例に合わせて準備し、登録APIの新しいレスポンスフィールド（条件付き必須フィールド情報）をパースして自動化ワークフローに組み込むことが推奨されます。

### 影響範囲・利用シーン

- **対象ユーザー**: メッセージングを利用するアプリ開発者、SRE/運用チーム、マーケティング担当者、登録自動化を行うSaaS/インテグレータ
- **利用シーン**: 10DLC/ショートコード/トールフリー/RCSの事前登録準備、AIやスクリプトでの自動申請、RCSエージェント動画の作成・提出
- **運用効果**: 申請却下や差し戻しの減少による承認までの時間短縮、申請プロセスの自動化が容易になり人的オペレーションの削減、AIエージェントを用いた正確なフォーム入力によるミス削減

### 技術的な注意点

- **IAM権限**: 登録API呼び出しや証拠アップロードに必要なIAM権限を事前に確認・付与してください（Register/Submit系の権限）。
- **API/スキーマ変更**: 登録APIレスポンスに条件付き必須フィールド情報が追加されています。既存の自動化がレスポンスを解析している場合は、新フィールドをパースして必須/任意判定に反映する必要があります。
- **リージョン制限**: 記事記載の通り「AWS End User Messagingの登録が利用可能な全リージョン」で有効です。リージョン毎のサービス提供状況は確認してください。
- **コスト**: 本アップデート自体による追加料金は明示されていませんが、10DLC/ショートコード/トールフリー/RCSの各キャリアや番号取得に伴う料金（キャリア手数料、番号費用など）は引き続き発生する場合があります。
- **データ/プライバシー**: オプトイン証拠やエージェント動画には個人情報が含まれる可能性があります。保存・送信時は暗号化・アクセス制御・保持ポリシーを適用してください。
- **自動化対応**: AIエージェントやCI/CDに組み込む場合、条件付き必須フィールドのロジックに従ったバリデーションと、サンプルに準拠したフォーマットチェックを追加してください。
- **互換性**: レスポンスの拡張により既存のパーサーがエラーを出す可能性があるため、堅牢なパース処理（未知フィールドの無視など）を実装してください。

## [General] AWS End User Messaging now supports Brand Profiles

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-end-user-messaging-now-supports-brand-profiles

### 概要

AWS End User MessagingにBrand Profiles機能が追加され、企業情報（社名、住所、税ID、連絡先など）を一度登録してSMS/RCS/WhatsAppなど複数チャネルや国の登録で再利用できるようになりました。登録の手間と人為的ミスを削減し、申請のスピードと整合性を向上させます。

### 変更内容・新機能の詳細

Brand Profilesは、キャリアやメッセージングプロバイダへのブランド登録時に必要となる会社情報をテンプレート化して保存・再利用できる機能です。標準フィールド（会社名、税ID、住所、連絡先など）を自動で埋めるほか、オプションの「スマートマッチ」を有効にするとAIを用いてフィールド名が異なる場合でも適切な値を推測して埋めます。Brand Profileは新規で作成することも、既存の登録情報から作成することも可能で、同一AWSアカウント下で複数ブランドを管理できます。登録開始時に保存済み情報を基にドラフトが生成され、ユーザーは送信前に内容を確認・編集できます。チャネル固有の審査や各国の規制・追加書類要件は従来どおり有効で、Brand Profilesはこれらを補助して登録作業を効率化します。なお、この記事のとおり、本機能はAWS End User Messagingが利用可能な全ての商用リージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: マーケティング/通知システム担当者、SRE/運用チーム、マルチブランドを扱う管理者
- **利用シーン**: 新規チャネル（SMS/RCS/WhatsApp）や国別のブランド登録フォームへの反復入力を短縮する場面、複数ブランドを単一アカウントで管理する場面
- **運用効果**: 登録作業時間の短縮、フォームへの入力ミスによる申請却下の低減、チャネル間・国間でのブランド情報整合性の確保

### 技術的な注意点

- **IAM権限**: Brand Profilesの管理・利用にはAWS End User Messaging関連の操作権限が必要です。管理者はプロフィール作成・編集・適用を行えるポリシーを付与してください。
- **リージョン制限**: 本機能はAWS End User Messagingが利用可能な全ての商用リージョンで提供されていますが、サービス自体のリージョン対応状況は確認してください。
- **コスト**: Brand Profiles自体の利用に追加料金は明記されていませんが、各キャリアやメッセージングプロバイダへの登録手数料やチャネル利用料（メッセージ送信コスト）は別途発生する場合があります。
- **データ整合性/プライバシー**: スマートマッチはAIを用いてフィールドを推測します。自動入力結果は必ずレビューして誤りや機密情報の流出がないか確認してください。
- **チャネル別要件**: Brand Profilesで自動入力しても、各国・各チャネル（キャリア、WhatsApp Businessなど）の追加書類提出や審査要件は引き続き適用されます。申請書類のフォーマット差異に注意してください。

## [General] AWS End User Messaging adds a guided wizard for RCS registration videos

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-end-user-messaging-adds-guided-wizard-rcs-registration-videos

### 概要

AWS End User MessagingがRCSエージェント登録用の画面録画を自動化するウィザードを追加しました。これにより、正しいメッセージ順での送信と録画が容易になり、RCS登録の承認取得が早まります。

### 変更内容・新機能の詳細

今回の更新では、RCS（Rich Communication Services）登録フォームに、画面録画（メッセージング体験のデモ）を正しく取得するためのガイド付きウィザードが組み込まれました。多くの国（米国を含む）でRCS登録には特定のメッセージシーケンスをテスト端末へ送信した上でのスクリーン録画提出が求められます。これまでは開発者が手動でメッセージをスクリプトして送信する必要があり、順序ミスや不完全な録画が発生しやすく、承認遅延の原因になっていました。ウィザードはフォーム上で各ステップを制御し、必要なメッセージを正しい順序でテスト端末に送出して録画を促します。結果として、準拠したビデオを初回で作成でき、エージェントの承認プロセスを短縮できます。ウィザードは、ビデオ提出が要求されるすべてのRCS登録フォームで利用可能です。実作業としては、RCS対応のテスト端末（電話番号・デバイス設定）を用意し、ウィザードの指示に従って画面録画を行うだけで済みます。

### 影響範囲・利用シーン

- **対象ユーザー**: RCSエージェントを登録する開発者、モバイル/メッセージング担当者、SRE・運用チーム
- **利用シーン**: RCS登録用のスクリーン録画作成（キャリア/国の提出要件に適合したデモ動画の取得）
- **運用効果**: 手動スクリプトによるミスを削減し、ビデオ不備による再提出を減らして承認までの時間を短縮
- **導入効果**: 登録作業の簡略化で開発工数が減り、リリーススケジュールの確実性が向上

### 技術的な注意点

- **IAM権限**: End User MessagingコンソールやRCS登録フォームへアクセスするための適切なIAM権限（サービス固有の権限）が必要。事前にポリシーを確認してください。
- **リージョン制限**: 機能自体はRCS登録が必要な国の登録フォームに表示されます。AWSリージョンとは別に、携帯事業者や国別の要件に依存します（記事では米国を含む複数国に言及）。
- **コスト**: 記事では追加料金の言及はありませんが、End User Messagingサービスの利用に関連する標準的な料金が適用される可能性があります。事前に価格ページを確認してください。
- **テスト端末**: RCS対応の実機（テスト電話番号、RCSが有効な端末）が必要。画面録画の権限（OSのスクリーンレコード許可）を事前に設定してください。
- **プライバシー/セキュリティ**: 録画には実際のメッセージのやり取りが含まれるため、機密情報や個人情報を含めないテストデータを使用してください。
- **互換性/要件**: キャリアや国ごとに求められるメッセージシーケンスや表示要件が異なる場合があります。ウィザードは一般的な手順を自動化しますが、最終的な提出要件は各国/キャリアの指示に従ってください。

## [General] AWS End User Messaging now offers managed OTP verification end-to-end

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-end-user-messaging-adds-end-to-end-managed-OTP

### 概要

AWS End User Messaging (Notify) がエンドツーエンドのワンタイムパスコード（OTP）管理機能を追加しました。Notify がコードの生成・配信・検証を一括で行えるようになり、電話番号やキャリア登録、配信ロジックの運用を不要にします。

### 変更内容・新機能の詳細

主な内容:
- マネージドOTP: Notify がワンタイムパスコードを生成し、指定したチャネルへ配信、受信者が入力したコードの検証まで行います。従来はお客様側でコードの生成・保存・期限管理・検証ロジックを実装していましたが、これを Notify 側で代行します。
- 対応チャネル: SMS（テキスト）、音声（ボイス）、および WhatsApp によるコード配信をサポートします。
- 設定（Notify code configuration）: コードの種類（例: 数字/英数字）、長さ、有効期限、許可試行回数、各チャネル用のメッセージテンプレートなどを一度設定します。以後、コード送信用の API 呼び出し（1回）で配信し、検証用の API 呼び出し（1回）で利用者が入力したコードを検証します。
- 電話番号・配信管理: AWS の電話番号と配信経路を利用するため、電話番号の取得・キャリア登録・配信方法の運用管理が不要です。
- 利用開始: 記事では「5 分未満で動く OTP ソリューションを構築可能」とあり、最小限の設定で動作させられることが特徴です。
- リージョン: AWS End User Messaging が提供されている商用リージョンで利用可能（Gov/China 等は別扱いの可能性あり）。
- 実装上の補足: UI 側でコード入力の受け取りやエラー表示、バックエンドで送信／検証 API を呼び出すフローは従来通り必要です。Notify がコードのライフサイクル（保存・失効）と検証を管理するため、サーバー側でのコード保存は不要になりますが、監査ログや送信履歴等の扱いは設計段階で検討してください。

### 影響範囲・利用シーン

- **対象ユーザー**: ユーザー認証や多要素認証(MFA)、電話番号ベースの確認を必要とするアプリケーション開発者、SRE、セキュリティ/運用チーム
- **利用シーン**: サインアップ時の電話番号確認、パスワードリセット、2段階認証、取引/重要操作のワンタイム確認コード送信（SMS/音声/WhatsApp）
- **運用効果**: コード生成・保存・期限管理・配信ロジックの実装と運用コストを削減し、実装時間を短縮（記事では数分程度でプロトタイプ可能と明記）
- **対応チャネル**: SMS・音声・WhatsApp を統合的に扱えるため、グローバルなデリバリー戦略の簡素化が可能

### 技術的な注意点

- **IAM権限**: Notify の送信／検証 API を呼び出すための IAM 権限が必要です。最小権限の原則に基づいて Notify 関連アクションのみ許可するポリシーを作成してください。
- **リージョン制限**: 商用の AWS リージョンで提供されます。GovCloud や中国リージョンは別扱いの可能性があるため、使用予定のリージョンでサービス提供状況を確認してください。
- **コスト**: SMS/音声/WhatsApp ごとの送信料金や電話番号の保有料金が発生します。Notify 自体に別途料金があるかはドキュメントと料金ページで確認してください（チャネル単位の課金が主）。
- **WhatsApp の注意点**: WhatsApp 送信はテンプレートや事前承認が必要な場合があります。WhatsApp 固有のポリシーやテンプレート承認手順を事前に確認してください。
- **利用制限/クォータ**: レート制限や同一番号への送信制限などが存在する可能性があります。大量送信やバーストが想定される場合はサービスクォータを確認し、必要に応じて引き上げ申請してください。
- **セキュリティ/コンプライアンス**: Notify がコード管理を行いますが、監査ログの取得・保持ポリシーや個人情報の取り扱い（データ居所／ログ保存）については自社のコンプライアンス要件に合わせて確認・設定してください。
- **実装上の注意**: フロントエンドでの再送制御、誤入力時のロックアウトやユーザー向けエラーメッセージ設計は引き続き実装が必要です。

## [General] Amazon DynamoDB Streams now supports timestamp-based stream processing

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-dynamodb-streams-timestamp-processing

### 概要

Amazon DynamoDB Streamsがタイムスタンプ指定によるストリーム処理をサポートしました。指定した時刻以降の最初のレコードから読み取りを開始でき、途中再開やデータリプレイが容易になります。

### 変更内容・新機能の詳細

新たに追加された AT_TIMESTAMP シャードイテレータタイプを使うことで、任意のタイムスタンプ（過去の時刻または現在付近）を指定して、その時刻に書き込まれた最初のレコード以降からストリームを読み始められます。従来は最古の保持レコード（最大24時間分）または新規書き込み分のみを開始点にできましたが、タイムスタンプ指定により再処理やスキップ、復旧後の同期などが柔軟になります。Amazon Kinesis Client Library（KCL）経由でも、DynamoDB Streams Kinesis アダプタを用いれば AT_TIMESTAMP を利用可能です。機能はすべての商用リージョン、AWS GovCloud (US)、中国リージョンで利用可能で、追加料金はなく標準の GetRecords API リクエスト料金のみが課金されます。

### 影響範囲・利用シーン

- **対象ユーザー**: アプリケーション開発者、データエンジニア、SRE/運用チーム
- **利用シーンまたは効果**: 中断からの復旧（指定時刻以降のみ再処理）、デバッグ/監査のための過去ポイントからのデータリプレイ、バックログをスキップしてほぼ最新から再開、PITR（ポイントインタイムリカバリ）のエクスポート後にエクスポート時刻から同期
- **運用効果**: 全ストリーム再処理の回避により処理時間とコストを削減し、必要な時間点から正確に復帰可能
- **リージョン**: すべての商用リージョン、AWS GovCloud (US)、中国リージョンで利用可能
- **コスト**: 機能自体に追加料金はなし（GetRecords等の標準APIコストは発生）

### 技術的な注意点

- **IAM権限**: dynamodbstreams:DescribeStream / GetShardIterator / GetRecords 等の権限が必要です。KCL利用時はKCLの実行ロールに適切な権限を付与してください
- **イテレータ指定方法**: AT_TIMESTAMP イテレータとともにタイムスタンプを指定して最初の該当レコード以降を取得します（APIのパラメータ形式はドキュメントを参照してください）
- **保持期間**: ストリームの保持ウィンドウは最大24時間です。指定タイムスタンプが保持期間より古い場合は対象のレコードを読めません
- **KCL/チェックポイント**: 既存のチェックポイントがある場合、KCLはチェックポイントから再開します。タイムスタンプ指定は新規開始やチェックポイントをリセットした上で使用するのが想定されます
- **時間精度と境界動作**: 実装は「指定時刻以降に書き込まれた最初のレコード」を返します。厳密な時間形式やタイムゾーンの扱い（例: ISO8601/エポック指定など）は公式ドキュメントで確認してください
- **コスト注意**: タイムスタンプで過去に遡って大量のレコードを取得すると GetRecords 呼び出しが増え、APIコストと処理負荷が増加します
- **リージョン制限**: 前述のとおり主要リージョン、GovCloud、Chinaで利用可能ですが、特殊リージョンやローカルの制限がないか利用リージョンのドキュメントで確認してください

- **運用効果**: ログやトレースの時刻ズレが削減され、根本原因解析や性能ボトルネック特定の精度が向上。低遅延配置（CPG）との併用で、より一貫した低遅延かつ高精度な動作が可能になる

- **配置制約**: PTPGは配置制約を導入するため、キャパシティの都合で起動失敗やアベイラビリティゾーン間配置の制約が発生する可能性があります

- **互換性**: 全てのアプリケーションがPHC/Timestamping APIを直接利用できるわけではないため、アプリ／ライブラリ側の対応が必要になる場合があります

## [CloudFront] Amazon CloudFront announces dual-stack support for VPC origins

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-vpc-origin-dualstack/

### 概要

Amazon CloudFrontがVPC内のプライベートオリジン（ALB/NLB/EC2）に対してエンドツーエンドでIPv6配信を行える「dual-stack VPC origins」をサポートしました。これにより、オリジンをパブリックにせずにIPv6アーキテクチャや規制要件に対応できます。

### 変更内容・新機能の詳細

CloudFrontのVPCオリジン機能は、Application Load Balancer、Network Load Balancer、またはEC2インスタンスをプライベートサブネットに配置し、CloudFrontのみが到達できるようにするものです。本アップデートではこれらのVPCオリジンをdual-stack（IPv4/IPv6両対応）として設定可能になり、CloudFrontがクライアントからのIPv6トラフィックをオリジン側へIPv6でそのまま届けられるようになりました。従来はパブリックオリジンに対してのみdual-stackが可能で、VPCオリジンへの接続はIPv4のみでした。今回の対応により、オリジンをパブリックサブネットに移すことなくIPv6通信を実現できます。dual-stack VPCオリジンは、VPCオリジンがサポートされるAWSのCommercialリージョンですべて利用可能で、利用自体に追加料金は発生しません。設定面では、オリジン（ALB/NLB/EC2）がIPv6を受け入れるようにリスナーやネットワーク設定を整え、セキュリティグループ／NACLでIPv6トラフィックを許可する必要があります。運用面ではCloudFrontアクセスログやオリジンログでIPv6接続の確認・監視を行うことを推奨します。

### 影響範囲・利用シーン

- **対象ユーザー**: Web/アプリ配信を行うクラウドエンジニア、SRE、ネットワーク／セキュリティ担当者
- **利用シーン**: IPv6必須の規制対応やIPv6ネイティブ環境でのコンテンツ配信（例: IPv6のみのクライアントを持つサービス）
- **運用効果**: オリジンをパブリックに曝け出すことなくエンドツーエンドでIPv6を実現でき、セキュリティ要件を維持しつつネットワークアーキテクチャの近代化が可能
- **コスト影響**: dual-stack自体に追加料金は無し。ただし通常のデータ転送料金やCloudFrontのログ／監視コストは発生する

### 技術的な注意点

- **IAM権限**: CloudFrontディストリビューションとVPCオリジンを設定・変更するためのCloudFrontおよびVPC/ELB/EC2関連の権限が必要です（例: cloudfront:UpdateDistribution、ec2:Modify*、elasticloadbalancing:*など）。
- **リージョン制限**: VPCオリジンがサポートされているCommercialリージョンで利用可能。詳細な対応リージョンは公式のリージョン一覧を確認してください。
- **セキュリティ設定**: オリジン側のセキュリティグループおよびNACLでIPv6トラフィックを受け入れるルールを追加する必要があります。CloudFrontからのIPv6送信元プレフィックスはAWSが公開するIPレンジ（IPv6部分）または管理プレフィックスリストで確認してください。
- **オリジン設定**: ALB/NLBやEC2側でIPv6リスナー/アドレスを有効にし、オペレーティングシステムやアプリケーションがIPv6接続を処理できることを確認してください。
- **コスト**: dual-stack機能自体は追加料金なし。従来通りのデータ転送費・リクエスト費用・ログ保存費用などは発生します。
- **テスト/監視**: デプロイ後はCloudFrontアクセスログ、オリジンアクセスログ、ALB/NLBの接続ログなどでIPv6経路が使用されているか検証してください。負荷テストでIPv6経路のパフォーマンスとTLS/ヘルスチェック動作を確認することを推奨します。

- **運用効果**: 本番導入前にインデックス挙動やautovacuumに関する問題を早期検出でき、アップグレード計画のリスク低減に寄与する
- **制約/注意**: プレビュー環境は一時的（最大60日）でスナップショットやインスタンスの持ち出し制限があるため、本番データの直接運用や長期保存には不向き

Amazon RedshiftのシステムテーブルデータをApache Iceberg形式のAmazon S3 Tablesへ長期保存できる機能が、追加のリージョンで利用可能になりました。これにより既定の7日間を超えて監査・可観測性データを保持できます。

- **運用効果**: カスタムETLやログ同期の削減により運用負荷を低減し、本番クラスターへのリソース競合を回避。IcebergフォーマットによりサードパーティツールやAthenaなどでの分析が容易になり、観測性向上とコンプライアンス対応がしやすくなる
- **リージョン**: 追加対応リージョンは Asia Pacific (New Zealand)、Canada West (Calgary)、AWS GovCloud (US‑East)、AWS GovCloud (US‑West)。その他のリージョンの対応状況はドキュメントを確認してください

- **セキュリティ/コンプライアンス**: 保存場所（リージョン／アカウント）と暗号化設定（SSE-S3/SSE-KMS等）の要件を確認し、必要に応じてKMSキーやアクセスログの管理を行ってください
