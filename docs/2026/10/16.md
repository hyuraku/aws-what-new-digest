## [Bedrock] Web Search on Amazon Bedrock AgentCore expands to AWS GovCloud and 3 Regions

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-bedrock-agentcore/

### 概要

Amazon Bedrock AgentCore の Web Search ツールが、US East (Ohio)、US West (Oregon)、Asia Pacific (Sydney)、および AWS GovCloud (US‑West) の4リージョンで利用可能になりました。これにより、エージェントが最新のウェブ情報で応答を強化でき、アプリケーションやエンドユーザーに近いリージョンで低遅延に動作させられます。

### 変更内容・新機能の詳細

Web Search は完全マネージドのツールで、AI エージェントに対してインターネット上の最新情報に基づく“grounding”（根拠情報）を提供します。主な機能はウェブからの情報取得、要約、質問応答向けの最新化されたコンテキスト供給で、AgentCore のツールとしてエージェントのチェーンやプラン内から呼び出して使用します。今回のリージョン拡張により、US East (Ohio)、US West (Oregon)、Asia Pacific (Sydney)、および規制対応が必要なワークロード向けの AWS GovCloud (US‑West) で利用可能になり、ユーザーと近いリージョンでの低遅延化とデータ居住性・コンプライアンス要件への対応がしやすくなります。利用にあたっては AgentCore のツール設定、ネットワーク経路（インターネットアクセス／VPC 設定）、および該当リージョンでの有効化が必要です。料金やリージョンの対応状況はそれぞれのページで確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: AI エージェントを導入・運用する開発者、データサイエンティスト、SRE、ガバメント／規制対象組織
- **利用シーン**: 研究・情報収集、記事やレポートの要約、最新情報に基づく質問応答システム、チャットボットのリアルタイム情報参照
- **運用効果**: アプリケーション近傍リージョンでの実行によりレイテンシ低減が期待でき、最新のウェブ情報で回答の正確性と信頼性が向上する
- **コンプライアンス効果**: AWS GovCloud (US‑West) での提供により、政府機関や規制要件のあるワークロードでデータ居住性・コンプライアンスの要件を満たしやすくなる

### 技術的な注意点

- **IAM権限**: AgentCore と Web Search ツールの呼び出しに必要な IAM ポリシー（AgentCore 実行権限など）を付与する必要があります
- **リージョン制限**: 今回追加された4リージョン（US‑Ohio, US‑Oregon, Asia Pacific (Sydney), AWS GovCloud (US‑West)）で利用可能。その他リージョンでは未対応の可能性があるため Supported AWS Regions を確認してください
- **GovCloud 注意点**: GovCloud は AWS の別パーティション（aws‑us‑gov）であり、アカウント、認証、エンドポイントが通常リージョンと異なります。GovCloud アカウントでの有効化と権限設定が必要です
- **コスト**: Web Search の利用は AgentCore の料金体系やデータ転送費用に影響します。利用量に応じた追加料金やネットワーク（egress）コストが発生する可能性があるため事前に料金ページで確認してください
- **ネットワーク**: Web 検索は外部ウェブへアクセスする性質上、VPC、NAT、プロキシ設定、ファイアウォールルールが影響します。プライベートサブネットやVPCエンドポイントの設計を確認してください
- **データ保護**: 取得するウェブコンテンツは外部情報であり、機密データの送信や保存ポリシーに注意してください。ログやキャッシュの保存場所・保持期間を設計することを推奨します
- **サービス可用性**: サービスの提供状況やリージョン別の稼働条件は変わる可能性があるため、最新のサポートページで確認してください

## [Sagemaker Studio] Amazon SageMaker Studio simplifies getting started for new AI/ML builders with new sign-in options

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: Sagemaker Studio
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/sagemaker-studio-new-sign-in-options/

### 概要

Amazon SageMaker Studioが新規ユーザー向けにGoogle、GitHub、Appleの外部クレデンシャルで簡単にサインインできるようになり、クレジットカード不要（多くの場合）で事前設定済みのStudio環境へ直接入場してすぐにモデルの微調整・評価・デプロイが可能になりました。

### 変更内容・新機能の詳細

新機能は以下を提供します。新規ユーザーはGoogle/GitHub/Appleの認証情報で簡易サインアップができ、従来のAWSアカウント作成（クレジットカード入力やコンソール内での環境構築）なしに、あらかじめ構成されたSageMaker Studio環境へ直接遷移します。Hugging FaceやAWS製品ページの深リンクからモデルをプリロードした状態で起動でき、Studio内でそのままファインチューニング、評価、エンドポイントデプロイが可能です。チーム招待はメールベースで行え、招待されたコラボレータは自分のメール認証で共有環境（モデル、ノートブック、エンドポイント）にアクセスできます。IAMユーザーの個別作成や詳細なIAM権限設定は不要です。新規サインアップにはAWS Free Tierの無料クレジットが付与され、ほとんどの場合クレジットカードの登録は不要です。プロジェクトが無料クレジットを超えた場合は有料プランへアップグレードでき、支出上限（Spend limit）を設定して予算管理できます。検証済みの顧客には、G5/G6/G6e/G4dn のGPUインスタンスがデフォルトで利用可能（エンドポイント、トレーニング、ノートブック）で、クォータ増加申請は不要です。本機能はAmazon SageMaker StudioがサポートされるすべてのAWS商用リージョンで利用できます。技術的には外部IDプロバイダとのフェデレーション（OAuth/OIDC等）と、短期的に管理されたStudio環境・IAMロールの自動プロビジョニングにより、低摩擦での開始を実現していると考えられます。

### 影響範囲・利用シーン

- **対象ユーザー**: AI/MLモデルを素早く試したい開発者、データサイエンティスト、プロトタイピング担当者
- **利用シーン**: Hugging Face等で見つけたモデルを即座にStudioでカスタマイズ・微調整して評価・デプロイするワークフロー
- **運用効果**: アカウント作成や初期設定の工数が大幅に削減され、PoCやラピッドプロトタイプの立ち上げが短時間で行える
- **チームコラボレーション**: メール招待による共有環境で、IAMユーザー作成なしに共同作業が可能（オンボーディングが簡素化）
- **コスト管理**: 無料クレジットで試用でき、課金開始時は有料プランへの移行と支出上限設定で予算管理が可能

### 技術的な注意点

- **IAM権限**: 招待ベースの共有は従来のIAMユーザー作成を不要にするが、管理者は必要に応じて組織側のアクセス管理・監査ポリシー（CloudTrail、SCP等）を併用すべき
- **リージョン制限**: Amazon SageMaker Studioがサポートされる全てのAWS商用リージョンで利用可能。リージョンごとのインスタンスタイプ提供状況やクォータは確認が必要
- **コスト**: 無料クレジットで試用可能だが、長期的・大規模なトレーニングや推論は有料。GPUインスタンス利用（G5/G6/G6e/G4dn等）はコストが高いため、支出上限や請求アラートの設定を推奨
- **セキュリティ**: 外部IDプロバイダでのフェデレーションを使用するため、IDプロバイダ側のアカウントセキュリティ（MFA等）と連携ポリシーの確認が必要
- **クレジットカード**: 多くのケースでクレジットカード不要だが、地域や条件によりカードが必要になる場合があるためサインアップ時の指示を確認してください
- **移行・スケール**: 無料環境から本格運用へ移行する際は、既存のAWSアカウントへ環境/リソースを移行する手順（IAMロール、S3バケット、VPC設定など）を計画する必要がある

## [Ec2] Amazon EC2 T8i instances are now available in South America (São Paulo)

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/ec2-t8i-instances-south-america/

### 概要

Amazon EC2の新しいT8iインスタンスが南米（サンパウロ）リージョンで利用可能になりました。従来のT3よりも高い計算性能とネットワーク/EBS帯域を低コストで提供するバースト型汎用インスタンスです。

### 変更内容・新機能の詳細

T8iはAWS専用のカスタム第6世代Intel Xeon 6プロセッサ上で動作し、第6世代AWS Nitroカードを搭載しています。インスタンスサイズは nano, micro, small, medium の4種類。T3世代と比較して「最大で30%の価格対性能改善」をうたっており、計算性能は最大で70%向上、ネットワーク帯域は1.25倍、EBS帯域は2.4倍向上しています。T3と同じCPUクレジット方式（StandardおよびUnlimited）を継承するため、T3からの移行が容易で、既存のバースト挙動やクレジット管理はそのまま適用できます。T8i.microとT8i.smallはAWS Free Tierの対象です。購入オプションは現時点でオンデマンドとスポットが利用可能で、Savings Planは「まもなく利用可能」と案内されています。利用可能リージョンにはUS East（N. Virginia, Ohio）、US West（Oregon, N. California）、Europe（Frankfurt, Ireland, London, Paris）、Asia Pacific（Hyderabad, Malaysia, Mumbai, Seoul, Singapore, Sydney, Tokyo）、Canada（Central）に加えて今回South America（São Paulo）が含まれます。想定ワークロードは低〜中程度のCPU利用の継続的またはバースト処理（データ処理、ログインゲートウェイ、小規模DB、バッチ処理、イベント駆動関数、CI/CD、マイクロサービス、低トラフィックWebサイト等）です。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウド移行を検討中の開発者/運用者、既存のT3利用者、コスト最適化を狙うSREやプラットフォームチーム
- **利用シーン**: 小〜中規模の永続インスタンスやバーストワークロード（マイクロサービス、CI/CDランナー、バッチ、小規模DB、ログインゲートウェイ、低トラフィックWebなど）
- **運用効果**: T3からの置き換えで同等以上の性能をより低コストで実現でき、TCO削減や性能余裕の向上が期待できる（CPUクレジット互換により移行コストが低い）
- **コスト影響**: 同等構成で最大約30%の価格対性能改善が見込める一方、利用量が増えると総コストは増加するためベンチマークで確認が必要
- **リージョン**: 南米（サンパウロ）に新規展開されたため、LATAMユーザーのレイテンシ改善とデータ主権対応に寄与

### 技術的な注意点

- **IAM権限**: 特別な権限は不要（通常のEC2起動/管理権限が必要）
- **リージョン制限**: リリース時点で利用可能なリージョンに制限あり（上位のリージョンリスト参照）。展開前に対象リージョンでの利用可否を確認してください
- **CPUクレジット**: T3と同じStandard/Unlimitedのクレジット方式を採用。継続的な高負荷ワークロードではクレジット枯渇や追加料金に注意
- **Free Tier**: T8i.microおよびT8i.smallがFree Tier対象。ただしFree Tierの利用条件を確認してください
- **購入オプション**: 現在はOn-DemandとSpotで購入可能。Savings Planは近日対応予定のため長期利用割引を検討する場合は対応状況を確認
- **EBS/ネットワーク**: EBS帯域がT3比で大幅に改善。NitroベースでEBS最適化は標準で提供されるが、必要なIOPS/スループットがある場合はEBSボリュームのタイプとサイズを合わせて設計してください
- **互換性/移行**: 同じクレジットモデルのためT3からの移行は容易だが、実運用負荷のプロファイリング（CPUクレジット消費、ネットワーク/ストレージ使用率）は事前に必須
- **コスト**: 短期的なパフォーマンス改善でTCOを下げられる可能性が高いが、長期的に高稼働が続くケースは他のインスタンスタイプ（汎用/汎用より高い連続性能）と比較検討を推奨

- https://aws.amazon.com/ec2/instance-types/t8i/

## [General] Amazon DynamoDB Streams now supports timestamp-based stream processing

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-dynamodb-streams-timestamp-processing

### 概要

Amazon DynamoDB Streamsがタイムスタンプ指定によるストリーム処理をサポートしました。指定した時刻以降の最初のレコードから読み取りを開始でき、途中再開やデータリプレイが容易になります。

### 変更内容・新機能の詳細

新たに追加された AT_TIMESTAMP シャードイテレータタイプを使うことで、任意のタイムスタンプ（過去の時刻または現在付近）を指定して、その時刻に書き込まれた最初のレコード以降からストリームを読み始められます。従来は最古の保持レコード（最大24時間分）または新規書き込み分のみを開始点にできましたが、タイムスタンプ指定により再処理やスキップ、復旧後の同期などが柔軟になります。Amazon Kinesis Client Library（KCL）経由でも、DynamoDB Streams Kinesis アダプタを用いれば AT_TIMESTAMP を利用可能です。機能はすべての商用リージョン、AWS GovCloud (US)、中国リージョンで利用可能で、追加料金はなく標準の GetRecords API リクエスト料金のみが課金されます。

### 影響範囲・利用シーン

- **対象ユーザー**: アプリケーション開発者、データエンジニア、SRE/運用チーム
- **利用シーンまたは効果**: 中断からの復旧（指定時刻以降のみ再処理）、デバッグ/監査のための過去ポイントからのデータリプレイ、バックログをスキップしてほぼ最新から再開、PITR（ポイントインタイムリカバリ）のエクスポート後にエクスポート時刻から同期
- **運用効果**: 全ストリーム再処理の回避により処理時間とコストを削減し、必要な時間点から正確に復帰可能
- **リージョン**: すべての商用リージョン、AWS GovCloud (US)、中国リージョンで利用可能
- **コスト**: 機能自体に追加料金はなし（GetRecords等の標準APIコストは発生）

### 技術的な注意点

- **IAM権限**: dynamodbstreams:DescribeStream / GetShardIterator / GetRecords 等の権限が必要です。KCL利用時はKCLの実行ロールに適切な権限を付与してください
- **イテレータ指定方法**: AT_TIMESTAMP イテレータとともにタイムスタンプを指定して最初の該当レコード以降を取得します（APIのパラメータ形式はドキュメントを参照してください）
- **保持期間**: ストリームの保持ウィンドウは最大24時間です。指定タイムスタンプが保持期間より古い場合は対象のレコードを読めません
- **KCL/チェックポイント**: 既存のチェックポイントがある場合、KCLはチェックポイントから再開します。タイムスタンプ指定は新規開始やチェックポイントをリセットした上で使用するのが想定されます
- **時間精度と境界動作**: 実装は「指定時刻以降に書き込まれた最初のレコード」を返します。厳密な時間形式やタイムゾーンの扱い（例: ISO8601/エポック指定など）は公式ドキュメントで確認してください
- **コスト注意**: タイムスタンプで過去に遡って大量のレコードを取得すると GetRecords 呼び出しが増え、APIコストと処理負荷が増加します
- **リージョン制限**: 前述のとおり主要リージョン、GovCloud、Chinaで利用可能ですが、特殊リージョンやローカルの制限がないか利用リージョンのドキュメントで確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/10/amazon-dynamodb-streams-timestamp-processing
- https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/streams.html

## [Lambda] AWS Lambda Durable Execution SDK for Go is now generally available

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-lambda-durable-go-sdk-support/

### 概要

AWS Lambda Durable Execution SDK for Go が GA（一般提供）になりました。Go 開発者はこの SDK を使い、チェックポイント付きで最大1年まで一時停止できる耐障害性の高い長時間ワークフロー（durable functions）をネイティブに実装できます。

### 変更内容・新機能の詳細

この SDK は Go 向けに最適化された Lambda Durable Execution の実装を提供します。主な機能は、進捗の自動チェックポイント化（checkpointing）、外部イベントや人間の承認を待つためのコールバック統合、人やエージェントを介したワークフロー（human/agent-in-the-loop）、信頼性の高い関数連鎖（durable invocation）、および効率的な待機（wait）操作です。待機状態は最大で1年までサスペンド可能で、開発者はカスタムの進捗追跡ロジックを実装することなく複雑なマルチステップ処理（例：インフラ自動化、ロールアウト + 承認ゲート、AI 呼び出しと人間によるレビューを含むパイプライン）を構築できます。Go への導入は go get でモジュールを追加し、provided.al2023 ランタイム上で単一の静的バイナリとしてデプロイする従来の Lambda Go ワークフローと同様です。ローカル環境では durabletest パッケージを使ってネットワークや AWS 資格情報なしにワークフロー全体をテストでき、durablelint アナライザで再開時に壊れる可能性があるコードパターンを検出できます。導入前にリージョン対応状況と料金を確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: Go で Lambda を使う開発者、SRE、プラットフォームエンジニア
- **利用シーン**: 長時間・ステートフルなワークフロー（承認付きデプロイ、インフラ自動化、AI パイプライン、ヒューマンレビューを含む処理）の実装
- **運用効果**: カスタム状態管理や進捗追跡の実装が不要になり、失敗からの復帰や外部イベント待ちを簡素化して保守性を向上
- **開発効果**: ローカルでの完全ワークフロー検証（durabletest）と静的解析（durablelint）によりデバッグ/CI を改善
- **コスト/運用面**: 長期待機や追加の耐久性メカニズムにより従来の短期 Lambda 実行とは異なる課金要素やリソース設計が必要となる可能性があるため事前確認が必須

### 技術的な注意点

- **IAM権限**: 関数作成・更新、実行および SDK が利用する耐久性関連 API（該当する場合）の権限、CloudWatch Logs 権限などを事前に確認・付与してください
- **リージョン制限**: 一部リージョンで未対応の可能性があるため、デプロイ前に AWS Capabilities by Region を確認してください
- **コスト**: Durable functions の待機/ストレージ/制御プレーンに伴う追加料金が発生する可能性があります。Lambda Pricing と機能別料金を確認してください
- **ランタイム/互換性**: provided.al2023 ランタイムでの単一静的バイナリとしてデプロイする設計です。Go モジュール化とビルドフロー（CGO 無効化など）に注意してください

- **運用効果**: ログやトレースの時刻ズレが削減され、根本原因解析や性能ボトルネック特定の精度が向上。低遅延配置（CPG）との併用で、より一貫した低遅延かつ高精度な動作が可能になる

### 技術的な注意点

- **起動要件**: マイクロ秒精度を利用するにはインスタンスをPTPGで起動（あるいはPTPGに関連付け）してPHCを有効化する必要があります
- **配置制約**: PTPGは配置制約を導入するため、キャパシティの都合で起動失敗やアベイラビリティゾーン間配置の制約が発生する可能性があります

- **既存の時刻設定との併用**: デフォルトのNTP/chrony設定とPHCを併用する際は設定の競合を避けるために設定変更（優先順位や参照クロックの指定）が必要です
- **互換性**: 全てのアプリケーションがPHC/Timestamping APIを直接利用できるわけではないため、アプリ／ライブラリ側の対応が必要になる場合があります

- **運用効果**: コネクタのフルマネージド運用によりインフラ運用負荷を削減、スキーマ検証により下流エラーや互換性問題を早期に防止
- **コスト影響**: MSK Connect は稼働リソースと転送、監視に基づく課金；Schema Registry 自体は無料機能だが、MSK ブローカー、データ転送、CloudWatch、ストレージ等の利用に伴う費用が発生
- **リージョン制限**: 本発表は AWS European Sovereign Cloud (Germany) に対する追加で、他リージョンとの対応状況は別途確認が必要

### 技術的な注意点

- **IAM権限**: MSK Connect 実行ロールやコネクタがアクセスする外部リソース（Secrets Manager、S3、RDS 等）への適切な IAM ポリシーが必要です
- **リージョン制限**: 対象は AWS European Sovereign Cloud (Germany) リージョン向けの提供開始。他のソブリンクラウドやリージョンでの可用性は別途確認してください
- **ネットワーク/セキュリティ**: MSK Connect は顧客 VPC 内でコネクタを実行するため、サブネット・セキュリティグループ・ルーティングの設定（プライベート接続や NAT、VPC エンドポイント）が必要です。MSK とコネクタ間は TLS による暗号化を利用できます
- **互換性**: Schema Registry は Avro/JSON/Protobuf をサポート。既存クライアントは AWS 提供のクライアントライブラリ（C#/Java）での統合検証が推奨されます。スキーマ互換性ポリシー（互換性モード）を事前に設計してください
- **運用監視**: MSK Connect のメトリクスとログは CloudWatch や Amazon Managed Service の監視機能で収集・可視化します。コネクタの障害時の再起動ポリシーやデッドレター処理を設計してください
- **コスト**: Schema Registry 自体は追加課金対象外だが、MSK Connect の実行、ストレージ、データ転送、CloudWatch ログ等で追加コストが発生します。見積もりを行ってから導入してください

## [CloudFront] Amazon CloudFront announces dual-stack support for VPC origins 

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/cloudfront-vpc-origin-dualstack/

### 概要

Amazon CloudFrontがVPC内のプライベートオリジン（ALB/NLB/EC2）に対してエンドツーエンドでIPv6配信を行える「dual-stack VPC origins」をサポートしました。これにより、オリジンをパブリックにせずにIPv6アーキテクチャや規制要件に対応できます。

### 変更内容・新機能の詳細

CloudFrontのVPCオリジン機能は、Application Load Balancer、Network Load Balancer、またはEC2インスタンスをプライベートサブネットに配置し、CloudFrontのみが到達できるようにするものです。本アップデートではこれらのVPCオリジンをdual-stack（IPv4/IPv6両対応）として設定可能になり、CloudFrontがクライアントからのIPv6トラフィックをオリジン側へIPv6でそのまま届けられるようになりました。従来はパブリックオリジンに対してのみdual-stackが可能で、VPCオリジンへの接続はIPv4のみでした。今回の対応により、オリジンをパブリックサブネットに移すことなくIPv6通信を実現できます。dual-stack VPCオリジンは、VPCオリジンがサポートされるAWSのCommercialリージョンですべて利用可能で、利用自体に追加料金は発生しません。設定面では、オリジン（ALB/NLB/EC2）がIPv6を受け入れるようにリスナーやネットワーク設定を整え、セキュリティグループ／NACLでIPv6トラフィックを許可する必要があります。運用面ではCloudFrontアクセスログやオリジンログでIPv6接続の確認・監視を行うことを推奨します。

### 影響範囲・利用シーン

- **対象ユーザー**: Web/アプリ配信を行うクラウドエンジニア、SRE、ネットワーク／セキュリティ担当者
- **利用シーン**: IPv6必須の規制対応やIPv6ネイティブ環境でのコンテンツ配信（例: IPv6のみのクライアントを持つサービス）
- **運用効果**: オリジンをパブリックに曝け出すことなくエンドツーエンドでIPv6を実現でき、セキュリティ要件を維持しつつネットワークアーキテクチャの近代化が可能
- **コスト影響**: dual-stack自体に追加料金は無し。ただし通常のデータ転送料金やCloudFrontのログ／監視コストは発生する

### 技術的な注意点

- **IAM権限**: CloudFrontディストリビューションとVPCオリジンを設定・変更するためのCloudFrontおよびVPC/ELB/EC2関連の権限が必要です（例: cloudfront:UpdateDistribution、ec2:Modify*、elasticloadbalancing:*など）。
- **リージョン制限**: VPCオリジンがサポートされているCommercialリージョンで利用可能。詳細な対応リージョンは公式のリージョン一覧を確認してください。
- **セキュリティ設定**: オリジン側のセキュリティグループおよびNACLでIPv6トラフィックを受け入れるルールを追加する必要があります。CloudFrontからのIPv6送信元プレフィックスはAWSが公開するIPレンジ（IPv6部分）または管理プレフィックスリストで確認してください。
- **オリジン設定**: ALB/NLBやEC2側でIPv6リスナー/アドレスを有効にし、オペレーティングシステムやアプリケーションがIPv6接続を処理できることを確認してください。
- **コスト**: dual-stack機能自体は追加料金なし。従来通りのデータ転送費・リクエスト費用・ログ保存費用などは発生します。
- **テスト/監視**: デプロイ後はCloudFrontアクセスログ、オリジンアクセスログ、ALB/NLBの接続ログなどでIPv6経路が使用されているか検証してください。負荷テストでIPv6経路のパフォーマンスとTLS/ヘルスチェック動作を確認することを推奨します。

- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-vpc.html

## [RDS] PostgreSQL 19 RC1 is now available in Amazon RDS Database Preview Environment

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/postgresql-19-rc1-amazon-rds-database-preview-environment/

### 概要

Amazon RDSのDatabase Preview Environmentで、PostgreSQL 19 Release Candidate 1（RC1）が利用可能になりました。主にBeta 4期間のバグ修正と安定性向上を中心としたリリースです。

### 変更内容・新機能の詳細

PostgreSQL 19 RC1は安定性に重点を置いたプレリリースで、Beta 4でのテスト期間に見つかった不具合修正や改善を含みます。主な改善点は以下のとおりです：
- 複雑なテキスト検索式（tsquery 等）に対するエラーハンドリングの改善により、異常系の挙動がより明確で予測可能になりました。
- 並列化された autovacuum の強化（hardening）により、複数ワーカー環境での自動バキュームの安定性と競合対策が向上しています。
- GIN（Generalized Inverted Index）インデックスのメンテナンスの信頼性向上により、更新やバキューム時のインデックス破損や不整合のリスクが低減されます。

注意点（Preview Environment固有）：
- Preview環境のDBインスタンスは最大60日間保持され、保持期間終了後に自動削除されます。
- Preview環境で作成したスナップショットはPreview環境内でのみ復元／作成に使用可能で、一般のRDS環境へ移行できません。
- データの入出力はpg_dump/pg_restoreなどのダンプ／ロード機能を使って行う必要があります。
- 料金はUS East (Ohio) リージョンの価格に準じて請求されます。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、DBエンジニア、アプリケーション開発者
- **利用シーン**: PostgreSQL 19の新機能と修正点を事前評価してアプリの互換性やクエリ挙動を検証する場面（テスト/検証環境）
- **運用効果**: 本番導入前にインデックス挙動やautovacuumに関する問題を早期検出でき、アップグレード計画のリスク低減に寄与する
- **制約/注意**: プレビュー環境は一時的（最大60日）でスナップショットやインスタンスの持ち出し制限があるため、本番データの直接運用や長期保存には不向き

### 技術的な注意点

- **IAM権限**: RDSインスタンス作成・削除・スナップショット操作（例: rds:CreateDBInstance, rds:DeleteDBInstance, rds:CreateDBSnapshot 等）の権限が必要です
- **リージョン制限**: 料金はUS East (Ohio)（us-east-2）に準拠しています。プレビュー環境の提供リージョン/可用性は限定される可能性があるため、コンソールで提供状況を確認してください
- **データ移行/バックアップ**: PreviewスナップショットはPreview内でのみ利用可能。データを外部に持ち出すにはpg_dump/pg_restoreやpg_dumpall等でダンプしてインポートする必要があります
- **コスト**: Previewインスタンスは課金対象です（US East (Ohio)の価格に基づく）。長期稼働や大規模インスタンス利用はコストに影響します
- **互換性/安定性**: RC（Release Candidate）であり、まだ最終安定版ではありません。本番環境への導入は避け、互換性テストやパフォーマンス検証に限定してください
- **自動削除**: 最大60日後にインスタンスが自動的に削除されるため、重要データは定期的にダンプして保存してください

## [Redshift] Amazon Redshift long-term system table retention with Amazon S3 Tables is now available in additional AWS Regions

- **公開日**: 2026-10-16 (JST)
- **カテゴリ**: Redshift
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/redshift-long-term-system-table-retention-expansion/

### 概要

Amazon RedshiftのシステムテーブルデータをApache Iceberg形式のAmazon S3 Tablesへ長期保存できる機能が、追加のリージョンで利用可能になりました。これにより既定の7日間を超えて監査・可観測性データを保持できます。

### 変更内容・新機能の詳細

この機能を有効化すると、Redshiftはシステムテーブル（クエリ実行履歴、スロット／ノード統計、監査ログ等）のデータを自動的にAmazon S3 Tables（Apache Iceberg形式）へ書き出します。書き出し後のパーティショニング、コンパクション、保持ポリシーはAWS側で管理されるため、自前のETLパイプラインや本番環境への負荷を心配せずに長期保持が可能です。保存されたIcebergデータはRedshiftから直接クエリできるほか、Amazon Athena、DuckDB、その他Iceberg互換エンジンで読み取り・分析できます。複数のデータウェアハウスのシステムテーブルを単一の場所に集約してクロスウェアハウスの可観測性分析を行う運用も容易になります。さらに、AWS Agent Toolkitによりシステムテーブルデータを用いたパフォーマンス可視化や最適化提案のスキルが提供されます。今回の展開で、追加リージョン（Asia Pacific (New Zealand)、Canada West (Calgary)、AWS GovCloud (US‑East)、AWS GovCloud (US‑West)）で利用可能となり、対応はAmazon RedshiftのProvisioned（RGおよびRA3インスタンス）とAmazon Redshift Serverlessに対して行われています。

### 影響範囲・利用シーン

- **対象ユーザー**: Redshiftを運用・監視するSRE/運用チーム、データエンジニア、監査・コンプライアンス担当者
- **利用シーン**: 長期監査ログ保存、クエリ性能履歴の長期分析、インシデント調査、複数クラスターのクロス分析／可観測性ダッシュボード作成
- **運用効果**: カスタムETLやログ同期の削減により運用負荷を低減し、本番クラスターへのリソース競合を回避。IcebergフォーマットによりサードパーティツールやAthenaなどでの分析が容易になり、観測性向上とコンプライアンス対応がしやすくなる
- **リージョン**: 追加対応リージョンは Asia Pacific (New Zealand)、Canada West (Calgary)、AWS GovCloud (US‑East)、AWS GovCloud (US‑West)。その他のリージョンの対応状況はドキュメントを確認してください

### 技術的な注意点

- **IAM権限**: RedshiftがS3 Tablesへ書き込むための適切なIAMロールやS3への書き込み権限が必要です。アクセス制御やクロスアカウント配置を行う場合は事前にポリシーを確認してください
- **リージョン制限**: 本リリースで挙げられた追加リージョンのみ拡張されています。利用前にターゲットリージョンでのサポート状況を公式ドキュメントで確認してください
- **サポートされるインスタンス/モード**: Amazon Redshift Provisioned（RGおよびRA3インスタンス）とAmazon Redshift Serverlessで利用可能と明記されています。既存の他インスタンスタイプの対応はドキュメント参照
- **データ形式と互換性**: 出力はApache Iceberg形式のS3 Tablesです。Iceberg互換エンジン（Redshift、Athena、DuckDBなど）で読み取り可能ですが、クエリ実行時の接続設定やIAM権限は各エンジン側で別途必要です
- **コスト**: S3への追加ストレージ料金およびS3リクエスト料金、Icebergデータに対するクエリ（Athena/Redshift/DuckDB等）実行時の課金が発生します。データ保持期間の長期化に伴いストレージコストが増加する点に注意してください
- **データ管理**: パーティション、コンパクション、保持はAWSが管理しますが、保持ポリシーの設定方法やデータ削除の運用ルールは事前に確認してください
- **セキュリティ/コンプライアンス**: 保存場所（リージョン／アカウント）と暗号化設定（SSE-S3/SSE-KMS等）の要件を確認し、必要に応じてKMSキーやアクセスログの管理を行ってください
