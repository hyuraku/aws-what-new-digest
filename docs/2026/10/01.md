## [Workspaces] Amazon WorkSpaces Core Managed Instances adds support for NVIDIA Blackwell GPU

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: Workspaces
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-workspaces-cmi-g7/

### 概要

Amazon WorkSpaces Core の Managed Instances が NVIDIA RTX PRO 4500 Blackwell（Graphics G7）を搭載した G7 インスタンスをサポート開始しました。グラフィックス指向ワークロードで従来の G6 比で最大2.1倍の性能向上を提供します。

### 変更内容・新機能の詳細

Graphics G7 は NVIDIA RTX PRO 4500 Blackwell Server Edition GPU（各 GPU に 32GB の GDDR7）と Intel Xeon 6 プロセッサを組み合わせたインスタンスファミリーです。G6 世代比で最大 2.1x のグラフィックス性能向上、メモリ帯域は 2.67x の高速化により、より大規模で複雑な 3D シーンや高解像度レンダリング、リアルタイム視覚化が可能です。提供されるインスタンスサイズは 1〜8 GPU をサポートする 6 種類で、vCPU は 8〜192、システムメモリは 32GB〜768GB の範囲です。Linux と Windows をサポートし、BYOL（Bring Your Own License）にも対応します。初期提供リージョンは 米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（スペイン）で、順次追加リージョンが拡大予定です。WorkSpaces Core Managed Instance の作成時に G7 タイプを指定するか、WorkSpaces Core のパートナーソリューション経由で G7 インスタンスタイプを選択して利用を開始できます。

### 影響範囲・利用シーン

- **対象ユーザー**: グラフィックス重視のデスクトップ仮想化を必要とするプロフェッショナル（CAD/CAM、3Dアーティスト、科学可視化、ビデオ編集、AI支援デザイン）
- **利用シーンまたは効果**: 高解像度レンダリングや大規模3Dモデルのインタラクティブ操作、リアルタイム視覚化、GPUアクセラレートされたクリエイティブ/解析ワークロードのクラウド移行
- **運用効果**: ローカル高性能ワークステーションからクラウドへの移行によりスケーラブルなリソース割当てと集中管理が可能になり、短時間で高性能環境をプロビジョニングできる
- **コスト影響**: 高性能 GPU を搭載するためインスタンス単価は上位となり、利用時間・GPU数に応じたコスト最適化（スポット利用、スケールダウン、適切なインスタンスタイプ選定）が重要
- **リージョン適用範囲**: 現時点では限定リージョンでの提供（US East (N. Virginia)、US East (Ohio)、US West (Oregon)、Europe (Spain)）、必要に応じて対応リージョンの拡大を確認する必要あり

### 技術的な注意点

- **IAM権限**: WorkSpaces Core および Managed Instances の作成/管理に必要な IAM 権限（WorkSpaces、EC2、VPC、IAM ロールの作成権限など）を事前に確認・付与してください
- **リージョン制限**: 初期提供は米国・欧州の限定リージョンのみ。東京などの他リージョンでは未対応のため、利用前に対象リージョンを確認してください
- **コスト**: G7 は高性能 GPU インスタンスのため時間課金は高め。長時間利用や複数GPU利用では料金が大きくなるため、予算試算と価格オプション（オンデマンド／リザーブド／Saving Plans）の検討を推奨します
- **OS/ライセンス**: Linux と Windows をサポート。Windows や一部アプリケーションは BYOL（持ち込みライセンス）ポリシーや追加ライセンスが必要になる場合があるため、利用ソフトウェアのライセンス要件を事前に確認してください
- **互換性**: GPU ドライバやプロフェッショナルアプリケーション（CAD、レンダラー等）の Blackwell 世代対応状況を確認し、必要に応じてドライバ更新やアプリ側設定の検証を行ってください
- **ネットワーク/ストレージ**: 大規模データセットや高フレームレート配信ではネットワーク帯域・ストレージ IOPS の要件が高くなるため、VPC 設計や接続（Direct Connect/VPN）・ストレージ性能を検討してください

## [Developer Tools] AWS CLI now supports bulk skill updates and version checks for the Agent Toolkit for AWS 

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: Developer Tools
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-cli-agent-toolkit-update-skill/

### 概要

AWS CLIにAgent Toolkit for AWS向けの新コマンドが追加され、インストール済みのエージェントスキル一覧を一括で確認・更新できるようになりました。これにより多数のスキルを管理する環境でのバージョン維持が容易になります。

### 変更内容・新機能の詳細

追加された主なコマンドは以下の2つです。
- aws agent-toolkit check-skill-updates: ローカル（または環境にインストールされた）すべてのエージェントスキルを、スキルレジストリ上の最新バージョンと比較し、どのスキルが古いかを報告します（現在のバージョンと最新バージョンなどの情報を返す想定）。
- aws agent-toolkit update-skill --all: レジストリ上で新しいバージョンが存在するすべてのスキルを一括で更新します。個別にupdateコマンドを繰り返す必要がなくなります。

Agent Toolkit for AWSの構成要素（AWS MCP Server、agent skills、plugins）についてもCLIからインストール、検索、設定が可能な既存機能にこれらが追加されています。これまで各スキルを個別に確認・更新していた運用が自動化・効率化され、特にサーバーレス、ストレージ、ネットワーキング、分析など多数のスキルを導入しているチームで有効です。

利用にあたってはAWS CLIバージョン2.37.0以上が必要です。AWS MCP Serverは現時点で米国東部（バージニア北部）と欧州（フランクフルト）リージョンで提供されています。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発者、SRE、プラットフォーム/DevOpsチーム、エージェント（Kiro、Claude Code、Codex、Cursorなど）を運用する組織
- **利用シーン**: 多数のagent skillを導入している環境でのバージョンチェックと一括更新（定期メンテナンス、リリース後の即時パッチ適用、セキュリティ/ガイダンスの最新化）
- **運用効果**: 手動で個別更新する工数削減、スキルの陳腐化防止、エージェントが常に最新のガイダンスで動作することによる品質向上と問題発生リスク低減

### 技術的な注意点

- **IAM権限**: AWS CLIからAgent Toolkit操作を行うための適切なIAM権限が必要です。実際のAPI/CLIアクションに対するポリシーはユーザーガイドで確認してください。
- **CLIバージョン**: AWS CLI v2.37.0以上が必須です（古いCLIでは新コマンドが利用できません）。
- **リージョン制限**: AWS MCP Serverは現時点で US East (N. Virginia) と Europe (Frankfurt) のみで提供されています。MCP Server依存の操作はこれらリージョンでのみ動作します。
- **ネットワーク/レジストリアクセス**: check-skill-updates/update-skillはスキルレジストリへのアクセスが必要です。オフライン環境やインターネット遮断環境では実行できないか、追加手順が必要になります。
- **互換性とテスト**: update-skill --allは複数スキルを同時に更新するため、本番環境で実行する前にステージングで互換性テストを行ってください。スキルの更新による挙動変化や依存関係の影響に注意が必要です。
- **コスト**: 直接的なAWSサービス課金は通常発生しませんが、更新ファイルのダウンロードに伴うネットワーク転送量やストレージ利用は発生する可能性があります。
- **バックアップ/ロールバック**: 大規模更新前に現在のスキル構成のバックアップ方法（設定保存やバージョン固定手段）を確認しておくことを推奨します。
- **対応エージェント**: Kiro、Claude Code、Codex、Cursorなどの一般的なコーディングエージェント向けのスキル管理を想定しています。個別エージェント固有の互換性も確認してください。

## [S3] Amazon S3 Vectors introduces metadata pre-filtering for up to 5x higher recall on filtered search

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: S3
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/s3-vectors-introduces-metadata-pre-filtering/

### 概要

Amazon S3 Vectorsがメタデータ事前フィルタリングをサポートしました。選択性の高いフィルタを使うと、フィルタ適用時の検索リコールが最大5倍向上し、パスやURL向けのプレフィックス演算子($startsWith)も追加されました。

### 変更内容・新機能の詳細

メタデータ事前フィルタリングは、まずメタデータ条件を評価して該当するベクトル集合を絞り込んでから類似検索（ベクトル検索）を実行する方式です。これにより、従来の「近傍探索で候補を取ってからメタデータで絞る」方式でフィルタに該当するベクトルが候補に含まれなかった場合に起きていた漏れ（リコール低下）を大幅に改善できます。Amazon S3 Vectorsはまた、パスやURLのような値に対するプレフィックス一致を行う$startsWith演算子を追加しました。新しいベクターバケットに作成されるインデックスでは事前フィルタリングがデフォルトで有効になり、PutVectorsやQueryVectorsの既存の呼び出し方を変更する必要はありません。既存のインデックスに対しては、UpdateIndexMode APIでインプレースに切り替え可能です。QueryVectorsのクエリごとパラメータで、事前フィルタリングと従来の振る舞いを比較して検証してからインデックスを更新することもできます。今回の機能は追加コストなしで、S3 Vectors提供リージョン（商用リージョンと中国リージョン）で利用可能となります。導入は段階的デプロイ中で、CLI/SDK/コンソールから操作できます。

### 影響範囲・利用シーン

- **対象ユーザー**: RAG/エージェント/セマンティック検索を実装する開発者、MLエンジニア、検索プラットフォーム担当者
- **利用シーン**: テナント別フィルタ、ファイルパスやURLでの絞り込み、時間範囲やカテゴリなど厳密なメタデータ条件を付けた埋め込み検索
- **運用効果**: フィルタを用いた検索のリコールが最大5x向上し、検索結果の完全性と関連度が改善されることでRAGの応答品質向上や誤回答低減に寄与する

### 技術的な注意点

- **IAM権限**: UpdateIndexModeやQueryVectors/PutVectorsを使えるIAM許可（S3 Vectors関連のAPI権限）を確認してください
- **リージョン制限**: 商用AWSリージョンおよびAWS中国リージョンで利用可能。段階的デプロイ中のため、すべてのリージョンで順次有効化されます
- **コスト**: 機能自体に追加課金はありませんが、事前フィルタリングを利用したクエリ設計によりクエリ回数や計算リソースの発生傾向が変わる可能性があるため、モニタリングしてください
- **既存インデックスの切替**: 既存インデックスはUpdateIndexMode APIでインプレースに切替可能。切替前にQueryVectorsのクエリ単位パラメータで事前フィルタリングとの比較検証を推奨します
- **クエリ互換性**: PutVectors / QueryVectors の呼び出し方法は変更不要。プレフィックス演算子は $startsWith の構文を利用します
- **パフォーマンス注意点**: フィルタの選択性が高い場合に最も効果が大きいです。逆に非常に非選択的なフィルタでは事前フィルタリングの効果が限定的で、ワークロードによってはレイテンシやリソース消費の特性が変わるためベンチマークを推奨します
- **監視と検証**: クエリリコール、レイテンシ、コスト指標を事前後で比較し、想定どおりの改善が出ているか検証してください

## [CloudWatch] Amazon Managed Grafana now supports creating Grafana 13.2 workspaces

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: CloudWatch
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-managed-grafana-now-supports-creating-grafana-13-2-workspaces

### 概要

Amazon Managed Grafana（AMG）で新規ワークスペース作成時にGrafana 13.2が選択可能になりました。Grafana 13.0〜13.2で追加されたGit Sync、Dynamic Dashboards、CloudWatchデータソースでのPromQLサポートなどの機能が利用できます。

### 変更内容・新機能の詳細

本リリースにより、Amazon Managed Grafanaで作成するワークスペースにGrafana 13.2を指定できるようになりました。主な追加・強化点は以下のとおりです。

- Git Sync（ダッシュボードをコード化）: ワークスペースをGitリポジトリと連携し、ダッシュボードの定義をリポジトリで管理できます。変更履歴の追跡、レビュー、ロールバックが可能になり、インフラ／ダッシュボードのコード管理（IaC的運用）が容易になります。

- Dynamic Dashboards（動的ダッシュボード）: データや変数の状況に応じてレイアウトやパネル表示を動的に切り替える機能。条件に応じて表示を最適化することで、用途別・コンテキスト別にレスポンシブな可視化が作れます。

- CloudWatchデータソースのPromQLサポート: Amazon CloudWatchデータソースプラグインでPrometheus Query Language（PromQL）を使用してクエリが可能になりました。これはCloudWatchがOpenTelemetry（OTLP）経由で取り込んだメトリクスに対して有効で、既存のMetric SearchやMetrics Insightsと並んで選択できます。

- 可用性: Grafana 13.2は、Amazon Managed Grafanaが一般提供されているすべてのリージョンで利用可能です。

注意: 発表は「新規ワークスペースの作成時にGrafana 13.2が選べる」ことを示しており、既存ワークスペースの自動アップグレードについては記載がありません。ワークスペースのアップグレード手順や互換性はドキュメントを確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: SRE、監視エンジニア、プラットフォーム／DevOpsチーム、ダッシュボード開発者
- **利用シーン**: ダッシュボードをGitで管理して変更履歴とワークフローを統制したい場合（Git Sync）
- **利用シーン**: ユーザやアプリケーションの状況に応じて自動的に表示を最適化する動的な可視化が必要な場合（Dynamic Dashboards）
- **利用シーン**: CloudWatchへOTLP経由で取り込んだメトリクスをPromQLでクエリしたい場合（PromQLサポート）
- **運用効果**: ダッシュボードのコード化によりレビュー／ロールバックが容易になり運用信頼性が向上。ダッシュボード設計の柔軟性が高まり、運用負荷・オペミスの低減が期待できる

### 技術的な注意点

- **IAM権限**: ワークスペース作成や管理にはAWS側で必要なIAM権限（AmazonManagedGrafana関連の権限）が必要です。既存のIAMポリシーを確認してください。
- **Gitリポジトリ認証**: Git Syncを使う場合はリポジトリへのアクセス方法（SSH鍵やPersonal Access Tokenなど）を準備し、認証情報の管理方法を検討してください。企業のVCSプロバイダ利用時はアクセス制御ポリシーを確認します。
- **OTLP要件**: CloudWatchでPromQLによるクエリを使うには、対象メトリクスがCloudWatchにOpenTelemetry（OTLP）経由で取り込まれている必要があります。OTLP経由での送信設定を確認してください。
- **既存ワークスペース**: 本発表は新規ワークスペース作成時のバージョン指定に関するもので、既存ワークスペースのアップグレード手順や互換性は別途確認が必要です。アップグレード時はダッシュボードやプラグインの互換性テストを推奨します。
- **コスト**: Grafanaバージョン選択自体に直接の追加料金が発生するとは限りませんが、CloudWatchでのクエリ（Metrics InsightsやPromQL相当の処理）やOTLP経由の取り込み、外部Gitサービス利用に伴うコストが発生する可能性があります。料金ページで詳細を確認してください。
- **リージョン制限**: 発表では「AMGが一般提供されているすべてのリージョンで利用可能」とありますが、利用前に対象リージョンでのサービス提供状況を確認してください。

## [General] AWS Parallel Computing Service now supports scaling logs

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-pcs-scaling-logs/

### 概要

AWS Parallel Computing Service (AWS PCS) が各計算ノードの状態遷移を記録する「スケーリングログ」をサポートしました。これによりノードの起動/登録/スケールダウン/起動失敗などの履歴を取得してスケーリング問題の診断が容易になります。

### 変更内容・新機能の詳細

スケーリングログはクラスタ内の各計算ノードについて「1件の状態遷移」を記録します（例：インスタンスの起動、ノードの登録、スケールダウン、起動失敗とその理由）。ログの配信はオプトイン方式で、出力先として Amazon CloudWatch Logs、Amazon S3、Amazon Kinesis Data Firehose を選択可能です。これにより、ノードがなぜターゲットサイズに到達しなかったか、容量不足で失敗した起動はどれか、特定ノードがいつ開始/停止したかといった調査が行えます。AWS PCS は Slurm を利用した HPC 環境をマネージドで提供するサービスであり、本機能は PCS が利用可能な全リージョンで有効です。導入方法や詳細設定は AWS PCS User Guide を参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: HPC運用者、クラウドエンジニア、SRE、研究用クラスター管理者
- **利用シーン**: スケーリング失敗の原因調査（容量不足、起動失敗理由の特定）、ノード起動/停止の時系列追跡、監査ログ収集や容量計画の検証
- **運用効果**: トラブルシューティング時間の短縮、スケール挙動の可視化による運用改善、容量計画やコスト最適化の精度向上

### 技術的な注意点

- **IAM権限**: CloudWatch Logs（logs:CreateLogGroup, CreateLogStream, PutLogEvents）、S3（s3:PutObject 等）、Firehose（firehose:PutRecord/PutRecordBatch）などの適切な権限を付与する必要があります。PCS側にログ配信用のサービスロールが必要な場合があります。
- **配送先設定**: スケーリングログはオプトインで有効化し、CloudWatch Logs グループ、S3 バケット、または Firehose デリバリーストリームを指定して配信します。配信先での設定（ロググループ名、バケットポリシー、Firehose 宛先設定）を事前に構成してください。
- **コスト**: CloudWatch Logs の取り込み/保存、S3ストレージとリクエスト、Firehose の転送・配信先費用が発生します。大量のノード・高頻度の遷移がある環境ではコストが増えるため保持期間やライフサイクルを設定してください。
- **リージョン制限**: 本機能は AWS PCS が提供されている各リージョンで利用可能です。PCS 自体が未提供のリージョンでは利用できません。リージョンごとのサービス提供状況を確認してください。
- **ログ形式と量**: 各エントリはタイムスタンプ、ノードID/インスタンスID、遷移タイプ、失敗理由などを含む想定です（正確なフィールドは User Guide を参照）。大規模クラスターではログ量が多くなるため、集約・フィルタリングや保持ポリシーを検討してください。
- **セキュリティ**: S3 へ配信する場合はバケットポリシーと暗号化（SSE-S3/SSE-KMS）を設定、CloudWatch Logs でも KMS による暗号化やアクセス制御を適用してください。KMS を使う場合は追加の IAM 権限が必要です。
- **有効化方法**: 管理コンソール、API/CLI 等から設定可能な想定です。詳細な手順は User Guide を参照してください。

- **利用シーンまたは効果**: agentic AI やボースト性の高い API、バッチ/イベント駆動処理で短時間に必要な DB キャパシティを迅速に確保し、応答性を改善します
- **運用効果**: ピーク時のスロットリングや遅延の低減、アイドル期間のコスト削減（ゼロスケール）による総合的なコスト最適化
- **移行影響**: プラットフォーム v1/v2 を利用中の既存クラスターは v4 へのアップグレード検討が必要（ダウンタイムと互換性確認要）

### 技術的な注意点

- **プラットフォームバージョン**: この高速スケーリングはプラットフォーム v3/v4 でデフォルト有効。v1/v2 は v4 へアップグレードが必要です
- **確認方法**: コンソールのインスタンス構成欄、または RDS API の ServerlessV2PlatformVersion パラメータで確認可能
- **リージョン制限**: 地域ごとの提供状況は Aurora の料金/リージョンページで確認してください（リージョンによっては未対応の可能性あり）

- **互換性/エンジン**: MySQL互換・PostgreSQL互換の各エンジンでの挙動やサポート状況はドキュメントで確認してください
- **IAM権限**: クラスターの確認・アップグレードを行うには適切な RDS 管理権限（rds:DescribeDBClusters / rds:ModifyDBCluster 等）が必要です

- **データ残留/コンプライアンス**: AWSは推論処理が呼び出しリージョン内で行われると明示していますが、最終的なコンプライアンス判断（規制当局への確認等）はユーザー側で行ってください

## [Aurora] Aurora PostgreSQL now supports querying of Apache Iceberg and Parquet data

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: Aurora
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aurora-postgresql-query-apache-iceberg-and-parquet/

### 概要

Aurora PostgreSQL で Apache Iceberg および Parquet 形式のデータを、既存の PostgreSQL アプリケーションやツールから直接クエリできる機能が一般提供されました。ETL やデータ複製を行わずに、S3 や Glue カタログ上のデータレイクをそのまま参照できます。

### 変更内容・新機能の詳細

本機能は PostgreSQL の外部テーブル（foreign table）を使って、S3 上の Iceberg テーブルや Parquet ファイル、S3 Tables、または AWS Glue Data Catalog に登録されたテーブルを参照できるようにします。クエリ実行時は PostgreSQL 内に組み込まれた高性能エンジン（DuckDB）を利用して Iceberg/Parquet データに対する列指向・プッシュダウン処理を行います。さらに、外部 Iceberg REST Catalog（IRC）互換カタログを AWS Glue Data Catalog を通じてフェデレーションし、データ移動なしにクエリ可能です。レイテンシが厳しいワークロード向けには、標準 SQL を用いて Iceberg/Parquet の外部データを Aurora のネイティブな PostgreSQL テーブルにマテリアライズ（取り込み）することも可能です。対応は Aurora PostgreSQL の 17.11、18.6 以降で、全ての商用リージョンと GovCloud (US) にて GA 提供され、追加の Aurora 利用料は発生しません。開始は RDS コンソールまたは任意の PostgreSQL クライアントから行えます。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース/データレイク利用者、データエンジニア、BI/分析チーム、アプリケーション開発者、SRE
- **利用シーン**: データレイク（Iceberg/Parquet）と業務系データを結合した分析・レポート、BI ツールからの直接クエリ、自動化ワークフローへのリアルタイム参照
- **運用効果**: ETL やデータ複製の削減により開発・運用負荷が低下し、スキーマ変更時の手戻りを抑制。データの最新性を保ったまま分析が可能
- **コスト影響**: Aurora の追加料金は不要だが、S3 の Get/Request/データ転送や Glue API 利用、クエリ実行時の S3 スキャンに伴うコストは発生。スキャン量削減のため Iceberg のパーティショニングやメタデータ活用が有効
- **リージョン**: GA は全商用リージョンおよび GovCloud (US) で利用可能（記事時点）。ただしクロスリージョン S3/Glue 参照では追加遅延や転送料金に注意が必要

### 技術的な注意点

- **IAM権限**: Aurora が S3 と Glue Data Catalog（およびフェデレーション先カタログ）にアクセスできるように、適切な IAM ロール/ポリシーをアタッチする必要があります（S3 オブジェクト読み取り、Glue カタログ読み取り等）
- **Auroraバージョン**: 対応は Aurora PostgreSQL 17.11、18.6 以降。該当バージョンであることを確認してください
- **データフォーマット互換性**: Iceberg テーブルと Parquet ファイルが対象。Iceberg のカタログ配置（S3 メタデータ or external catalog）や一部高度な Iceberg 機能の対応状況は事前確認を推奨
- **パフォーマンス**: DuckDB による列指向処理とプッシュダウン最適化があるものの、S3 上のデータスキャンがボトルネックになり得ます。低レイテンシが必要な場合はマテリアライズを検討してください
- **コスト**: Aurora の追加料金はないが、S3 リクエスト/データ転送、Glue API 呼び出し、クエリ時のデータスキャン量に基づく料金が発生します。クエリプランと Iceberg のパーティション/メタデータでスキャン削減を行ってください
- **セキュリティ/ガバナンス**: データアクセス制御は Glue カタログの権限制御や S3 バケットポリシー、KMS 暗号化設定などを組み合わせて管理してください
- **運用設定**: 外部テーブル作成やカタログフェデレーションの設定は RDS コンソールか通常の PostgreSQL クライアントで実行可能。詳細な SQL 構文やオプションは公式ドキュメントを参照してください
- **制限事項**: 一部の Iceberg/Parquet 機能（例: 特定のデータ型、カスタムファイルレイアウト、最新の Iceberg 機能）が未対応の可能性があります。移行前に検証を行ってください

### 参考情報

- https://docs.aws.amazon.com/aurora/latest/aurora-postgresql/

## [RDS] Amazon RDS for MySQL supports MySQL 26.7 in Amazon RDS Database Preview Environment

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/rds-mysql-26-7-preview-environment/

### 概要

Amazon RDS for MySQL 26.7 が Amazon RDS Database Preview Environment で利用可能になりました。MySQL 26.7 は新しい YY.M カレンダーバージョニングを採用したイノベーションリリースで、バグ修正・セキュリティパッチに加え、Change Stream Applier などの新機能を含みます。

### 変更内容・新機能の詳細

Amazon RDS のプレビュー環境で MySQL 26.7 の事前評価が可能になりました。MySQL 26.7 は YY.M（Year.Month）形式のバージョニングを初めて採用するイノベーションリリースで、主な新機能として Change Stream Applier（モジュール式のレプリケーション applier）を導入しています。Change Stream Applier は apply スループットの向上とバックログからの回復性能を改善することを目的としており、テストワークロードで有効です。加えて一般的なバグ修正とセキュリティパッチが含まれます。RDS Database Preview Environment のインスタンスは最大60日間保持され、自動的に削除されます。プレビュー環境で作成した DB スナップショットは同じプレビュー環境内でのみ復元可能で、外部（本番アカウントや他リージョン）への移行はできません。プレビュー環境の課金は US East (Ohio) リージョンの料金に準じます。詳細は MySQL 26.7 のリリースノートおよび Amazon RDS Database Preview Environment のドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者(DBA)、アプリケーション開発者、SRE/運用チーム
- **利用シーン**: 新機能（Change Stream Applier）や互換性の検証、アプリケーションのリグレッションテスト、レプリケーション/バックログ回復の性能評価
- **運用効果**: 本番導入前に MySQL 26.7 の機能や既存アプリケーションとの互換性を検証でき、レプリケーションのスループット改善効果を確認して移行リスクを低減できる

### 技術的な注意点

- **リージョン制限**: プレビュー環境は US East (Ohio) の課金に準じる（利用可能リージョンが限定される可能性あり）。
- **保持期間**: プレビューインスタンスは最大60日で自動削除されるため、長期評価や本番移行には不向き。
- **スナップショット制限**: プレビュー環境で作成した DB スナップショットは同プレビュー環境内でのみ使用可能。プレビューから本番環境へ直接移行することはできない。
- **本番利用**: プレビューは事前評価用であり、本番ワークロードでの利用は推奨されない。
- **コスト**: プレビュー環境は課金が発生（US East (Ohio) の料金に準拠）。評価コストを見積もる必要あり。
- **互換性**: MySQL 26.7 は新しい YY.M バージョニングを採用。アプリケーションやレプリケーション設定の互換性テストを事前に実施することを推奨。
- **IAM権限**: プレビュー環境の作成・管理に必要な RDS/IAM 権限を事前に確認すること（通常の RDS 操作権限が必要）。
- **バックアップ/監視**: プレビュー環境の自動バックアップや監視設定・ログの取り扱いは通常環境と挙動が異なる可能性があるため、設定を確認すること。

## [Cloudtrail] Uncover blind spots in AWS data plane operations with CloudTrail Event Coverage

- **公開日**: 2026-10-01 (JST)
- **カテゴリ**: Cloudtrail
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-cloudtrail-event-coverage/

### 概要

AWS CloudTrailに新しいコンソール機能「Event Coverage」が追加され、アカウント／組織単位でデータプレーン（Data Events）のログ適用状況を可視化できるようになりました。サポートされるデータイベントソースのカバレッジ確認と、ダッシュボードからの直接サブスクライブが可能です。

### 変更内容・新機能の詳細

Event CoverageはCloudTrailコンソール内の新しい視覚化機能で、環境内の各サービスおよびリソース種別に対してデータイベント（Data Events）が有効になっているか否かを一覧で確認できます。データイベントはS3のGetObject/PutObjectのようなデータプレーン操作を記録するもので、不正なデータアクセスやデータ流出などの検出に重要です。Event Coverageはサポートされる全データイベントソースを一箇所で表示し、カバレッジの欠落（ブラインドスポット）を素早く特定できます。さらに、ダッシュボードから直接データイベントのサブスクリプション（有効化）処理が行えるため、複数アカウントを管理する組織での追跡・修正作業を数クリックで完了できます。本機能はAWS CloudTrailがサポートされている全ての商用リージョンで利用可能です。詳細なデータイベントの取扱いやサポート対象はCloudTrailの公式ドキュメントを参照してください。例として、Amazon S3（オブジェクト操作）、AWS Lambda（関数呼び出しの記録）、Amazon DynamoDB（アイテムレベル操作）などがデータイベントの代表例です。

### 影響範囲・利用シーン

- **対象ユーザー**: セキュリティ／コンプライアンス担当者、クラウド／インフラエンジニア、SRE、組織管理者
- **利用シーン**: マルチアカウント環境でのデータアクセス監査、S3オブジェクトアクセスの不正検出、組織全体のログ収集ポリシー確認と一括有効化
- **運用効果**: ログ未取得による監視の盲点を迅速に発見でき、ダッシュボードから直接サブスクライブしてカバレッジを短時間で改善できるため、インシデント検出率とコンプライアンス遵守が向上する

### 技術的な注意点

- **IAM権限**: Event Coverageの表示・操作にはCloudTrailの読み取り／設定権限（例: cloudtrail:DescribeTrails, cloudtrail:GetEventSelectors, cloudtrail:PutEventSelectors など）および対象サービスのログ設定権限が必要です
- **組織設定**: 組織単位での可視化や一括設定を行う場合、AWS Organizationsの設定や委任された管理アカウントの構成が必要になる場合があります
- **コスト**: データイベントの有効化は追加のCloudTrailデータイベント課金の対象となるため、対象サービス・リソース数による料金影響を事前に見積もってください
- **リージョン制限**: この記事の通り、CloudTrailがサポートする全ての商用リージョンで利用可能です（リージョンごとのドキュメントで対応状況を確認してください）
- **設定単位**: データイベントはサービス／リソース単位（例: S3バケット単位）で設定されるため、細かなターゲティングが可能ですが、設定漏れに注意してください
