# 2026年10月07日

## [Bedrock] Claude Haiku 5.5 is now available on AWS 

- **公開日**: 2026-10-07 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/claude-haiku-5-5-aws/

### 概要

Claude Haiku 5.5 が AWS で利用可能になりました。Haiku 系列の中で最も高速かつコスト効率の高いモデルで、サブエージェントや高ボリューム・コスト敏感なワークロード向けに設計されています。

### 変更内容・新機能の詳細

Claude Haiku 5.5 は Anthropic の Claude 5.5 ファミリーに属する軽量・高効率モデルで、従来の Haiku 4.5 に比べ多くのタスクで約75%低コスト（同社公表値）を実現するとされています。性能面ではコード生成、ツール利用、ブラウザ自動化やエージェント動作などで Haiku 4.5 を上回る能力を示しつつ、レイテンシとスループットに優れるためリアルタイム音声エージェント、ライブサポート、アプリ内アシスタントなどの即時応答が求められるユースケースや、分類・要約・ドキュメントからのキー抽出等の高頻度バッチ処理に適しています。Haiku 5.5 は「effort controls（コストと知能のトレードオフを調整する仕組み）」を初めて備え、タスクごとに計算量（＝コスト）と応答品質のバランスをチューニングできます。アーキテクチャ上は、より高能力な Claude Opus 5.5 のようなモデルが計画や高レベル意思決定を行い、定義済みのコーディングやツール操作、ブラウザ自動化タスクを Haiku に委譲することで、多数のサブエージェントを並列運用する実用性が高まります。AWS からの利用方法は2通り：Amazon Bedrock 経由（AWS インフラ内でのリージョナルなデータレジデンシー、Bedrock のガードレールやKnowledge Bases 等の AWS 管理機能を利用可能）と、Claude Platform on AWS（Anthropic ネイティブのプラットフォーム体験を AWS コンソール経由で直接利用、Anthropic の API/機能をそのまま使いつつ AWS 課金・認証と統合）です。導入時は各サービスのリージョン対応・データ処理ポリシー・料金体系を確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: サブエージェント設計者、チャット/音声ボット開発者、SRE/運用チーム、機械学習エンジニア
- **利用シーン**: リアルタイム音声エージェント、ライブサポート、アプリ内アシスタント、ドキュメント分類や要約などの高頻度バッチ処理
- **運用効果**: レイテンシ削減と処理コストの大幅低減（Haiku 4.5 比で同社公表値で約75%のコスト減が見込める場面あり）、多数のサブエージェントを並列運用しやすくなる
- **コスト影響**: 単体モデルのコスト低減により全体アーキテクチャの運用コスト削減が期待できる（ただし呼び出し頻度や並列度で費用は変動）

### 技術的な注意点

- **IAM権限**: Amazon Bedrock 利用時は Bedrock API へのアクセス権（IAM ポリシー）と必要な KMS/ログ周りの権限を設定してください
- **リージョン制限**: 全リージョンで即時利用可能とは限りません。Bedrock 側のリージョン対応状況や Claude Platform の地域提供範囲を事前に確認してください
- **コスト**: Anthropic の公表値では Haiku 4.5 比で約75% 安だが、実際の請求は Bedrock/Claude Platform の料金体系、呼び出し回数、出力トークン量に依存します
- **データ処理と居住性**: Bedrock 経由では AWS インフラ内で処理されリージョナルデータレジデンシーを活用できます。Claude Platform on AWS を使う場合は Anthropic 側での処理フロー・データ保持方針を確認してください（機密データやコンプライアンス要件がある場合は特に注意）
- **API/互換性**: Claude Platform on AWS は Anthropic ネイティブ API/コンソール体験を保持します。Bedrock 経由は Bedrock の統一 API/SDK を通して利用するため、既存の Bedrock ワークフローに統合しやすいです
- **ガードレールとナレッジベース**: Bedrock では AWS 管理のガードレールや Knowledge Bases を活用できます。セキュリティや出力制約の運用ポリシーを Bedrock 側で設計してください
- **チューニング（effort controls）**: effort controls を使って応答品質とコストのバランスを調整可能です。最適値はタスクごとに異なるため性能・コストの計測を行い閾値を決める運用が必要です

## [Bedrock] Claude Haiku 5.5 is now available on AWS GovCloud (US)

- **公開日**: 2026-10-07 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/claude-haiku-5-5-aws-govcloud/

### 概要

Anthropic の Claude Haiku 5.5 が Amazon Bedrock を通じて AWS GovCloud (US) で利用可能になりました。Haiku ファミリー中で最速かつコスト効率に優れ、サブエージェントや高頻度・低コスト重視のワークロード向けに設計されています。

### 変更内容・新機能の詳細

Claude Haiku 5.5 は Haiku 4.5 に比べて多くのタスクで約75%のコスト削減が見込まれる（Anthropic 提供の試算）高速・低コストモデルです。コード生成、ツール利用、エージェント動作、一般的なコンピュータ操作などで Haiku 4.5 より性能が向上しており、初めて「エフォートコントロール（処理努力の強度を調整して知性とコストをトレードオフ）」を備えています。用途としては低遅延を要求するリアルタイム体験（音声エージェント、ライブサポート、アプリ内アシスタント）や、大量処理が必要な分類、要約、ドキュメントからのキー抽出などに最適です。アーキテクチャ的には、より計画立案が得意な Claude Opus 5.5 をプランナーにして、Haiku 5.5 を実行（サブエージェント）に割り当てる運用が想定され、これにより多数のエージェントを並列で実行しやすくなります。Amazon Bedrock 経由で提供されるため、データは AWS インフラ内（リージョン内）に留まり、Bedrock のガードレールや Knowledge Bases といったマネージド機能と組み合わせて利用できます。アクセスは Bedrock の統一 API/コンソールを通じて行います。

### 影響範囲・利用シーン

- **対象ユーザー**: 米国政府機関・政府向けクラウド利用者、規制業務を行う企業、SRE/運用チーム、アプリ開発者、AIエンジニア
- **利用シーン**: 低遅延を要求する音声エージェントやライブチャットサポート、アプリ内アシスタント、分類・要約・帳票抽出などの高頻度バッチ処理、エージェントオーケストレーションでのサブエージェント運用
- **運用効果**: 処理コストの大幅削減（Anthropic 比で多くのケースで約75%）、低遅延化によるリアルタイム体験向上、大量のサブエージェントを並列実行しやすくなることでスケーラビリティが向上

### 技術的な注意点

- **IAM権限**: Bedrock を呼び出すための IAM 権限が必要（例: bedrock:InvokeModel 等）。必要なロールやポリシーを準備してください。
- **リージョン制限**: 本追加は AWS GovCloud (US) 向けの提供です。他リージョンでの利用可否はドキュメントで確認してください。
- **コスト**: モデル使用料（呼び出し回数、トークン/処理量に応じた課金）が発生します。Anthropic の節約試算は参考値であり、実際のコストは Bedrock の料金体系と利用パターンに依存します。負荷試験で実コストを測定してください。
- **コンプライアンス**: GovCloud は政府向け要件に対応する領域ですが、FedRAMP/ITAR 等の個別要件がある場合は自組織のコンプライアンス担当と照合してください。
- **レイテンシ／スループット**: Haiku 5.5 は高速設計ですが、実運用での遅延やスループットは Bedrock のサービスクォータやネットワークに依存します。スロットリングや同時実行数の上限を事前に確認し、必要に応じてサービスクォータ引き上げを申請してください。
- **エフォートコントロール**: 新しいパラメータ（エフォート）により品質とコストをトレードオフ可能です。適切な設定値はタスクごとに異なるため、A/B テストやプロンプト改良を行って最適化してください。
- **データ取扱**: Bedrock はデータをリージョン内に保持しますが、ログやメトリクス、Knowledge Base の管理方法については設計段階で確認してください。

## [General] AWS Batch now publishes job metrics to Amazon CloudWatch

- **公開日**: 2026-10-07 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-batch-job-cloudwatch-metrics/

### 概要

AWS Batchがジョブのライフサイクルに関するメトリクスをAmazon CloudWatchへネイティブに公開するようになりました。ジョブキューの状態遷移や所要時間を可視化でき、バッチワークロードの監視・アラート・可観測性が向上します。

### 変更内容・新機能の詳細

AWS Batchはジョブのライフサイクルに沿ったメトリクス（状態遷移のカウントおよび状態間の所要時間）を自動的にCloudWatchの名前空間 AWS/Batch に出力します。各メトリクスは JobQueueName のディメンションを持ち、例えば submitted→runnable→running→succeeded/failed といった状態に入ったジョブ数をカウントする「状態遷移メトリクス」と、submission→runnable や submission→end（総実行時間）などの「期間（Duration）メトリクス」が含まれます。これらのメトリクスはAWS Batchコンソール、CloudWatchコンソール、AWS CLI、SDK経由で参照でき、ダッシュボードやアラーム作成、外部監視ツールとの連携に利用できます。メトリクスはAWS Batchが利用可能な全リージョンで公開されます。運用上は失敗率の可視化、キュー遅延の検出、SLA/SLO監視や自動スケーリングトリガーのための根拠として活用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: バッチワークロードを運用・監視するSRE/運用チーム、データ処理/ETL開発者、プラットフォームエンジニア
- **利用シーン**: ジョブキューの健全性監視（キュー滞留時間の可視化）、失敗率のトラッキングとアラート、ジョブ実行時間の分析や性能ボトルネックの特定
- **運用効果**: 障害や遅延の早期検出、アラートによる迅速な対応、メトリクスに基づく自動スケーリングやSLO監視の実装が容易になる

### 技術的な注意点

- **Namespace/Dimension**: メトリクスは AWS/Batch 名前空間に公開され、JobQueueName ディメンションが付与されます
- **メトリクス種別**: 状態遷移カウント（submitted, runnable, running, succeeded, failed 等）と状態間のDuration（例: submission→runnable、総実行時間）を提供します
- **IAM権限**: CloudWatchのメトリクス参照には cloudwatch:ListMetrics、cloudwatch:GetMetricData / GetMetricStatistics が必要です。アラーム作成には cloudwatch:PutMetricAlarm 等が必要になります。Batchコンソールでの表示権限は該当するAWS Batch関連の読み取り権限も影響します
- **リージョン制限**: AWS Batchが利用可能なすべてのリージョンでメトリクスが公開されます（ただし、対象リージョンでの利用可否は事前に確認してください）
- **コスト**: CloudWatchのAPI呼び出し、GetMetricData、ダッシュボード、アラームなどはCloudWatchの料金体系が適用されます。AWSサービスが発行するメトリクス自体は通常CloudWatchで利用可能ですが、ダッシュボードや詳細取得による追加コストに注意してください
- **解像度/保持**: メトリクスの解像度（標準1分/高解像度）や保持期間の詳細はドキュメントで確認してください。監視要件に応じてサンプリング間隔やアラーム閾値を設計することを推奨します
- **実装上の注意**: メトリクス名・ディメンションを固定してダッシュボード/アラームを作成することで、ジョブキュー単位での監視が可能です。外部システムでの自動化（例: Lambdaでのアラート処理やApplication Auto Scalingトリガー）はCloudWatchイベント/アラームを組み合わせて利用してください
