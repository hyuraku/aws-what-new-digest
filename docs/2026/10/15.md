## [CloudWatch] Amazon CloudWatch announces log routing and chained log parsers

- **公開日**: 2026-10-15 (JST)
- **カテゴリ**: CloudWatch
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/cloudwatch-pipelines-log-routing/

### 概要

Amazon CloudWatch Pipelinesが条件付きログルーティングとチェインドパーサーをサポートしました。これにより、同一パイプライン内で複数フォーマットのログを順次解析し、解析結果に基づいて適切なCloudWatchロググループへ振り分けられます。

### 変更内容・新機能の詳細

CloudWatch Pipelines（フルマネージドなログ受信・変換・ルーティングサービス）に新たに「条件付きログルーティング」と「チェインドパーサー」が追加されました。条件付きログルーティングでは、パイプライン内で処理・抽出されたフィールドの値に基づきルート（route）を定義し、イベントごとに別々のCloudWatchロググループへ振り分けできます（例：severity、source、typeによる分離）。チェインドパーサーでは複数のパーサープロセッサを順に適用でき、先のパーサーが生成したフィールドを後続のパーサーが消費します（例：まずJSONエンベロープをパースして内部フィールドを取り出し、そのフィールドに対してGrokや正規表現パーサーを適用する）。これらを組み合わせることで、多様なネストされたログ形式を1つのパイプラインで構造化・振り分けし、各ロググループごとに適切な保持期間やアクセス制御を適用できます。設定はAWS Management Console、AWS CLI、AWS SDKsから行えます。機能はCloudWatch Pipelinesが一般提供されているすべての商用AWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: ログ設計者、SRE、プラットフォーム/インフラ運用者、セキュリティチーム
- **利用シーンまたは効果**: ネストされた/混在フォーマットのログを一つの取り込み経路で解析・分岐し、重複設定なしにログを適切なロググループへ振り分け可能
- **運用効果**: 保持ポリシーやアクセス制御をログ種別ごとに分離できるためコンプライアンス対応が容易になり、検索・監視の効率が向上
- **開発効果**: パーサーを連鎖して細かくデータを抽出できるため、ダッシュボードやアラートの精度が上がる

### 技術的な注意点

- **IAM権限**: CloudWatch Pipelinesの作成・更新・実行、対象ロググループへのPut権限、必要なKMS/ロール権限を事前に確認してください（パイプライン作成には適切なService Roleが必要）
- **リージョン制限**: 本機能はCloudWatch Pipelinesが一般提供されている商用リージョンで利用可能です。リージョンによっては未対応の可能性があるため利用前にリージョンのサービス可用性を確認してください
- **コスト**: Pipelinesの処理・データ転送・保存に対する通常のCloudWatch Pipelines／Logsの料金が適用されます。ルーティングや複数パーサーの適用により処理量が増えると料金に影響する可能性があるため想定トラフィックでのコスト見積りを推奨します
- **クォータ／制限**: 既存のCloudWatch PipelinesおよびLogsのスループット・イベントサイズ・ルート数・パーサー数に関する制限が適用されます。大規模導入時はドキュメントでクォータを確認し、必要ならサポートへ引き上げ依頼してください
- **挙動／互換性**: ルーティング条件は「処理済みフィールド」に対して評価されるため、パーサーの順序がルーティング結果に影響します。チェインドパーサーを設計する際はパーサーの入出力フィールドを明確にし、意図した順序で適用されるよう注意してください
- **デバッグ／テスト**: 本番適用前にサンプルイベントでパーサーチェーンとルーティング条件を検証し、期待される抽出結果と送信先ロググループを確認してください

## [General] ARC Region switch adds four new capabilities

- **公開日**: 2026-10-15 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/region-switch-target-health-ssm-lambda/

### 概要

Amazon Application Recovery Controller (ARC) の Region switch に 4 つの新機能が追加されました。SSM Run Command 実行ブロック、カスタム Lambda 実行ブロックへのペイロード渡し、サービスクォータのパリティチェック（および自動引上げ申請）、およびターゲットグループのヘルス待機機能が含まれます。

### 変更内容・新機能の詳細

今回の追加機能はフェイルオーバー計画の自動化と信頼性を高めるためのものです。

- AWS Systems Manager Run Command 実行ブロック: フェイルオーバー中にマネージドインスタンス（EC2 やハイパーバイザー上の VM 等）へ Run Command を送信できるようになります。Recovery Plan の評価段階で、ドキュメントが有効なターゲットを指しているか、必要な IAM 権限が設定されているかを検証します。

- カスタムアクション Lambda 実行ブロックのペイロード: カスタム Lambda を実行するブロックに対して任意のペイロードを渡せるようになり、同じ Lambda 関数を複数のリカバリプランや状況で再利用しやすくなります。ペイロードにより呼び出し先での処理分岐やパラメータ指定が可能です。

- サービスクォータチェック（Service quota parity checks）: プライマリ Region とスタンバイ Region 間で主要サービスのクォータ差分を検出します。不足がある場合は自動的にクォータ増加のリクエストを提出でき、フェイルオーバー時にクォータ不足でリカバリが失敗するリスクを低減します（ただしクォータ増加の反映は即時ではない場合があります）。

- ターゲットグループのヘルス待機（Wait for target group health）: Amazon ECS のサービススケーリングブロックや EC2 Auto Scaling グループの実行ブロックにおいて、起動したインスタンス/タスクが実際にターゲットグループでヘルスチェックをパスしてトラフィックを受けられる状態になるまで待機するオプションを追加。これにより“容量は確保したがサービスがまだ応答できない”という状態を避け、トラフィック切替の精度を向上させます。

### 影響範囲・利用シーン

- **対象ユーザー**: マルチリージョンで高可用性・障害対策を設計・運用する SRE、クラウドアーキテクト、災対担当者
- **利用シーンまたは効果**: リージョン障害時の自動フェイルオーバー実行（構成変更、インスタンス内コマンド実行、カスタム処理呼び出し、必要クォータの確保、プロビジョニング後のヘルス確認）により、計画通りの復旧時間を達成しやすくなる
- **運用効果**: 手動作業やチェックの削減、クォータ不足による想定外の失敗削減、切り替え時のサービス停止リスク低下、リカバリプランの再利用性向上

### 技術的な注意点

- **IAM権限**: SSM Run Command、Lambda Invoke、Service Quotas へのクォータ申請、ECS/Auto Scaling/ELB の操作とヘルスチェック閲覧など、各機能に応じた細かな権限が必要です（実行前に最小権限ポリシーを確認してください）。
- **リージョン制限**: ARC と各実行機能が利用可能なリージョンでのみ動作します。プライマリ／スタンバイ両 Region で対象サービスが利用可能か、クォータリソースが存在するかを事前に確認してください。
- **コスト**: SSM Run Command の実行、Lambda 実行、追加インスタンス/タスクのプロビジョニング、ヘルスチェック待機による稼働時間増加などによりコストが発生します。クォータ増加自体は無料申請ですが、増加後のリソース利用は課金対象です。
- **クォータ申請の即時性**: 自動でクォータ増加リクエストを提出できますが、承認までは時間を要する場合があり、即時に反映されない点を考慮して計画してください。
- **タイムアウトと待機時間**: ターゲットグループのヘルス待機を有効にすると復旧シーケンスが長くなる可能性があります。適切なタイムアウト値とリトライ設定を設計してください。
- **検証要件**: Run Command のドキュメントが正しいターゲット（インスタンス ID、タグ、マネージャー登録状態）を指しているか、Lambda が渡されるペイロードを処理できるか、ターゲットグループのヘルスチェック設定が適切かを事前検証してください。

## [License Manager] AWS License Manager now supports license type conversions for Ubuntu Pro purchased through AWS Marketplace

- **公開日**: 2026-10-15 (JST)
- **カテゴリ**: License Manager
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-license-manager-conversions-ubuntu-pro-marketplace/

### 概要

AWS License Managerで、既存のEC2上のUbuntu LTSインスタンスをAWS MarketplaceのUbuntu Proへインプレースでアップグレード（ライセンスタイプ変換）できるようになりました。再構築やAMI置換を行わずに長期のセキュリティパッチと追加パッケージの保守を受けられます。

### 変更内容・新機能の詳細

License Managerの変換ワークフローにより、EC2上のUbuntu LTSインスタンスをそのままCanonicalのUbuntu Proサブスクリプションに登録・有効化できます。変換はコンソール上で実行でき、既にAWS MarketplaceでCanonical Ubuntu Proを購入済みの顧客はワークフロー中に既存サブスクリプションを紐付け可能です。未購読の場合はLicense ManagerコンソールからMarketplace購読が可能です。Ubuntu Proは標準のLTSサポート（最大10年、Legacyアドオンで最大15年に拡張）に加え、NGINX、PostgreSQL、MongoDB、Redisなど多くの追加OSSパッケージへのセキュリティ修正を含みます。また、Kernel Livepatchをサポートしており、重要なカーネル修正を再起動なしで適用してダウンタイムを最小化できます。この機能はAWS License Managerが利用可能な全ての商用リージョンで利用できます。実際の変換では、インスタンスのサブスクリプション登録、リポジトリの有効化やパッケージ適用（apt等）などが行われるため、SSMエージェントやネットワーク接続、必要なIAM権限が前提になります。課金はUbuntu ProのMarketplaceサブスクリプションに基づき発生します。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウド/サーバ運用者、セキュリティ/コンプライアンス担当、SRE
- **利用シーン**: 既存のEC2 Ubuntu LTS環境を再構築せずに長期のセキュリティサポートや追加パッケージのパッチを適用したい場面
- **運用効果**: フリートの再デプロイを避けつつセキュリティポスチャを強化でき、Kernel Livepatchにより再起動を抑えてダウンタイム低減が可能
- **コスト影響**: Ubuntu ProのMarketplaceサブスクリプション費用が発生（License Manager自体の機能利用は管理下で行われる）

### 技術的な注意点

- **IAM権限**: AWS License ManagerとEC2インスタンスを操作できる権限（License Manager操作、EC2のタグ/インスタンス変更、必要に応じてSSM実行権限など）を用意してください
- **前提条件**: 対象はUbuntu LTSのEC2インスタンスで、インスタンスがネットワークアクセス（インターネットまたは必要なリポジトリへアクセスできる経路）を持ち、必要に応じてSSMエージェントが稼働していることを推奨します
- **再起動/ダウンタイム**: Kernel Livepatchで多くのカーネル修正は再起動不要ですが、すべてのアップデートが再起動不要とは限らないため、重要なワークロードでは事前に影響確認を行ってください
- **サポートされるOSバージョン**: 対象はCanonicalが定めるUbuntu LTSリリース（事前にサポート対象のLTSバージョンを確認してください）
- **リージョン制限**: AWS License Managerが提供される全ての商用リージョンで利用可能とされていますが、AWS ChinaリージョンおよびAWS GovCloud等の特殊リージョンは別扱いの可能性があるため事前確認を推奨します
- **コスト**: Ubuntu ProはMarketplace経由のサブスクリプション課金が発生します。組織のコスト管理ポリシーに合わせて購読前に見積もりを確認してください

## [General] AWS HealthOmics introduces resource fallback order for Nextflow workflows

- **公開日**: 2026-10-15 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/aws-healthomics-resource-fallback-for-Nextflow/

### 概要

AWS HealthOmicsがNextflowワークフロー向けに「resource fallback」ディレクティブを導入しました。タスクごとに優先するアクセラレータ（GPU等）を順序指定でき、利用不可時に自動で代替へフォールバックし、最終的にCPUを指定することも可能です。

### 変更内容・新機能の詳細

resource fallbackディレクティブにより、Nextflowワークフロー内の各タスクでアクセラレータの優先順を定義できます。指定した優先順に沿ってHealthOmicsが自動的にアクセラレータを探索し、各アクセラレータプロファイルに対して個別のタイムアウトを設定可能です。タイムアウトの値を短く設定するとフォールバック順を速やかに進められ、長く設定すると優先アクセラレータを確保できる確率が高まります。最終フォールバックにCPUプロファイルを含めることで、アクセラレータが全て利用不可でもインスタンスの確保成功率を高められます。フォールバックは再送信（resubmission）を伴わずに実行されるため、ユーザーが手動でジョブを再投入して診断・調整する工数が削減されます。サービスはHIPAA適合（Eligibility）で、以下のリージョンで利用可能です：US East (N. Virginia, Ohio), US West (Oregon), Europe (Frankfurt, Ireland, London), Israel (Tel Aviv), Asia Pacific (Seoul, Singapore, Tokyo)。詳細はAdvanced Resource ConfigurationおよびNextflow向けのドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: 研究者、バイオインフォマティシャン、クラウド上でNextflowワークフローを運用するSRE/運用チーム
- **利用シーン**: GPU/その他アクセラレータの空きが不安定な大規模ゲノム解析やバッチ解析パイプライン、プロダクションのNextflowジョブの継続実行
- **運用効果**: アクセラレータ不足による手動再投入やデバッグ時間を削減し、ワークフローのスループットと稼働率を向上させる
- **コスト影響**: 優先アクセラレータが確保できない場合にCPUへフォールバックすると実行時間が延び、結果としてコストが増加する可能性がある

### 技術的な注意点

- **IAM権限**: HealthOmicsでインスタンス・アクセラレータを予約するためのIAM権限（ジョブ実行、インスタンス割当関連）が必要です。事前に必要権限を確認してください。
- **リージョン制限**: 現在利用可能なリージョンは記事記載の通り（US East (N. Virginia, Ohio), US West (Oregon), Europe (Frankfurt, Ireland, London), Israel (Tel Aviv), Asia Pacific (Seoul, Singapore, Tokyo)）です。その他リージョンでは未対応の可能性があります。
- **タイムアウト設定**: 各アクセラレータプロファイルに対し探索タイムアウトを設定できます。短いと迅速にフォールバック、長いと優先アクセラレータの確保確率が上がるため、ワークロード特性に応じた調整が必要です。
- **CPUフォールバックの影響**: 最終フォールバックでCPUを指定すると高確率でインスタンスが確保できますが、実行時間とコストが大きく変わることがあるため、コスト試算やSLAへの影響を評価してください。
- **Nextflow互換性**: Nextflowのresourceディレクティブにフォールバック順を記述する方式のため、既存のNextflowスクリプトへ適用可能ですが、記述方法やプロファイル名はHealthOmicsのNextflow固有仕様に従ってください（公式ドキュメントでの確認を推奨）。
- **コンプライアンス**: HealthOmicsはHIPAA適合（Eligibility）であり、医療・ライフサイエンス用途での利用が可能です。
- **コスト**: フォールバックに伴う実行時間の変化や異なるインスタンスタイプ利用により課金が変動します。ジョブのコスト見積りを事前に行ってください。
