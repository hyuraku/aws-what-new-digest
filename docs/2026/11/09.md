## [Redshift] AWS Analytics services now support Workday Data Cloud integration

- **公開日**: 2026-11-09 (JST)
- **カテゴリ**: Redshift
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-analytics-workday-data-cloud/

### 概要

AWSとWorkday Data Cloudの間で双方向かつゼロコピーの統合が提供され、ETL不要でAWSの分析サービスからWorkdayデータにオンザフライでクエリ可能になりました。既存のアクセス制御を保持したままデータを移動せずに分析やMLに利用できます。

### 変更内容・新機能の詳細

今回の統合は、AWS側とWorkday側の双方からデータを直接参照できる双方向（bi-directional）で、データの複製やコピーを不要とするゼロコピー（zero-copy）連携を実現します。AWSからは Amazon SageMaker Unified Studio、Amazon EMR、AWS Glue、Amazon Redshift、Amazon Athena を使って、Workday Live Data Query 経由でWorkdayデータをクエリしたり、カタログフェデレーションを通じて Workday Data Cloud の Apache Iceberg テーブルへフェデレートして参照できます。設定は SageMaker Unified Studio、AWS Glue、または AWS Lake Formation のコンソールで接続を構成するだけで即時クエリが可能です。アクセス制御は AWS と Workday 両方の権限で管理されます。逆に Workday 側からは、AWS Glue Data Catalog の Iceberg REST エンドポイントを Workday Analytics の外部カタログとして登録することで、AWS 上の Iceberg テーブルを Workday から直接クエリできます。典型的なユースケースは、従業員データと事業データの結合（タレント分析、ワークフォースプランニング）、および機械学習の特徴量結合などです。サービスは AWS Glue が利用可能な全ての商用リージョンで提供されます。

### 影響範囲・利用シーン

- **対象ユーザー**: データエンジニア、データサイエンティスト、SRE/運用チーム、人事/タレントアナリティクス担当者
- **利用シーン**: Workday の人事データと AWS 上の売上・顧客・製造データを結合してのタレント分析、ワークフォースプランニング、機械学習用データ準備
- **運用効果**: ETLパイプラインの開発・保守負荷を削減し、データコピーを避けつつリアルタイム／近リアルタイムで横断クエリが可能
- **セキュリティ影響**: 両側の既存アクセス制御（IAM、Lake Formation、Workday 権限）を維持したまま利用できるため、ガバナンスを保ったデータ共有が容易になる
- **コスト影響**: データ複製によるストレージ増加が不要になる一方、クエリ処理（Athena/Redshift/SageMaker/EMR等）の実行コストと Glue カタログ関連の料金は発生する

### 技術的な注意点

- **IAM権限**: AWS側は該当サービス（Athena/Redshift/SageMaker/EMR/Glue）を操作するためのIAMロール/ポリシー、Lake Formationを利用する場合は適切な許可設定が必要です。Workday 側でも外部カタログ登録やクエリ許可を与える設定が必要です。
- **カタログフェデレーション**: Workday Data Cloud と連携するには Apache Iceberg テーブルと Glue Data Catalog のフェデレーション設定、または Workday Live Data Query 経由の接続設定が必要です。RESTエンドポイントの登録手順に従ってください。
- **ネットワーク/接続**: ゼロコピーとはいえ、クエリ実行時にデータアクセスが発生するため、ネットワーク遅延やスループットがクエリ性能に影響します。クロスリージョンやオンプレ経由の場合は注意が必要です。
- **リージョン制限**: 提供は "AWS Glue が利用可能な全ての商用リージョン" としているため、Glue未対応リージョンでは利用不可です。リージョンごとのWorkday側の対応状況も確認してください。
- **コスト**: データ移動のストレージコストは削減できるが、クエリ実行コスト（Athena/Redshift/EMR/SageMakerなど）およびGlue Data Catalog利用料、Workday側のAPI/クエリ利用料が発生する可能性があります。
- **ガバナンス/監査**: アクセスは双方の権限設定で制御されるため、アクセスログ（CloudTrail、Workdayの監査ログ等）の設定と確認を推奨します。
- **互換性**: Iceberg テーブル形式を利用するワークフローが前提になるケースがあるため、既存データ形式との整合性を確認してください。

## [Fsx For Openzfs] Amazon S3 Access Points for Amazon FSx are now available in additional AWS Regions

- **公開日**: 2026-11-09 (JST)
- **カテゴリ**: Fsx For Openzfs
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/s3-access-points-fsx-regions/

### 概要

Amazon S3 Access Points を Amazon FSx（NetApp ONTAP / OpenZFS）に紐付けできるリージョンが拡大されました。S3 API 経由で FSx 上のファイルデータをコピーせずに S3 対応サービスから利用できます。

### 変更内容・新機能の詳細

S3 Access Points for Amazon FSx は、S3 ベースのアプリやサービスが Amazon FSx for NetApp ONTAP および Amazon FSx for OpenZFS 上のファイルデータへ、データの移動や複製なしに Amazon S3 API を通じてアクセスできるエンドポイントです。本アップデートにより、FSx for NetApp ONTAP 用にさらに 4 リージョン、FSx for OpenZFS 用にさらに 20 リージョンで利用可能になりました。これにより、生成系AI（例：Amazon Bedrock の Knowledge Bases）や Amazon Athena、AWS Glue、AWS Transfer Family（SFTP/FTPS/FTP）、サーバーレスコンピューティング（Amazon ECS / AWS Fargate）や自社の S3 ベースアプリから、FSx 上の同一データにそのままアクセスして検索・変換・共有が可能です。S3 Access Point の作成および FSx へのアタッチは、Amazon FSx コンソール、AWS CLI、または AWS SDK から行えます。詳細なリージョン対応状況や実装手順は FSx for ONTAP / OpenZFS のユーザーガイドを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: データサイエンティスト、MLエンジニア、アナリスト、ストレージ管理者、アプリ開発者、およびFSx（ONTAP/OpenZFS）を運用するSRE/運用チーム
- **利用シーン**: 生成AIのナレッジベース構築（Amazon Bedrockとの連携）、Athenaによる大規模ファイル検索、AWS GlueによるETL、Transfer Family経由でのファイル共有、ECS/Fargate等のサーバーレスでのファイルアクセス、S3準拠アプリからの直接利用
- **運用効果**: データ複製を避けて既存FSxデータをS3エコシステムで活用できるため、ストレージ重複の削減・データ同期コストの低減・導入の工数短縮が期待できる
- **リージョン影響**: ONTAPは追加4リージョン、OpenZFSは追加20リージョンで利用可能（詳細はユーザーガイドで確認）

### 技術的な注意点

- **IAM権限**: S3 Access Point の作成・管理権限や FSx 側のアタッチ操作権限が必要（例: s3:CreateAccessPoint など、FSx 側の API/アクション権限も必要）。実運用前に最小権限ポリシーを検討してください
- **リージョン制限**: 本機能はリージョン単位で有効化されます。利用可能リージョンはファイルシステム種別（ONTAP / OpenZFS）ごとに異なるため、導入前にユーザーガイドで対応リージョンを確認してください
- **ネットワーク/アクセス制御**: S3 Access Point ポリシー、IAM ポリシー、VPC エンドポイント条件等でアクセスを制御できます。必要に応じて VPC エンドポイントやセキュリティグループ設定を確認してください
- **セキュリティ/権限マッピング**: ファイルシステム上の POSIX 権限や ONTAP のボリューム権限がアクセスに影響するため、FSx 側のファイル/ディレクトリ権限との整合性を確認してください
- **コスト**: Access Point 自体に特別料金は発生しない可能性がありますが、FSx のストレージ費用、データ転送費用、S3 API リクエスト相当の操作に伴う料金や他サービス利用料が発生します。クロスリージョンアクセスやリージョン間転送がある場合は追加コストに注意してください
- **互換性/制限**: 一部の S3 固有機能（例: オブジェクトバージョニングや特定のメタデータ慣習）が FSx 上のファイルマッピングと異なる挙動を示す可能性があります。既存アプリとの互換性は検証してください
- **導入手順**: コンソール/CLI/SDK から Access Point を作成し、対象の FSx ファイルシステムにアタッチして利用を開始します。詳細手順はユーザーガイドを参照してください

## [EKS] Introducing AWS Nitro Sandboxes on Amazon EKS, ECS and EC2 for hardware isolated pods, tasks and VMs

- **公開日**: 2026-11-09 (JST)
- **カテゴリ**: EKS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/nitro-sandboxes-eks-ecs-ec2/

### 概要

AWS Nitro SandboxesがAmazon EKS、ECS、EC2で利用可能になりました。各Pod/タスク/軽量VMをAWS Nitro Systemによるハードウェア分離の仮想マシンとして実行できる機能です。

### 変更内容・新機能の詳細

Nitro SandboxesはNitroハイパーバイザが管理する軽量VMで、EKSのPod、ECSのTask、あるいは単独の軽量VM（AIエージェント等）をハードウェア分離された環境で実行します。各ワークロードはNitroアイソレーション境界（Nitroハイパーバイザ由来）を得るため、同一EC2インスタンス上で未検証/マルチテナント/規制対象ワークロードを安全に併存させられます。性能はほぼネイティブなEC2に近く、暗号的アテステーションによりサンドボックスの整合性を検証してからシークレットをリリースすることが可能です。EKS/ECSでの有効化はワンラインの変更で済み、Pod Identity、VPC CNI、EBS/EFS/S3、CloudWatchなど既存のネイティブ機能はそのまま動作します。直接EC2上で自分のAMIやオーケストレーション、VMMを使ってNitro Sandboxesを動かすこともでき、Amazon LinuxとFirecrackerがネイティブサポートされています（その他のVMMはパッチ提供あり）。NitroベースのほとんどのEC2インスタンスで利用可能で、全商用リージョンで提供、追加料金は発生しません。詳細と導入手順はEKS/ECSユーザーガイドおよびEC2のNitro Sandboxesドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: コンテナ/クラウド基盤エンジニア、セキュリティチーム、SRE、AI/エージェントプラットフォーム開発者
- **利用シーン**: マルチテナント環境での安全なコンテナ分離、LLMや自動化エージェントの隔離実行、規制準拠が必要なワークロードの隔離、単一EC2インスタンス上での複数エージェント運用による資源効率化
- **運用効果**: ハードウェアレベルの分離により脅威の横移動を低減、シークレットの安全な供与が可能、Pod/TaskごとにVMレベルの境界を持たせつつEKS/ECSの既存機能を維持
- **コスト効果**: 追加のAWS課金は不要だが、サンドボックスを多数起動するとEC2インスタンスのサイズや数、ストレージ/ネットワークコストに影響するため、利用効率の最適化で総コスト低減が期待できる

### 技術的な注意点

- **IAM権限**: EKS/ECSクラスタやサービスの設定変更（クラスタ管理権限、タスク/Podの実行設定変更）が必要。EC2で直接運用する場合はインスタンス管理やAMI操作の権限が必要
- **リージョン制限**: 記事時点ではほとんどのNitroベースEC2で利用可能、全商用リージョンで提供されています
- **コスト**: Nitro Sandboxes自体に追加料金は発生しないが、同一ホスト上での複数サンドボックス運用はインスタンスのCPU/メモリ/ネットワーク/ストレージ利用を増加させるため、インスタンス選定とスケーリング設計でコストに影響します
- **互換性**: Amazon LinuxとFirecrackerがネイティブサポート。他のVMMはパッチ提供あり。既存のPod Identity/VPC CNI/EBS/EFS/S3/CloudWatchはサポート済み
- **パフォーマンス**: EC2のネイティブ性能に近いが仮想化オーバーヘッドは存在する可能性があるため、レイテンシ/スループット要件の検証が必要
- **セキュリティ運用**: 暗号的アテステーションを活用するには信頼チェーン・鍵管理（KMS等）やシークレット配布フローの設計が必要
- **導入運用**: EKS/ECSでは“ワンライン”での有効化が可能だが、Pod/Task定義や監視（ログ/メトリクス）、ライフサイクル管理（起動/終了）を見直すことを推奨
- **制限**: Nitroベースのインスタンスタイプのみ対応。レガシーハイパーバイザや非-Nitroホストでは利用不可

## [Route 53] Amazon Route 53 Profiles now supports multiple Profiles per VPC

- **公開日**: 2026-11-09 (JST)
- **カテゴリ**: Route 53
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-profiles-multiple-per-vpc/

### 概要

Amazon Route 53 Profilesで1つのVPCに複数のProfileを関連付けできるようになりました。Profileごとに優先度を設定でき、優先度順（数値が小さいほど高優先）に評価されます。

### 変更内容・新機能の詳細

従来はVPCごとに1つのRoute 53 Profileしか関連付けられなかったため、DNS Firewall、プライベートホストゾーン、Resolverフォワーディングルールなどを管理する複数チームが同一Profileを共有する必要がありました。本アップデートにより、同一VPCに対して複数のProfileを関連付け可能になり、Profileごとに優先度（数値）を指定できます。Route 53はVPCに関連付けられたProfileを優先度の昇順（最小値から順）で評価します。これにより、共有設定（共通のDNS Firewallルールグループなど）を1つのProfileに、チーム固有の設定（チームAのプライベートホストゾーンやResolverルールなど）を別のProfileに分けて管理でき、マージ不要で責任分離が可能になります。また、2026年3月に導入された細粒度のIAM権限と組み合わせることで、各チームに最小権限でProfileの作成・管理を委任でき、セキュリティ体制が向上します。機能はRoute 53 Profilesが利用可能な全リージョンで有効で、Profile-VPCごとの関連付けは標準のRoute 53 Profilesの課金が適用されます。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウド/ネットワーク管理者、セキュリティチーム、SRE、DevOpsチーム
- **利用シーン**: チームごとにDNS Firewallルール、プライベートホストゾーン、Resolverルールを分離して管理したい場合（例: セキュリティチームはDNS Firewall、ネットワークチームはResolverフォワーディングを個別管理）
- **運用効果**: チーム単位での権限分離と責任範囲の明確化が可能になり、設定の衝突を優先度で解決できるため運用ミスや管理負荷が低減される
- **セキュリティ効果**: 各チームに最小権限のIAMを割り当ててProfile単位で管理させることで、横展開リスクや権限乱用を低減できる
- **コスト影響**: VPCとProfileの各関連付けごとに課金されるため、関連付け数が増えると費用が増加する可能性がある

### 技術的な注意点

- **IAM権限**: Profileの作成・関連付け・管理には対応するRoute 53 ProfilesのIAMアクションが必要です。細粒度の権限モデルを利用して最小権限を設定してください（具体的なアクション名は公式ドキュメントで確認）
- **リージョン制限**: Route 53 Profilesが利用可能なリージョンで有効です。すべてのリージョンで利用可能とは限らないため、利用リージョンの対応状況を確認してください
- **コスト**: 各Profile-VPC関連付けは標準のRoute 53 Profiles料金が適用されます。関連付け数が増えると月次費用が増加する点に注意してください（料金はAWS Route 53の料金ページを参照）
- **優先度設定**: 優先度は数値で指定し、Route 53は小さい数値を先に評価します。複数Profileに同種のリソースがある場合は優先度で意図した挙動になるよう設計してください
- **既存環境との移行**: 既存の単一Profile運用から分割する際は、関連付けの変更順序と優先度を事前に設計して競合や一時的な解釈差異が発生しないよう移行計画を立ててください
- **操作方法**: コンソール・AWS CLI・APIでProfileとVPCの関連付けが可能です。自動化する場合は対応するCLI/APIを利用して優先度を明示的に設定してください
- **監査・ログ**: Profileの作成・更新・関連付け操作はCloudTrailで記録されます。監査要件がある場合はCloudTrailと組み合わせて変更履歴を追跡してください
