## [Rds For Oracle] Amazon RDS for Oracle now supports Kerberos authentication with self-managed Active Directory

- **公開日**: 2026-11-05 (JST)
- **カテゴリ**: Rds For Oracle
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-kerberos-self-managed-ad/

### 概要

Amazon RDS for Oracleがセルフ管理のMicrosoft Active Directoryと直接ドメイン参加し、Kerberos認証を利用できるようになりました。これにより、AWS Managed Microsoft ADや信頼関係の構築なしで既存のADユーザーでDB認証・認可が行えます。

### 変更内容・新機能の詳細

今回の変更により、RDS for OracleのDBインスタンスをオンプレミス、Amazon EC2上、または他クラウド上で稼働する“self‑managed” Active Directory ドメインへ直接参加させられます。参加後はADドメイン内のユーザーがKerberosを使ってRDS for Oracleへ認証できます。以前はセルフ管理ADを使う場合、AWS Managed Microsoft ADを導入し両ドメイン間で信頼関係を構築する必要がありましたが、本機能により追加ディレクトリや信頼のセットアップが不要になります。設定はAWS Management Console、AWS CLI、またはAWS SDKで実行可能です。セルフ管理ADを使うこと自体に追加料金は発生しません。サービスはAmazon RDS for Oracleが提供される全ての商用リージョンで利用可能です。なお、実運用では（1）VPCからADドメインコントローラーへのネットワーク接続（ルーティング、セキュリティグループ、必要なポート開放）、（2）DNS解決の確保、（3）時刻同期（Kerberosは時刻差に敏感）、（4）AD側でのコンピュータアカウント作成権限または事前作成アカウントの用意、（5）Oracle側での外部認証ユーザー設定（外部認証/IDENTIFIED EXTERNALLYなど）の確認が必要です。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、セキュリティ担当者、クラウド移行/ハイブリッド環境を運用するエンジニア
- **利用シーン**: 既存のオンプレADユーザーでRDS for Oracleへシングルサインオン（Kerberos）を実現するハイブリッド接続、クラウド移行時の認証基盤をそのまま再利用
- **運用効果**: AWS Managed Microsoft AD導入やドメイン間信頼の運用負荷・コストを削減し、既存ADポリシーやアカウント管理を継続して利用可能
- **セキュリティ面の効果**: 中央のADで認証・アカウント管理を一元化でき、パスワードポリシーや監査を継承可能

### 技術的な注意点

- **IAM権限**: RDS操作（DBインスタンスの変更やディレクトリ関連操作）を行えるIAM権限を持つことを推奨。具体的なAPI/権限はドキュメントで確認してください。
- **ネットワーク**: RDSインスタンスのVPCからADドメインコントローラーへ到達できること（ルート、VPN/Direct ConnectまたはVPC Peering等）、セキュリティグループ/ACLで必要ポートを許可することが必須です。
- **必要ポート例**: Kerberos(UDP/TCP 88)、LDAP(389)/LDAPS(636)、DNS(53)、RPC/Netlogon(135, 139, 445)、Kerberos passwd(464)、NTP(123)など（利用環境に応じて調整してください）。
- **DNS/時刻同期**: RDSからAD DCへの名前解決ができるDNS構成（VPC DNS設定や条件付きフォワーダー）と、NTPによる時刻同期（Kerberosは時刻差に厳しい）を確保してください。
- **AD側の準備**: ドメイン参加時にADでコンピュータアカウントを作成する権限を持つユーザーの認証情報を提供するか、事前にコンピュータアカウントを作成・委任しておく必要があります。
- **Oracle側の設定**: ADを使った外部認証（Kerberos）を用いる場合、Oracleの外部認証ユーザー作成やマッピング設定が必要です（例: IDENTIFIED EXTERNALLY 等）。RDS上での具体的手順はドキュメント参照。
- **コスト**: セルフ管理ADの利用に対する追加料金は発生しませんが、RDS利用料、ネットワーク転送費、VPN/Direct Connect費用、セルフAD側のインフラコスト（オンプレ/EC2等）は別途発生します。
- **リージョン制限**: Amazon RDS for Oracle が提供される全ての商用リージョンで利用可能と明記されていますが、実際の利用可否はリージョン毎のRDSエンジンバージョンや機能ロールアウトを確認してください。
- **注意事項**: 既存の運用ポリシーやADセキュリティ要件（LDAPS要件、委任ポリシー等）を満たすよう事前に設計・検証を行ってください。

## [Govcloud Us] AWS Security Hub Network Scanning now available in AWS GovCloud (US)

- **公開日**: 2026-11-05 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-network-scanning-govcloud/

### 概要

AWS Security Hub の Network Scanning 機能が AWS GovCloud (US) で利用可能になりました。インターネット側から実際に到達可能かを検証し、到達可能なポートやサービスごとに Security Hub の検出結果を生成します。

### 変更内容・新機能の詳細

Network Scanning はインターネットからお客様のパブリック IP、仮想マシン、ロードバランサー等をプローブして、実際に到達可能なポートとその背後で稼働するサービスを検出します。従来の Security Hub の "ネットワーク到達可能性"（セキュリティグループやルート設定から到達可能性を推定する静的検出）を補完し、設定が実際に外部から到達可能かどうかを確認します。発見された各到達ポートについては、ポート番号や検出されたサービスのエビデンスを含む個別の Security Hub finding が作成され、Security Hub Exposures がこれらの結果と他の検出事項・リソース構成を自動で相関して、より広範なリスク評価を行います。既存の顧客は個別アカウント・リージョン単位で有効化するか、組織単位で構成ポリシーにより有効化できます。新規の Security Hub 利用者ではデフォルトで有効になります。Network Scanning は Security Hub Essentials に含まれ、追加料金なしで利用可能（Security Hub をサポートするすべての商用リージョンと GovCloud (US) リージョンに適用）です。

### 影響範囲・利用シーン

- **対象ユーザー**: セキュリティ運用チーム（SOC）、クラウドセキュリティ担当者、コンプライアンス担当者、SRE
- **利用シーンまたは効果**: 実際にインターネットから到達できるサービスの検出と優先度付け（脆弱性対応、パブリックエンドポイントの可視化、インシデント対応の初動）
- **運用効果**: 設定ベースの到達可能性検出のみでは見落とされる“実際に露出している”サービスを把握できるため、誤検知の削減と修復優先度の向上、より確度の高いリスク評価が可能
- **組織管理**: AWS Organizations を通じて組織全体で有効化・一元管理できるため、ガバナンス適用が容易
- **規制・監査**: 実際の外部到達性に関する証跡が得られるため、セキュリティ監査・コンプライアンス証跡として利用可能

### 技術的な注意点

- **IAM権限**: Security Hub を有効化・設定するための管理者権限が必要（コンソール/API での有効化や組織設定には Security Hub 管理権限および Organizations 管理権限が関わる）
- **リージョン制限**: 本アップデートは AWS GovCloud (US) でのサポート追加。利用可能なリージョンは Security Hub のサポート状況に依存するため、利用前に対象リージョンを確認してください
- **コスト**: Security Hub Essentials に含まれ、追加料金は発生しない旨が発表されていますが、関連するログ保存や他サービス（例: S3、CloudWatch Logs 等）の利用に伴う通常のコストは発生します
- **スキャンの影響**: スキャンはインターネット発のプローブを送信するため、IDS/IPS、WAF、外部脆弱性スキャン検出製品でアラートを引き起こす可能性があります。運用ポリシーに応じてホワイトリスト/通告が必要になる場合があります
- **有効化方法**: 既存顧客は個別アカウント・リージョンで手動有効化、または Organizations を用いた構成ポリシーで組織単位で有効化。新規顧客ではデフォルトで有効
- **検出出力**: 各到達ポートごとに Security Hub finding が生成され、ポート番号と検出されたサービスに関するエビデンスが含まれます
- **注意点**: スキャンの頻度・スコープや AWS 側のスキャン IP 範囲等の運用詳細はドキュメントで確認してください（必要に応じて事前調整を推奨）

## [Lambda] AWS Lambda durable functions increases default execution and API quotas

- **公開日**: 2026-11-05 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/lambda-durable-functions-default-quotas/

### 概要

AWS Lambda Durable Functions のデフォルトクォータ（実行数と関連APIのリクエスト率）が引き上げられました。これにより追加申請なしで並列実行数や監視／操作APIの呼び出し頻度を大幅に増やせます。

### 変更内容・新機能の詳細

今回のアップデートでは、Durable Functions のデフォルトクォータが以下のとおり増加しました（増加前 → 増加後）。
- Running durable executions per account: 1,000,000 → 5,000,000
- Function invocation rate to start durable executions: 300 rps → 3,000 rps
- CheckpointDurableExecution / GetDurableExecutionState: 1,000 rps → 10,000 rps
- SendDurableExecutionCallbackSuccess / SendDurableExecutionCallbackFailure / SendDurableExecutionCallbackHeartbeat: 300 rps → 3,000 rps
- GetDurableExecution / StopDurableExecution: 30 rps → 300 rps
- GetDurableExecutionHistory / ListDurableExecutionsByFunction: 15 rps → 150 rps
注: US East (N. Virginia), US West (Oregon), Europe (Ireland) の各リージョンは上記の“新しいクォータ”の2倍のデフォルト上限が適用されます（例: Running durable executions は 10,000,000 など）。

Durable Functions は最長1年間の実行、チェックポイント保存、自動リトライ、待機（wait）中はコンピュート課金が発生しない仕組みを提供します。今回のクォータ増加により、注文処理やドキュメントパイプラインなど多くの並列実行を必要とするワークロードが、追加のクォータ申請なしでより多く走らせられます。また、外部イベント待ちが多く発生するワークフローでは、待機からの再開（resume）が同時に多数発生しても処理できる余地が増えます。監視・運用用スクリプトやダッシュボードが行うステータス確認、一覧取得、履歴取得、停止といった操作は少なくとも10倍の頻度で行えるようになります。

より詳細な制限・調整は「Lambda quotas（AWS Lambda Developer Guide）」を参照してください。必要に応じて Service Quotas から上限の引き上げをリクエストできます。

### 影響範囲・利用シーン

- **対象ユーザー**: Durable Functions を用いてマルチステップワークフローやAIパイプライン、長時間実行ジョブを運用する開発者およびSRE/運用チーム
- **利用シーンまたは効果**: 注文処理/ドキュメントパイプラインなどの大量並列実行、外部イベント待ちのワークフローの同時復帰、ダッシュボードや自動化スクリプトによる実行状態確認や履歴読み取りの高頻度化
- **運用効果**: 追加クォータ申請なしでより多くの実行を並列に維持できるため、スループット向上と復旧タイミングの改善が期待できる（監視頻度向上により問題検出・対処も迅速化）

### 技術的な注意点

- **IAM権限**: Durable Functions 関連の API を呼ぶには対応する Lambda 実行/管理権限（lambda:InvokeFunction 等）および必要な管理権限を確認してください
- **リージョン制限**: 新クォータは Durable Functions が利用可能な全リージョンに適用。ただし US East (N. Virginia), US West (Oregon), Europe (Ireland) はここで示した値の2倍がデフォルトで適用されます
- **コスト**: 待機中の実行はコンピュート課金されませんが、実行再開時の実行時間や関数呼び出し、外部API呼び出し等は従来どおり課金対象です。クォータ増加により実行数・API呼び出しが増えると合計コストが増加する可能性があるため監視を強化してください
- **関連クォータ・制限**: Durable Functions の実行数増加はアカウント全体の Lambda 同時実行上限や個別関数の同時実行設定（Reserved Concurrency）に依存します。これらの上限も確認・調整が必要です
- **クォータ変更手続き**: さらに上限が必要な場合は AWS Service Quotas コンソールまたはサポート経由で引き上げを申請してください
- **注意点**: API レート上限を超えるとスロットリングされるため、大量ポーリングやバーストを行うクライアントは指数バックオフやリトライ設計を実装してください

### 参考情報

- https://docs.aws.amazon.com/lambda/latest/dg/limits.html

## [Sagemaker Studio] Amazon SageMaker AI Studio Now Supports IAM Identity Center Multi-Region Replication

- **公開日**: 2026-11-05 (JST)
- **カテゴリ**: Sagemaker Studio
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-sagemaker-ai-studio-iam/

### 概要

Amazon SageMaker AI StudioがIAM Identity Center（IdC）のマルチリージョンレプリケーションをサポートしました。これにより、IdCのプライマリインスタンスと異なるリージョンにSageMaker AI Studioドメインを配置でき、データ居住性やコンプライアンス要件に沿った運用が可能になります。

### 変更内容・新機能の詳細

従来はSageMaker AI Studioドメインを作成するリージョンにIdCのプライマリインスタンスが存在する必要がありましたが、今回の対応によりIdCのプライマリを別リージョンに維持しつつ、目的のリージョンへIdC設定をレプリケーションしてそこにSageMaker AI Studioドメインを展開できます。これにより中央集権的なアイデンティティ管理（SSO、ユーザー/グループ管理など）を維持しつつ、データ主権やリージョン制約に応じたワークロード配置が可能です。管理者はIdCのマルチリージョン設定（IAM Identity Center User Guide参照）に従って追加リージョンへのレプリケーションを有効化した後、対象リージョンでSageMaker AI Studioドメインを作成します。マルチリージョンIdCレプリケーションは、SageMaker AI Studioがサポートする標準的なAWSリージョン（例：アジアパシフィック（東京）、欧州（アイルランド）、米国東部（バージニア北部）など）で利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: SageMaker管理者、データサイエンティスト、クラウドアーキテクト、セキュリティ/コンプライアンス担当者
- **利用シーンまたは効果**: データ主権やリージョン制約があるプロジェクトで、中央のIdCを維持しつつ対象リージョンでSageMaker Studioドメインを運用する場合に有効
- **運用効果**: 中央管理による一貫したアクセス制御とSSOを維持しつつ、リージョンごとのデータ居住要件を満たせるため、コンプライアンス対応やグローバル展開が容易になる

### 技術的な注意点

- **IAM権限**: SageMakerドメイン作成／管理に必要な権限（例: AmazonSageMakerFullAccess相当）と、IAM Identity Center（旧AWS SSO）の設定・レプリケーションを行うためのIdentity Center管理権限が必要です。具体的なAPI/権限はIAM Identity Centerのドキュメントを参照してください。
- **リージョン制限**: マルチリージョンIdCレプリケーションはSageMaker AI Studioがサポートする標準リージョンで利用可能です（例: Asia Pacific (Tokyo), Europe (Ireland), US East (N. Virginia), US East (Ohio), US West (Oregon), Europe (Frankfurt), South America (São Paulo), Asia Pacific (Seoul), Europe (London), Asia Pacific (Singapore), Asia Pacific (Sydney), Canada (Central), Asia Pacific (Mumbai), Europe (Paris), Europe (Stockholm)）。特定リージョンでの利用可否は事前に確認してください。
- **コスト**: IdCレプリケーション自体に明確な追加料金が発生する場合と発生しない場合があるため、最新ドキュメントを確認してください。複数リージョンでSageMakerドメインや関連リソース（インスタンス、ストレージ、データ転送）を稼働させると、当然コストは増加します。
- **同期/伝搬遅延**: レプリケーション後のユーザー/グループ設定やポリシーの反映に時間がかかることがあるため、ドメイン作成前に同期状態を確認してください。
- **運用上の注意**: ロール／プロファイルや信頼関係、アクセスログ（CloudTrail等）のリージョン配置を考慮し、監査・コンプライアンス要件を満たすよう設定してください。マルチリージョン運用では監視とアクセス制御の整合性が重要です。

## [WAF] AWS WAF AI traffic monetization now supports fiat payouts through Stripe

- **公開日**: 2026-11-05 (JST)
- **カテゴリ**: WAF
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-waf-stripe-fiat-payouts/

### 概要

AWS WAFのAIトラフィック収益化機能がStripeと連携し、発行者やAPI提供者がAIエージェントからの支払いを法定通貨でStripe残高に直接受け取れるようになりました。これによりステーブルコインを保有したり暗号ウォレットを管理する必要がなくなります。

### 変更内容・新機能の詳細

今回の連携では、AWS WAFのAI traffic monetizationにStripeが新しいペイアウト方式として追加されます。セットアップはAWS WAFコンソールからStripe Connectを使ってStripeアカウントを接続するだけで、既存の価格設定やエージェントポリシーに変更はありません。保護対象のコンテンツへエージェントがアクセスすると、AWS WAFは受け付ける有効な支払い認証タイプを含むHTTP 402レスポンスを返します。エージェントが有効な支払い認証を付けて再リクエストすると、コンテンツはブロック解除されて返されます。収益は既存のステーブルコインでの支払い方法と並んでStripe経由（法定通貨でStripe残高へ入金）で受け取り可能になり、全ての支払いプロバイダの収益はAWS WAFコンソールのRevenue Analyticsに集約されます。利用対象は、CloudFront配下でAWS WAFのWeb ACLが関連付けられているすべてのエッジロケーションで利用可能です。AWS側に追加の利用料はかかりませんが、標準のAWS WAF料金およびStripeの処理手数料は適用されます。

### 影響範囲・利用シーン

- **対象ユーザー**: コンテンツ発行者、API提供者、広告/データ販売事業者
- **利用シーン**: AIボット／エージェントによる有料コンテンツやAPIアクセスの課金（エージェントに対するアクセスゲーティング）
- **運用効果**: ステーブルコインの保有や暗号ウォレット管理を不要にし、法定通貨で即時にStripe残高へ受け取れるため会計・運用の負担を軽減
- **収益可視化**: すべての支払いプロバイダの売上がAWS WAFコンソールのRevenue Analyticsに統合され、収益分析が容易
- **導入の容易さ**: Stripe Connectを通じてコンソールから接続するだけで既存ポリシーは変更不要、短期間で運用開始可能
- **コスト影響**: AWS側の追加料金はないが、AWS WAFの標準料金とStripeの処理手数料（決済・為替等）は発生する

### 技術的な注意点

- **IAM権限**: Stripe接続およびWAF設定を行うために適切なAWS IAM権限（WAF設定編集、CloudFront関連の権限）が必要です

- **運用効果**: ホストの直接マウントやroot権限不要でログ収集を統一でき、エージェント設定やコスト効率の改善、ログのコンテナ単位トレーサビリティ（コンテナIDでの紐づけ）が可能になる

### 変更内容・新機能の詳細

RDS for Oracle はオプショングループを使って DB の追加機能（例: 特定オプションの有効化や設定）を管理します。オプショングループはリージョン固有のリソースでしたが、従来はスナップショットを別リージョンへコピーする場合、オプショングループを手動でターゲットリージョンに再作成する必要がありました。今回の更新により、CopyDBSnapshot API（および対応する CLI コマンド）の boolean パラメータ CopyOptionGroup を true に設定すると、スナップショットのクロスリージョンコピーと同一リクエスト内でオプショングループをターゲットリージョンへコピーできます。クロスアカウントコピーも同様にサポートされます。コピー後はターゲットリージョンにオプショングループが作成され、スナップショット復元時に同等のオプション設定を利用できるようになります。本機能は全ての商用リージョンおよび AWS GovCloud (US) で利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: RDS for Oracle を運用・バックアップ/復旧/レプリケーションするクラウドエンジニア、DBA、SRE
- **利用シーン**: 異なる AWS リージョンへスナップショットをコピーして DR（ディザスタリカバリ）やリージョン移行、リージョン間バックアップを行う場面で、オプション設定も含めて一括で移行したい場合
- **運用効果**: スナップショットコピーとオプショングループの再作成を別工程で行う必要がなくなり、手戻り・ヒューマンエラーを削減して復元や移行作業を効率化できる

### 技術的な注意点

- **IAM権限**: CopyDBSnapshot API を呼び出せる権限（rds:CopyDBSnapshot 等）と、ターゲットリージョンでオプショングループを作成できる権限を確認してください。クロスアカウントの場合は適切な共有/許可設定が必要です
- **リージョン制限**: 本機能は全商用リージョンおよび AWS GovCloud (US) で利用可能とされていますが、必ず使用するリージョンでのサポート状況を確認してください
- **コスト**: クロスリージョンのスナップショットコピーはデータ転送・スナップショット保存に対する料金が発生します。オプショングループ自体のコピーに別料金が発生するかは通常ありませんが、関連する復元や追加リソースの利用コストは考慮してください
- **互換性/制限**: オプショングループはエンジンとバージョンに依存する設定を含むため、ターゲットリージョンで同一のエンジンバージョンや該当オプションがサポートされていない場合はコピーや復元が失敗する可能性があります
- **リソース参照**: オプション設定が地域固有のリソース（例: 特定リージョンの S3 バケット、IAM ロール、KMS キーなど）を参照している場合、コピー後にそれらの参照先を手動で調整する必要があります
- **名前衝突**: ターゲットリージョンに同名のオプショングループが既に存在する場合の挙動（上書きされるか、新しい名前で作成されるか等）を事前に確認してください
- **CLI/SDK**: AWS CLI/SDK では CopyDBSnapshot 呼び出し時に CopyOptionGroup を true に設定します（例: aws rds copy-db-snapshot --source-db-snapshot-identifier ... --target-db-snapshot-identifier ... --copy-option-group）。API ドキュメントのパラメータ仕様を参照してください

- **運用効果**: クロスコネクト発注やオンプレ側ルータ設定の手間を削減し、導入時間を短縮。Quad冗長とBGP/VLAN/ASNの事前設定により高可用性運用が容易になる

### 技術的な注意点

- **IAM権限**: コンソール／CLI／APIでDirect Connect周りの操作を行うために必要なIAM権限（Direct Connect関連の作成・参照・削除権限）を事前に確認してください（環境に応じてポリシーを最小権限で設定することを推奨）。
- **リージョン制限**: プレビューは米国西部（北カリフォルニア）へのサンノゼ経路と米国東部（北バージニア）へのノーザンバージニア経路の1 Gbpsのみ。GA時点で他リージョンや帯域（最大100 Gbps）に拡張されますが、リージョン対応状況を公式情報で確認してください。
- **コスト**: プレビュー中のAWS側1 Gbpsは無料ですが、Equinixのポート料金やデータセンター側のクロスコネクト／ポート使用料、パートナー側の課金が別途発生する可能性があります。GA時はAWS Direct Connectの通常料金が適用されます。
- **セキュリティ**: トランスポート層はAWS⇔Equinixエッジ間でMACsecにより暗号化されますが、MACsecがカバーする範囲（最後尾のオンプレISEや内部ネットワーク）を設計段階で確認してください。BGPとASNの事前設定によりルート設計の確認が必要です。
- **オンプレ前提条件**: Equinixファシリティまでの物理的接続（お客様設備→Equinixポート）やEquinix Fabric OneのプロジェクトIDが必要です。オンプレ側での経路設計や接続先冗長性の検討は必須です。
- **運用/監視**: BGPセッションやVLAN、帯域利用の監視、SLA逸脱時のエスカレーションフローを事前に整備してください。
- **API/自動化**: コンソールに加えCLI/APIでの作成が可能。パートナー向けのオープンAPIパッケージ（GitHub）を利用してプロビジョニングの自動化ができます。

## [Connect] Amazon Connect Customer now shows associated cases in contact records

- **公開日**: 2026-11-05 (JST)
- **カテゴリ**: Connect
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-connect-cases-contact-records/

### 概要

Amazon Connect のコンタクトレコードに、関連する Cases のケースIDおよび参照番号が表示されるようになりました。スーパーバイザーやアナリストがどの顧客課題（例：返金、請求トラブル）がコンタクト量を生んでいるかを即座に把握できます。

### 変更内容・新機能の詳細

Connect の Contact Details ページ上で、該当のインタラクションに紐づく Cases のケースIDと参照番号が表示されるようになりました。これにより、スーパーバイザーは個々の通話やチャットの詳細画面を開くだけで関連ケースを確認でき、個別にケース検索する手間が省けます。また、同情報は DescribeContact API とコンタクトイベントストリームでも取得可能になり、アナリストはケースごとのインタラクション数を計測・集計できます。Cases は複数のやり取りやチームにまたがる顧客問題（返金要求、請求異議など）を追跡する機能で、今回の連携によりオペレーションの可視化と分析が容易になります。対応リージョンは US East (N. Virginia)、US West (Oregon)、Canada (Central)、Europe (Frankfurt)、Europe (London)、Asia Pacific (Seoul)、Asia Pacific (Singapore)、Asia Pacific (Sydney)、Asia Pacific (Tokyo)、Africa (Cape Town) です。導入方法や詳細は Cases の製品ページとドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: コンタクトセンターのスーパーバイザー、品質管理者、データアナリスト、SRE/運用チーム
- **利用シーン**: 通話・チャットごとの関連ケース確認、ケース単位のコンタクト集計やレポーティング、エスカレーションの追跡
- **運用効果**: 個別ケースとコンタクトの紐付きを即時確認できるため、原因分析・優先順位付けが高速化され、対応漏れや無駄な検索工数が削減される

### 技術的な注意点

- **IAM権限**: DescribeContact やコンタクトイベントストリームの閲覧に必要な Connect の権限（および関連する Kinesis/S3 などの権限）を付与してください
- **API/イベント**: DescribeContact API でケースIDを取得可能。コンタクトイベントストリームで継続的に集計する設計にする場合はストリーム有効化とイベント処理の実装が必要です
- **リージョン制限**: 本機能は発表時点で指定のリージョン（N. Virginia, Oregon, Canada Central, Frankfurt, London, Seoul, Singapore, Sydney, Tokyo, Cape Town）のみ対応です
- **コスト**: Cases の利用やコンタクトイベントのストリーミング（Kinesis、S3 など）には追加料金が発生する可能性があります。利用量に応じた請求影響を事前に確認してください
- **有効化・設定**: Connect インスタンスで Cases を有効化している必要があります。既存の Connect 環境では追加設定や権限調整が必要になる場合があります
- **データの遡及性**: 過去のコンタクトに対するケース紐付けが自動的にバックフィルされるかは環境依存のため、導入前にドキュメントで確認してください
