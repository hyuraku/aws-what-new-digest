## [General] Amazon CloudWatch Omni now supports Microsoft Azure platform logs, metrics and traces

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-cloudwatch-omni-microsoft-azure

### 概要

Amazon CloudWatch Omni が Microsoft Azure のリソースログ、Azure Monitor のプラットフォームメトリクス、VNet フローログ、Application Insights のトレース収集に対応しました。AWS と Azure のテレメトリを CloudWatch に集約し、複数クラウドにまたがる監視や障害調査を一元化できます。

### 変更内容・新機能の詳細

Microsoft Entra ID テナントを AWS アカウントおよびリージョンに接続し、収集対象のテレメトリ種別、Azure サブスクリプション、Azure リージョン、リソースタイプ、タグを選択して設定します。収集した Azure テレメトリは Amazon CloudWatch に取り込まれ、CloudWatch Omni のスペースで AWS のテレメトリとあわせてアプリケーションやインフラストラクチャを監視できます。たとえば、Azure 上のサービスで発生した遅延リクエストを、AWS 上の依存先までコンソールを切り替えずに追跡できます。コネクターは CloudWatch Omni コンソールまたは AWS CLI から設定できます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS と Azure の両方でワークロードを運用する中央運用、DevOps、SRE チーム
- **利用シーン**: Azure のログ・メトリクス・トレースと AWS のテレメトリを一元的に監視
- **運用効果**: クラウド間の依存関係を追跡しやすくなり、障害調査時のコンソール切り替えや個別監視基盤の運用を減らせます

### 技術的な注意点

- **認証・接続**: AWS アカウントおよびリージョンに Microsoft Entra ID テナントを接続して設定します
- **収集範囲**: サブスクリプション、Azure リージョン、リソースタイプ、タグ、テレメトリ種別を選択できます
- **リージョン制限**: Azure Public Regions のテレメトリを収集でき、取り込み先は CloudWatch Omni が利用可能な AWS リージョンです
- **コスト**: Azure テレメトリの CloudWatch への取り込みや保存・監視に伴う料金が発生する場合があります。最新の料金は CloudWatch の料金ページを確認してください

- https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Omni.html
- https://aws.amazon.com/cloudwatch/pricing/

## [Bedrock] Web Search on Amazon Bedrock expands language support and country-aware search 

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/web-search-amazon-bedrock/

### 概要

Amazon Bedrock の Web Search が、スペイン語・フランス語・ドイツ語・イタリア語・日本語と米国以外の英語に対応しました。検索結果を特定の国に寄せる任意の国コード指定も追加され、地域に関連した情報を取得しやすくなります。

### 変更内容・新機能の詳細

Web Search は、AI エージェントやアプリケーションが最新の Web 情報を検索し、出典付きで回答を生成するための機能です。今回の言語拡張により、対象言語で利用するエージェントは、その言語のローカルな情報源を含む検索結果を得られます。また、任意の country フィールドに ISO 3166-1 alpha-2 形式の国コード（例: JP、DE）を指定すると、その国の情報源を優先するよう検索結果を調整できます。これにより、現地の規制、価格、行政関係者など、場所によって答えが異なる質問や、複数の国の利用者向けサービスに対応しやすくなります。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Bedrock または Amazon Bedrock AgentCore の Web Search を利用する開発者、AI エージェントの運用者
- **利用シーン**: 日本語などの複数言語での検索、国ごとに異なる規制・価格・公的情報の回答、地域に関連する情報源の提示
- **運用効果**: 利用者の言語や指定国に合った検索結果を得やすくなり、地域性の高い回答の精度向上が期待できます
- **データ所在地**: クエリは呼び出し先リージョンで処理されるため、データレジデンシー要件への対応に役立ちます

### 技術的な注意点

- **対応言語**: スペイン語、フランス語、ドイツ語、イタリア語、日本語、および米国以外の英語に対応します
- **国コード**: country フィールドは任意です。指定する場合は ISO 3166-1 alpha-2 形式（例: JP、DE）を使用します
- **リージョン制限**: AgentCore の Web Search は米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、アジアパシフィック（シドニー、東京）、欧州（アイルランド）で利用できます。Amazon Bedrock の Web Search は米国リージョンで利用できます
- **既存利用者**: 新しい言語機能は自動的に利用可能で、コード変更は不要です。国指定を利用する場合はリクエストに country フィールドを追加します
- **コスト**: 言語による料金差はありません。記事では国コード指定による追加料金については明記されていません

## [Rds For Oracle] Amazon RDS for Oracle now supports Primary Endpoint

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: Rds For Oracle
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-primary-endpoint-v2/

### 概要

Amazon RDS for Oracleに、レプリカ構成の現在のプライマリDBインスタンスを指す「Primary Endpoint」が追加されました。スイッチオーバー後も接続先のDNS名を維持できるため、アプリケーションの接続文字列を変更せずに新しいプライマリへ接続できます。

### 変更内容・新機能の詳細

Primary Endpointは、レプリカ構成における現在のプライマリDBインスタンスへ名前解決されるDNSエンドポイントです。プライマリをレプリカへスイッチオーバーすると、Amazon RDSがこのエンドポイントの参照先を新しいプライマリに切り替えます。同一AWSリージョン内のレプリカへの切り替えだけでなく、クロスリージョンレプリカへの切り替えにも利用できます。各RDS for Oracle Enterprise Edition DBインスタンスに追加料金なしで提供され、作成作業は不要です。従来のインスタンスエンドポイントも引き続き利用できるため、既存アプリケーションへの影響はありません。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for Oracle Enterprise Editionでレプリカ構成を利用するDB管理者、アプリケーション運用チーム
- **利用シーン**: 災害復旧訓練や計画メンテナンスで、同一リージョンまたはクロスリージョンのレプリカへスイッチオーバーする場合
- **運用効果**: アプリケーションの接続文字列やDNSレコードをスイッチオーバーのたびに変更する作業を削減できます

### 技術的な注意点

- **対象エディション**: Primary EndpointはRDS for Oracle Enterprise EditionのDBインスタンスに提供されます
- **接続先の切り替え**: スイッチオーバー後にDNSの参照先が新しいプライマリへ切り替わります。アプリケーション側でDNSキャッシュを長時間保持する場合や既存接続が残る場合は、再接続の挙動を確認してください
- **既存エンドポイント**: Primary Endpointはインスタンスエンドポイントに追加して提供されるため、既存の接続設定はそのまま利用できます
- **リージョン**: RDS for Oracleが提供されているすべての商用AWSリージョンで利用可能です
- **コスト**: 追加料金はありません

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-primary-endpoint-v2/
- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_Oracle.html

## [General] AWS Lambda now publishes Event Function state change events to Amazon EventBridge 

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-function-state-events/

### 概要

AWS Lambdaが、関数バージョンの状態変更イベントをAmazon EventBridgeに自動発行する機能を提供しました。EventBridgeルールでイベントを検知して後続処理を起動できるため、GetFunction APIを定期的にポーリングする必要がなくなります。

### 変更内容・新機能の詳細

関数の作成、更新、発行、削除など、利用者の操作によってLambda関数バージョンの状態が変化するたびに、LambdaがEventBridgeへイベントを発行します。EventBridgeでは、関数ARN、イベントのdetail type、状態などのフィールドを条件にルールを作成し、一致したイベントをAWS Step Functions、AWS Lambda、Amazon SNS、Amazon SQSなどへルーティングできます。これにより、関数が呼び出し可能な状態になった後の統合テスト実行や、更新完了後のエイリアストラフィック切り替え、操作失敗時の通知などをイベント駆動で自動化できます。コンソール、AWS CLI、AWS SDK、CloudFormation、CDK、SAMからルールを作成できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Lambdaを利用するプラットフォームチーム、DevOpsチーム、開発チーム
- **利用シーン**: 関数の状態変更を契機に、デプロイ後のテスト、エイリアス切り替え、失敗通知などを自動実行
- **運用効果**: GetFunction APIのポーリングや独自の再試行処理を減らし、処理の遅延やAPIクォータ消費、運用負荷を抑制
- **適用範囲**: 商用AWSリージョンで利用可能

### 技術的な注意点

- **イベント対象**: 利用者の操作によって関数バージョンの状態が変化した際にイベントが発行されます。イベントの詳細なスキーマや状態値はLambda Developer Guideで確認してください
- **ルール設定**: 関数ARN、detail type、状態などを条件にEventBridgeルールを構成できます
- **料金**: Lambdaによるイベント発行に追加料金はありません。ルールが呼び出すターゲットには通常の料金が適用されます
- **リージョン制限**: 商用AWSリージョンで利用可能です。GovCloudや中国リージョンの対応は記事に記載されていません

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-function-state-events/
- https://docs.aws.amazon.com/lambda/latest/dg/
- https://docs.aws.amazon.com/eventbridge/latest/userguide/

## [General] AWS Network Firewall introduces automated Internet firewall in public preview

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/network-firewall-automated-internet/

### 概要

AWS Network Firewallの「automated Internet firewall」がパブリックプレビューとして提供されました。VPCごとにファイアウォール用サブネットやルートを構成せず、対象VPCのインターネットゲートウェイで通信を検査し、NATやログ記録を一元管理できます。

### 変更内容・新機能の詳細

automated Internet firewallモードでは、AWS Network Firewallのセキュリティルールを中央で定義し、対象VPCのインターネットゲートウェイを通過するインバウンド／アウトバウンド通信に適用します。対象は選択したVPC、アカウント全体、AWS Organizationsの組織または組織単位（OU）から指定できます。従来のように各VPCへファイアウォールエンドポイントを配置し、サブネットのルートを更新する必要がなく、新たなインターネット経路が制御を迂回していないか監視する負担も軽減されます。
組み込みのNAT機能により、アウトバウンド専用のインターネット接続に必要なNATと通信フィルタリングを組み合わせられます。また、インターネットゲートウェイを通る通信のログを記録できます。初期設定用のデフォルトセキュリティポリシーには、AWS管理ルールグループ（AWS独自の脅威インテリジェンスを利用するActive Threat Defenseを含む）が用意されています。独自のルールグループやAWS Marketplaceの管理ルールグループも利用できます。新しく作成されるVPCなどへ組織のセキュリティポリシーを自動的に拡張する設定も可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数のVPCやアカウントのインターネット通信を一元的に保護・管理するネットワーク／セキュリティチーム
- **利用シーン**: VPC単位のファイアウォールエンドポイントやルート設定を行わず、インターネットゲートウェイ経由の通信を集中管理する場合
- **運用効果**: ファイアウォールの展開とルート管理を簡素化し、新規VPCへのポリシー適用や通信のログ記録を一元化できます
- **適用範囲**: 選択したVPC、アカウント全体、Organizationsの組織またはOUを対象にできます

### 技術的な注意点

- **提供状況**: パブリックプレビューです。本番環境で利用する場合は、プレビュー中の制約やサービス条件を事前に確認してください
- **リージョン制限**: AWS GovCloud（米国）および中国リージョンを除くAWSリージョンでプレビュー提供されています
- **通信経路**: 対象となるのはインターネットゲートウェイ経由の通信です。ほかの経路の通信まで自動的に検査されるとは限らないため、保護対象のネットワーク経路を確認してください
- **NAT**: 組み込みNATはアウトバウンド専用のインターネット接続用途として説明されています。既存のNAT構成との併用・移行方法は公式ドキュメントを確認してください
- **ルール**: デフォルトのAWS管理ルールに加えて、独自ルールグループやAWS Marketplaceの管理ルールグループを利用できます。適用範囲とルールの動作を確認してください
- **コスト**: AWS Network Firewallの利用料金やログ保存先の料金が発生する可能性があります。導入前に公式料金ページで対象リージョンと構成に応じた費用を確認してください

### 参考情報

## [Rds For Oracle] Amazon RDS for Oracle now supports Replica First Patching for reduced downtime

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: Rds For Oracle
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-replica-first-patching/

### 概要

Amazon RDS for OracleのEnterprise Edition DBインスタンスで、マイナーバージョンアップグレード時の停止時間を抑える「Replica First Patching」が利用可能になりました。レプリカを先にアップグレードし、任意のタイミングでプライマリに切り替えられます。

### 変更内容・新機能の詳細

同一AWSリージョン内のレプリカに新しいマイナーエンジンバージョンを先行適用する間、プライマリDBインスタンスは引き続きトラフィックを処理します。レプリカが読み取り専用の場合は、読み取りトラフィックを使って新バージョンを検証できます。所定のスイッチオーバー期間内に切り替えると、レプリカが新しいプライマリとなり、Amazon RDSがアップグレードを完了します。その後、旧プライマリを含むほかのレプリカも同じマイナーバージョンに更新されます。期間内に切り替えなかった場合、レプリカは元のマイナーバージョンにロールバックされます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for OracleのEnterprise Editionを利用し、マイナーバージョンをアップグレードする運用チーム
- **利用シーン**: 本番プライマリの処理を継続しながら、レプリカで新バージョンを事前検証し、低トラフィック時間帯に切り替える
- **運用効果**: アップグレードに伴う停止時間や業務への影響を抑え、重要なOracleワークロードをより計画的に最新化できる
- **料金**: Replica First Patching自体の追加料金はありません。ただし、レプリカDBインスタンスには通常の料金が適用されます

### 技術的な注意点

- **対象範囲**: Enterprise EditionのDBインスタンスが対象です。マイナーバージョンアップグレードに利用します
- **リージョン**: Amazon RDS for Oracleが提供されているすべての商用AWSリージョンで利用できます。レプリカはプライマリと同じリージョンに配置します
- **切り替え期限**: 指定されたスイッチオーバー期間内に切り替えない場合、レプリカは元のマイナーバージョンにロールバックされます
- **接続先**: アプリケーションにはPrimary Endpointの利用が推奨されます。スイッチオーバー後もDNSが新しいプライマリを指すため、接続文字列の変更を避けられます
- **レプリカの更新**: スイッチオーバー後、旧プライマリを含むほかのレプリカも同じマイナーバージョンにアップグレードされます

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-replica-first-patching/
- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_UpgradeDBInstance.Oracle.html

## [Cognito] Amazon Cognito extends multi-Region replication to additional AWS Regions

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: Cognito
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-mrr-opt-in-regions/

### 概要

Amazon Cognitoのマルチリージョンレプリケーション（MRR）が、新たにアジア太平洋、カナダ、欧州などのAWSリージョンで利用可能になりました。ユーザーやマシンIDのデータを待機系ユーザープールへほぼリアルタイムで複製し、認証の可用性やデータレジデンシー要件への対応を強化できます。

### 変更内容・新機能の詳細

MRRは、プライマリのユーザープールにあるユーザーおよびマシンIDのデータを、指定した別リージョンの待機系ユーザープールに同期する機能です。対象には認証情報、ユーザープール設定、フェデレーション設定が含まれます。プライマリリージョンで障害が発生した場合、待機系リージョンへトラフィックを切り替えることで、認証サービスの継続を支援します。
今回追加されたリージョンは、アジアパシフィック（ハイデラバード、香港、ジャカルタ、マレーシア、メルボルン、ニュージーランド、大阪、台北、タイ）、カナダ西部（カルガリー）、欧州（ミラノ、スペイン、チューリッヒ）、イスラエル（テルアビブ）、メキシコ（中部）、アフリカ（ケープタウン）です。これらの追加により、従来の16商用リージョンおよびAWS GovCloud（米国）リージョンに加えて、より多くの地域でMRRを利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Cognitoを利用するアプリケーション開発者、セキュリティ担当者、SRE／運用チーム
- **利用シーン**: リージョン障害に備え、認証用ユーザープールを別リージョンに複製する災害対策（DR）構成
- **利用シーン**: ユーザーデータの保管地域に関するデータレジデンシーやコンプライアンス要件への対応
- **運用効果**: 待機系リージョンにIDデータを保持し、障害時の認証継続を支援

### 技術的な注意点

- **利用条件**: MRRはEssentialsまたはPlus機能プランのユーザープール向けアドオンです
- **暗号化キー**: マルチリージョンAWS KMSカスタマーマネージドキー（CMK）が必要です
- **フェイルオーバー**: MRRはデータを複製しますが、障害時のアプリケーショントラフィック切り替えも考慮した構成が必要です
- **リージョン**: 今回追加されたリージョンで利用できます。対象リージョンと組み合わせの最新情報はAWSのリージョン別サービス一覧およびCognitoの開発者ガイドで確認してください
- **コスト**: MRRはアドオン機能です。料金はCognitoの料金ページで確認してください

Prometheus メトリクスについては、標準の ServiceMonitor および PodMonitor リソースに記述されたターゲットを Agent がスクレイプします。Prometheus Operator の運用や、既存のスクレイプ設定を変更することなく利用できます。各チームはアプリケーションと同じ場所で監視対象を定義でき、ラベルセレクターで CloudWatch が収集する Monitor を選択できます。

OTLP と Prometheus のどちらのテレメトリにも、アドオンが付与する Kubernetes、ホスト、クラウド、サービスの属性が含まれます。そのため、アプリケーションのテレメトリとクラスターのメトリクスを関連付けて分析できます。

- **利用シーン**: OpenTelemetry SDK を使ったアプリケーションの計装データを、追加のコレクターを運用せず CloudWatch に集約
- **利用シーン**: ServiceMonitor／PodMonitor を使い、チームごとに Prometheus のスクレイプ対象を定義・管理
- **運用効果**: アプリケーションのテレメトリと Kubernetes クラスターのメトリクスを共通属性で関連付け、調査や分析を効率化

### 技術的な注意点

- **バージョン**: EKS アドオンまたは Helm chart のバージョン 8.0.0 以降が必要です
- **対応リージョン**: CloudWatch が OpenTelemetry メトリクスをサポートするすべての AWS リージョンで利用できます
- **Prometheus**: ServiceMonitor／PodMonitor の利用に Prometheus Operator は不要です。ラベルセレクターを使って収集対象を選択してください
- **エンドポイント**: OTLP エンドポイントは各ノードの CloudWatch Agent が提供し、デフォルトで有効です。アプリケーションからの送信先設定を確認してください
- **コスト**: テレメトリ取り込みには Amazon EKS OpenTelemetry の取り込み料金が適用され、記事記載の料金は 1 GB あたり 0.08 USD です。最新の料金は公式料金ページを確認してください

## [Msk] Amazon MSK now supports in-place upgrade from Standard brokers to Express brokers

- **公開日**: 2026-11-21 (JST)
- **カテゴリ**: Msk
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-msk-standard-brokers-to-express-brokers-in-place-upgrade

### 概要

Amazon MSK Provisioned クラスターで、Standard ブローカーから Express ブローカーへ、クラスターを作り直さずにインプレースでアップグレードできるようになりました。エンドポイントとコンシューマーオフセットを維持しながら移行できるため、アプリケーションの変更や切り替えを抑えられます。

### 変更内容・新機能の詳細

アップグレードでは Express ブローカーを既存クラスターに追加し、トピックを Express ブローカーへ移行します。移行は自動で進める方法と、バッチ単位で制御する方法を選べます。Standard ブローカーは、利用者が廃止を選ぶまでクラスター内に残るため、アプリケーションの動作を検証してからアップグレードを完了できます。
Express ブローカーは Standard ブローカーと比べて、ブローカーあたり最大3倍のスループット、最大20倍速いスケールアップ、最大90%速い復旧を実現するよう設計されています。ストレージは従量課金で自動的に拡張され、ベストプラクティスに基づく設定が組み込まれています。M7g または M8g インスタンスを選択でき、M8g の Express ブローカーは M7g と比べて最大30%のコスト削減が可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon MSK Provisioned の Standard ブローカーを利用しており、Express ブローカーへの移行を検討しているチーム
- **利用シーン**: 新規クラスターを構築せず、既存の Kafka ワークロードを Express ブローカーへ段階的に移行する
- **運用効果**: エンドポイントを変更せず、コンシューマーオフセットも維持できるため、アプリケーションの切り替えやデータ再処理のリスクを抑えられる
- **性能・コスト効果**: ブローカーあたりのスループット向上や復旧時間の短縮が期待でき、M8g を選ぶと Express ブローカーの M7g 比で最大30%のコスト削減が可能

### 技術的な注意点

- **前提条件**: 対象は Apache Kafka 3.9 を KRaft モードで実行する、Standard ブローカーの MSK Provisioned クラスターです
- **リージョン制限**: Express ブローカーが利用可能な AWS リージョンで利用できます。対象リージョンは公式ドキュメントで確認してください
- **インスタンスタイプ**: アップグレード先の Express ブローカーは M7g または M8g です
- **移行と切り戻し**: トピックの移行方法は自動またはバッチ単位で選択できます。Standard ブローカーは利用者が廃止するまで残るため、検証後にアップグレードを完了できます
- **アプリケーション互換性**: クラスターエンドポイントとコンシューマーオフセットは維持されます。ステートフルな Apache Flink や Kafka Streams の処理で再処理や重複を避けやすくなります
- **コスト**: アップグレード自体の追加料金はありませんが、移行中は Standard と Express の両方のブローカー料金が発生します

Node.js 26 は、管理対象ランタイムとして Web Functions と Event Functions で利用できます。また、コンテナイメージのベースイメージとしても提供されますが、こちらは Event Functions が対象です。Temporal API による日付・時刻・タイムゾーン処理の改善や、Fetch API の機能強化を利用できます。Powertools for AWS Lambda (TypeScript) と組み合わせることもでき、Lambda コンソール、AWS CLI、AWS SAM、AWS CDK、AWS CloudFormation などのツールでデプロイ・管理できます。Node.js 26 は最新の長期サポート（LTS）リリースで、Node.js のセキュリティ修正およびバグ修正は2029年4月まで予定されています。

- **更新適用**: AWS は管理対象ランタイムを更新します。コンテナイメージを利用する場合は、更新されたベースイメージを取り込んでイメージを再ビルド・再デプロイする必要があります
- **サポート期間**: 2029年4月までという記載は Node.js 26 のセキュリティ修正・バグ修正の予定です。Lambda ランタイムのサポート期限や廃止予定は別途確認してください

- **設定変更**: 既存の読み取りリクエストにも全AWSリージョンで自動適用され、アプリケーションの変更は不要です
- **コスト**: 追加料金はなく、通常のS3リクエスト料金が適用されます
