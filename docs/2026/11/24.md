## [Ec2] Amazon EC2 X8i instances are now available in the Asia Pacific (New Zealand) Region 

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-ec2-x8i-new-zealand/

### 概要

Amazon EC2 X8i インスタンスがアジアパシフィック（ニュージーランド）リージョンで利用可能になりました。メモリ集約型ワークロード向けに、前世代の X2i と比べて性能、メモリ容量、メモリ帯域幅が向上しています。

### 変更内容・新機能の詳細

X8i は AWS 専用のカスタム Intel Xeon 6 プロセッサを搭載し、SAP 認定を受けたインスタンスです。X2i と比較して、最大 43% 高い性能、1.5 倍のメモリ容量（最大 6 TB）、3.3 倍のメモリ帯域幅を提供します。ワークロード別では、最大で SAPS 性能が 50%、PostgreSQL 性能が 47%、Memcached 性能が 88%、AI 推論性能が 46%向上するとされています。インスタンスサイズは large から 96xlarge までの 14 種類で、ベアメタルタイプも 2 種類あります。購入方法は Savings Plans、オンデマンド、Spot に対応しています。

### 影響範囲・利用シーン

- **対象ユーザー**: SAP HANA、データベース、データ分析、EDA など、メモリ集約型ワークロードを運用するユーザー
- **利用シーン**: 大規模なインメモリデータ処理や、メモリ帯域幅が性能を左右するワークロードの実行
- **運用効果**: X2i から移行することで、対象ワークロードの性能向上や、より大きなメモリ容量の活用が期待できます

### 技術的な注意点

- **リージョン**: アジアパシフィック（ニュージーランド）リージョンで利用可能です。利用可能なサイズは AWS マネジメントコンソールで確認してください
- **性能指標**: 記載された性能向上率は X2i との比較で、いずれも最大値です。実際の効果はワークロードや設定によって異なります
- **購入方法**: Savings Plans、オンデマンド、Spot を利用できます。料金や割引条件は購入方法によって異なるため、事前に確認してください
- **インスタンスサイズ**: large から 96xlarge までの 14 種類があり、うち 2 種類はベアメタルです

## [Identity And Access Management] AWS Sign-In introduces configurable Sign-in duration of up to 90 days

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: Identity And Access Management
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/configurable-aws-sign-in-duration/

### 概要

AWS Sign-Inで、IAMユーザーおよびIAMロールごとにOAuthサインインセッションの有効期間を設定できるようになりました。管理者が設定すれば、AWS CLIの`aws login`などで最大90日間サインイン状態を維持でき、長時間実行する処理の再認証を減らせます。

### 変更内容・新機能の詳細

Sign-in durationは、OAuthを利用するAWS Sign-Inセッションが有効な期間を制御する設定です。IAMユーザーやロールごとに、IAMコンソール、AWS CLI、またはIAM APIから構成できます。AWS CLIの`aws login`、AWS MCP Server、その他のOAuth対応アプリケーションが対象です。セッションで利用する認証情報は短期間有効で更新可能なため、静的なアクセスキーを長期間保持する方法に代わる選択肢になります。既存のセッション期間の上限は、管理者がより長い期間を明示的に設定しない限り変更されません。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS CLIやAWS MCP Server、OAuth対応アプリケーションを使う開発者、AIエージェント、およびIAM管理者
- **利用シーン**: 長時間実行する開発・自動化ワークフローで、頻繁なサインインや同意確認による中断を減らす
- **運用効果**: 静的アクセスキーを使わず、更新可能な短期認証情報でサインイン状態を維持しやすくなる
- **適用範囲**: AWS商用リージョンで利用可能。AWS Management Consoleのセッションには影響しない

### 技術的な注意点

- **設定単位**: IAMユーザーまたはIAMロールごとに設定し、最大90日まで指定できます
- **既存設定**: 管理者が長い期間を明示的に設定しない限り、既存のセッション期間の上限は変わりません
- **対象サービス**: AWS CLIの`aws login`、AWS MCP ServerなどのOAuth対応アプリケーションが対象です。Management Consoleのセッション期間を延長する設定ではありません
- **セキュリティ**: セッション期間を長くすると再認証までの時間も延びるため、ユーザーやロールの権限、認証情報の保護、必要に応じた条件キーによる制御を確認してください
- **リージョン**: AWS商用リージョンで利用可能です
- **コスト**: 記事に追加料金の記載はありません

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/configurable-aws-sign-in-duration/
- https://docs.aws.amazon.com/signin/latest/userguide/

## [General] Amazon SageMaker HyperPod now supports managed observability and user management extensions for Slurm clusters

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/sagemaker-hyperpod-extensions/

### 概要

Amazon SageMaker HyperPod の Slurm クラスターで、監視とユーザー管理の機能をマネージド拡張機能として利用できるようになりました。設定の適用や更新を HyperPod に任せられるため、ライフサイクルスクリプトを変更してノードを再作成・再実行する作業を減らせます。

### 変更内容・新機能の詳細

SageMaker AI コンソールまたは API から、拡張機能のインストール、設定、更新、削除を行えます。利用者は拡張機能ごとに設定を宣言し、HyperPod が内容を検証してクラスター内の全ノードに適用します。後から追加したノードにも設定が反映され、拡張機能の状態と各ノードの健全性を確認できます。

監視拡張機能は、ノード、GPU、Elastic Fabric Adapter（EFA）、Slurm ジョブ、Slurm クラスターのメトリクスを収集し、Amazon CloudWatch または Amazon Managed Service for Prometheus に送信します。Amazon Managed Grafana のダッシュボードも追加できます。

ユーザー管理拡張機能は、全ノードで同一の ID を持つユーザーとグループを作成します。また、ノードの種類ごとに SSH ログインや sudo の利用者を制御でき、ローカルユーザー、Active Directory、または両方を利用できます。組織独自のソフトウェアについては、従来どおりライフサイクルスクリプトやカスタム AMI を使用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon SageMaker HyperPod で Slurm クラスターを運用する機械学習基盤チーム、SRE、セキュリティ管理者
- **利用シーン**: クラスターのメトリクス監視、GPUやEFAの状態確認、Slurmジョブの可視化、ユーザー・グループおよびSSH／sudo権限の一元管理
- **運用効果**: 設定変更のたびにライフサイクルスクリプトを編集してノードを置き換える作業を減らし、追加ノードを含めて設定を一貫して適用できます
- **コスト**: クラスター拡張機能自体は追加料金なしです。CloudWatch、Amazon Managed Service for Prometheus、Amazon Managed Grafana など、利用するAWSリソースには通常の料金が発生する場合があります

### 技術的な注意点

- **対象範囲**: 本機能は SageMaker HyperPod の Slurm クラスター向けです
- **設定適用**: 拡張機能の設定は HyperPod によって検証・適用され、後から追加したノードにも反映されます。適用後は拡張機能の状態とノードの健全性を確認してください
- **ユーザー管理**: 全ノードでユーザーとグループのIDを揃える設計です。SSHログインおよびsudoの許可範囲をノードタイプごとに確認し、ローカルユーザーとActive Directoryの利用方式を選択してください
- **監視データ**: メトリクスの送信先として CloudWatch または Amazon Managed Service for Prometheus を利用できます。Grafanaダッシュボードを追加する場合は、関連サービスの設定と権限も確認してください
- **リージョン制限**: SageMaker HyperPod が提供されているすべてのAWSリージョンで利用できます
- **コスト**: 拡張機能自体は無料ですが、メトリクス保存・取り込みやダッシュボードなど、関連AWSサービスの利用料金は別途発生する可能性があります

## [Elasticsearch Service] Amazon OpenSearch Service now supports OpenSearch version 3.9

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: Elasticsearch Service
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-opensearch-opensearch-3-9

### 概要

Amazon OpenSearch ServiceでOpenSearch 3.9を利用できるようになりました。ベクトル検索のメモリ・ストレージ効率、検索品質評価、AIエージェントの応答性、共有リソースのアクセス制御が強化されています。

### 変更内容・新機能の詳細

ベクトル検索では、各次元を16ビットで格納するhalf-floatベクトル型とbf16エンコーダーが追加され、ベクトルインデックスのメモリとストレージを削減できます。また、2ビット／4ビットのスカラー量子化を選択でき、圧縮率と検索再現率（recall）のバランスをワークロードに合わせて調整できます。Base64形式のベクトル取り込みはリクエストペイロードを小さくし、一括ロードの高速化に役立ちます。radial searchではグラフ探索が再設計され、recallとスループットの改善が図られています。

Search Relevance WorkbenchのLLM-as-a-Judgeは、ML Commonsコネクターを通じてAmazon Bedrockやその他のLLMプロバイダーを利用できるようになりました。失敗したドキュメントの再試行、評価の編集、過去の判定の再利用にも対応し、LLM呼び出しの繰り返しを抑えられます。

さらに、モデル推論とエージェント実行でgRPCストリーミングを利用できます。生成結果をトークン単位で受け取れるため、アプリケーションは回答を生成途中から表示できます。新しいリソース共有・アクセス制御フレームワークでは、異常検知器や機械学習モデルなどを特定のユーザーやロールと共有し、広範な権限付与を避けられます。

### 影響範囲・利用シーン

- **対象ユーザー**: OpenSearchの運用担当者、検索・データエンジニア、生成AI／エージェントアプリケーションの開発者
- **利用シーン**: 大規模なベクトル検索インデックスの省メモリ化、LLMを用いた検索品質評価、生成中の回答表示、MLリソースのユーザー間共有
- **運用効果**: 圧縮方式を選んでベクトル検索のコストと検索品質を調整でき、LLM呼び出しの再利用やきめ細かな共有権限によって運用効率とアクセス管理を改善できます
- **リージョン**: Amazon OpenSearch Serviceが提供されているすべてのAWSリージョンで利用可能です
- **コスト**: ベクトルのメモリ・ストレージ削減は関連コストの低減につながる可能性がありますが、実際の費用はドメイン構成、利用量、LLMプロバイダーの料金などに依存します。

### 技術的な注意点

- **アップグレード**: 適用前にAmazon OpenSearch Serviceのアップグレード手順を確認し、互換性や移行要件を検証してください
- **ベクトル量子化**: 2ビット／4ビット量子化や16ビット表現は、圧縮率とrecallのトレードオフがあるため、実データと検索条件で品質を評価してください
- **LLM接続**: Bedrockやその他のLLMプロバイダーとの接続では、ML Commonsコネクターの設定と必要な認証情報・権限を確認してください
- **gRPCストリーミング**: クライアント側がgRPCストリーミングに対応している必要があります
- **アクセス制御**: 共有対象のユーザー／ロールとリソース権限を適切に設定し、必要最小限のアクセスにしてください
- **リージョン制限**: 記事によると、OpenSearch Service提供中の全AWSリージョンで利用可能です

## [General] AWS WAF introduces simplified pricing

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-waf-introduces-simplified-pricing/

### 概要

AWS WAFの料金体系が、Web ACLやルールの数ではなく、保護対象リソース・検査するリクエスト・適用する保護レベルに基づく方式に変更されました。ルールの追加や変更による料金変動を抑え、導入前にコストを見積もりやすくします。

### 変更内容・新機能の詳細

新しい料金は、主に次の3要素で構成されます。
・保護対象リソース料金: AWS WAFで保護するリソースごとに発生します。
・基本リクエスト料金: AWS WAFが検査するリクエストごとに発生します。
・プレミアムリクエスト料金: Bot Controlのターゲット保護、Fraud Control、API Security、AI Securityなど、高度な保護機能で評価されたトラフィックに対して発生します。
各Web ACLには最大2,500 WCU（Web ACLのルール処理能力を表す単位）が追加料金なしで含まれます。記事によると、従来の1,500 WCUから増加しています。また、Bot Controlの共通保護やAnti-DDoSルールグループを追加しても追加料金は発生しません。新料金では、ルールの追加や変更そのものでは料金が変わらず、保護するリソース、検査リクエスト数、高度な保護機能の利用状況がコストを左右します。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS WAFを利用中、または導入を検討しているクラウド運用チーム、セキュリティ担当者、コスト管理担当者
- **利用シーン**: WebアプリケーションやAPIの保護コストを導入前に見積もる場合、既存のWeb ACLにルールを追加・変更する場合
- **運用効果**: ルール構成の変更による料金変動が抑えられ、保護内容とコストの関係を把握しやすくなります
- **料金への影響**: 保護対象リソース数と検査リクエスト数に加え、高度な保護機能で評価されるトラフィックに応じて料金が発生します

### 技術的な注意点

- **WCU**: 各Web ACLに最大2,500 WCUが追加料金なしで含まれます。WCU上限やルールの要件は、利用する機能に応じて確認してください
- **追加料金**: Bot Controlの共通保護やAnti-DDoSルールグループは追加料金なしとされていますが、高度な保護機能の対象トラフィックにはプレミアムリクエスト料金が発生します
- **料金確認**: 具体的な単価はリージョンや利用状況に応じてAWS WAF料金ページで確認してください。実際の費用見積もりでは保護リソース数、リクエスト数、高度な保護機能の適用範囲を考慮してください
- **提供リージョン**: 記事によると、AWS商用リージョン、AWS GovCloud、AWS中国リージョン、AWS Isolated Regionsで利用可能です

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/aws-waf-introduces-simplified-pricing/
- https://aws.amazon.com/waf/pricing/
- https://docs.aws.amazon.com/waf/latest/developerguide/what-is-aws-waf.html

## [API Gateway] AWS WAF announces automated discovery and protection for LLM, MCP, and A2A endpoints using Amazon Bedrock Guardrails

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: API Gateway
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/waf-ai-endpoint-discovery-protection/

### 概要

AWSは、AWS環境内のLLM・MCP・A2Aエンドポイントを自動検出し、AWS WAFで保護する機能を一般提供しました。API Gateway API Portalによる検出と、Amazon Bedrock Guardrailsを利用するAWS WAF AI Securityマネージドルールグループによる保護を組み合わせ、独自ルールを作成せずにAIエンドポイントの発見から防御まで行えます。

### 変更内容・新機能の詳細

API Gateway API Portalは、AWS Organization内のAmazon API Gateway、Application Load Balancer、Amazon CloudFrontの背後にあるAPIを、トラフィックログやサービス設定情報から自動的に検出します。そのうちLLM、Model Context Protocol（MCP）、Agent2Agent（A2A）に関係するエンドポイントを識別し、文書化されていない公開MCPサーバーなども「シャドーAPI」として把握できます。エージェントの導入やログの転送は不要です。

未保護のAIエンドポイントには、AWS WAF AI Securityマネージドルールグループを適用できます。同ルールグループはMCPおよびA2Aのプロトコルを認識し、不正な形式のメッセージやプロトコル準拠違反をブロックします。コンテンツ検査を有効にすると、Amazon Bedrock GuardrailsのInvokeGuardrailsCheck APIを呼び出し、リクエスト内のプロンプトインジェクション、ジェイルブレイクの試み、有害な内容や、レスポンス内の機密情報を検出します。AWS Managed Rulesや独自のWAFルールと併用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: API Gateway、Application Load Balancer、CloudFrontでAI関連APIを公開している開発者、セキュリティ担当者、クラウド運用チーム
- **利用シーン**: AWS Organization内のLLM・MCP・A2Aエンドポイントや、未登録の公開MCPサーバーを発見し、AWS WAFで保護する
- **運用効果**: エージェント導入やログ転送、独自ルールの作成を行わずに、AIエンドポイントの把握からプロトコル検査・コンテンツ検査まで一貫して実施できる
- **提供リージョン**: API Gateway API Portalは32リージョンで利用可能です。AWS WAF AI Securityは米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（ロンドン、ストックホルム）、アジアパシフィック（東京、シドニー）で利用できます。機能ごとにリージョン提供状況が異なります。
- **コスト**: AWS WAFの追加料金が発生し、コンテンツ検査で利用するAmazon Bedrockの呼び出し料金も別途発生します。

### 技術的な注意点

- **検出対象**: API Gateway API Portalはトラフィックログとサービス設定情報を利用してAPIを検出します。エージェントの導入やログの転送は不要です。
- **コンテンツ検査**: Amazon Bedrock GuardrailsのInvokeGuardrailsCheck APIを利用します。コンテンツ検査を有効にした場合は、Bedrock側の料金も発生します。
- **リージョン制限**: API PortalとAWS WAF AI Securityの提供リージョンは異なります。AI Securityを利用する環境が対応リージョンにあることを事前に確認してください。
- **ルール構成**: AI SecurityはAWS Managed Rulesやカスタムルールと併用できます。既存のWAF Web ACLへの追加を含め、適用対象とルールの優先順位を確認してください。

- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-cloudfront-http2-origins/

### 概要

Amazon CloudFront が、カスタムオリジンおよび VPC オリジンへの接続で HTTP/2 をサポートしました。複数のリクエストを少ない接続で送信できるため、オリジン側の接続負荷や TLS ハンドシェイクを減らし、応答性能の向上が期待できます。

### 変更内容・新機能の詳細

従来、CloudFront からオリジンへの接続は HTTP/1.1 のみで、1つの接続で同時に処理できるリクエストが限られていました。HTTP/2 では複数のリクエストを少数の接続上で多重化できるため、リクエストが集中した場合もオリジンが処理する接続数や TLS ハンドシェイク数を抑えられます。API 呼び出しや、AI エージェントから MCP サーバーへの複数のツール呼び出しなど、短時間に多くのリクエストが発生するワークロードで効果が見込まれます。拡張 CONNECT に対応する WebSocket 接続でも HTTP/2 を利用できます。オリジンが HTTP/2 に対応していない場合、CloudFront は自動的に HTTP/1.1 にフォールバックします。

### 影響範囲・利用シーン

- **対象ユーザー**: CloudFront のカスタムオリジンまたは VPC オリジンを利用するアプリケーション開発者、インフラ・運用担当者
- **利用シーン**: API バックエンド、AI エージェントと MCP サーバー間の通信、モバイル・Web アプリからのバックエンド呼び出し、拡張 CONNECT 対応 WebSocket
- **運用効果**: オリジンへの接続数や TLS ハンドシェイクを削減し、リクエスト集中時のオリジン負荷低減と応答性能向上が期待できます
- **提供範囲**: すべての CloudFront エッジロケーションで利用可能です
- **コスト**: HTTP/2 によるオリジン接続に追加料金はありません

### 技術的な注意点

- **オリジン要件**: HTTP/2 を利用するには、オリジンが HTTP/2 に対応している必要があります。未対応の場合は HTTP/1.1 に自動的にフォールバックします
- **WebSocket**: HTTP/2 での WebSocket 接続には、オリジン側が拡張 CONNECT に対応している必要があります
- **設定確認**: 利用するオリジンの HTTP バージョンに関する設定や要件を CloudFront Developer Guide で確認してください
- **リージョン制限**: すべての CloudFront エッジロケーションで利用可能です
- **コスト**: HTTP/2 のオリジン接続による追加料金はありません

## [RDS] Amazon Aurora serverless for MySQL now supports up to 384 ACUs 

- **公開日**: 2026-11-24 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-serverless-mysql-supports-384-acu/

### 概要

Aurora Serverless for Aurora MySQL-Compatible Edition の最大容量が、従来の256 ACUから384 ACUに拡大しました。最大768 GiB相当のメモリを利用でき、利用状況に応じたスケーリングと、アイドル時のゼロまでの縮小に対応します。

### 変更内容・新機能の詳細

1 ACUは約2 GiBのメモリと、それに対応するCPU・ネットワーク性能を提供します。最大384 ACUでは、データベース容量を最大768 GiB相当まで拡張できます。新規クラスターでは、対応するAurora MySQLエンジンバージョンを選択し、最大容量を384 ACUまで設定します。既存クラスターは、Platform Version 4であれば最大容量を変更でき、必要に応じてエンジンバージョンも更新できます。Platform Version 4より古いクラスターは、保留中のメンテナンスアクションを通じてPlatform Version 4へアップグレードします。

### 影響範囲・利用シーン

- **対象ユーザー**: Aurora Serverless for Aurora MySQLを利用するアプリケーション開発者、データベース管理者、運用チーム
- **利用シーン**: エージェント型AIなど、負荷が突発的に増加し、長いアイドル時間や予測しにくいトラフィックを伴うワークロード
- **運用効果**: 最大容量が50%増加し、より大きな負荷にも対応しやすくなります。アイドル時は容量をゼロまで縮小し、使用した容量に応じた課金を継続できます。

### 技術的な注意点

- **対応バージョン**: Aurora MySQL 3.14および8.4.10が対象です
- **プラットフォーム要件**: 384 ACUの利用にはPlatform Version 4が必要です
- **既存クラスターの変更**: Platform Version 4上のクラスターは、最大容量の変更時にダウンタイムは発生しません。古いプラットフォームバージョンの場合は、Platform Version 4へのアップグレードが必要です
- **容量の目安**: 1 ACUあたり約2 GiBで、384 ACUは最大768 GiB相当です
- **リージョン制限**: 提供リージョンはリージョンごとに異なるため、Auroraの料金ページで確認してください
- **コスト**: 使用した容量に応じた料金が適用されます。利用リージョンや構成に応じた料金を事前に確認してください

- https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless-v2.html
