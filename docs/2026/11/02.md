## [Ec2] EC2 Amazon Machine Images can now be scanned for vulnerabilities through Amazon Inspector

- **公開日**: 2026-11-02 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/ec2-amis-scanned-through-inspector/

### 概要

Amazon InspectorがEC2のAmazon Machine Images（AMIs）に対する脆弱性スキャンをサポートしました。インスタンスを起動したりエージェントを導入せずにAMIsのソフトウェア脆弱性を検出でき、デプロイ前に問題を是正できます。

### 変更内容・新機能の詳細

新機能により、Amazon InspectorはAMIsの内容を直接解析してOSパッケージやライブラリに対する既知の脆弱性（CVE等）を検出します。インスタンスを起動する必要がなく、継続的評価（AMIカタログを常時監視して新たに発見された脆弱性に再評価）や特定のAMIに対するワンタイムスキャンをEC2コンソールから実行可能です。アカウント単位または組織全体でAMIスキャンを有効化でき、Security Hubを利用している場合は組織全体のアドオンとして有効化し、検出結果をSecurity Hubへ連携できます。検査結果に基づき「Allowed AMIs」設定を有効化して、AMIsが満たすべきセキュリティ基準（例：許容する最大脆弱度レベルや禁止すべきCVEの有無）を定義し、Declarative Policiesを使って組織全体で強制できます。EC2 Image Builderと統合すれば、AMIビルドパイプライン内でスキャンを組み込み、基準を満たさないAMIの配布を自動的に制限することが可能です。結果はInspectorコンソール、EC2コンソール、Security Hub、ならびにAPI/CLIを通じて取得でき、既存のCI/CDや運用自動化と組み合わせて早期検出・修正（shift-left）を実現します。なお、本機能はAmazon Inspectorが利用可能な全ての商用リージョンで提供されます。

### 影響範囲・利用シーン

- **対象ユーザー**: セキュリティチーム、クラウド/プラットフォームエンジニア、SRE、CI/CD担当者
- **利用シーン**: AMIを配布する前の脆弱性検査（ビルドパイプライン内のゲート）、既存AMIカタログの継続的なリスク監視、組織全体でのセキュリティ基準適用
- **運用効果**: インスタンス起動前に問題を修正できるため、脆弱なイメージの展開リスクを低減し、運用後の対応コストを削減
- **組織管理**: 組織単位でのスキャン有効化・「Allowed AMIs」設定とDeclarative Policiesによる一元管理が可能で、ガバナンスを強化
- **統合効果**: EC2 Image Builderや既存CI/CDと組み合わせることで自動的な不適合AMIのブロックや通知が可能
- **コスト影響**: Inspectorのスキャンに基づく利用料やSecurity Hubアドオン料金が発生する可能性があるため、コスト設計が必要

### 技術的な注意点

- **IAM権限**: Inspector、EC2、Organizations、Security Hubを操作・閲覧するための適切なIAM権限（サービスロールや組織レベルの権限）を事前に確認・付与してください
- **リージョン制限**: 本機能はAmazon Inspectorが利用可能な商用リージョンで提供されます。利用前に対象リージョンでInspectorの提供状況を確認してください
- **コスト**: Amazon Inspectorのスキャン・検出結果の保存やSecurity Hubアドオンには料金が発生する可能性があります。事前にInspectorの料金ページで課金モデルを確認してください
- **スキャン方式**: インスタンス起動やエージェント不要でAMIの内容を解析しますが、詳細な検出対象（OSパッケージ、言語ライブラリ等）や検出ルールはInspector側の定義に依存します
- **出力と連携**: 検出結果はInspectorとSecurity Hubに送られ、API/CLI/コンソールから取得可能。CI/CDやImage Builderと組み合わせて自動化する場合はAPI/イベント連携を利用してください
- **Declarative Policies**: 「Allowed AMIs」設定を組織全体へ強制するには組織管理者権限やInspector側のポリシー設定が必要です。実運用前に適用範囲と例外ハンドリングを設計してください
- **既存パイプライン統合**: Image Builderやパイプライン内でのブロック・通知設定を行う場合、スキャン結果に基づく自動化（例：ビルド失敗、配布停止）を実装する必要があります

## [General] Amazon Textract now available in Asia Pacific (Tokyo) and Europe (Zurich)

- **公開日**: 2026-11-02 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/textract-tokyo-zurich/

### 概要

Amazon TextractがAsia Pacific (Tokyo)およびEurope (Zurich)リージョンで利用可能になりました。これにより、テキスト検出とドキュメント解析APIをローカルリージョンで利用できます。

### 変更内容・新機能の詳細

Amazon Textractは機械学習を用いてスキャン文書から印字・手書きテキストや構造化データを抽出するサービスで、従来のOCRを超えてフォームや表の解析も行います。今回のリージョン追加時点でサポートされる操作は、同期系のDetectDocumentText、AnalyzeDocumentと、非同期ジョブを開始／取得するStartDocumentTextDetection、GetDocumentTextDetection、StartDocumentAnalysis、GetDocumentAnalysisです。AnalyzeExpense、AnalyzeID、AnalyzeLending、およびCustom Queries（アダプタ）はこれらのリージョンでは未対応です。今回の追加によりTextractは合計18リージョンで利用可能となり、利用前にリージョンごとのAPI対応状況、エンドポイント、クォータ、料金を確認する必要があります。非同期APIはジョブIDを用いた取得やSNS/SQS連携などの実装が必要となる点に注意してください。

### 影響範囲・利用シーン

- **対象ユーザー**: ドキュメント処理を行うアプリケーション開発者、データエンジニア、SRE/運用チーム
- **利用シーンまたは効果**: ローカル（東京/チューリッヒ）リージョンでのスキャン文書からのテキスト/構造化データ抽出、レイテンシ短縮やデータレジデンシ要件の対応
- **運用効果**: リージョン内での処理によりネットワーク越しの転送を減らし、応答性・セキュリティ・コンプライアンス要件の順守を向上
- **制約**: 東京/チューリッヒではExpense/ID/Lending解析やCustom Queriesが未対応のため、それら機能に依存するワークフローは利用不可または別リージョン利用が必要

### 技術的な注意点

- **IAM権限**: Textract API呼び出しに加え、文書をS3に置く場合はS3の読み取り権限（s3:GetObject等）が必要です。非同期処理でSNS/SQSを使う場合はそれらの権限も必要になります
- **リージョン制限**: TokyoおよびZurichではDetectDocumentText/AnalyzeDocument系の基本APIと非同期ジョブのみサポート。AnalyzeExpense、AnalyzeID、AnalyzeLending、Custom Queriesは未対応です
- **コスト**: APIごとに課金体系が異なります（同期/非同期、ページ単位など）。大量処理や非同期ジョブの利用はコスト増につながるため事前に料金ページで確認してください
- **エンドポイント/クォータ**: 各リージョンのエンドポイントやAPIクォータに差異がある可能性があるため、導入前に確認してください
- **データ保護/コンプライアンス**: データは指定リージョン内で処理されますが、保存・転送の要件に応じてS3バケットの場所や暗号化、アクセス制御を設計してください

## [EKS] Announcing AWS for Fluent Bit 3.0.0 based on Fluent Bit 4.1.1

- **公開日**: 2026-11-02 (JST)
- **カテゴリ**: EKS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2025/10/aws-fluent-bit-3-0-0-based-4-1-1

### 概要

AWS for Fluent Bit がバージョン 3.0.0 にアップデートされ、Fluent Bit 4.1.1 と Amazon Linux 2023 ベースイメージを採用しました。コンテナログ収集のパフォーマンス向上、OpenTelemetry のネイティブ対応（OTLP）、および TLS 周りのセキュリティ強化が主な変更点です。

### 変更内容・新機能の詳細

主な変更点
- Fluent Bit のバージョンを 4.1.1 に更新：JSON パース高速化や vCPU あたりの処理数向上、レイテンシ低下といったパフォーマンス改善が含まれます。
- ベースイメージを Amazon Linux 2023 に更新：OS レベルのセキュリティ・パッチとサポートの恩恵を受けます。
- OpenTelemetry (OTel) ネイティブサポート：OTLP プロトコルでのログ/メトリクス/トレースの受信および転送をサポートし、AWS SigV4 認証を用いた送信が可能です（記事更新によりサポート範囲は明確化されています）。
- TLS 制御の強化：出力先への TLS 最小バージョンや許可する暗号スイートを設定可能になり、組織の TLS ポリシーを適用できます。
- 配布と入手方法：AWS for Fluent Bit 3.0.0 イメージは Amazon ECR Public Gallery と Amazon ECR に公開されており、ソースや追加ガイダンスは GitHub リポジトリで確認できます。
導入方法（概要）
- Amazon ECS：タスク定義内の FireLens（log-router）コンテナのイメージタグを 3.0.0 に更新してデプロイします。
- Amazon EKS：Helm リリースをアップグレードするか、DaemonSet のイメージを 3.0.0 に変更して適用します。
互換性・移行のポイント
- Fluent Bit のマイナーバージョンアップに伴い、プラグイン設定や構成オプションの挙動が変わる場合があります。既存のフィルタ/出力設定は検証のうえ本番へ反映してください。
- SigV4 を用いる送信先（CloudWatch Logs、Kinesis、Firehose、S3 など）へは、適切な実行ロール/認証設定（ECS のタスクロール、EKS の IRSA など）が必要です。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon ECS/EKS を利用する開発者、SRE、ログ/観測基盤担当
- **利用シーン**: コンテナログの収集・加工・転送（CloudWatch Logs、Data Firehose、Kinesis Data Streams、S3 など）、OTLP を介した OpenTelemetry データの受け渡し
- **運用効果**: JSON パース高速化と vCPU あたりの処理向上によりログ処理性能が改善され、CPU コスト削減や低レイテンシ転送が期待できる
- **セキュリティ効果**: TLS 最小バージョンや暗号スイート制御により送信時のプロトコル姿勢（protocol posture）が強化され、コンプライアンス対応が容易になる
- **移行作業影響**: ECS はタスク定義の FireLens イメージ更新、EKS は Helm/DaemonSet 更新が必要で、事前に設定互換性検証が推奨される

### 技術的な注意点

- **IAM権限**: SigV4 での送信や各出力先（CloudWatch Logs、Kinesis、Firehose、S3）への書き込みには適切な実行ロール（ECS タスクロール、EKS の IRSA）やポリシーが必要です。ECR からプライベートイメージを取得する場合はイメージプル権限も必要です。
- **リージョン制限**: AWS for Fluent Bit 自体は Amazon ECR Public Gallery で公開されていますが、プライベートな Amazon ECR レポジトリを利用する場合や出力先サービスのエンドポイントはリージョン固有です。導入先リージョンでのエンドポイント/リージョン対応を確認してください。
- **互換性**: Fluent Bit 4.1.1 へのアップグレードにより一部のプラグイン設定やフィルタの挙動が変わる可能性があります。既存の構成をステージ環境で検証し、設定ファイル（parsers、filters、outputs）の互換性チェックを行ってください。
- **OpenTelemetry 範囲**: 記事更新によりサポート範囲が明確化されています。OTLP（logs/metrics/traces）の受信と転送をサポートしますが、利用する受信/送信エンドポイントの認証方式やフォーマット（例：SigV4 対応の有無）を事前確認してください。
- **TLS 設定**: TLS の最小バージョンや暗号スイートを厳格に設定すると、古いエンドポイントや中間機器との互換性問題が発生する場合があります。出力先で許容される TLS 設定を確認してください。
- **コスト**: エージェント自体の利用に追加料金は通常ありませんが、転送先サービス（CloudWatch Logs、Kinesis、Firehose、S3 等）の利用料金や、ログ量増加によるネットワーク/ストレージコストは発生します。パフォーマンス改善により CPU 使用料は低下する可能性があります。

## [CloudFront] Amazon CloudFront now supports self-service increases in AWS Service Quotas

- **公開日**: 2026-11-02 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-self-service-quotas/

### 概要

Amazon CloudFrontがService Quotasに対応し、CloudFrontの28のクォータ（上限）をService Quotasコンソール/APIから表示・監視・増枠申請できるようになりました。Business Support以上の契約では、公開された閾値内の増枠申請は自動承認されます。

### 変更内容・新機能の詳細

技術的には、CloudFrontの28個のリソースクォータ（例：ディストリビューション数、キャッシュポリシー数、オリジン数、ディストリビューションあたりの代替ドメイン名数など）がAWS Service Quotasに登録され、Service QuotasコンソールまたはService Quotas API/CLI（aws service-quotas）から現在値の確認、増枠リクエストが可能になりました。これまで増枠はサポートケースを開く必要があり手動レビューを伴っていましたが、AWS Business Support以上のサポートプランを契約している場合、公開された増枠閾値内のリクエストは自動的に承認されます（例：ディストリビューション上限を500→1,000、ディストリビューション当たりの代替ドメイン名を100→500へ増加）。さらに、一部のクォータについては使用率メトリクスが5分ごとにAmazon CloudWatchへ出力されるため、アラームを設定して上限到達前に増枠をトリガーすることができます。本機能はCloudFrontがサポートされるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: CloudFrontを大量に利用するSRE/インフラチーム、CDNをスケールさせるプロダクトチーム、運用担当者
- **利用シーン**: ディストリビューションやオリジンの大規模展開、マルチドメイン運用、トラフィック増加に伴う上限変更、オートスケール前の事前増枠準備
- **運用効果**: サポートケースによる手動プロセスを削減し、Business/Enterprise契約では公開閾値内の増枠が自動承認されるため迅速にスケール可能。CloudWatchメトリクス連携により上限到達前にアラート→増枠申請の自動化運用がしやすくなる

### 技術的な注意点

- **IAM権限**: Service Quotas関連のAPIを使うには service-quotas:ListServiceQuotas、service-quotas:RequestServiceQuotaIncrease 等の権限が必要。CloudWatchメトリクス確認やアラーム作成には cloudwatch:GetMetricData 等の権限も必要。
- **サポートプラン**: 自動承認はAWS Business Support以上が対象。無い場合は従来どおりサポートケースでの手動レビューとなる可能性が高い。
- **増枠の範囲**: 公開された閾値内は自動承認だが、閾値を超える要求や特殊なケースは引き続き手動レビュー/サポートケースが必要となる。
- **CloudWatchメトリクス**: 一部クォータのみ5分間隔でメトリクスを出力。すべてのクォータでメトリクスが出るわけではないため、対象クォータはService Quotas/ドキュメントで確認すること。
- **リージョン制限**: 本機能はCloudFrontがサポートされる全リージョンで利用可能とされている。ただしCloudFrontはグローバルサービスの側面があり、クォータの適用範囲（グローバル/リージョン）はクォータ毎に異なるため確認が必要。
- **コスト**: Service Quotasの使用自体に追加料金は通常発生しないが、増枠によりリソースを増やすとCloudFront使用料や、それに伴うCloudWatchのメトリクス/アラーム利用料金が増加する可能性がある。
- **API/CLI**: 増枠はService Quotasコンソールのほか、Service Quotas API/CLIで自動化可能（aws service-quotas request-service-quota-increase）。
- **注意事項**: 大幅な増枠や特殊なリクエストは自動承認の対象外となることがあるため、事前にドキュメントとService Quotasの閾値説明を確認すること。

## [Textract] Announcing an updated text detection model for Amazon Textract

- **公開日**: 2026-11-02 (JST)
- **カテゴリ**: Textract
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/textract-text-detection-model/

### 概要

Amazon Textractのテキスト検出モデルが更新され、精度向上と多言語対応の拡張、テーブル抽出の耐性強化を提供します。既存のDetectDocumentTextおよびAnalyzeDocument APIをそのまま利用でき、アプリケーション側の変更は不要です。

### 変更内容・新機能の詳細

今回の更新はTextractのテキスト検出モデル自体の改善で、DetectDocumentTextおよびAnalyzeDocumentの呼び出しに自動適用されます（APIリクエスト／レスポンスのスキーマや呼び出し方に変更はありません）。主な技術的変更点は以下の通りです：
- 言語サポートの拡張: 40以上の言語（アルバニア語、アラビア語、バスク語、ベラルーシ語、ボスニア語、ブルガリア語、中国語（簡体/繁体）、クロアチア語、チェコ語、デンマーク語、オランダ語、英語、エストニア語、フィンランド語、フランス語、ドイツ語、ヘブライ語、ヒンディー語、ハンガリー語、アイスランド語、イタリア語、日本語、韓国語、ラトビア語、リトアニア語、ルクセンブルク語、ノルウェー語、ポーランド語、ポルトガル語、ルーマニア語、ロシア語、セルビア語（キリル/ラテン）、スロバキア語、スロベニア語、スペイン語、スウェーデン語、トルコ語、トルクメン語、ウクライナ語 等）を新たに安定的に処理可能にしています。
- 精度改善: 長い単語の認識精度向上、手書きテキスト（handwriting）の検出精度改善を含みます。
- テーブル抽出の強化: マージセル（結合セル）、傾き・回転したテーブル、部分的または損傷したテーブルに対する多言語テーブル抽出の堅牢性が向上しました。
- 導入方法: 既存呼び出しはそのまま継続可能で、モデル切替や追加パラメータは不要。アプリ側でのコード変更は不要です。
- 可用性: Amazon Textractが利用可能な全リージョンで更新モデルが利用可能とされています。
これらの改善により、請求書・フォーム・身分証明書など多言語・複雑な文書の大規模処理における誤検出削減や自動化精度の向上が期待できます。

### 影響範囲・利用シーン

- **対象ユーザー**: ドキュメント処理を行うSRE/開発者、データエンジニア、RPA/ワークフロー構築担当者
- **利用シーン**: 請求書や注文書のOCR自動化、フォーム項目抽出、身分証明書や申請書類の解析、複数言語を含む帳票やテーブルの抽出
- **運用効果**: 認識精度の向上により手動修正が減り自動化率が向上、テーブル抽出の堅牢性向上でデータ欠落や誤結合が減少
- **スケーラビリティ**: 既存API呼び出しをそのまま利用可能なため、既存運用・バッチ処理への影響は小さく、短期的な改修不要で恩恵を受けられる
- **多言語対応の恩恵**: 従来未サポートだったスクリプトや言語を含むワークロードでの採用が容易に（グローバル処理パイプラインでの適用が加速）

### 技術的な注意点

- **互換性**: APIのリクエストおよびレスポンススキーマに変更はなく、既存コードはそのまま動作します
- **IAM権限**: 既存のTextract向けIAMポリシー（textract:DetectDocumentText, textract:AnalyzeDocument等）で引き続きアクセス可能です
- **リージョン制限**: 発表では"Textractが利用可能な全リージョンで利用可能"とされており、基本的にリージョン依存の制限はありません。利用中のリージョンで未対応の場合はサービスページで確認してください
- **コスト**: モデル更新自体に別途料金は明示されていません。課金は従来通りのTextractのAPI呼び出し単位（ページ単位等）に基づきますが、精度向上により再処理や手作業が減れば総コストは低下する可能性があります
- **テスト推奨**: 本番適用前に代表的な文書サンプルで検証し、抽出精度・フォーマット（テーブルセル結合や座標情報）を確認してください
- **フォールバック設計**: 手書きや非常に損傷した文書に対しては事前フィルタ（画像前処理）や後処理ルール、検出信頼度に基づくヒューマンインザループを検討してください
- **ログ/監視**: 抽出結果の品質指標（誤認識率、未検出率）を継続的に監視し、必要に応じてワークフローを調整してください
