## [S3] Amazon S3 Access Grants now support listing grants across multiple AWS accounts

- **公開日**: 2026-11-10 (JST)
- **カテゴリ**: S3
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-s3-access-grants-list-across-regions/

### 概要

Amazon S3 Access Grantsで、AWSアカウント間で共有された全てのAccess Grantsを単一API呼び出しで一覧できるようになりました。これにより、各アカウントを個別に問い合わせる必要がなくなります。

### 変更内容・新機能の詳細

ListCallerAccessGrants APIに新しいパラメータ InstanceScope を追加し、これを ALL に設定することで、自分のS3 Access GrantsインスタンスとAWS Resource Access Manager（AWS RAM）を通じて共有されたすべてのインスタンスを横断してグラントを検索・一覧化します。レスポンスは各グラントごとに所有アカウントを識別する情報を含む結合されたリストとして返されます。さらに、GetDataAccess APIで InstanceScope=ALL を指定してS3パスに対する認証情報を要求すると、S3 Access Grantsが対象の所有アカウントを自動検出してそのインスタンスへリクエストをルーティングし、該当するグラントに対応する認証情報（短期クレデンシャル等）を返します。この機能はS3 Access Grantsが利用可能な全リージョンで追加料金なしに利用可能で、AWS SDK、API、CLIから利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドセキュリティ/アクセス管理者、データプラットフォーム担当者、SRE/運用チーム
- **利用シーン**: 複数AWSアカウントに跨るS3データアクセス権の可視化、横断的なアクセス権監査、アプリケーションが参照できるS3パスに対する短期認証情報の取得
- **運用効果**: 各アカウントを個別に問い合わせる手間が不要になり、アクセス権の集約確認やトラブルシューティングが効率化される。アクセス情報の一括取得により監査・レポーティングが容易になる

### 技術的な注意点

- **IAM権限**: ListCallerAccessGrants, GetDataAccess等のアクセス権（例: s3-access-grants:ListCallerAccessGrants, s3-access-grants:GetDataAccess）を付与する必要があります。所有アカウント側で該当インスタンスがRAMで共有されていることが前提です。
- **InstanceScope**: ListCallerAccessGrants/GetDataAccessのInstanceScopeパラメータに ALL を指定すると、共有されたすべてのインスタンスを横断します。デフォルトのスコープ（自身のみ）とは挙動が異なります。
- **AWS RAM依存**: 他アカウントのインスタンスを列挙・利用するためには、そのインスタンスがAWS RAMで明示的に共有されている必要があります。共有されていないインスタンスのグラントは返りません。
- **リージョン制限**: S3 Access Grantsが利用可能なリージョンで有効です。全リージョン対応ではなく、サービス未対応リージョンでは利用できません。最新の対応リージョンは公式ページで確認してください。
- **コスト**: 発表時点では追加料金なしで利用可能です。ただし、関連するAPI呼び出しや認証トークン発行に伴う通常のリソース利用（例: S3アクセス、データ転送等）は別途発生する可能性があります。
- **互換性/SDK・CLI**: SDK/CLIでInstanceScopeパラメータをサポートするバージョンが必要です。古いクライアントではパラメータを指定できない場合があるため、SDK/CLIの最新版を使用してください。
- **セキュリティ影響**: この機能はグラント情報の集約表示と短期クレデンシャル発行を簡便にしますが、アクセス権の横断的な可視化は権限付与設計の見直しを促すため、適切な最小権限と監査ログ（CloudTrail等）の確認を推奨します。
- **既存のアクセス制御との関係**: この変更はS3のバケットポリシーやIAMポリシー、オブジェクトACLの挙動を直接変更するものではありません。Access Grants経由で付与されるアクセスは、該当するグラントの条件に従います。

## [Bedrock] Amazon Bedrock adds bedrock-runtime endpoint support for Daybreak models

- **公開日**: 2026-11-10 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/openai-gpt-daybreak-on-amazon-bedrock-runtime/

### 概要

OpenAIのセキュリティ特化モデル Daybreak Blue (GPT-5.6 Sol) と Daybreak Red (GPT-5.6 Cyber) が、対象顧客向けにAmazon Bedrockの bedrock-runtime エンドポイントで利用可能になりました。利用にはOpenAI側のDaybreakアクセス登録とAWSアカウントチーム経由の申請が必要です。

### 変更内容・新機能の詳細

Daybreak Blue（GPT-5.6 Sol）は防御系ワークフロー（脆弱性発見、検出エンジニアリング、インシデント対応など）向けの出発点として設計されています。Daybreak Red（GPT-5.6 Cyber）は脆弱性調査、脆弱性再現、緩和策開発など高度で許可された作業向けに設計されており、拒否閾値を低く設定する代わりに、強化された本人確認、監査、アクセス制御が求められます。bedrock-runtime エンドポイントでは、USおよびGlobalのクロスリージョン推論（CRIS）プロファイルを通じてこれらのモデルにアクセスできます。推論データはモデル学習に使用されず、OpenAIへのデータ共有のオプトインは不要です。DaybreakアクセスはOpenAIへの登録が前提で、登録審査後にAWS側でのアクセス付与をアカウントチームと連携して行います。地域単位の提供（bedrock-mantle 経由）や詳細は公式ドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: セキュリティチーム（検出/対応エンジニア、脆弱性研究者、レッドチーム）、MSSP、セキュリティ自動化を導入するSRE/DevSecOps
- **利用シーンまたは効果**: Daybreak Blueは脆弱性発見や検出ルール作成、インシデント対応支援に利用可能。Daybreak Redは許可された脆弱性リサーチやエクスプロイト再現・緩和策設計の迅速化に寄与
- **運用効果**: 高度なセキュリティ調査の精度と速度が向上。Redは低い拒否閾値により深い調査が可能だが、強化された本人確認と監査ログが運用に必要になる
- **導入条件**: OpenAIのDaybreakアクセス登録とAWS側でのアクセス承認が必須。全顧客へ即時開放ではない点に注意

### 技術的な注意点

- **IAM権限**: Bedrockのbedrock-runtimeおよびCRISを使うためのIAM権限（bedrock:InvokeModel など）や関連のKMS/CloudWatch/CloudTrail権限を事前に確認・付与してください
- **リージョン制限**: bedrock-runtimeではUSおよびGlobalのCRISプロファイルで提供。地域別の提供（bedrock-mantle経由）は別途ドキュメント参照／リージョンにより未対応の可能性あり
- **アクセス要件**: OpenAIのDaybreakプログラムへの登録・承認が必要。登録はOpenAIへ、承認後はAWSアカウントチーム経由でアクセス申請を行います
- **データ利用**: 推論データはモデル訓練に使用されないと明示されています。OpenAIへのデータ共有のオプトインは不要です
- **監査・セキュリティ**: Daybreak Redは低い拒否閾値に伴い強化された本人確認、モニタリング、アクセス制御および監査ログを要求する運用プロセスが必要です
- **コスト**: CRISや高性能推論はリージョン間通信や専用料金が発生する可能性があるため、使用前に料金表を確認してください
- **パフォーマンス**: CRIS経由のクロスリージョン推論は遅延やスループット要件に影響する可能性があります。レイテンシ要件が厳しい用途は事前に検証してください

## [Simple Storage Service] Amazon S3 Tables now support S3 server access logging

- **公開日**: 2026-11-10 (JST)
- **カテゴリ**: Simple Storage Service
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-s3-tables-server-access-logging/

### 概要

Amazon S3 Tablesでサーバーアクセスログがサポートされました。S3 Tablesへ行われたリクエストの詳細な記録を、既存のS3サーバーアクセスログと同じ形式で取得できます。

### 変更内容・新機能の詳細

S3 Tablesのテーブルを含む「テーブルバケット」に対してサーバーアクセスロギングを有効化すると、そのバケット内のすべてのテーブルとネームスペースへのリクエストが同じアカウントかつ同リージョン内の一般用途バケットへ配信されます。各ログレコードはリクエスター、操作（operation）、テーブル名、ネームスペース、レスポンスステータス、リクエストのタイミング等をキャプチャし、スペース区切りのS3サーバーアクセスログ形式と互換性があります。これにより既存のログ解析ワークフロー（例：Amazon Athena、DuckDB、任意のクエリエンジン）をそのまま利用できます。ログ配信自体に追加料金はなく、ログファイルの保存に対するS3料金のみ発生します。サポートされるリージョンはS3 Tablesが利用可能なすべてのリージョンで、設定はAWS Management Console、AWS CLI、AWS SDK、AWS CloudFormationから行えます。ログはテーブル操作、ネームスペース管理、データアクセスの監査、アクセス分析、コスト配賦のためのソースデータとして利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドセキュリティ担当者、コンプライアンス/監査チーム、データエンジニア、SRE/運用チーム
- **利用シーンまたは効果**: テーブル操作やネームスペース変更の監査、ユーザー/サービス別のアクセス解析、アクセスに基づくコスト配賦、不正アクセス調査やフォレンジック
- **運用効果**: 既存のS3ログ解析パイプライン（AthenaやDuckDB等）を再利用してS3 Tablesの操作ログを可視化でき、監査・アラート・費用配賦の自動化がしやすくなる
- **コスト影響**: ログ配信自体は追加料金不要だが、ログ保存・クエリ実行（Athena）のS3/クエリ料金および長期保存対策（ライフサイクル）の設計が必要

### 技術的な注意点

- **IAM権限**: ログ出力先バケットへの書き込みをS3が行えるように、出力先バケットの所有者/バケットポリシーで適切な許可（クロスアカウントにする場合は特に注意）を設定してください
- **リージョン制限**: S3 Tablesが提供されているリージョンで利用可能です。同一アカウントかつ同リージョンのバケットへ配信されます
- **ログ配信先設定**: 出力先は一般用途のS3バケット（同アカウント・同リージョン推奨）。出力先のバケットでライフサイクルルールや暗号化（SSE）を設定して保存コストとセキュリティを管理してください
- **ログ遅延**: サーバーアクセスログはリアルタイムではなく配信に遅延（数分〜数時間）が発生する可能性があります。即時監視用途には向きません
- **ログフォーマット**: 出力は既存のS3サーバーアクセスログと同じスペース区切り形式で、リクエスター、操作、テーブル名、ネームスペース、レスポンスステータス、タイミング等を含みます。既存の解析パーサをそのまま利用可能です
- **コスト**: ログファイルのS3保存料金、およびログ解析時のクエリ料金（例: Athena）やデータ取り出し費用が発生します。長期保管の場合はライフサイクルでS3 Intelligent‑Tiering/Glacier等の利用を検討してください

- https://aws.amazon.com/s3/tables/
- https://docs.aws.amazon.com/AmazonS3/latest/userguide/server-access-logging.html

### 技術的な注意点

- **対象製品**: 利用量課金型（usage-based）のSaaSオファーに限定されます。サブスクリプション固定料金型や他カテゴリは対象外の可能性があります
- **試用期間設定**: 販売者側で7日〜90日の範囲で設定可能です（デフォルトや最小/最大は設定画面で確認してください）
- **請求/メータリング**: トライアル終了後はAWS Marketplaceのメータリング/請求サービスにより利用実績に基づいて課金されます。販売者はMetering APIなどの統合状態を確認してください
- **キャンセルルール**: 購入者は変換前はいつでも無料でキャンセル可能です。変換後は利用に応じた請求が発生します
- **設定手順**: 販売者はAWS Partner Centralで新規作成または既存オファーの更新を行います。必要な権限（Partner Centralへのアクセス、オファー編集権限）を事前に確認してください
- **権限（IAM等）**: 販売者側はPartner CentralおよびMarketplace関連APIを扱うためのアカウント権限が必要です。購入者側は特別なIAM設定は不要（Marketplace購読フローに従う）
- **リージョン制限**: パブリックオファーについて、AWS Marketplaceが利用可能なすべてのリージョンで有効とされていますが、国やリージョンの規制、販売者のオファー構成によっては利用不可の場合があります
- **コスト**: 販売者はトライアル期間中の無償提供コスト、変換後の利用料金設定を考慮する必要があります。購入者はトライアル終了後に課金が始まるため、継続利用の意思がなければ事前にキャンセルする必要があります
- **既存オファーの影響**: 既存の無料トライアルを自動変換に変更すると、そのオファーを利用している購読者フローに影響するため、販売者は変更時にドキュメントや通知を整備してください
- **通知**: 購入者へ変換前にリマインダーメールが送られますが、販売者側でも独自の告知（メールやダッシュボード表示）を行うことを推奨します

## [VPC] AWS Network Firewall launches next-generation firewall policy

- **公開日**: 2026-11-10 (JST)
- **カテゴリ**: VPC
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/network-firewall-launches-ngfw-policy/

### 概要

AWS Network FirewallにNGFW（次世代ファイアウォール）ポリシーが追加され、ファイアウォールとIPSを分離した新しいポリシーモデルにより、ルール構造の簡素化とルール容量の拡大が提供されます。既存ポリシーとの互換性を保ちつつ、全ルールがステートフルかつ接続コンテキストで評価されます。

### 変更内容・新機能の詳細

NGFWポリシーはファイアウォール（アクセス制御）とIPS（侵入防止）を重ねて適用するレイヤードモデルを採用します。これにより、アクセス制御ルール（デフォルト拒否のホワイトリスト型ポリシーやドメイン制限など）とIPSルール（署名ベースの検出/阻止）が独立したキャパシティプールを持ち、それぞれのルール数や複雑さを相互にトレードオフする必要がなくなります。IPSについてはAWSやAWS Marketplaceパートナー提供のマネージドルールグループを利用可能で、自動更新により新たな脅威に追従します。カスタムIPSルールグループの作成も可能です。ポリシー内で共有しないルールグループは組み込み（embedded）として作成でき、事前割当てなしにオンデマンドで容量を消費します。全ルールはステートフルで、接続全体のコンテキスト（ソース/宛先/ポート/接続状態など）を基に一貫した評価が行われるため、予測可能なトラフィック処理が可能です。既存のAWS Network Firewallポリシーは変更不要で継続利用でき、IPSルールの後方互換性も維持されます。NGFWポリシー自体は追加料金なしで全商用リージョンおよびAWS GovCloud (US)で利用可能ですが、マネージドルールやマーケットプレイス製品は別途料金が発生する場合があります。

### 影響範囲・利用シーン

- **対象ユーザー**: ネットワーク／セキュリティエンジニア、クラウドSRE、ガバナンス/コンプライアンスチーム
- **利用シーンまたは効果**: VPC境界での厳格なアクセス制御（deny-by-default）と署名ベースの脅威防御を同時に適用したいケース。マネージドルールでゼロデイや新たな脅威に自動対応しつつ、カスタムルールで固有要件に対応可能
- **運用効果**: ルール管理の単純化（ファイアウォールとIPSの分離によりポリシー設計が明確化）とスケーラビリティ向上。ルール容量の競合が解消され、予測可能なパフォーマンスと一貫したトラフィック評価が得られる
- **コスト影響**: NGFWポリシー自体は追加料金不要。ただしAWS Marketplaceやサードパーティのマネージドルールは別途ライセンス/実行コストが発生する可能性あり
- **既存環境への影響**: 既存のポリシーはそのまま継続利用でき、段階的にNGFWポリシーへ移行可能。IPSの後方互換性が維持されるため大規模なルール書き換えは不要

### 技術的な注意点

- **IAM権限**: Create/Update/Delete/Associate系のNetwork Firewall API（例: network-firewall:CreateFirewallPolicy, UpdateFirewallPolicy, CreateRuleGroup, AssociateFirewallPolicy など）の権限が必要です。マネージドルール導入時はMarketplaceやManagedRuleGroup関連のアクセス権や購買権限も確認してください
- **リージョン制限**: 発表では全商用リージョンとAWS GovCloud (US)で利用可能と記載されていますが、利用前にAWS Capabilities by Regionで利用可否を確認してください

## [Security Token Service] AWS STS now supports cross-partition federation for AWS identities

- **公開日**: 2026-11-10 (JST)
- **カテゴリ**: Security Token Service
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-sts-cross-partition

### 概要

AWS STS が異なる AWS パーティション間で IAM アイデンティティを使ったフェデレーション（短期認証情報の取得）をサポートしました。長期キーを保持せずに、あるパーティションの IAM 身元で別パーティションのロールを引き受けられます。

### 変更内容・新機能の詳細

今回の拡張により、ワークロードは自身のパーティション内で短期トークンを AWS STS から取得し（GetWebIdentityToken）、そのトークンを別パーティション側で AssumeRoleWithWebIdentity を呼び出して一時的な AWS 認証情報に交換できます。パーティションは商用（aws）、AWS GovCloud (US)、中国リージョン、AWS European Sovereign Cloud (Germany) 等のグループであり、各パーティションは独立した IAM を持つため従来は強い境界がありました。本機能により、長期アクセスキーに依存することなくクロスパーティションでのアクセスを実現できます。ロール側の信頼ポリシーとアイデンティティの許可設定により、どのアイデンティティがロールを引き受けられるかを制御可能で、両パーティションの AWS CloudTrail でトークン利用を監査できます。既に組織で PKI を運用している場合は IAM Roles Anywhere を代替手段として利用可能です。クロスパーティションフェデレーションは追加料金なしで、商用リージョン、AWS GovCloud (US)、中国リージョン、AWS European Sovereign Cloud (Germany) で利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: マルチパーティションでサービスや運用を行うクラウドエンジニア、セキュリティチーム、SRE、コンプライアンス担当者
- **利用シーン**: 異なるパーティション（例: 商用 ⇄ GovCloud、商用 ⇄ 中国）間での集中化された運用ツール、セキュリティ/コンプライアンス集約、監査用の一時的認証情報付与
- **運用効果**: 長期アクセスキーを削減して秘匿情報漏洩リスクを低減、中央集権的なガバナンスとクロスパーティション監査を実現し、運用と監査の一貫性が向上

### 技術的な注意点

- **IAM権限**: ソース側で短期トークンを取得する際に適切な STS API 呼び出し権限（例: sts:GetWebIdentityToken）と、ターゲット側ロールでの sts:AssumeRoleWithWebIdentity を許可する必要があります。ターゲットロールの信頼ポリシーはソース側アイデンティティを明示的に許可するよう設定してください。
- **リージョン制限**: 機能は商用リージョン、AWS GovCloud (US)、中国リージョン、AWS European Sovereign Cloud (Germany) で利用可能です。各パーティションは独立した IAM を持つためアカウント構造やコンプライアンス要件の確認が必要です。
- **コスト**: クロスパーティションフェデレーション自体に追加料金はありませんが、関連するサービス利用（データ転送、CloudTrail 保存、ログ集約等）には通常の料金が発生します。
- **監査/ログ**: CloudTrail を両パーティションで有効にしておくことで、トークン発行とロール引受けのログを収集できます。クロスパーティションの監査設計を事前に検討してください。
- **互換性/代替**: 組織で PKI を運用している場合は IAM Roles Anywhere が代替となります。既存の ID プロバイダーと連携する場合は、信頼チェーンとトラストポリシーの設定に注意してください。

- **運用効果**: カスタムETLを作らずにSQLで直接分析できるため、導入工数と運用負荷が低減され、コスト最適化や異常検知が迅速に行える
- **リスク/留意点**: 利用データにはクエリテキストやテーブル名など機微情報が含まれる可能性があるため、アクセス制御と保持ポリシーの設計が重要

- **データ遅延**: 利用データは『数分以内』に反映されますが、厳密なリアルタイム要件がある用途では遅延を考慮してください
- **互換性**: データはApache Iceberg形式のため、Iceberg互換のクエリエンジン（DuckDB、Amazon RedshiftのIceberg対応、Amazon EMR等）で照会可能
- **プライバシー/ガバナンス**: クエリ内容に機密情報が含まれる場合は、アクセス権限・ログ保存期間・監査ポリシーを適切に設定してください

Anthropicの最新大規模モデル「Claude Fable 5.2」がAWS上で利用可能になりました。ソフトウェア開発、科学研究、定量ファイナンスなど高い判断力・反復・精度が必要な技術業務向けに最適化されています。

### 変更内容・新機能の詳細

Claude Fable 5.2は、コーディング、数学、科学分野の難易度の高い課題へ対応できる能力を強化したAnthropicの汎用モデルです。長時間（数時間〜数日）にわたる自律的な作業を行えるよう設計されており、複数リポジトリやモノレポに跨る大規模で曖昧なエンジニアリング問題に取り組み、自己テストや結果の再現性チェックを行いながら根本原因を探索します。Anthropicの試験では多数のサブエージェントを協調して統括するリードエージェントとしての運用や、再現しない結果のフラグ付けが可能であることが示されています。Claude Mythos 5.2は同一の基盤モデルで、サイバー／バイオ関連の能力（リスク帯域を含む）を保持し、Anthropicの検証プログラム経由で提供されます。Bedrock上の提供に際して、Fable 5.2／Mythos 5.2は“covered model”に指定されており、安全性監視のためのデータ保持要件があります。ただし、Enterprise Frontier Safeguardsが利用可能になるまでの間、条件を満たす顧客はゼロデータ保持でFable 5.2を利用できるオプションがあります。AWSでのアクセス方法は主にAmazon BedrockとClaude Platform on AWSの二通りで、利用には各プラットフォームのドキュメントやリージョン提供状況を確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: ソフトウェアエンジニア、データサイエンティスト、研究者（ライフサイエンス含む）、クオンツ/ファイナンスエンジニア
- **利用シーンまたは効果**: 大規模リポジトリ横断の自動化的コード改修、複雑な数理解析や実験デザインの補助、定量取引戦略の先端的推論・リスク評価
- **運用効果**: 自律的に長時間稼働して多段階タスクを実行・自己検証するため、人的介入を減らし大規模プロジェクトの生産性を向上
- **制約・リスク**: Mythos系（サイバー/バイオ能力保持）はアクセス制限・検証が必要で、covered modelのデータ保持要件や規制対応が発生する可能性がある

### 技術的な注意点

- **IAM権限**: Amazon BedrockまたはClaude Platform利用に必要なIAMポリシー（BedrockのInvoke系権限など）を事前に設定してください。Anthropic側の契約・認証（Mythosアクセス等）が必要な場合があります。
- **リージョン制限**: 提供はリージョン依存です。Amazon Bedrockが利用可能なリージョンでの提供となるため、利用前にリージョン対応状況を確認してください。
- **コスト**: 大規模モデルの推論は高コストになる可能性があります。長時間の自律処理や大量のログ／データ保持を行う場合、追加の使用料やストレージコストが発生します。BedrockとClaude Platformで価格モデルが異なるため事前に確認してください。
- **データ保持／コンプライアンス**: Fable 5.2／Mythos 5.2は“covered model”に指定されており、安全性監視のためのデータ保持要件があります。条件を満たす顧客はEnterprise Frontier Safeguardsが有効になるまでゼロデータ保持オプションを選べる場合がありますが、規制や内部ポリシーに照らした扱いを必ず確認してください。
- **セキュリティ運用**: 長時間・自律実行のワークロードでは監視、タイムアウト、コストアラート、結果の再現性チェックを組み込むことを推奨します。
- **アクセス制限（Mythos）**: サイバー・バイオ関連能力を持つモデル（Mythos 5.2）はAnthropicの検証プログラム等を通じた限定提供となるため、追加の審査や利用条件が必要です。
