## [Rds For Oracle] Amazon RDS for Oracle now supports M8i and R8i instances in additional AWS Regions

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: Rds For Oracle
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-m8i-r8i-instances-new-regions/

### 概要

Amazon RDS for OracleがM8iおよびR8iインスタンスを追加リージョンでサポート開始しました。カスタムIntel Xeon 6プロセッサを採用し、前世代のIntelベースインスタンスに比べて価格性能が最大15%向上、メモリ帯域幅は最大2.5倍に改善しています（BYOLでEE/SE2対応）。

### 変更内容・新機能の詳細

追加されたリージョン: Asia Pacific (New Zealand) と Canada West (Calgary) でM8iおよびR8iが利用可能。さらにR8iは Europe (Milan, Stockholm, Zurich) と Israel (Tel Aviv) でも利用可能になりました。これらのインスタンスはAWS専用のカスタムIntel Xeon 6プロセッサを搭載しており、クラウド向けの同クラスIntelプロセッサと比較して最高の性能および最速のメモリ帯域を提供します。性能面では最大15%の価格性能改善と、2.5倍のメモリ帯域幅向上をうたっています。Amazon RDS for OracleではBring Your Own License (BYOL) モデルで提供され、サポートされるエディションはOracle Database Enterprise Edition (EE) と Oracle Database Standard Edition 2 (SE2)です。インスタンスサイズは、EEがlarge〜48xlargeおよびbare metalのmetal-48xl/metal-96xl、SE2がlarge〜4xlargeおよびbare metalのmetal-48xl/metal-96xlが利用可能です。利用可能な構成・価格・リージョンはAmazon RDS for Oracleの料金ページを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: OracleデータベースをRDSで運用するDBA、クラウドアーキテクト、SRE/運用チーム（特にBYOLでOracle EE/SE2を利用する組織）
- **利用シーン**: トランザクション処理やメモリ帯域が重要な分析ワークロードでの性能改善を目的とした新規デプロイや既存RDSインスタンスのサイズ変更・リプレイス
- **運用効果**: 最大15%の価格性能改善や2.5xのメモリ帯域向上により、同コストで性能向上、もしくは同性能でコスト削減が期待できる
- **展開効果**: 指定された追加リージョン（ニュージーランド、カルガリー、ミラノ、ストックホルム、チューリッヒ、テルアビブ）でレイテンシ要件やデータ主権要件に応じたリージョン選択が可能になる

### 技術的な注意点

- **IAM権限**: 特別な新権限は不要だが、RDSインスタンス作成・変更に必要な標準IAM/RDS権限（例: rds:CreateDBInstance, rds:ModifyDBInstance 等）を持っていること
- **リージョン制限**: 本発表で列挙されたリージョンに追加されるため、利用前にターゲットリージョンでの提供状況を公式ドキュメントで確認すること
- **ライセンス**: BYOL（Bring Your Own License）のみサポート。License IncludedモデルではM8i/R8iでのOracle利用は提供されていないため、Oracleライセンス契約とライセンスルールの順守が必要
- **インスタンス仕様**: EEはlarge〜48xlargeおよびbare metal(metal-48xl/metal-96xl)、SE2はlarge〜4xlargeおよび同bare metalサイズが提供される点に注意
- **互換性/移行**: 既存のRDS for Oracleからのスケールアップ／スケールダウンは可能だが、CPUアーキテクチャやメモリ帯域の差によりベンチマークでの動作確認を推奨
- **コスト**: インスタンス自体の価格はリージョン／サイズにより異なる。記事の性能改善は相対的指標のため、実運用での総コスト（ライセンスコスト含む）評価が必要
- **その他**: 本発表はRDS for Oracle向けの対応であり、他のRDSエンジンやEC2での適用状況は別途確認すること

### 参考情報

## [Govcloud Us] Haiku 5.5 now available on Kiro in AWS GovCloud (US)

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/kiro-haiku-5-5-aws-govcloud-us/

### 概要

AWS GovCloud (US) の Kiro IDE/CLI で Anthropic の新モデル「Claude Haiku 5.5」が利用可能になりました。Haiku 5.5 はClaude 5.5 ファミリーの中で最速を目指したモデルで、大量・低レイテンシ処理向けに最適化されています。

### 変更内容・新機能の詳細

Haiku 5.5 は Claude 5.5 ファミリーの3モデルが Kiro 上で GovCloud (US) に揃ったアップデートの一部です。Haiku 5.5 は Haiku 4.5 から性能向上しており、長いコンテキストの要約・圧縮、分類・ルーティング、大量テキストのバッチ処理、複数ファイルに対する小規模な編集など“高スループットかつ低レイテンシ”が求められる用途向けに設計されています。Opus 5.5 / Sonnet 5.5 が複雑な設計やコーディングといった高負荷タスクを担当する際の並列レビューサブエージェントとしても使いやすい構成です。Haiku 5.5 は「5 段階の effort レベル（low→max）」に適応するアダプティブ思考を採用しており、デフォルトは medium。コンテキストウィンドウは最大 1M トークンに対応します。料金面では標準リクエストが 0.06x のクレジット乗数で提供され、100K トークンを超えるリクエストは 0.3x 乗数で課金されます。Kiro IDE/CLI を最新版に更新して再起動すると、モデルセレクタから Haiku 5.5 を選択可能になります。詳細は GovCloud 向けドキュメントやモニタリング/トラッキングガイド、または AWS アカウントチームに問い合わせてください。

### 影響範囲・利用シーン

- **対象ユーザー**: GovCloud (US) を利用する開発者、SRE、データ処理チーム、セキュリティ／コンプライアンス対応が必要な公共機関や国内準拠企業
- **利用シーンまたは効果**: 大量テキストの高速要約・分類・バルク処理、複数ファイルに対する小さな変更の並列適用、レビューサブエージェントによる並列検証ワークフローの導入
- **運用効果**: レイテンシ低下とスループット向上によりバッチ処理やリアルタイムパイプラインの処理時間短縮、モデル階層（Haiku/Opus/Sonnet）の使い分けでコスト効率と精度を両立

### 技術的な注意点

- **リージョン制限**: 現在は AWS GovCloud (US) リージョン向けの提供です（他リージョンでは未提供の可能性あり）
- **IDE/CLI バージョン**: Kiro IDE または CLI を最新バージョンに更新し、再起動が必要です
- **課金／コスト**: 標準リクエストは 0.06x クレジット乗数、100K トークン超は 0.3x 乗数。1M トークンの大きなコンテキスト使用はコストとレイテンシに影響します
- **IAM権限**: Kiro とモデル利用に必要な IAM ポリシー／ロールがアカウントで設定されていることを確認してください（GovCloud 特有のアクセス制御や許諾が必要な場合があります）
- **互換性とワークフロー**: Haiku は高スループット・短反応向け。複雑な計画やコード生成には Opus/Sonnet と組み合わせて運用する設計が推奨されます
- **監視とログ**: 大量トークン利用時はモニタリング／トラッキングを有効にして、課金および性能の監視を行ってください（GovCloud 向けの監視ドキュメントを参照）
- **サポート/契約**: GovCloud 向けの利用可否や商用利用条件は AWS アカウントチームと確認してください

## [RDS] Amazon RDS now supports per snapshot billing

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-per-snapshot-billing/

### 概要

Amazon RDSのスナップショット課金がスナップショット単位で表示可能になりました。これにより、個々のスナップショットごとのコストをCost ExplorerやCost and Usage Reportで把握できます。

### 変更内容・新機能の詳細

従来、RDSのスナップショット料金はデータベースインスタンス単位で集約されて表示されていましたが、本日よりスナップショット単位の課金明細（per snapshot billing）が有効になりました。主なポイントは以下です。
- スナップショットごとのコストをCost ExplorerおよびCost and Usage Report（CUR）で確認可能。
- スナップショットに対してコスト配分タグ（cost allocation tags）を設定し、タグ別にスナップショット課金を集計できる。
- この機能はデフォルトで全RDSスナップショットに対して有効で、追加料金は発生しない。
- すべてのRDSエンジン（MySQL、PostgreSQL、MariaDB、Oracle、SQL Server、Amazon Auroraなど）で利用可能。
- 商用リージョンおよびAWS GovCloud (US) リージョンでサポートされる。
- 技術的影響としては、CURの行数や粒度が増えるためCURファイルサイズや解析クエリ（Athena等）の集計ロジックを更新する必要がある点に注意。タグをCost Explorer/CURに反映させるには、Billingコンソールで該当タグを「活性化（activate）」する必要がある。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドコスト管理者、SRE、DBA、FinOps担当者
- **利用シーン**: スナップショット単位でバックアップ費用を可視化してコスト配分（プロジェクト別、チーム別、環境別）を行う場面
- **運用効果**: バックアップ関連の無駄なコストの特定や予算配分の精緻化が可能になり、不要スナップショット削除や保持ポリシーの改善につながる
- **注意点**: CURの粒度が上がるため既存のコスト集計スクリプトやダッシュボードの修正が必要になる場合がある

### 技術的な注意点

- **IAM権限**: Cost and Usage ReportやCost Explorer、スナップショットのタグ操作に必要なIAM権限（billing, cur, rds:ListTagsForResource等）を確認・付与してください
- **リージョン制限**: 商用AWSリージョンおよびAWS GovCloud (US)で利用可能。特定リージョンでの差異がある場合はドキュメントを参照してください
- **コスト**: per snapshot billing自体に追加料金は発生しませんが、CURの行数増加によりS3保存コストやCUR処理に使用するAthena/Glue等のクエリコストが増える可能性があります
- **タグの有効化**: スナップショットにタグを付与しても、Billingコンソールで該当タグをCost allocation tagsとして有効化しないとCost Explorer/CURに反映されません
- **既存処理への影響**: CURフォーマットや列（resource_id等）を参照する集計クエリを運用している場合、スナップショット単位の行が追加されるためクエリ/ETLの調整が必要です

- https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/cost-alloc-tags.html
- https://docs.aws.amazon.com/cur/latest/userguide/what-is-cur.html
- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithSnapshots.html

## [General] Amazon Quick on desktop now uses your organization's existing Amazon Quick sign-in

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-quick-desktop-organization-sign-in/

### 概要

Amazon Quickのデスクトップアプリが、組織で既にWeb版Quickに使っているサインイン方式をそのまま利用できるようになりました。管理者側で個別にOIDCアプリを登録したりデスクトップ用のサインインを別途設定する必要がなくなります。

### 変更内容・新機能の詳細

今回の変更により、デスクトップアプリは組織がWeb版Amazon Quickで利用している認証フロー（IAM Identity Center、IAMフェデレーション、またはネイティブなAmazon Quickユーザーを含む）を再利用してサインインできます。管理者はAmazon Quickコンソールで一度だけ「デスクトップコネクタ」を追加すれば、ユーザーはQuickアカウント名を入力してSign Inを選び、ブラウザ経由で既存のサインイン手順を完了するだけでデスクトップ利用が可能になります。組織がデスクトップのサインインを個別管理したい場合は、Microsoft Entra ID、Google Workspace、Okta、Ping Identityなどを用いた専用のIDプロバイダ設定を引き続き構成できます。デスクトップは、Amazon Quickのフル機能セットをサポートするAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: 組織のエンドユーザー（Quick利用者）、ID管理者、SRE/運用チーム
- **利用シーン**: 既存のWebサインインを使ってデスクトップアプリへシームレスにアクセスさせたい場面（オンボーディングの簡素化、ユーザー利便性向上）
- **運用効果**: 管理者がOIDCアプリ登録や個別デスクトップ設定を行う工数削減、ユーザー側の初期設定負荷の低減、サインイン一貫性によるサポート件数の削減

### 技術的な注意点

- **IAM権限**: デスクトップコネクタを追加する操作は管理者権限が必要です（コンソール上の権限設定を確認してください）
- **リージョン制限**: Amazon Quickのフル機能セットをサポートするリージョンでのみデスクトップが利用可能です。対象リージョンはドキュメント/コンソールで確認してください
- **コスト**: 新たなAWS利用料金は特に発生しない想定ですが、外部IDプロバイダの契約／ライセンス費用やSAML/OIDC設定に伴う運用コストは別途発生する可能性があります
- **既存IdP互換性**: IAM Identity Center、IAMフェデレーション、ネイティブユーザーに対応。専用管理を希望する場合はMicrosoft Entra ID、Google Workspace、Okta、Ping Identityなどで専用構成が可能です
- **ブラウザ依存**: デスクトップのサインインはブラウザ経由での認証フローを利用するため、ユーザーの端末でブラウザが利用可能である必要があります

- https://docs.aws.amazon.com/quick/latest/userguide/

## [Aurora] Amazon Aurora MySQL 8.4.10 is now generally available

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: Aurora
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-aurora-mysql-8410-available/

### 概要

Amazon Aurora MySQL-Compatible Edition 8.4 が MySQL 8.4.10 をサポートすることが一般提供されました。今回のリリースでは GTID タグサポートと DB インスタンスあたり最大 50,000 同時接続のサポートが追加されています。

### 変更内容・新機能の詳細

主な変更点は次のとおりです。

- GTID タグ: GTID（Global Transaction Identifier）にユーザ定義のタグを付与できる機能が追加されました。これにより、バイナリログやレプリケーション環境で関連するトランザクション群を識別・グループ化しやすくなり、障害復旧やデバッグ、監査での追跡が容易になります。

- 最大同時接続数の拡張: DB インスタンスあたり最大 50,000 の同時接続をサポートするようになりました。接続集中型アプリケーション（大量のクライアント接続を伴うウェブアプリ、IoT バックエンドなど）がコネクションプーリング層を追加せずにスケール可能になります。ただし実際の最大接続数はインスタンスサイズやメモリに依存するため、インスタンス選定とパラメータグループの調整が必要です。

- セキュリティ／バグ修正／性能改善: MySQL コミュニティによる 8.4.10 の修正が反映されており、既存バージョンの CVE 修正、バグフィックス、パフォーマンス改善が含まれます。

- アップグレード方法: スケジュールされたメンテナンスウィンドウ中の自動マイナーバージョンアップ、あるいはインプレース（クラスターの通常アップグレード）／スナップショット復元によるアップグレードが可能です。大規模運用向けに AWS Organizations の Upgrade Rollout Policy を使った段階的ロールアウトで低優先度環境で検証してから本番を上げる運用設計が推奨されます。

- リージョン対応: Aurora MySQL が利用可能なすべての AWS リージョンでサポートされています。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、SRE、アプリケーション開発者（接続集中型サービス、レプリケーションを利用するシステム）
- **利用シーン**: バイナリログやレプリケーションのトランザクションをタグで整理して障害対応や監査を行う場面、接続数が非常に多いアプリケーションをコネクションプールなしでスケールさせたい場面
- **運用効果**: GTID タグでトランザクションの追跡とグルーピングが容易になりデバッグ/復旧時間を短縮。最大同時接続数の引き上げにより、接続集中型アプリケーションでのスケール性向上とアーキテクチャ単純化が期待される
- **注意点（運用）**: インスタンスサイズやパラメータグループ設定により実効的な最大接続数が変わるため、負荷試験と段階的ロールアウトで検証する必要がある

### 技術的な注意点

- **IAM権限**: マイナーバージョンアップやパラメータグループ変更、スナップショット作成には rds:ModifyDBCluster、rds:ModifyDBInstance、rds:CreateDBClusterSnapshot 等の適切な RDS/Aurora 権限が必要です
- **リージョン制限**: Aurora MySQL が利用可能な全リージョンでサポートされています（記事記載）。ただし、リージョンごとのサービス提供状況は常に確認してください
- **互換性/検証**: マイナーバージョンアップは互換性問題が少ない傾向ですが、アプリケーション固有の挙動や拡張機能に影響する可能性があるためステージング環境で事前検証を必須としてください
- **インスタンス要件**: 最大接続数はインスタンスの CPU/メモリに依存します。大量接続を想定する場合は上位インスタンスへのスケールやパラメータ調整（max_connections 等）を検討してください
- **コスト**: 同時接続増加に対応するためにより大きなインスタンスを選択するとコストが増加します。また、アップグレード時のスナップショット保管やテスト環境でのリソース使用にもコストが発生します
- **アップグレード運用**: 自動マイナーバージョンアップを有効にすることで運用が簡素化されますが、事前のスナップショット取得と段階的ロールアウト（AWS Organizations の Upgrade Rollout Policy）による検証を推奨します

## [General] AWS Lambda now supports queues for Apache Kafka in self-managed Kafka event sources

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-queue-kafka-esm/

### 概要

AWS Lambdaが自己管理（self-managed）のApache Kafkaイベントソースマッピング（ESM）でキューモード（Queue）をサポートしました。これによりパーティション数に依存せずに並列処理を拡張でき、スパイク時のスループット向上と処理の回復性向上が期待できます。

### 変更内容・新機能の詳細

今回の拡張では、Kafkaの「share groups」（Apache Kafka 4.2で一般提供）を利用することで、同一パーティションから複数のイベントポーラーが同時に消費できるモード（Queue）が自己管理Kafka向けESMに追加されました。従来のKafka消費モデル（コンシューマグループ）は1パーティションにつき1コンシューマが割り当てられるため、並列度はパーティション数に制約されていました。Queueモードではプロデューサやトピック設定、関数コードを変更することなく並列処理をパーティション数から切り離せます。実装的には複数のイベントポーラーが同一パーティションを同時にポーリング可能で、各イベントポーラーは最大10の同時インボケーションをサポートします。これにより、画像/動画エンコード、不正検知、通知配信、テレメトリ取り込みなど、イベントごとに独立して処理できるワークロードでスループット向上と処理遅延の局所化（遅いイベントが同一パーティション全体を停滞させない）を実現します。一方でQueueモードはパーティション内順序を保持しないため、順序保証が必要なワークロードには適しません。利用開始は、自己管理KafkaのESMを作成するときにConsumptionModeを"Queue"に設定するだけで、AWS Management Console、Lambda API、AWS CLI、CloudFormation、AWS SAM、AWS CDKのいずれからでも設定可能です。要件としてはshare groups対応のKafkaクラスター（例: Apache Kafka 4.2以降）または同等機能を提供するマネージドサービス（例: Confluent Cloud）であることが必要です。料金は標準のLambda課金が適用され、Provisionedモードを選択した場合はEvent Poller Unit（EPU）の使用量も課金対象になります。

### 影響範囲・利用シーン

- **対象ユーザー**: Kafkaを自己管理または対応するマネージドサービス上で運用し、Lambdaでイベント駆動処理を行う開発者/プラットフォーム運用者
- **利用シーンまたは効果**: 画像・動画エンコード、異常検知、通知配信、テレメトリ取り込み等、イベント単位で独立した処理を高スループットで行いたいケース。パーティション数を増やさずに同時処理数を上げられるため、トラフィックスパイク時の応答性と耐障害性が向上します。
- **運用効果**: パーティション過少によるスループットボトルネックの回避、遅延を引き起こす個別イベントの影響を局所化できるため、安定した処理継続が期待できます。
- **制約**: Queueモードはパーティション内の順序を保持しないため、順序保証が必要なワークロードでは使用できません。
- **コスト影響**: 同時実行数が増えることでLambda実行時間に基づく課金が増加する可能性があり、Provisionedモード使用時はEPUの追加費用が発生します。

### 技術的な注意点

- **必要条件**: Kafkaクラスターがshare groupsをサポートしていること（Apache Kafka 4.2以降、または同等機能を持つマネージドサービス）。
- **設定方法**: ESM作成時にConsumptionModeを"Queue"に設定（Console, API, CLI, CloudFormation, SAM, CDKで指定可能）。
- **順序性**: Queueモードはパーティション内順序を保証しません。順序が必要な処理では使用しないでください。
- **並列度制限**: 複数のイベントポーラーが同一パーティションから同時に消費可能。各イベントポーラーは最大10の同時インボケーションをサポートします（合計並列度は設定・EPU等に依存）。
- **ネットワーク/認証**: 自己管理Kafkaへの接続にはネットワーク（VPC、サブネット、セキュリティグループ）と認証（TLS/SASL、Secrets Managerなど）の正しい設定が必要です。必要な資格情報をLambdaが参照できるようにIAM権限を付与してください。
- **IAM権限**: ESM作成・更新には lambda:CreateEventSourceMapping / lambda:UpdateEventSourceMapping 等の権限、及びシークレットアクセスが必要な場合は secretsmanager:GetSecretValue 等の付与を確認してください。
- **リージョン制限**: 商用AWSリージョンで自己管理Kafka ESMが利用可能なリージョンで提供されます。China/GovCloudなどの特別リージョンや未対応リージョンでは利用できない可能性があるため、リージョン対応状況を確認してください。
- **コスト**: 標準のLambda実行料が適用されます。Provisionedモードを選択した場合はEvent Poller Unit（EPU）使用料が追加で発生します。並列数増加による実行回数/実行時間増加がコストを押し上げる点に注意してください。
- **運用注意**: Queueモードにより重複実行や順不同での再実行が起こりやすくなるため、関数は冪等（idempotent）に実装し、失敗時のリトライ/デッドレターの設計を行ってください。

## [Aurora] Amazon Aurora MySQL 3.14 (compatible with MySQL 8.0.46) is generally available

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: Aurora
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-aurora-mysql-314-available/

### 概要

Amazon Aurora MySQL-Compatible Edition 3（MySQL 8.0互換）のマイナー更新版 3.14（MySQL 8.0.46互換）が一般提供開始されました。コミュニティの修正やAurora固有の改善に加え、ポスト量子（PQ）対応のTLS鍵交換（PQ-TLS）がサポートされます。

### 変更内容・新機能の詳細

Aurora MySQL 3.14 は MySQL 8.0.46 を基盤にしており、MySQLコミュニティのバグ修正と Aurora 固有の改善が含まれます。主要な追加機能として、トラフィックの暗号化に対する将来の耐性を高めるためのポスト量子鍵交換（PQ-TLS）サポートが導入されました。アップグレードはスケジュールされたメンテナンスウィンドウ中に自動マイナーアップグレードを使って実行できます。大規模運用向けには自動マイナーアップグレードを有効化し、AWS Organizations の Upgrade Rollout Policy を使ってクラスタ群を段階的にロールアウトすることが推奨されます。マイナーアップグレードはインプレース（既存クラスタの更新）またはスナップショット復元による方法が利用可能です。本リリースは、Aurora MySQL が利用可能な全リージョンでサポートされています。なお、Aurora自体はスケールトゥゼロのサーバーレス、Aurora Global Database、I/O最適化オプション、組み込みのセキュリティおよび継続的バックアップなどの特徴を持ちます。

### 影響範囲・利用シーン

- **対象ユーザー**: データベース管理者、SRE／運用チーム、セキュリティチーム、アプリケーション開発者
- **利用シーン**: トラフィック暗号化の将来対策（PQ-TLS導入）やセキュリティ強化、MySQL 8.0.46 の修正を取り込んだ安定性向上、複数クラスタを段階的に一括アップデートする運用
- **運用効果**: 自動マイナーアップグレードとOrganizationsのロールアウト機能で大規模環境のパッチ適用が容易に（段階導入でリスク低減）。ただしPQ-TLS利用にはクライアント側の対応が必要で、動作確認が必要

### 技術的な注意点

- **IAM権限**: アップグレードには rds:ModifyDBCluster／rds:ModifyDBInstance 等の権限が必要。Organizations経由でのロールアウトには Organizations 関連権限も確認してください
- **リージョン制限**: 本リリースは Aurora MySQL が提供されている全リージョンでサポートされています（公開情報に基づく）。
- **アップグレード手順**: 自動マイナーアップグレードはメンテナンスウィンドウ中に実行。段階ロールアウトには AWS Organizations の Upgrade Rollout Policy を使用。インプレースアップグレードの他、スナップショットを復元してアップグレード後に切り替える方法も利用可能
- **互換性と検証**: MySQL 8.0.46 の変更点／修正によって SQL 挙動やパフォーマンスに影響する可能性があるため、事前にステージ環境で回帰テストを実施してください
- **PQ-TLS対応クライアント**: PQ-TLS を有効にする場合、接続クライアント（ミドルウェア／ドライバ）および OS の TLS ライブラリが該当のポスト量子鍵交換スイートをサポートしている必要があります。クライアント側非対応だと接続障害が発生します
- **パフォーマンスとコスト**: PQ 鍵交換は計算量が増える可能性があり、CPU負荷やレイテンシが若干増加する場合があるため性能検証を推奨します。マイナーアップグレード自体に追加料金は通常発生しませんが、アップグレード方法（スナップショット復元や追加検証環境）に伴う一時的なコストは考慮してください
- **バックアップとロールバック**: アップグレード前にスナップショット取得を推奨。問題発生時はスナップショットからの復元でロールバック可能です

## [General] Amazon Connect Customer now supports Model Context Protocol (MCP) tools in flows

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/connect-flows-mcp-tools/

### 概要

Amazon Connect Customerのフローで新しい「External Tool」ブロックを使い、Model Context Protocol (MCP) 対応のツールを呼び出せるようになりました。これにより、Amazon Bedrock AgentCore Gateway経由でサードパーティアプリと連携し、カスタムLambdaを書かずにデータ取得やアクション起動が可能になります。

### 変更内容・新機能の詳細

今回の機能追加で、Amazon Connect Customerのフロー内に配置できる「External Tool」ブロックを介してMCP準拠のツールを直接呼び出せます。External ToolブロックはAmazon Bedrock AgentCore Gatewayを通じてエージェント的な（agentic）体験で使っている同じツールを再利用し、CRMのケース履歴や銀行の取引詳細など外部システムのコンテキストを取得したり、外部システムに対して操作（チケット作成、トランザクション検索など）をトリガーできます。これにより、従来必要だったカスタムLambda関数の実装・運用が不要になり、フローの開発効率と保守性が向上します。 本機能は現時点で以下のリージョンで利用可能です: US East (N. Virginia)、US West (Oregon)、Canada (Central)、Europe (Frankfurt)、Europe (London)、Asia Pacific (Seoul)、Asia Pacific (Singapore)、Asia Pacific (Sydney)、Asia Pacific (Tokyo)。管理者向けの設定や具体的なフロー例は管理者ガイドを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: コンタクトセンター開発者、クラウド/プラットフォームエンジニア、ソリューションアーキテクト
- **利用シーン**: 顧客からの問い合わせ時にCRMや銀行プラットフォームから該当ケースや取引データをフロー内で取得して応対コンテキストを補完する場面
- **運用効果**: カスタムLambdaの実装・運用コストを削減し、フロー開発のスピードと再利用性が向上。外部システム呼び出しをフロー内で一元管理できるため運用負荷が低減

### 技術的な注意点

- **IAM権限**: Amazon ConnectがBedrock AgentCore Gatewayや対象ツールへアクセスするための適切なIAMロール/ポリシーの設定が必要になる可能性があります。管理者ガイドで推奨設定を確認してください。
- **リージョン制限**: 本機能は発表時点で指定されたリージョン（US East (N. Virginia)、US West (Oregon)、Canada (Central)、Europe (Frankfurt)、Europe (London)、Asia Pacific (Seoul)、Asia Pacific (Singapore)、Asia Pacific (Sydney)、Asia Pacific (Tokyo)）で利用可能です。他リージョンでは未対応の可能性があります。
- **コスト**: Bedrock（AgentCore Gateway経由の呼び出し）やAmazon Connectの利用に伴う追加料金、外部サービスのAPI利用料が発生する可能性があります。実運用前にコスト見積もりを確認してください。
- **セキュリティ/プライバシー**: 外部ツールへ顧客データを送信する場合はデータ保護・コンプライアンス要件を満たす必要があります。送信データのマスキングやログ保存ポリシーを検討してください。
- **エラーハンドリング**: 外部ツールの応答遅延やエラーに対するフォールバック（タイムアウト設定、代替フロー）をフロー内で設計することを推奨します。
- **互換性**: 呼び出すツールはModel Context Protocol (MCP) 準拠である必要があります。
- **設定手順**: 管理者ガイドに従いExternal Toolブロックの設定（エンドポイント/ツール選択、認証情報の設定、パラメータマッピング）を行ってください。

## [General] Amazon Connect Customer now supports Cases and External Tool events in the Wait block

- **公開日**: 2026-11-03 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/10/connect-wait-block-cases-tool-events/

### 概要

Amazon Connect CustomerのフロービルダーにあるWaitブロックで、Lambda完了待ちに加えてConnect Casesのフィールド条件や外部ツール（External Tool）の呼び出し完了を待てるようになりました。リアルタイムのデータ変化に応じてフローを停止・再開できるため、無駄な転送を減らし顧客・エージェント双方の待ち時間を短縮できます。

### 変更内容・新機能の詳細

従来のWaitブロックは主にLambda実行の完了待ちをサポートしていましたが、本アップデートにより以下が可能になりました。
- Connect Caseフィールド条件での待機: 指定したケース（Connect Cases）のフィールドがある値・状態に変わるまでフローを停止できます（例: 返金ステータスが"完了"になるまで待つ）。
- External Tool完了待ち: 外部ツール呼び出し（コールアウト／連携の完了）を検出して、その完了をトリガーにフローを再開できます。
これにより、重要な情報（例: 審査結果、決済完了、外部システムのレスポンス）を受け取るまでインタラクションをホールドし、条件に基づいて自動的にルーティングや次の処理を行えます。設定はAmazon Connectのフロービルダー内のWaitブロックで行い、待機条件・タイムアウト・代替パス（タイムアウト時の処理）を併せて設定するのが一般的です。また既存のLambda待ち機能は引き続き利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: コンタクトセンター管理者、フロー設計者、SRE/運用チーム
- **利用シーンまたは効果**: ケースのステータス反映（例: 返金、審査）や外部システム応答を待ってから顧客対応を継続し、無駄な転送や重複作業を削減
- **運用効果**: エージェントの割り当て効率向上、顧客の待ち時間短縮、フローの自動分岐による応答品質向上
- **ビジネス上の影響**: リアルタイム状態に応じた柔軟なルーティングで解約やクレーム対応の改善が期待できる

### 技術的な注意点

- **IAM権限**: Connectのフロー編集・Casesアクセス・External Tool統合を操作するための適切なIAM権限が必要です（管理者/ロールの確認を推奨）。
- **リージョン制限**: 機能のリージョン対応状況はドキュメントで確認してください（リージョンによっては未対応の可能性があります）。
- **コスト**: External Tool呼び出しや関連するLambda実行、追加のAPIリクエストにより料金が発生する可能性があります。CloudWatchログ等の利用もコストに影響します。
- **前提条件・設定**: Connect CasesおよびExternal Tool連携が事前に構成されている必要があります。フロービルダーで待機条件・タイムアウト・代替パスを明示的に設定してください。
- **可観測性**: 待機中・再開時の挙動はCloudWatchログ/Connectログで確認できます。デバッグ用にログ出力やメトリクス設定を推奨します。
- **フォールバック/タイムアウト**: 長時間待機や外部システム未応答時の代替処理（タイムアウト分岐）を必ず設計してください。
- **互換性**: 既存のLambda待機フローはそのまま利用可能。新機能はフローのWaitブロックで選択して切り替えます。
