## [Marketplace] AWS Marketplace now supports agentic payments with AgentCore

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Marketplace
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/marketplace-agentic-payments-agentcore/

### 概要

AWS Marketplaceから、Amazon Bedrock AgentCoreのAgentCore paymentsを通じて、AIエージェントがx402プロトコル対応の対象商品をリクエスト単位で購入できるようになりました。購入代金は既存のAWS請求に計上され、暗号資産ウォレットは不要です。

### 変更内容・新機能の詳細

顧客はAgentCore paymentsでAWS Marketplaceの支払いコネクタを有効にし、AgentCore GatewayのAWS Marketplaceコネクタを通じて、エージェントが利用できる商品を検索・購入します。たとえば、調査エージェントがWeb検索を1回購入したり、コーディングエージェントが有料のガードレールサービスを呼び出したりできます。販売者はAWS Marketplaceに登録し、対象リスティングでagentic paymentsを設定したうえで、AWS Marketplace x402 SDKを統合します。顧客からの支払いの回収と販売者への支払いはAWS Marketplaceが行い、販売者への支払いは通常のMarketplace取引と同様に処理されます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Marketplaceを利用するAIエージェントの開発者・運用者、およびAIエージェント向けAPIやデータなどを販売するAWS Marketplace販売者
- **利用シーン**: エージェントがタスクの途中で必要に応じて、有料API、検索、データ、コンテンツなどをリクエスト単位で購入
- **運用効果**: 顧客は販売者ごとのアカウント作成や支払い方法の登録を省略でき、販売者は独自のサインアップや請求システムを構築せずにエージェント向けの従量課金を提供可能
- **可視性と制御**: 支出上限、承認済み販売者、ガードレールを設定でき、取引はAWS CloudTrailとAWS Cost Explorerで確認可能。Private Marketplaceのポリシーも引き続き適用されます。

### 技術的な注意点

- **利用条件**: AgentCore paymentsでAWS Marketplace支払いコネクタを有効にし、AgentCore GatewayのAWS Marketplaceコネクタを利用します。販売者側はAWS Marketplaceへの登録、リスティングの設定、AWS Marketplace x402 SDKの統合が必要です
- **リージョン制限**: AgentCore paymentsが利用可能なすべてのAWSリージョンで利用できます。利用可能な具体的リージョンはAgentCore paymentsの対応リージョンを確認してください
- **コスト**: 購入した商品・サービスのリクエスト単位の料金が発生し、顧客のAWS請求に計上されます。個別商品の料金や条件は各リスティングで確認してください
- **ガバナンス**: エージェントに支出上限、承認済み販売者、ガードレールを設定してください。Private Marketplaceを利用している場合は、そのポリシーが引き続き取引に適用されます
- **監査**: 取引はAWS CloudTrailおよびAWS Cost Explorerで確認できます。必要な監査・コスト管理の運用に応じて確認手順を整備してください

## [Cognito] Amazon Cognito now supports client ID metadata documents

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Cognito
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-client-id-metadata-documents/

### 概要

Amazon Cognito が OAuth クライアント ID メタデータドキュメント（CIMD）に対応しました。MCP クライアントや AI エージェントは、HTTPS URL をクライアント ID として使用でき、クライアントごとに Cognito アプリクライアントを作成・管理せずにユーザー認証を開始できます。

### 変更内容・新機能の詳細

CIMDでは、クライアントが自身の HTTPS URL に JSON 形式のメタデータドキュメントを公開し、その URL を OAuth のクライアント ID として使用します。サインイン開始時に Cognito がドキュメントを取得・検証し、クライアントの識別と認証リクエストの検証に利用します。管理者は CIMD ポリシーで URL パターンを許可し、それぞれを既存のアプリクライアントに対応付けます。認証時に利用できるスコープとグラントタイプは、アプリクライアントとメタデータドキュメントの両方で許可されているものに制限されます。これにより、外部クライアントごとのアプリクライアント作成や、不要になったクライアントの削除といった運用負荷を軽減できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Cognito User Pool を利用する開発者、MCP サーバー運用者、AI エージェント提供者
- **利用シーン**: 外部の MCP クライアントや AI アシスタントに、個別のアプリクライアントを登録せずにユーザー認証を提供する
- **運用効果**: クライアントごとの登録・管理・クリーンアップを減らし、URL パターン単位で受け入れるクライアントを制御できる

### 技術的な注意点

- **利用プラン**: Essentials および Plus の機能プランで利用できます
- **リージョン制限**: Amazon Cognito が提供されているすべての AWS リージョンで利用できます
- **アクセス制御**: CIMD ポリシーで許可する URL パターンを慎重に設定してください。スコープとグラントタイプは、アプリクライアントとメタデータドキュメント双方の許可範囲に制限されます
- **メタデータの公開**: クライアント ID として使う HTTPS URL で JSON メタデータを公開し、Cognito が取得・検証できる状態を維持してください
- **コスト**: Essentials または Plus のプラン要件により、利用中のプランによっては料金への影響が生じる場合があります。詳細は Cognito の料金を確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-client-id-metadata-documents/
- https://docs.aws.amazon.com/cognito/latest/developerguide/cimd.html

## [CloudFront] Amazon CloudFront adds IP based routing and connection logs to SaaS Manager

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-ip-based-routing-connection-logging

### 概要

CloudFront SaaS Managerで、同じワイルドカードドメインのテナントを接続元IPアドレスに基づいて異なる設定へ振り分けられるようになりました。HTTPS接続ログにも対応し、クライアントの接続状況を調査しやすくなります。

### 変更内容・新機能の詳細

従来はドメイン名を基準に設定が選ばれ、同じドメインは常に同じ設定に振り分けられていました。今回の機能では、同じワイルドカードドメインを複数のAnycast Static IPリストに登録し、各リストを異なるテナント設定に対応付けられます。たとえば、プレミアム／プロ向けには専用IPリストと個別設定を使い、無料プラン向けには共有CloudFront IPアドレスを使う構成を、同じ「*.example.com」配下で実現できます。クライアントをどのIPリストに接続させるかはサービス側で制御できるため、顧客側の設定変更なしにサービス階層間でトラフィックを移行できます。また、TLSハンドシェイクでSNI（Server Name Indication）を送信しないIoT機器、組み込みSDK、旧式TLSクライアント向けに、Viewer fallbackを設定できます。この場合、指定したディストリビューションが接続を受け付け、HTTPリクエストのHostヘッダーを使ってコンテンツを振り分けます。さらに、これらのテナントへのHTTPS接続を接続ログに記録でき、接続トラブルの調査に役立ちます。

### 影響範囲・利用シーン

- **対象ユーザー**: CloudFront SaaS Managerを利用するWeb開発プラットフォームおよびSaaS事業者
- **利用シーン**: 同一のワイルドカードドメインで、顧客プランやテナントごとに異なるCloudFront設定を提供する
- **運用効果**: 接続先IPリストの制御により、顧客側の変更なしでサービス階層間のトラフィックを移行できる
- **対応クライアント**: SNIを送信しないIoT機器、組み込みSDK、旧式TLSクライアントの接続にも対応できる
- **トラブルシューティング**: HTTPS接続ログを利用して、クライアントの接続状況を調査できる

### 技術的な注意点

- **利用条件**: IPアドレスによる振り分けにはAnycast Static IPリストと、リストごとのテナント設定が必要です
- **SNI非対応クライアント**: Viewer fallbackで受け付けるディストリビューションを指定し、Hostヘッダーに基づく振り分けを構成します
- **ログ**: 接続ログの対象はテナントへのHTTPS接続です。記録項目や保存先などの詳細は公式ドキュメントを確認してください
- **リージョン**: CloudFrontのすべてのエッジロケーションで利用できます
- **コスト**: Anycast Static IPリストやログの利用に伴う料金条件は、導入前にCloudFrontの最新料金情報を確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-ip-based-routing-connection-logging
- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Welcome.html

## [CloudFront] Amazon CloudFront simplifies domain moves and onboarding for SaaS Manager

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-domain-moves-distribution-tenants

### 概要

CloudFrontでは、SaaS事業者などが顧客ドメインをマルチテナントディストリビューションへ、通信を停止せずに移行できるようになりました。証明書の発行・設定が完了する前にドメインを追加し、準備中はHTTPでリクエストを処理することもできます。

### 変更内容・新機能の詳細

新しいOnDomainTakeoverオプションを使うと、テナントの作成または更新時に、DNSレコードによるドメイン所有権の確認とCloudFront上のドメイン移行を1回のリクエストで行えます。1つまたは複数のドメインに対応し、同一AWSアカウント内だけでなく、アカウントをまたぐ移行も可能です。従来必要だった移行元ディストリビューションの無効化、ワイルドカードによる回避策、AWS Supportへの問い合わせをせずに、既存の顧客ドメインを共有設定のマルチテナント構成へ移せます。ドメイン追加時にTLS証明書が未設定の場合、証明書をACMなどで検証・発行してアタッチするまでHTTPでリクエストを処理できます。

### 影響範囲・利用シーン

- **対象ユーザー**: 顧客ごとのドメインを管理するWeb開発プラットフォーム、SaaSプロバイダー、CloudFront運用担当者
- **利用シーン**: 既存の顧客ドメインを、CloudFrontのマルチテナントディストリビューションへ移行する場合
- **運用効果**: 移行元ディストリビューションの停止を避け、単一リクエストで複数ドメインを移行できるため、切り替え作業を簡素化できます
- **コスト**: 本機能の利用による追加料金はありません

### 技術的な注意点

- **所有権確認**: CloudFrontがDNSレコードを確認します。ドメイン移行前に、必要なDNSレコードを設定してください
- **証明書未設定時**: 証明書をアタッチするまではHTTPで配信されます。暗号化が必要な通信や機密情報を扱う場合は、TLS証明書の設定完了後に利用してください
- **証明書の準備**: ACMまたは別の認証局でドメインを検証し、発行された証明書をCloudFrontにアタッチします
- **アカウント範囲**: 同一アカウント内の移行とアカウントをまたぐ移行の両方に対応します
- **リージョン**: すべてのCloudFrontエッジロケーションで利用できます

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-domain-moves-distribution-tenants
- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/

- **必要なイメージ**: 2026年10月20日以降にリリースされたWorkSpaces Applicationsエージェントを含むイメージが必要です

- **リージョン制限**: Aurora PostgreSQL with express configurationが利用可能なAWSリージョンで提供されます
- **コスト**: 記事に本機能の追加料金に関する記載はありません。移動後の構成に伴う通常のAWS利用料金は発生します

## [Msk] Amazon MSK Connect now supports restarting existing connectors

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Msk
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-msk-connect-restart-existing-connectors

### 概要

Amazon MSK Connectで、コネクタとそのタスクを削除・再作成せずに再起動できるようになりました。すべてのタスク、または失敗したタスクだけを選んで再起動でき、ストリーミングデータパイプラインの復旧を迅速化できます。

### 変更内容・新機能の詳細

Amazon MSK Connectは、Amazon MSKと連携するApache Kafka Connectコネクタをマネージド環境で実行・監視・スケーリングするサービスです。従来は障害からの復旧にコネクタの削除と再作成が必要でしたが、新機能では既存および新規作成したコネクタをその場で再起動できます。コネクタと全タスクを再起動する方法に加え、失敗したタスクだけを選んで再起動する方法も利用できます。また、失敗タスクがない場合でも、外部システムや依存関係の一時的な問題への対処、変更の反映を目的にコネクタを再起動できます。Amazon MSKコンソール、AWS CLI、AWS SDK、AWS CDKから操作できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon MSK ConnectでKafka Connectコネクタを運用する開発者、データエンジニア、SRE・運用チーム
- **利用シーン**: コネクタやタスクの障害、一時的な外部依存先の問題からの復旧
- **運用効果**: コネクタを削除・再作成せずに復旧でき、作業負荷や停止時間の削減が期待できます
- **料金**: この再起動機能の追加料金はありません

### 技術的な注意点

- **再起動対象**: コネクタと全タスク、または失敗したタスクを選択して再起動できます
- **適用対象**: 既存のコネクタと新規作成したコネクタが対象です
- **利用方法**: Amazon MSKコンソール、AWS CLI、AWS SDK、AWS CDKから操作できます
- **リージョン制限**: Amazon MSK Connectが利用可能なすべてのAWSリージョンで利用できます
- **運用上の注意**: 再起動はコネクタの処理に影響するため、対象とタイミングを確認して実行してください

## [General] Amazon Aurora DSQL now supports multi-Region peering across continents

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-dsql-intercontinental-multi-region-clusters/

### 概要

Amazon Aurora DSQLで、異なる大陸にあるAWSリージョン同士を組み合わせたマルチリージョンクラスターを作成できるようになりました。2大陸のアプリケーションから、強い一貫性を保った単一のデータベースに読み書きできます。

### 変更内容・新機能の詳細

これまでは、マルチリージョンクラスターを構成するリージョンは同じ地理的なリージョンセット内にある必要がありました。今回の変更により、たとえば米国東部（バージニア北部）と欧州（アイルランド）のように、異なる大陸のリージョンをピアリージョンとして選択できます。クラスター作成時には、2つのピアリージョンに加えて witness リージョンを指定します。片方のリージョンが利用できなくなった場合も、コミット済みの書き込みは保持され、もう一方のリージョンで読み書きを継続できます。利用可能なリージョンは、Aurora DSQLのマルチリージョンクラスターに対応しているリージョンです。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数大陸でサービスを提供するアプリケーションの開発者、データベース管理者、SRE/運用チーム
- **利用シーン**: 大陸ごとのユーザーに近いリージョンへデータベースを配置し、低遅延のアクセスを目指す構成
- **運用効果**: 大陸をまたぐリージョン障害への耐性を高め、片方のリージョンが利用できない場合も、もう一方で読み書きを継続できます
- **設計上の効果**: 2つのピアリージョンとwitnessリージョンを選び、必要な耐障害性に応じて障害ドメインを広く分離できます

### 技術的な注意点

- **リージョン要件**: Aurora DSQLのマルチリージョンクラスターに対応しているリージョンが対象です。利用前に公式のリージョン一覧を確認してください
- **構成要素**: 2つのピアリージョンとwitnessリージョンを指定します。各リージョンの役割や配置要件をユーザーガイドで確認してください
- **一貫性と障害時の動作**: 強い一貫性を提供し、コミット済み書き込みはリージョン障害時にも保持されます。アプリケーション側の接続先や再試行動作も含めて障害時の動作を検証してください
- **コスト**: リージョン間のデータ転送などにより費用が発生する可能性があります。構成と利用量に応じた料金を事前に確認してください

- https://docs.aws.amazon.com/aurora-dsql/latest/userguide/
