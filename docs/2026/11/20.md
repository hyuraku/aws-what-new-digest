## [Lambda] AWS Lambda adds support for Python 3.15

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-python-315/

### 概要

AWS LambdaでPython 3.15が利用可能になりました。Event Functionsでは一般提供、Web Functionsではパブリックプレビューとして提供され、PythonでWebアプリケーションやAPIを構築できます。

### 変更内容・新機能の詳細

Python 3.15は、Lambdaのマネージドランタイムとして利用できます。また、Event Functionsではベースコンテナイメージも選択できます。AWSは、マネージドランタイムとベースイメージに対し、更新が提供され次第、自動で更新を適用します。Python 3.15の明示的な遅延インポートは関数の起動時間短縮に役立つ可能性があり、新しい組み込み型のfrozendictやsentinel、改善されたJITコンパイラーも利用できます。Powertools for AWS Lambda (Python)や、Lambdaコンソール、AWS CLI、AWS SAM、AWS CDK、AWS CloudFormationを使った開発・デプロイにも対応します。

### 影響範囲・利用シーン

- **対象ユーザー**: PythonでLambda関数、Webアプリケーション、APIを開発・運用する開発者
- **利用シーン**: Event FunctionsでPython 3.15の新機能を使ったサーバーレス処理を構築する場合
- **利用シーン**: Web Functionsのパブリックプレビューを利用して、Python製のWebアプリケーションやAPIを試作する場合
- **運用効果**: マネージドランタイムやベースイメージの更新が自動適用され、ランタイム更新の運用負荷を軽減できます

### 技術的な注意点

- **提供状況**: Event Functionsでは一般提供、Web Functionsではパブリックプレビューです。本番利用時はプレビュー機能の制約や変更可能性を考慮してください
- **コンテナイメージ**: Python 3.15のベースコンテナイメージはEvent Functionsで利用できます
- **リージョン**: Event FunctionsおよびWeb Functionsが提供されているすべてのリージョンで利用可能です
- **ランタイム更新**: AWSによる自動更新が適用されます。更新の制御や互換性確認が必要な場合は、ランタイム管理方法を確認してください
- **コスト**: Python 3.15固有の料金変更は記事に記載されていません。通常のLambda利用料金が適用されます

## [General] AWS launches standardized cost and rate columns in CUR 2.0 and Cost Explorer

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-cur-cost-explorer/

### 概要

AWS CUR 2.0とCost Explorerに、購入オプションをまたいで比較できる標準化されたコスト・レート項目が追加されました。CUR 2.0では設定を有効にすると、コミットメントや割引による削減額、償却コストを共通の方法で分析できます。

### 変更内容・新機能の詳細

CUR 2.0では、新規エクスポートの作成時または既存エクスポートの編集時に「Include standardized cost and rate columns」を有効にすると、cost_analytics_で始まる14個の列が追加されます。これらの列は、オンデマンド、Savings Plans、リザーブドインスタンス、EC2 Spot、EC2 Capacity Blocks for MLなどの購入オプションに対応します。
各明細行には、請求額・実効コスト・リスト価格・契約価格・公開オンデマンド価格などのコストと、それぞれに対応するレートが含まれます。割引適用前の公開価格に基づく請求額・実効コスト相当額も確認できるため、Savings Plansのレートや公開価格表を別途組み合わせたり、購入オプションごとに異なる列を使って償却コストを計算したりする作業を減らせます。
Cost Explorerでは、Advanced optionsから新しいコストタイプを選択すると、同じ種類のコストを確認できます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWSの利用コストを分析するFinOps担当者、財務担当者、クラウドエンジニア
- **利用シーン**: Savings Plansやリザーブドインスタンスなどのコミットメント、割引、段階料金によるコスト削減額の比較
- **運用効果**: 購入オプションごとに異なる計算方法を統一し、償却コストや割引効果をCUR 2.0およびCost Explorerで分析しやすくなります。

### 技術的な注意点

- **有効化方法**: CUR 2.0の新規作成時または既存エクスポートの編集時に「Include standardized cost and rate columns」を選択してください。既存エクスポートに自動で追加される設定ではありません。
- **列名**: 追加される14列の名前にはcost_analytics_のプレフィックスが付きます。
- **リージョン制限**: AWS GovCloud (US) リージョンおよび中国リージョンでは利用できません。
- **コスト**: 標準化コスト・レート列の利用に追加料金はかかりません。
- **Cost Explorer**: 新しいコストタイプはAdvanced optionsから選択します。

- https://docs.aws.amazon.com/cur/latest/userguide/table-dictionary.html

## [Cloudformation] AWS CloudFormation increases the default stacks per account quota to 300,000

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Cloudformation
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cloudformation-stacks-per-account-quota/

### 概要

AWS CloudFormationのアカウント・リージョンごとのスタック数のデフォルトクォータが、2,000から300,000に引き上げられました。対応するAWSリージョンで追加申請なしに多数のスタックを利用でき、既存スタックへの変更は不要です。

### 変更内容・新機能の詳細

CloudFormationは、関連するAWSリソースをスタックとしてまとめて作成・更新・削除するサービスです。今回の変更により、1つのAWSアカウントかつ1つのリージョンで利用できるスタック数のデフォルト上限が300,000になりました（従来は2,000）。顧客、環境、開発者ごとにスタックを分ける構成でも、従来より大規模に展開できます。上限はCloudFormationコンソール、AWS CLI、AWS SDK、AWS CDK、AWS SAMのいずれから作成する場合にも適用されます。現在のクォータはService Quotasコンソールで確認できます。

### 影響範囲・利用シーン

- **対象ユーザー**: 多数の顧客・環境・開発者ごとにCloudFormationスタックを分けて運用するチーム、SaaS事業者
- **利用シーン**: 顧客ごと、環境ごと、開発者ごとにスタックを作成するマルチテナント構成や大規模な環境分離
- **運用効果**: 1アカウント・1リージョンあたり最大300,000スタックまで、通常はクォータ引き上げ申請なしで拡張できます。既存スタックの変更は不要です。

### 技術的な注意点

- **適用範囲**: CloudFormationが利用可能なすべてのAWSリージョンで適用されます。クォータはアカウントおよびリージョンごとです
- **クォータ確認**: Service Quotasコンソールでスタック数のクォータを確認できます
- **コスト**: クォータ引き上げによる追加料金はありません。スタックが作成するAWSリソースには通常の利用料金が発生します
- **上限**: 300,000はスタック数のクォータです。利用するAWSサービスやリソースなど、関連する他のクォータも別途確認してください

## [Bedrock] AgentCore runtime instances now support Amazon EC2 G7 instances

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/agentcore-ec2-g7/

### 概要

Amazon Bedrock AgentCore Runtime の実行インスタンスで、NVIDIA RTX PRO 4500 Blackwell Server Edition GPU を搭載した Amazon EC2 G7 インスタンスが利用可能になりました。G7 をキャパシティプロバイダーの許可対象に追加することで、エージェントの 3D レンダリングやモデル推論に GPU を利用できます。

### 変更内容・新機能の詳細

AgentCore Runtime は、実行環境となる EC2 インスタンスのプロビジョニング、パッチ適用、スケーリング、ライフサイクル管理を担います。今回、G7.2xlarge から G7.48xlarge までのインスタンスタイプが GPU 選択肢に加わり、既存の G6e や G7e などと用途に応じて選べます。利用するには、キャパシティプロバイダーの許可対象インスタンスタイプに G7 を追加します。AgentCore がインスタンスに NVIDIA ドライバーをインストールするため、通常はコンテナイメージにドライバーを含めずに GPU ワークロードを実行できます。たとえば、エージェントのセッション内で 3D シーンのレンダリングやビジョンモデルの推論を実行でき、セッションは最大 14 日間利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Bedrock AgentCore Runtime で GPU を使うエージェントを開発・運用するチーム
- **利用シーン**: エージェントによる 3D レンダリング、ビジョンモデルなどの GPU 推論
- **運用効果**: AgentCore がインスタンスの管理と NVIDIA ドライバーのインストールを担うため、GPU 環境の構築・運用負荷を軽減できます

### 技術的な注意点

- **利用設定**: G7.2xlarge～G7.48xlarge をキャパシティプロバイダーの許可対象インスタンスタイプに追加してください
- **リージョン制限**: 米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（フランクフルト、ロンドン、ストックホルム）、アジアパシフィック（ムンバイ、シドニー）で利用可能です
- **コンテナ**: AgentCore が NVIDIA ドライバーをインストールします。コンテナイメージへのドライバー同梱は不要ですが、アプリケーションやフレームワーク側の GPU 対応は別途確認してください
- **セッション上限**: セッションは最大 14 日間です
- **コスト**: プロビジョニングされたコンピューティングの管理に対する料金に加えて、Amazon EC2 の料金が発生します。利用するインスタンスタイプや稼働状況を踏まえて見積もってください

## [RDS] ​​​Amazon RDS for Db2 now supports renaming databases​ 

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: RDS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-db2-supports-rename-databases

### 概要

Amazon RDS for Db2で、データベースをバックアップ・復元せずに、インスタンス上で名前変更できるようになりました。新しいストアドプロシージャ `rdsadmin.rename_database` を使って実行し、処理状況は `rdsadmin.get_task_status` で確認できます。

### 変更内容・新機能の詳細

従来、データベース名を変更するには、データベースをバックアップし、新しい名前で復元する必要がありました。今回の機能では、データをその場に保持したまま名前を変更できるため、バックアップと復元を行う方法より短時間で作業できます。

たとえば、バックアップから復元したデータベースを本番用に切り替える場合、元のデータベースの名前を変更し、復元したデータベースに元の名前を付けることで、アプリケーションの接続文字列を変更せずに置き換えられます。名前変更はバックグラウンドタスクとして実行されます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for Db2のデータベース管理者、移行・運用を担当するエンジニア
- **利用シーン**: バックアップから復元したデータベースへの切り替えや、データベース名の変更
- **運用効果**: バックアップと復元を使った従来の手順より迅速に切り替えられ、接続文字列を変更せずに済む場合があります

### 技術的な注意点

- **実行方法**: `rdsadmin.rename_database` ストアドプロシージャを呼び出して名前を変更します
- **処理状況の確認**: 名前変更はバックグラウンドタスクとして実行されるため、`rdsadmin.get_task_status` で状態を確認してください
- **リージョン制限**: Amazon RDS for Db2が提供されているすべてのAWSリージョンで利用できます
- **事前確認**: 実行時の要件や制約を、Amazon RDS for Db2のユーザーガイドで確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-db2-supports-rename-databases
- https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/db2.html

## [VPC] Amazon Route 53 now supports Availability Zone (AZ) affinity routing

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: VPC
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-affinity-routing/

### 概要

Amazon Route 53 に AZ アフィニティルーティングが追加されました。VPC 内のクライアントからの DNS クエリに対し、同じ AZ にあるリソースを優先して応答することで、AZ 間通信を抑え、レイテンシの低減を支援します。

### 変更内容・新機能の詳細

AZ アフィニティレコードでは、応答先の場所を Availability Zone、Zone Group、Region、Global のいずれかとして指定します。クエリ元のクライアントが属する AZ のレコードがあればそれを返し、該当レコードがない場合は Zone Group、Region、Global の順に、より広い範囲のレコードへフォールバックします。AZ を指定する場合は、AZ 名ではなく use1-az1 のような AZ ID を使用します。

AZ、Zone Group、Region のレコードにはヘルスチェックを関連付けられます。エンドポイントが正常でない場合、Route 53 は次の場所のレコードにフォールバックします。パブリックホストゾーンとプライベートホストゾーンの両方で利用でき、Global レコードはインターネットなど、VPC 外からのクエリにも応答します。レコードは Route 53 コンソール、API、AWS CLI、AWS SDK、CloudFormation から作成できます。

### 影響範囲・利用シーン

- **対象ユーザー**: VPC 内のクライアントから複数 AZ のエンドポイントへ接続するアプリケーションの設計者、ネットワーク／運用チーム
- **利用シーン**: AZ ごとに配置したアプリケーションやサービスへ、クライアントと同じ AZ 内から接続させたい場合
- **期待される効果**: AZ 間の通信を抑え、レイテンシの低減とアプリケーション応答性能の向上を支援
- **適用範囲**: パブリック／プライベートホストゾーンで利用可能。Route 53 のホストゾーンが利用できる AWS 商用リージョンで提供

### 技術的な注意点

- **AZの指定**: Availability Zone レコードには AZ 名ではなく AZ ID（例: use1-az1）を指定します
- **フォールバック**: 対象 AZ のレコードがない場合は Zone Group、Region、Global の順に評価されます。ヘルスチェックで異常と判定された場合も、次の場所のレコードへフォールバックします
- **Globalレコード**: VPC 外からのクエリ（インターネットからのクエリなど）に応答するレコードとして利用できます
- **ヘルスチェック**: AZ、Zone Group、Region のレコードに関連付け可能です。ヘルスチェックの設定と料金は Route 53 の仕様を確認してください
- **料金**: Route 53 の料金が適用されます。DNS クエリやヘルスチェックなど、利用する機能に応じた料金を料金ページで確認してください

### 影響範囲・利用シーン

- **利用シーン**: DynamoDBのバックアップを1時間ごとから週次までの頻度でスケジュールし、任意の復旧ポイントからテーブルを復元
- **運用効果**: 変更分のみを保存することでバックアップストレージを削減でき、クロスリージョンコピーでも削減効果を期待できます
- **適用範囲**: AWS BackupがDynamoDBを保護するすべてのAWSリージョン

### 技術的な注意点

- **フルバックアップ周期**: 初回のフルバックアップ後、AWS Backupは15日ごとに新しいフルバックアップを作成します
- **既存利用者の設定**: 既存のDynamoDBバックアップでは、AWS Backup設定の高度な機能から増分バックアップを有効化できます。設定はアカウントおよびリージョン単位で管理します

## [Route 53] Amazon Route 53 private hosted zones now support public DNS fallback

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Route 53
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-public-dns-fallback/

### 概要

Route 53 のプライベートホストゾーンで、ゾーン内にレコードがない名前への問い合わせをパブリック DNS にフォールバックできるようになりました。これにより、プライベート DNS に必要なレコードだけを定義し、それ以外は既存のパブリック DNS で解決できます。

### 変更内容・新機能の詳細

これまで、VPC に関連付けられたプライベートホストゾーンは、そのドメインに対して権威を持つものとして扱われていました。そのため、プライベートホストゾーンに該当レコードがない名前を問い合わせると、パブリック DNS に同名レコードがあっても NXDOMAIN が返されていました。今回のパブリック DNS フォールバックを有効にすると、プライベートホストゾーンで該当する名前が見つからない場合、Route 53 がパブリック DNS から回答を取得します。たとえば、プライベートホストゾーンの example.com で example.com をプライベートエンドポイントに向けつつ、プライベートゾーンには定義していない partner.example.com をパブリック DNS で解決できます。利用するには、プライベート Advanced Hosted Zone を新規作成するか既存のプライベートホストゾーンをアップグレードし、フォールバックを有効にします。Route 53 コンソール、API、AWS CLI、AWS SDK、CloudFormationから設定できます。

### 影響範囲・利用シーン

- **対象ユーザー**: プライベートホストゾーンとパブリック DNS の両方を利用するネットワーク管理者、クラウドエンジニア
- **利用シーン**: 一部の名前だけをプライベートエンドポイントへ向け、その他の名前はパブリック DNS で解決する構成
- **運用効果**: パブリックゾーンのレコードをプライベートゾーンへ複製して同期する手間を削減できます
- **適用範囲**: Route 53 プライベートホストゾーンが利用可能なすべての AWS 商用リージョン

### 技術的な注意点

- **前提条件**: パブリック DNS フォールバックは Advanced Hosted Zones の機能です。新規作成または既存ゾーンのアップグレード後に有効化してください
- **解決動作**: フォールバックされるのはプライベートホストゾーンに該当レコードがない名前です。プライベートゾーンにレコードがある名前は、引き続きそのプライベートレコードに基づいて解決されます
- **依存関係**: フォールバック対象の名前はパブリック DNS のレコードに依存するため、公開側のレコード変更や削除が VPC 内の名前解決にも影響します
- **コスト**: Advanced Hosted Zones の料金が適用される可能性があります。アップグレード前に Route 53 の料金ページで確認してください
- **リージョン制限**: Route 53 プライベートホストゾーンが利用可能な AWS 商用リージョンで利用できます

## [EKS] AWS Secrets Store CSI Driver Provider now supports AssumeRole for cross-account secret access

- **公開日**: 2026-11-20 (JST)

### 概要

AWS Secrets Store CSI Driver Provider（ASCP）がクロスアカウントの AssumeRole に対応しました。EKS Pod がシークレットやパラメータの保存先アカウントの IAM ロールを引き受けて取得できるため、個々のシークレットへのリソースポリシー設定を簡素化できます。

### 変更内容・新機能の詳細

SecretProviderClass に取得先アカウントの IAM ロールを指定すると、ASCP がそのロールを AssumeRole して Secrets Manager のシークレットや Systems Manager Parameter Store のパラメータを取得します。従来のクロスアカウントアクセスでは、各シークレットにリソースポリシーを設定し、Secrets Manager の AWS 管理 KMS キー（aws/secretsmanager）を利用できないため、カスタマーマネージド KMS キーを用意する必要がありました。今回の方式では、取得先アカウントのロールに信頼ポリシーを設定することで、アクセス設定を集約できます。対象ロールのセッション名にはワークロード固有の情報が記録され、取得先アカウントの CloudTrail でアクセス元を追跡しやすくなります。IRSA と EKS Pod Identity の両方で、初回マウントおよびローテーション時の取得に対応し、フェイルオーバーリージョンもサポートします。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数の AWS アカウントや EKS クラスターでシークレットを管理するプラットフォームチーム、セキュリティチーム、アプリケーション開発者

- **運用効果**: 各シークレットへのリソースポリシー設定を避け、取得先アカウントのロールに信頼ポリシーを集約できます。AWS 管理 KMS キーで暗号化されたシークレットもクロスアカウントで取得できます
- **監査**: CloudTrail の AssumeRole セッション情報から、アクセスしたワークロードを識別しやすくなります

### 技術的な注意点

- **IAM権限**: EKS ワークロード側の IAM アイデンティティには対象ロールを引き受ける権限を、取得先ロールにはワークロード側を信頼する信頼ポリシーと、対象リソースを読み取る権限を設定してください
- **SecretProviderClass**: AssumeRole の対象ロールを指定し、取得先アカウントのロール ARN や対象リソースを正しく設定してください
- **認証方式**: IRSA と EKS Pod Identity の両方に対応します。利用中の認証方式に応じた EKS 側の設定が必要です

- **コスト**: Secrets Manager や Parameter Store の利用料金が適用されます。既存の料金体系を確認してください

従来は、別のVPCへ移すには移動先に新しいクラスターを作成してデータを移行し、アプリケーションの接続先も更新する必要がありました。今回の機能では、既存クラスターに対してModifyDBCluster APIを呼び出すか、RDSコンソールの変更操作を行うことで移動できます。データはクラスター内に保持され、エンドポイントも変わりません。IPアドレス空間の拡張、CIDR範囲が重複しないネットワークへの移行、ネットワーク構成の統合、セキュリティ・コンプライアンス要件の変更などに対応しやすくなります。Aurora Global Database、Amazon RDS Proxy、Amazon RDS Blue/Green Deploymentsなど、現在のVPCに関連付けられた機能は移動前に無効化し、移動後に新しいVPCで再設定する必要があります。

### 影響範囲・利用シーン

- **対象ユーザー**: Aurora PostgreSQLまたはAurora MySQLクラスターを運用するAWS利用者、ネットワーク・セキュリティ担当者
- **利用シーン**: IPアドレス空間の不足、CIDRの重複解消、ネットワーク構成の統合、セキュリティやコンプライアンス要件の変更に伴うVPC移行
- **運用効果**: データ移行や接続先エンドポイントの変更を避けながらクラスターを移動でき、移行作業を簡素化できます。移動中には短時間の接続中断が発生します。

### 技術的な注意点

- **対象機能**: Aurora Global Database、RDS Proxy、RDS Blue/Green Deploymentsなど、現在のVPCに関連付けられた機能は移動前に無効化し、移動後に再設定してください
- **接続性**: エンドポイントは維持されますが、移動中は接続が短時間中断します。移動先VPCからのルーティング、サブネット、セキュリティグループなどの接続条件を事前に確認してください
- **リージョン制限**: Aurora PostgreSQL with express configurationが利用可能なAWSリージョンで提供されます
- **コスト**: 記事に本機能の追加料金に関する記載はありません。移動後の構成に伴う通常のAWS利用料金は発生します

## [Msk] Amazon MSK Connect now supports restarting existing connectors

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: Msk
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-msk-connect-restart-existing-connectors

### 概要

Amazon MSK Connectで、コネクタとそのタスクを削除・再作成せずに再起動できるようになりました。すべてのタスク、または失敗したタスクだけを選んで再起動でき、ストリーミングデータパイプラインの復旧を迅速化できます。

### 変更内容・新機能の詳細

Amazon MSK Connectは、Amazon MSKと連携するApache Kafka Connectコネクタをマネージド環境で実行・監視・スケーリングするサービスです。従来は障害からの復旧にコネクタの削除と再作成が必要でしたが、新機能では既存および新規作成したコネクタをその場で再起動できます。コネクタと全タスクを再起動する方法に加え、失敗したタスクだけを選んで再起動する方法も利用できます。また、失敗タスクがない場合でも、外部システムや依存関係の一時的な問題への対処、変更の反映を目的にコネクタを再起動できます。Amazon MSKコンソール、AWS CLI、AWS SDK、AWS CDKから操作できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon MSK ConnectでKafka Connectコネクタを運用する開発者、データエンジニア、SRE・運用チーム
- **利用シーン**: コネクタやタスクの障害、一時的な外部依存先の問題からの復旧
- **運用効果**: コネクタを削除・再作成せずに復旧でき、作業負荷や停止時間の削減が期待できます
- **料金**: この再起動機能の追加料金はありません

### 技術的な注意点

- **再起動対象**: コネクタと全タスク、または失敗したタスクを選択して再起動できます
- **適用対象**: 既存のコネクタと新規作成したコネクタが対象です
- **利用方法**: Amazon MSKコンソール、AWS CLI、AWS SDK、AWS CDKから操作できます
- **リージョン制限**: Amazon MSK Connectが利用可能なすべてのAWSリージョンで利用できます
- **運用上の注意**: 再起動はコネクタの処理に影響するため、対象とタイミングを確認して実行してください

## [General] Amazon Aurora DSQL now supports multi-Region peering across continents

- **公開日**: 2026-11-20 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aurora-dsql-intercontinental-multi-region-clusters/

### 概要

Amazon Aurora DSQLで、異なる大陸にあるAWSリージョン同士を組み合わせたマルチリージョンクラスターを作成できるようになりました。2大陸のアプリケーションから、強い一貫性を保った単一のデータベースに読み書きできます。

### 変更内容・新機能の詳細

これまでは、マルチリージョンクラスターを構成するリージョンは同じ地理的なリージョンセット内にある必要がありました。今回の変更により、たとえば米国東部（バージニア北部）と欧州（アイルランド）のように、異なる大陸のリージョンをピアリージョンとして選択できます。クラスター作成時には、2つのピアリージョンに加えて witness リージョンを指定します。片方のリージョンが利用できなくなった場合も、コミット済みの書き込みは保持され、もう一方のリージョンで読み書きを継続できます。利用可能なリージョンは、Aurora DSQLのマルチリージョンクラスターに対応しているリージョンです。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数大陸でサービスを提供するアプリケーションの開発者、データベース管理者、SRE/運用チーム
- **利用シーン**: 大陸ごとのユーザーに近いリージョンへデータベースを配置し、低遅延のアクセスを目指す構成
- **運用効果**: 大陸をまたぐリージョン障害への耐性を高め、片方のリージョンが利用できない場合も、もう一方で読み書きを継続できます
- **設計上の効果**: 2つのピアリージョンとwitnessリージョンを選び、必要な耐障害性に応じて障害ドメインを広く分離できます

### 技術的な注意点

- **リージョン要件**: Aurora DSQLのマルチリージョンクラスターに対応しているリージョンが対象です。利用前に公式のリージョン一覧を確認してください
- **構成要素**: 2つのピアリージョンとwitnessリージョンを指定します。各リージョンの役割や配置要件をユーザーガイドで確認してください
- **一貫性と障害時の動作**: 強い一貫性を提供し、コミット済み書き込みはリージョン障害時にも保持されます。アプリケーション側の接続先や再試行動作も含めて障害時の動作を検証してください
- **コスト**: リージョン間のデータ転送などにより費用が発生する可能性があります。構成と利用量に応じた料金を事前に確認してください

- https://docs.aws.amazon.com/aurora-dsql/latest/userguide/
