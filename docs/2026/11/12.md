## [General] AWS Quick enhances granular governance with the ability to restrict structured data sources

- **公開日**: 2026-11-12 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-quick-structured-data-source-restrictions/

### 概要

AWS QuickのEnterpriseエディションで、構造化データソースの作成・更新・共有を、コネクタの種類ごとに制御できる機能が一般提供されました。管理者はカスタム権限プロファイルを使い、セルフサービス分析を維持しながらデータガバナンスを強化できます。

### 変更内容・新機能の詳細

管理者はQuickのUI、API、またはAWS CLIからカスタム権限プロファイルを設定し、ユーザーが操作できる構造化データソースの種類を制限できます。たとえば、Amazon Redshiftのデータソース作成は許可しつつ、ファイルアップロードによるデータソース作成を禁止できます。また、特定のコネクタのデータソース共有を禁止することも可能です。作成・更新・共有の制限はそれぞれ独立して設定でき、すべてのデータソースに一律の制限をかける方式より細かく制御できます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Quick Enterpriseエディションを利用する組織の管理者、データガバナンス担当者、セルフサービス分析を行うユーザー
- **利用シーン**: 利用者や部門ごとに、作成・更新・共有を許可するデータソースのコネクタを制御する
- **運用効果**: 承認済みのデータソース利用を促しながら、ユーザーのセルフサービス分析を継続できる

### 技術的な注意点

- **エディション**: カスタム権限プロファイルによる設定はEnterpriseエディションが対象です
- **設定方法**: QuickのUI、API、AWS CLIから設定できます。組織の管理者に必要な権限があることを確認してください
- **制御範囲**: 作成・更新・共有の制限は独立して設定できます。設定するコネクタと操作の組み合わせを事前に整理してください
- **リージョン**: 対応するAWS Quickリージョンで利用できます。利用予定リージョンが対象か、記事および公式ドキュメントで確認してください
- **コスト**: 記事には追加料金に関する記載がありません。料金への影響は公式料金情報で確認してください

## [Route 53] Amazon Route 53 Domains now supports self-service restore for expired and deleted domains

- **公開日**: 2026-11-12 (JST)
- **カテゴリ**: Route 53
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/route-53-domains-self-service-restore/

### 概要

Amazon Route 53 Domains では、期限切れまたは最近削除されたドメインを、AWS Supportへの問い合わせなしで復元できるようになりました。Route 53 コンソール、AWS CLI、AWS SDKsから手続きできます。

### 変更内容・新機能の詳細

復元するドメイン名を入力し、復元料金を確認して請求に同意したうえでリクエストを送信します。Route 53 が該当するトップレベルドメイン（TLD）のレジストリと連携し、ドメイン登録を再有効化してAWSアカウントに戻します。復元に対応するTLDは多くありますが、復元可能な期間は各レジストリが定めています。更新忘れ、支払い方法の期限切れ、誤削除などで失われたドメインを復旧し、そのドメインに依存するWebサイト、メール、アプリケーションの再開に役立ちます。

### 影響範囲・利用シーン

- **対象ユーザー**: Route 53 Domainsでドメインを管理するAWS利用者、Webサイト・メール・アプリケーションの運用担当者
- **利用シーン**: 更新漏れ、支払い方法の期限切れ、誤削除などで期限切れまたは削除されたドメインの復元
- **運用効果**: AWS Supportへの問い合わせを介さずに復元を申請でき、ドメインに依存するサービスの復旧を進めやすくなります
- **コスト影響**: 復元料金が発生し、通常の新規登録や更新より高額になる場合があります

### 技術的な注意点

- **対応TLD**: 多くのTLDで復元できますが、すべてのTLDが対象とは限りません。対応状況は公式のTLD一覧で確認してください
- **復元期限**: 復元できる期間はTLDレジストリごとに異なります。期限切れ・削除後は早めに手続きを確認してください
- **料金**: 申請時に表示される復元料金を確認し、請求に同意する必要があります。料金は新規登録や通常更新より高くなる場合があります
- **復元結果**: レジストリによる再有効化後、ドメインはAWSアカウントに戻ります。復元後にWebサイトやメールが利用可能か、DNS設定なども確認してください
- **操作方法**: Route 53コンソール、AWS CLI、AWS SDKsから利用できます

- https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/registrar-tld-list.html

## [Fsx For Lustre] Amazon FSx for Lustre lowers the entry cost of Intelligent-Tiering file systems by 75%

- **公開日**: 2026-11-12 (JST)
- **カテゴリ**: Fsx For Lustre
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/fsx-lustre-intelligent-tiering-lower-throughput/

### 概要

Amazon FSx for Lustre の Intelligent-Tiering ファイルシステムで、設定可能な最小スループット容量とメタデータ IOPS が従来の 4分の1になりました。小規模なデータセットから始める HPC や機械学習のワークロードで、より低い初期コストから利用できます。

### 変更内容・新機能の詳細

最小スループット容量は 4,000 MBps から 1,000 MBps に、最小メタデータ性能は 6,000 IOPS から 1,500 IOPS に引き下げられました。スループット容量はファイルサーバーが提供する読み書き速度に関係し、メタデータ IOPS はファイルやディレクトリの作成・読み取り・削除を処理できる頻度に関係します。Intelligent-Tiering は、アクセス頻度の高いデータと低いデータが混在し、常時 SSD 相当の性能を必要としないワークロード向けの、弾力性の高い Lustre ストレージクラスです。新しい最小値は、Intelligent-Tiering が利用可能なすべての AWS リージョンで、新規ファイルシステムに適用されます。

### 影響範囲・利用シーン

- **対象ユーザー**: HPC、機械学習、データ処理基盤を構築・運用するクラウドエンジニア
- **利用シーン**: 小規模なデータセットから開始し、データ量や処理需要の増加に合わせて拡張するワークロード
- **運用効果**: 最小スループット容量とメタデータ IOPS が低くなり、Intelligent-Tiering を導入する際の容量・性能面の初期コストを抑えやすくなります
- **適合性**: ホットデータとコールドデータが混在し、一定の SSD レベル性能を常時必要としないワークロードに適しています

### 技術的な注意点

- **適用対象**: 引き下げ後の最小値は新規の Intelligent-Tiering ファイルシステムで利用できます。既存ファイルシステムへの適用可否は、変更前に公式ドキュメントで確認してください
- **最小設定値**: スループット容量は 1,000 MBps、メタデータ性能は 1,500 IOPS です
- **リージョン制限**: Intelligent-Tiering が提供されている AWS リージョンが対象です
- **性能特性**: Intelligent-Tiering は常時 SSD レベルの性能を必要とする用途向けではありません。ワークロードのアクセス特性と必要性能を確認してください
- **コスト**: 最小設定値の引き下げにより初期コストを抑えやすくなりますが、実際の料金は選択するストレージやプロビジョニング設定などに応じて確認してください

### 参考情報

- https://docs.aws.amazon.com/fsx/latest/LustreGuide/

## [Backup] AWS Backup adds logically air-gapped vault support for Amazon EBS Snapshots Archive

- **公開日**: 2026-11-12 (JST)
- **カテゴリ**: Backup
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-backup-lag-vault-ebs-archive/

### 概要

AWS Backupの論理的エアギャップボールトに保存したAmazon EBSバックアップを、低コストのEBS Snapshots Archiveへ移行できるようになりました。長期保管やコンプライアンス要件に対応しながら、スナップショットの保管コストを削減できます。

### 変更内容・新機能の詳細

AWS Backupのバックアッププランで、論理的エアギャップボールトをバックアップ先またはコピー先に指定し、ライフサイクル設定で「Archive Amazon EBS snapshots」を有効にします。ウォームストレージに保管する期間を設定すると、その期間の経過後にEBSスナップショットがArchiveへ移行します。対象のバックアッププランルールは、月次またはそれより低い頻度で実行する必要があります。論理的エアギャップボールトは、デフォルトでロックされたイミュータブルなバックアップを保管し、AWS所有キーまたはカスタマー管理キーによる暗号化に対応します。また、アカウント間やAWS Organizations内でバックアップを安全に共有し、直接リストアできます。

### 影響範囲・利用シーン

- **対象ユーザー**: EBSスナップショットを長期保管するAWS運用担当者、バックアップ管理者、コンプライアンス担当者
- **利用シーン**: 月次以下の頻度で取得するEBSバックアップを、論理的エアギャップボールトで保護しながらArchiveへ移行
- **運用効果**: アクセス頻度の低いスナップショットの保管コストを抑えつつ、イミュータブルな保護と長期保持を実現
- **利用可能リージョン**: 論理的エアギャップボールトとEBS Snapshots Archiveの両方が利用可能なAWSリージョン

### 技術的な注意点

- **バックアップ頻度**: 対象のバックアッププランルールは月次またはそれより低い頻度で実行する必要があります
- **設定方法**: AWS Backupコンソール、AWS CLI、AWS SDKから設定できます。バックアップ先またはコピー先の指定に加え、ルールのライフサイクルでArchiveへの移行とウォームストレージ期間を設定してください
- **復元**: Archive層のスナップショットは、通常のウォーム層より復元に時間がかかる場合があります。復旧目標時間に合うか事前に確認してください
- **コスト**: Archiveの保管料金は低コストですが、移行・保管期間や復元に伴う料金を含め、最新の料金条件を確認してください
- **リージョン制限**: 利用可否は両機能が提供されているリージョンに限られます。詳細は公式ドキュメントで確認してください

- https://docs.aws.amazon.com/aws-backup/latest/devguide/logicallyairgappedvault.html

### 影響範囲・利用シーン

- **運用効果**: 互換性と出力プロファイルの検証により、更新後のジョブ動作を確認しながら、セキュリティ修正や性能改善、新しいテーブル形式への対応を取り込みやすくなる
- **適用範囲**: AWS Commercial Regionsで利用可能

### 技術的な注意点

- **設定**: ジョブのAWS Glueバージョンに「Auto」を指定します。Glue Studio、AWS CLI、API、SDKから設定できます
- **アップグレード制御**: 新しいバージョンでジョブを実行する前に利用者の同意を得る仕組みが含まれます。組織内の承認・変更管理手順との整合を確認してください
- **互換性と検証**: ジョブの互換性に加え、出力スキーマ、データ量、レイテンシー、形式に基づく検証が行われます。コード変更が必要なジョブは現行バージョンで実行を継続します
- **リージョン制限**: AWS Commercial Regionsで利用可能です。その他のAWS環境での提供状況は公式ドキュメントを確認してください
- **コスト**: 記事では自動アップグレード機能の追加料金について明記されていません。ジョブの実行時間や実行回数の変化に伴うGlue利用料金は確認してください

### 技術的な注意点

- **設定方法**: 変換ルールをYAMLファイルで定義し、EKSバックアップの復元時に適用します
- **適用範囲**: Amazon EKSバックアップの復元が対象です。記事では、商用AWSリージョンおよびAWS GovCloud (US) リージョンで利用可能とされています
- **事前確認**: 変換後のIAMロールや接続先などが復元先環境に存在し、復元後のワークロードから利用できることを確認してください
- **コスト**: 記事に追加料金の有無は記載されていません。最新の料金情報をAWS Backupの料金ページで確認してください

これまでCloud WAN Routing PolicyでBGPコミュニティを評価できるのは、Site-to-Site VPNおよびConnectアタッチメントのルートでした。今回、Direct Connectアタッチメントにも対応したことで、オンプレミスのルーターからルートにコミュニティを付与し、そのタグをCloud WANのルーティングポリシーで条件として利用できます。たとえば、本番系と災害復旧系の経路を識別してフィルタリングする、特定の経路を優先する、伝搬先のリージョンを制限するといった制御が可能です。また、Cloud WANからオンプレミスのルーターへコミュニティを伝搬し、オンプレミス側のルーティング判断にも活用できます。これにより、VPNオーバーレイや各拠点でのポリシー手動複製に頼らず、ハイブリッドネットワークの経路制御を一元化しやすくなります。

### 影響範囲・利用シーン

- **利用可能リージョン**: AWS Direct ConnectとAWS Cloud WANの両方が利用可能なすべてのAWSリージョン

- **コスト**: enhanced snapshotの保存にはGB-month単位の料金が発生します。ブルー/グリーンデプロイでは新旧アプリケーションを並行稼働させる期間の利用料金も考慮してください

### 変更内容・新機能の詳細

M8idおよびR8idはAWS専用のカスタムIntel Xeon 6プロセッサを搭載し、最大384 vCPU、3 TiBメモリ、22.8 TBのローカルNVMe SSDストレージに対応します。記事によると、M5dおよびR5dインスタンスと比べて、vCPU数とメモリは最大4倍、ローカルストレージは6倍超です。これらのインスタンスを選択すると、RDS for SQL ServerがtempdbのデータファイルとログファイルをローカルNVMeインスタンスストアに自動配置します。一方、データベースのデータファイルとログファイルは引き続きAmazon EBSに保存されます。インスタンスストア上のtempdbファイルはスナップショットに含まれないため、スナップショットのサイズとバックアップストレージ使用量を抑えられます。既存インスタンスの変更または新規インスタンスの作成は、RDSコンソール、AWS SDK、AWS CLIから行えます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for SQL Serverを利用するデータベース管理者、開発者、運用チーム

- **運用効果**: tempdbの低レイテンシ化が期待でき、スナップショットにtempdbが含まれないことでバックアップストレージ使用量の削減につながる

### 技術的な注意点

- **ストレージの配置**: tempdbのデータファイルとログファイルはローカルNVMeインスタンスストアに配置されますが、データベースのデータファイルとログファイルは引き続きEBSに保存されます
- **耐久性**: インスタンスストアは一時ストレージです。tempdbは一時データ用ですが、アプリケーションや運用手順で永続ストレージとして扱わないでください
- **バックアップ**: インスタンスストア上のtempdbファイルはスナップショットに含まれません
- **変更時の確認**: インスタンスクラス変更に伴う適用タイミングや停止の有無、SQL Serverのエディション・バージョンなどの要件を、実施前にRDSの公式ドキュメントで確認してください
