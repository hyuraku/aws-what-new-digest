## [Govcloud Us] Grok 4.7 now available on Kiro in AWS GovCloud (US)

- **公開日**: 2026-11-13 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/kiro-grok-4-7-aws-govcloud-us/

### 概要

Kiro IDEおよびCLIで、AWS GovCloud（US）リージョン向けにGrok 4.7が利用可能になりました。実験的サポートとして提供され、最大500Kトークンのコンテキストウィンドウに対応します。

### 変更内容・新機能の詳細

Grok 4.7は、長時間にわたる複雑な作業で集中を保ち、次の作業に進む前に結果を確認することを特徴とするモデルです。記事によると、Grok 4.6と比べて、リポジトリ全体に関わるコーディング作業での計画立案とエラーからの復旧がより安定しています。コンテキストウィンドウは最大500Kトークンです。Kiroのクレジット消費倍率は、リクエストが200Kトークン以下の場合は2.7倍、200Kトークンを超える場合は5.4倍です。組織の管理者は、ユーザーが利用できるモデルを制御できます。利用するにはIDEまたはCLIを最新バージョンに更新して再起動し、モデル選択メニューからGrok 4.7を選びます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS GovCloud（US）でKiro IDEまたはCLIを利用する開発者、およびモデル利用を管理する組織管理者
- **利用シーン**: 大規模なコードリポジトリの調査・変更や、長時間にわたるコーディングおよび知識作業
- **運用効果**: 計画立案やエラー復旧の改善により、複雑な開発作業を支援できます。管理者は利用可能なモデルを組織のポリシーに合わせて制御できます。
- **コスト影響**: Kiroクレジットの消費倍率は200Kトークン以下で2.7倍、200Kトークン超で5.4倍です。

### 技術的な注意点

- **提供状況**: 実験的サポートとして提供されます。業務利用前に、組織の要件や運用ポリシーへの適合性を確認してください。
- **リージョン**: 対象はAWS GovCloud（US）リージョンです。
- **利用条件**: Kiro IDEまたはCLIを最新バージョンに更新して再起動し、モデル選択メニューから選択してください。
- **管理者設定**: Kiro管理者がユーザーに公開するモデルを制御できます。
- **コンテキストとコスト**: 最大500Kトークンに対応します。リクエストが200Kトークンを超える場合は、クレジット消費倍率が5.4倍になります。

## [Rds For Oracle] Amazon RDS for Oracle reduces downtime for automatic minor version upgrades and scheduled maintenance

- **公開日**: 2026-11-13 (JST)
- **カテゴリ**: Rds For Oracle
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/rds-oracle-reduces-maintenance-downtime-for-amvu-scheduled-upgrades/

### 概要

Amazon RDS for Oracleで、マイナーバージョンアップグレードやOS更新などのメンテナンス時に必要なリソースを、メンテナンスウィンドウ開始前に準備するようになりました。これにより、DBインスタンスの停止時間を短縮できます。

### 変更内容・新機能の詳細

RDSは従来、メンテナンス開始後に必要なリソースを準備していたため、その準備時間もDBインスタンスの停止時間に含まれていました。今回の改善では、最大30分前からDBインスタンスがワークロードを処理し続けている間にリソースを準備します。メンテナンスウィンドウ開始時には準備済みのリソースを利用できるため、インスタンスがオフラインになる時間が短くなります。対象は、自動マイナーバージョンアップグレード、およびメンテナンスウィンドウに設定されたマイナーバージョンアップグレードとOS更新です。Enterprise EditionとStandard Edition 2の両方に適用され、自動マイナーバージョンアップグレードを有効にしている場合は自動的に利用できます。準備の開始・完了・未完了を知らせる新しいRDSイベントも通知されます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon RDS for Oracleを利用するDB管理者、アプリケーション運用チーム
- **利用シーン**: 自動または予定されたマイナーバージョンアップグレード、OS更新の適用
- **運用効果**: メンテナンス時の停止時間を短縮し、アプリケーションへの影響を抑えながら更新を適用しやすくなります
- **監視**: 新しいRDSイベントで、事前準備の開始・完了・未完了を確認できます

### 技術的な注意点

- **対象エディション**: Enterprise EditionおよびStandard Edition 2のDBインスタンスが対象です
- **事前準備**: メンテナンスウィンドウ開始の最大30分前に行われ、準備中もDBインスタンスは利用可能です
- **競合時の動作**: 事前準備と競合する変更が行われた場合、準備済みリソースはロールバックされ、ユーザーの変更が優先されます
- **準備未完了時**: 事前準備を完了できなくても、予定されたメンテナンスはメンテナンスウィンドウ内で実施されます
- **リージョン**: Amazon RDS for Oracleが利用可能なすべての商用AWSリージョンおよびAWS GovCloud (US) リージョンで利用できます
- **コスト**: 追加料金はありません
- **停止時間**: 短縮されますが、メンテナンス時の停止がなくなる機能ではありません

## [Organizations] AWS Security Hub CSPM now supports centralized configuration with AWS Organizations declarative policies

- **公開日**: 2026-11-13 (JST)
- **カテゴリ**: Organizations
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/security-hub-cspm-org-policies/

### 概要

AWS Security Hub CSPMをAWS Organizationsの宣言型ポリシーで一元管理できるようになりました。組織内のアカウントやリージョンに対して、Security Hub CSPMの有効化やセキュリティ標準・コントロールの設定を適用し、構成のばらつきを抑えられます。

### 変更内容・新機能の詳細

宣言型ポリシーでは、組織内のすべてのアカウントとリージョンに一律で設定を適用するほか、特定のアカウントとリージョンの組み合わせを対象にすることもできます。Security Hub CSPMの有効化に加え、どのセキュリティ標準やコントロールを有効にするかを定義できます。ポリシーはアカウントの設定をポリシーに沿った状態に保つため、構成ドリフトの防止に役立ちます。また、新規アカウントにも自動適用でき、作成時からベースライン設定を適用できます。
AWSは、組織全体でSecurity Hub CSPMを管理する方法として宣言型ポリシーを推奨しています。既存の中央設定は移行準備が整うまで継続利用でき、Security Hub CSPMコンソールの移行プロセスを使うと、既存の中央設定ポリシーを宣言型ポリシーに変換し、適切なアカウントとリージョンに適用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Organizationsで複数アカウントを管理するセキュリティ担当者、クラウド管理者、運用チーム
- **利用シーン**: Security Hub CSPMの有効化、セキュリティ標準・コントロールの設定を組織全体または対象アカウント／リージョンに適用
- **運用効果**: 新規アカウントへのベースライン適用や構成ドリフトの抑制により、組織内の設定を統一しやすくなる
- **移行**: 既存の中央設定は継続利用でき、準備ができた段階でコンソールから宣言型ポリシーへ移行可能

### 技術的な注意点

- **リージョン**: 商用リージョン、AWS GovCloud (US)、中国リージョンで利用可能
- **適用範囲**: 組織全体への適用に加え、アカウントとリージョンを指定した適用が可能
- **移行**: Security Hub CSPMコンソールの移行プロセスで中央設定ポリシーを変換して適用します。移行前に対象アカウントとリージョンへの適用結果を確認してください
- **料金**: Security Hub CSPMは30日間無料で試用できます。無料期間後の料金は利用状況に応じて発生する可能性があるため、料金ページを確認してください

## [Bedrock] Amazon Bedrock AgentCore Identity now supports OAuth 2.0 discovery URLs

- **公開日**: 2026-11-13 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/bedrock-agentcore-oauth2-discovery/

### 概要

Amazon Bedrock AgentCore Identityで、OIDCのディスカバリーURLに加えて、OAuth 2.0認可サーバーのディスカバリーURLを利用できるようになりました。これにより、OIDCを実装していないOAuth 2.0認可サーバーも、受信JWT認可や送信OAuth認証情報プロバイダーに接続できます。

### 変更内容・新機能の詳細

従来、AgentCore Identityの設定で指定できるディスカバリーURLはOIDCのものに限られていました。今回の更新により、JWT authorizer（AgentCoreへの受信リクエストのJWT認可）およびカスタムOAuth credential provider（AgentCoreから外部サービスへ接続する際のOAuth認証情報）の設定で、OIDCまたはOAuth 2.0認可サーバーのディスカバリーURLを選択できます。OAuth 2.0のみを実装するサーバーが公開する認可サーバーメタデータを利用できるため、OIDC対応を前提とせずに既存の認証基盤と連携できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Bedrock AgentCoreを利用する開発者、認証・ID基盤の設計者
- **利用シーン**: OIDCを提供しないOAuth 2.0認可サーバーを、AgentCoreの受信JWT認可または送信OAuth認証情報プロバイダーに接続する場合
- **運用効果**: OIDCへの対応を認可サーバー側に求めず、既存のOAuth 2.0認証基盤をAgentCoreと連携しやすくなります

### 技術的な注意点

- **設定対象**: JWT authorizerまたはカスタムOAuth credential providerの構成時に、利用する認可サーバーに対応したディスカバリーURLを指定します
- **互換性**: OIDCとOAuth 2.0のディスカバリーURLを利用できます。認可サーバーが公開するメタデータ形式に合ったURLを選択してください
- **リージョン制限**: Amazon Bedrock AgentCoreが利用可能なすべてのAWSリージョンで提供されます
- **コスト**: 本機能の追加料金はありません

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/bedrock-agentcore-oauth2-discovery/
- https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/

## [Secrets Manager] AWS Secrets Manager now supports cross-account replication

- **公開日**: 2026-11-13 (JST)
- **カテゴリ**: Secrets Manager
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/secrets-manager-cross-account/

### 概要

AWS Secrets Managerで、シークレットを別のAWSアカウントへレプリケーションできるようになりました。プライマリの値やローテーション結果を、別アカウントの独立したシークレットへ自動反映できます。

### 変更内容・新機能の詳細

従来のマルチリージョンレプリケーション機能がアカウント間にも拡張されました。プラットフォームまたはセキュリティチームがプライマリシークレットを一元管理・ローテーションし、利用側アカウントには常に最新のローカルコピーを保持できます。レプリカは独立したAWSリソースであり、レプリカ側アカウントが所有するカスタマーマネージドKMSキーで暗号化されます。プライマリの値が変更された場合、ローテーションによる更新も含めてSecrets Managerがレプリカを自動更新します。重要なシークレットを復旧用・フェイルオーバー用の専用アカウントに保持し、必要に応じてレプリカを単独のシークレットへ昇格できます。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数アカウントを運用するプラットフォームチーム、セキュリティチーム、アプリケーション運用チーム
- **利用シーン**: 各アカウントで必要なシークレットをローカルに保持し、アカウント間のアクセス許可や共有KMSキーに依存せず利用する
- **運用効果**: シークレットの集中管理とローテーションを維持しながら、バックアップや災害復旧、フェイルオーバーに備えられる
- **コスト**: レプリカを含む利用料金が発生する可能性があるため、Secrets Managerの料金体系を確認してください

### 技術的な注意点

- **暗号化**: レプリカはレプリカ側アカウントが所有するカスタマーマネージドKMSキーで暗号化されます。キーの準備や利用権限を確認してください
- **同期と独立性**: レプリカは独立したリソースですが、プライマリからの更新が自動反映されます。昇格後の動作や運用手順は公式ドキュメントを確認してください
- **リージョン制限**: Secrets Managerが提供されているすべてのAWSリージョンで利用可能です
- **IAM権限**: レプリケーションの設定・管理に必要なIAM権限を確認してください。APIの詳細はAssociateCrossAccountReplicaのリファレンスを参照してください

- https://docs.aws.amazon.com/secretsmanager/latest/userguide/replicate-secrets.html

- **新規ナビゲーション項目**: レイアウトを設定済みのdesignationでは、新しい項目は管理者が追加するまで非表示です
- **アクセス制御**: レイアウトは画面上の表示を制御する機能です。実際のデータやリソースへの権限管理の代替として扱わず、必要なアクセス制御も別途設定してください

## [Govcloud Us] AWS Batch on Amazon EKS adds Linux capabilities, seccomp, and pod-level settings

- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-batch-eks-security-context/

### 概要

AWS Batch on Amazon EKS で、ジョブ定義に Linux capabilities、seccomp プロファイル、Pod レベルのセキュリティコンテキストを設定できるようになりました。必要な権限やシステムコールだけを許可する構成を取りやすくなり、Pod Security Standards の restricted プロファイルを適用したクラスターでのジョブ実行に役立ちます。

### 変更内容・新機能の詳細

RegisterJobDefinition API のジョブ定義で、コンテナの securityContext に capabilities と seccompProfile を指定できます。また、podProperties の securityContext で fsGroup などの Pod 全体に適用する設定を定義できます。コンテナレベルの設定がある場合は、Pod レベルのデフォルトより優先されます。設定は AWS Management Console、AWS CLI、AWS SDK、AWS CloudFormation から行えます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon EKS 上で AWS Batch を利用する開発者、プラットフォームエンジニア、セキュリティ担当者
- **利用シーン**: Pod Security Standards の restricted プロファイルを適用したクラスターで、ジョブに必要な Linux 権限やシステムコールだけを許可して実行する
- **運用効果**: Pod やコンテナのセキュリティ設定をジョブ定義で管理でき、最小権限の適用や既存のセキュリティポリシーとの整合性を図りやすくなる

### 技術的な注意点

- **設定箇所**: コンテナ固有の設定はコンテナの securityContext、Pod 共通の設定は podProperties.securityContext に指定します
- **設定の優先順位**: コンテナレベルの設定は Pod レベルのデフォルトより優先されます
- **リージョン**: AWS Batch が利用可能なすべての AWS リージョンでサポートされます
- **コスト**: この機能自体による追加料金は発表されていません。通常の AWS Batch、Amazon EKS などの利用料金は発生します

## [Cognito] Amazon Cognito now supports OAuth 2.0 token exchange

- **公開日**: 2026-11-13 (JST)
- **カテゴリ**: Cognito
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cognito-token-exchange/

### 概要

Amazon CognitoがOAuth 2.0のトークン交換（RFC 8693）に対応しました。ユーザーのトークンを、特定の下流サービス向けに権限を絞ったトークンへ交換でき、ユーザーに代わって動作するサービスやAIエージェントの認可を扱いやすくなります。

### 変更内容・新機能の詳細

サービスやAIエージェントがユーザーに代わって別のサービスを呼び出す際、従来は元のユーザートークンを転送するか、独自のトークン発行機構を構築・運用する必要がありました。今回の機能では、OAuth 2.0トークン交換を使って、元のトークンより狭いスコープを持ち、単一のaudience（利用対象）に限定された新しいトークンを発行できます。交換後のトークンにはリフレッシュトークンは含まれません。中継するサービスやエージェントのトークン（actor token）を指定すると、Cognitoは交換後のトークンにactクレームを追加し、誰がユーザーに代わって処理したかを下流サービスが識別できるようにします。たとえば、MCPサーバーがユーザーのトークンをバックエンドAPI専用のトークンに交換し、actクレームでMCPサーバーを中継者として記録できます。トークン交換は、OAuthトークンエンドポイントまたは新しいGetDerivedToken APIから利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Cognitoを利用するアプリケーション開発者、API・マイクロサービスの設計者、AIエージェントやMCPサーバーの開発者
- **利用シーン**: ユーザーの認証情報を使って、エージェントや中継サービスが特定のバックエンドAPIを呼び出す場合
- **セキュリティ効果**: 元のユーザートークンを複数のサービスへ転送せず、利用先と権限を限定したトークンを渡せます
- **監査効果**: actクレームにより、ユーザー本人の直接操作と、サービスやエージェントがユーザーに代わって行った操作を区別しやすくなります

### 技術的な注意点

- **対応プラン**: EssentialsおよびPlusの機能プランで利用できます
- **リージョン**: Amazon Cognitoが利用可能なすべてのAWSリージョンで提供されます
- **トークンの性質**: 交換後のトークンは単一のaudience向けで、元のトークンより狭いスコープを設定できます。リフレッシュトークンは含まれません
- **下流サービスの検証**: 下流サービスではトークンの署名に加え、audience、scope、必要に応じてactクレームを検証してください
- **コスト**: 利用にはEssentialsまたはPlusの機能プランが必要です。料金への影響は利用プランと契約条件を確認してください
