## [Lambda] AWS Lambda now supports orchestrating MicroVMs with Lambda durable functions 

- **公開日**: 2026-11-26 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/lambda-durable-microvm/

### 概要

AWS Lambdaが、Lambda durable functionsからLambda MicroVMを起動・管理する拡張機能の開発者プレビューを発表しました。チェックポイントや自動リトライを活用し、隔離環境でのコード実行を含む長時間の処理をオーケストレーションできます。

### 変更内容・新機能の詳細

この拡張機能は、MicroVM上で個別のタスクを実行する操作や、複数タスクでファイルとメモリを共有するMicroVMセッションを提供します。durable functionがMicroVMのライフサイクルを管理し、タスクごとに進捗をチェックポイントとして保存し、失敗時には自動で再試行します。また、必要に応じてMicroVMのトークンを更新します。1つのdurable functionから複数のMicroVMを並列に制御でき、Amazon SQSやAmazon EventBridgeなどのイベントソースを起点にできます。MicroVMイメージ内にオプションのワーカーライブラリを組み込むと、タスクの受信、ハートビート送信、結果報告を行えます。Lambda durable functionsは、組み込みのチェックポイントとリトライにより、最大1年間実行されるマルチステップ処理やAIワークフローを構築できます。拡張機能はAWS Durable Execution SDKのTypeScriptおよびPythonで利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Lambdaで長時間の処理やAIワークフローを構築する開発者、CI/CD・セキュリティ運用チーム
- **利用シーン**: 信頼できないコードやAI生成コードをMicroVMの隔離環境で実行するソフトウェアファクトリー、セキュリティスキャナー、CI/CDジョブ
- **運用効果**: タスクの進捗保存、失敗時の自動再試行、MicroVMのライフサイクル管理をdurable functionに集約できます
- **イベント連携**: Amazon SQSやAmazon EventBridgeを起点に処理を開始でき、複数のMicroVMを並列にオーケストレーションできます

### 技術的な注意点

- **提供状況**: 開発者プレビューです。仕様変更の可能性があるため、本番ワークロードには使用しないでください
- **SDKと言語**: AWS Durable Execution SDKのTypeScriptおよびPython向けです。Lambda関数には拡張パッケージ、MicroVMイメージには対応するワーカーライブラリを追加します
- **リージョン制限**: Lambda durable functionsとLambda MicroVMの両方をサポートするAWSリージョンで利用できます
- **実行特性**: durable functionは最大1年間実行でき、進捗のチェックポイントと失敗時の自動リトライを利用できます
- **セキュリティ**: MicroVMはVMレベルの隔離を提供しますが、実行するコードやワーカーの権限・通信先などは別途適切に制御してください
- **コスト**: LambdaおよびMicroVMの利用に伴う料金が発生する可能性があります。プレビューの料金条件を含め、利用前に最新の料金情報を確認してください

## [CloudWatch] Amazon CloudWatch Omni now integrates with PagerDuty

- **公開日**: 2026-11-26 (JST)
- **カテゴリ**: CloudWatch
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-cloudwatch-omni-pagerduty/

### 概要

Amazon CloudWatch OmniのアラートからPagerDutyインシデントを自動作成できるようになりました。既存のオンコール体制やエスカレーションポリシーを利用して通知・対応を進められ、手動通知の削減とMTTR短縮が期待できます。

### 変更内容・新機能の詳細

CloudWatch Omniでアラートが発生すると、PagerDutyにインシデントが作成されます。インシデントはPagerDutyに設定済みのオンコールスケジュールとエスカレーションポリシーに従って担当者へ通知されます。アラートには重大度、影響を受けるサービス、CloudWatch Omni上の関連データへのリンクが含まれるため、対応者は状況を確認して原因調査を開始できます。

### 影響範囲・利用シーン

- **対象ユーザー**: CloudWatch Omniで監視を行う運用チーム、SRE、オンコール担当者
- **利用シーン**: OmniのアラートをPagerDutyの既存インシデント管理フローへ連携し、担当者への通知やエスカレーションを自動化
- **運用効果**: 手動での通知作業を減らし、必要なコンテキストを伴う一貫した対応によってMTTRの短縮が期待できます

### 技術的な注意点

- **リージョン制限**: PagerDuty連携の提供リージョンはCloudWatch Omniの対応リージョンと異なる場合があります。利用前に公式の対応リージョン一覧を確認してください
- **連携設定**: PagerDuty側のオンコールスケジュールやエスカレーションポリシーを確認し、アラートが意図した担当者へ届くよう設定してください
- **コスト**: 記事に料金の詳細は記載されていません。CloudWatch OmniおよびPagerDutyの料金条件をそれぞれ確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-cloudwatch-omni-pagerduty/
- https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Omni.html

Amazon EC2 M8g インスタンスがイスラエル（テルアビブ）リージョンで利用可能になりました。AWS Graviton4 を搭載した汎用インスタンスで、Graviton3 ベースの M7g と比べて最大 30% 高いパフォーマンスを提供します。

M8g はアプリケーションサーバー、マイクロサービス、ゲームサーバー、中規模データストア、キャッシュなどの汎用ワークロード向けです。AWS の発表によると、M7g と比較してデータベースで最大 40%、Web アプリケーションで最大 30%、大規模 Java アプリケーションで最大 45% 高速です。また、M7g より最大 3 倍多い vCPU とメモリを備えるインスタンスサイズが用意されています。AWS Nitro System により、CPU 仮想化、ストレージ、ネットワーク機能の一部を専用ハードウェアとソフトウェアにオフロードし、ワークロードの性能とセキュリティを支援します。テルアビブリージョンでは、Savings Plans、オンデマンド、Spot Instances、Dedicated Instances、Dedicated Hosts で利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: イスラエル（テルアビブ）リージョンで EC2 を利用するアプリケーション開発者、インフラ・運用チーム
- **利用シーン**: アプリケーションサーバー、マイクロサービス、ゲームサーバー、中規模データストア、キャッシュなどの汎用ワークロード
- **期待できる効果**: Graviton3 ベースの M7g からの移行により、ワークロードに応じた性能向上や、より大きな vCPU・メモリ構成の利用が期待できます
- **購入方法**: Savings Plans、オンデマンド、Spot Instances、Dedicated Instances、Dedicated Hostsを選択できます

### 技術的な注意点

- **リージョン**: 利用可能になったリージョンはイスラエル（テルアビブ）です。利用可能なインスタンスタイプやサイズは、リージョン内の提供状況を確認してください
- **アーキテクチャ**: Graviton ベースのため Arm 対応の OS、AMI、アプリケーション、ライブラリが必要です。x86 向けソフトウェアを利用している場合は、移行前に互換性を検証してください
- **性能値**: 記載された性能向上率は M7g との比較における「最大」値であり、実際の効果はワークロードや構成によって異なります
- **コスト**: 料金はインスタンスサイズ、購入方法、利用時間などによって異なります。Savings Plans や Spot Instances の適用条件を確認してください

## [Elastic Load Balancing] Elastic Load Balancing for Envoy is now generally available

- **公開日**: 2026-11-26 (JST)
- **カテゴリ**: Elastic Load Balancing
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/elastic-load-balancing-for-envoy-generally-available

### 概要

AWSは、オープンソースのEnvoyプロキシをマネージドで運用する新しいロードバランサー「ELB for Envoy」の一般提供を開始しました。プロキシのパッチ適用やキャパシティ管理をAWSに任せながら、Envoyの拡張性や既存設定を活用できます。

### 変更内容・新機能の詳細

ELB for Envoyは、各ロードバランサーのプロキシを専用のAmazon EC2インスタンス上で実行し、AWS Nitro Systemによるハードウェア分離を提供します。EnvoyおよびOSの脆弱性（CVE）を監視し、パッチを自動適用するため、利用者がプロキシのアップグレードやセキュリティパッチ適用、アベイラビリティーゾーン間のキャパシティ管理を行う負担を軽減できます。
既存のEnvoy設定、拡張機能、コントロールプレーンを利用でき、AWS Certificate Manager（ACM）やAWS WAFとの連携も最小限の設定で追加できます。KubernetesでEnvoy Gatewayを利用している場合は、リモートインフラストラクチャプロバイダーを導入することで、Gateway APIリソースを書き換えずにプロキシをELB for Envoyへ移行できます。WebAssembly、Luaスクリプト、外部処理によるカスタムロジックにも対応します。
VPC内で動作し、VPCセキュリティグループおよびVPC暗号化と連携します。一般提供時点では、米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（アイルランド、フランクフルト、ストックホルム、スペイン）、アジアパシフィック（シドニー、香港、東京、シンガポール、ムンバイ、マレーシア、タイ）の14リージョンで利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Envoyをセルフマネージドで運用するプラットフォームチーム、Kubernetes運用チーム、Envoyの拡張性を必要とするアプリケーション開発者
- **利用シーン**: Kubernetes ingress、Envoy Gatewayの移行、カスタム認証、リクエスト変換、高度なトラフィックルーティング
- **運用効果**: EnvoyやOSのパッチ適用、プロキシのキャパシティ管理などの運用負荷を軽減できます
- **セキュリティ効果**: Nitro Systemによるハードウェア分離と自動パッチ適用により、プロキシの脆弱性対応と影響範囲の抑制を支援します

### 技術的な注意点

- **リージョン制限**: 一般提供時点で利用できるのは、米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（アイルランド、フランクフルト、ストックホルム、スペイン）、アジアパシフィック（シドニー、香港、東京、シンガポール、ムンバイ、マレーシア、タイ）の14リージョンです
- **既存環境との連携**: Envoyの既存設定、拡張機能、コントロールプレーンを利用できます。Envoy Gatewayから移行する場合は、リモートインフラストラクチャプロバイダーを使用します
- **ネットワーク**: VPC内で動作し、VPCセキュリティグループおよびVPC暗号化に対応します
- **セキュリティ運用**: EnvoyとOSの脆弱性を監視し、パッチを自動適用します
- **コスト**: 料金の詳細はELBの料金ページで確認してください
