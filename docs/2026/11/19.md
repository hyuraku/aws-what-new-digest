## [Marketplace] AWS Marketplace now supports buyer contact sharing at subscription

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Marketplace
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/marketplace-buyer-contact-sharing/

### 概要

AWS Marketplaceで製品を購入する際、購入者が連絡先情報を販売者と共有できるようになりました。販売者は共有された情報を、導入支援やサポート、製品情報の案内に活用できます。

### 変更内容・新機能の詳細

購入者は、AWS Marketplaceの購入ページにある「deployment contact information」欄で、氏名、メールアドレス、会社名、国または地域を販売者に共有できます。入力欄には、過去の購入、AWS Profile、またはAWSアカウントの情報が利用可能な場合に自動入力されます。購入者は各項目を確認・編集してから購入でき、共有した情報はAWS Marketplaceコンソールの契約詳細ページで確認できます。販売者はAWS Partner Centralの契約詳細ページで情報を確認できるほか、新しいGetAgreementContacts APIで取得し、オンボーディングやサポートのワークフローに連携できます。SaaS販売者は、このAPIを使って自社の登録ページに情報を事前入力し、購入者に内容を確認してもらうこともできます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Marketplaceで製品を購入する顧客、および製品を提供する販売者
- **利用シーン**: サブスクリプション開始時の導入ガイド送付、初期設定支援、技術サポート、製品更新情報の案内
- **運用効果**: 販売者が購入直後から購入者へ連絡しやすくなり、SaaS登録ページなどでの情報再入力も削減できます

### 技術的な注意点

- **共有情報**: 氏名、メールアドレス、会社名、国または地域が対象です。購入者は購入前に入力内容を確認・編集できます
- **API連携**: 販売者はGetAgreementContacts APIで連絡先を取得できます。具体的なAPI権限やリクエスト仕様はAPIリファレンスを確認してください
- **リージョン制限**: AWS Marketplaceが提供されているすべての商用AWSリージョンで利用できます
- **コスト**: 本機能に伴う追加料金について、記事には記載されていません

## [Bedrock] AgentCore runtime instances now support Nested Virtualization

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/agentcore-nested-virtualization/

### 概要

Amazon Bedrock AgentCore Runtimeのインスタンスで、KVMを使ったネスト仮想化が利用可能になりました。エージェントのセッション内で仮想マシンやエミュレーターを実行できます。

### 変更内容・新機能の詳細

ネスト仮想化を有効にすると、AgentCore Runtimeインスタンス上で動作するエージェントが、Kernel-based Virtual Machine（KVM）を利用して独自の仮想マシンを起動できます。利用するにはLinux capacity providerの作成時にネスト仮想化を有効にします。そのcapacity providerのインスタンス上で実行される各セッションからKVMを利用できます。たとえば、Androidエミュレーターを使ったモバイルアプリのビルド・テストや、エージェントが実行するコードを軽量VM内で隔離する用途に適しています。対応インスタンスファミリーはIntelベースのC7i、C8i、M7i、M8i、R7i、R8iで、AgentCore Runtimeインスタンスが利用可能なAWSリージョンのうち、対応インスタンスタイプが提供されるリージョンで利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Bedrock AgentCoreでエージェントを構築・運用する開発者、プラットフォームエンジニア
- **利用シーン**: エージェントのセッション内でAndroidエミュレーターや仮想マシンを起動し、アプリのテストやコード実行環境の分離を行う
- **運用効果**: AgentCoreによるプロビジョニング、パッチ適用、スケーリング、ライフサイクル管理を利用しながら、VMを必要とするツールをエージェントに組み込める
- **コスト**: VM実行に伴うインスタンスリソースの消費が増える可能性があります。適用される料金はAgentCoreの料金情報と利用するインスタンスタイプを確認してください

### 技術的な注意点

- **有効化方法**: Linux capacity providerの作成時にネスト仮想化を有効にします。既存構成での有効化可否や設定手順は公式ガイドを確認してください
- **対応インスタンス**: IntelベースのC7i、C8i、M7i、M8i、R7i、R8iファミリーが対象です。利用前に各リージョンでのインスタンスタイプ提供状況を確認してください
- **適用範囲**: 有効化したcapacity providerのインスタンスで実行される各セッションからKVMを利用できます
- **リージョン制限**: AgentCore Runtimeインスタンスが利用可能なリージョンのうち、対応インスタンスタイプを利用できるリージョンに限られます
- **リソース管理**: VMやエミュレーターの起動はCPU・メモリなどの消費を増やすため、capacity providerの構成とエージェントの同時実行数を考慮してください

### 参考情報

- https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-nested-virtualization.html

## [General] AWS Systems Manager Parameter Store raises API throughput limits

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/parameter-store-raises-api-throughput-limits/

### 概要

AWS Systems Manager Parameter Storeで、高スループット設定を有効にしている場合の5つのAPI操作のクォータが引き上げられました。起動時や一括処理時に発生するリクエストの集中に、より対応しやすくなります。

### 変更内容・新機能の詳細

引き上げ後のスループット上限は、GetParametersByPathが100から500 TPS、PutParameterが10から50 TPS、DeleteParameterが5から50 TPS、DescribeParametersが10から100 TPS、GetParameterHistoryが10から100 TPSです。TPSは1秒あたりのトランザクション数を表します。対象となるのは高スループット設定を有効にしているアカウントです。設定値や構成情報の取得、パラメータの作成・更新・削除などを短時間に多数実行するワークロードで、スロットリングの発生を抑えやすくなります。

### 影響範囲・利用シーン

- **対象ユーザー**: Parameter Storeを利用するアプリケーション開発者、インフラ担当者、運用チーム
- **利用シーン**: 多数のLambda関数が同時起動してパス単位で設定を取得する場合、IaCデプロイでパラメータを大量に作成・更新する場合、古いパラメータを一括削除する場合
- **運用効果**: 対象APIの処理余力が増え、リクエスト集中時のスロットリングを軽減しやすくなります

### 技術的な注意点

- **適用条件**: 引き上げ後のクォータを利用するには、高スループット設定を有効にする必要があります
- **スロットリング対策**: 上限内でも一時的な制限が発生する可能性があるため、指数バックオフによる再試行などを引き続き実装してください
- **コスト**: 高スループットの有効化やAPI利用には追加料金が発生する場合があります。適用条件と料金は最新の料金ページで確認してください
- **リージョン**: 利用するリージョンでの設定状況とクォータを確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/parameter-store-raises-api-throughput-limits/
- https://docs.aws.amazon.com/systems-manager/latest/userguide/parameter-store-throughput.html
- https://aws.amazon.com/systems-manager/pricing/

## [Bedrock] AWS Revenue Measurement now supports closed-source models in Amazon Bedrock

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/revenue-measurement-bedrock/

### 概要

AWS Revenue MeasurementがAmazon Bedrockのクローズドソースモデルに対応しました。これにより、パートナーは自社ソリューションが生み出すBedrock利用料について、従来より包括的な収益帰属情報を確認できます。

### 変更内容・新機能の詳細

これまでは、Amazon NovaなどのAmazonモデルとオープンウェイトモデルの利用料がAWS Revenue Measurementの対象でした。今回の拡張により、クローズドソースモデルの利用も含めたAmazon Bedrockの料金全体が収益測定の対象になります。BedrockでResource Tagging、User Agent文字列、Identity Tagging、またはSaaS Account Taggingをすでに利用しているパートナーは、追加の実装なしで拡張された対象範囲のメリットを得られます。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon Bedrockを利用するパートナー、およびAWS Revenue Measurementでソリューションの収益を測定しているチーム
- **利用シーン**: クローズドソースモデルを含むBedrock利用料を、自社ソリューションに帰属する収益として把握
- **運用効果**: Amazonモデルやオープンウェイトモデルに限られていた測定範囲が拡大し、Bedrock経由で生み出す収益をより包括的に確認可能
- **導入負荷**: 対応するタグ付けや識別方法をすでに利用していれば、追加実装は不要

### 技術的な注意点

- **利用条件**: Bedrockの利用料を帰属させるには、Resource Tagging、User Agent文字列、Identity Tagging、SaaS Account Taggingのいずれかを利用している必要があります
- **リージョン**: AWS Revenue Measurementはすべての商用リージョンで一般提供されています
- **料金**: 本機能は利用料の測定・帰属範囲を拡張するもので、Bedrockの実際の利用料金が変更されることを示すものではありません。モデルの利用料金は別途発生します
- **確認事項**: 設定やベストプラクティスはAWS Revenue Measurementのオンボーディングガイドを確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/revenue-measurement-bedrock/

## [Connect] Amazon Connect Customer enables Cases by default for new instances

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Connect
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/connect-cases-enabled-by-default/

### 概要

Amazon Connectの新規インスタンスで、顧客の問い合わせ・課題を追跡して解決する「Cases」が初期状態で有効になります。既存インスタンスでも、AWS Management Consoleから関連機能との連携を有効化できます。

### 変更内容・新機能の詳細

新規インスタンスでは、CasesがSLA設定用のルール、顧客情報を活用するCustomer Profiles、ケース更新を他の業務アプリケーションへ通知するAmazon EventBridgeと連携した状態で提供されます。これにより、管理者による初期設定を行わずに、ケースの追跡や対応プロセスを開始できます。既存インスタンスでは、AWS Management Consoleからワンクリックでこれらの連携を有効化できます。また、新しく追加したケースフィールドは連携先へ自動的に同期されるため、フィールド追加のたびに連携設定を更新する必要がありません。

- **利用シーン**: 顧客の問い合わせや課題をケースとして管理し、SLAに基づく対応やCustomer Profilesを使った個別対応を行う
- **運用効果**: 新規インスタンスでは初期設定の手間を減らして運用を開始でき、既存インスタンスでも簡単に連携を追加できる
- **連携活用**: EventBridgeを通じて、ケース更新を契機に他の業務アプリケーションの処理を実行できる

### 技術的な注意点

- **利用可能リージョン**: 米国東部（バージニア北部）、米国西部（オレゴン）、カナダ（中部）、欧州（フランクフルト、ロンドン）、アジアパシフィック（ソウル、シンガポール、シドニー、東京）、アフリカ（ケープタウン）です
- **既存インスタンス**: 連携は自動で有効化されず、AWS Management Consoleで有効化が必要です
- **ケースフィールド**: 新規追加フィールドは自動的に連携先へ同期されます
- **コスト**: 記事に料金の詳細は記載されていません。利用する機能やEventBridgeのイベント処理に応じた料金を、各サービスの料金ページで確認してください

## [Elastic Block Store] AWS Transform supports optimized storage for server migration

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Elastic Block Store
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-transform-optimized-storage/

### 概要

AWS Transform for migrations が、移行対象サーバーごとの性能・容量データに基づき、最適なストレージ種別と構成を推奨する機能を提供します。コストまたは性能を重視する方針を選択でき、承認した設定は移行時に自動適用されます。

### 変更内容・新機能の詳細

推奨対象は Amazon EBS と Amazon FSx for NetApp ONTAP です。AWS Transform は各サーバーの観測済みの性能・容量データを使い、ストレージの過剰なプロビジョニングによるコスト増や、移行後の性能問題を抑える構成を提案します。FSx for NetApp ONTAP では、ファイルシステムのレイアウトとサイズも推奨されます。移行前に想定コストを確認し、承認した設定を起動時に適用できます。評価から起動まで推奨内容が一貫するため、サーバーごとの手作業による選定を減らせます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Transform for migrations を利用する移行担当者、クラウドアーキテクト、インフラ運用チーム
- **利用シーン**: サーバー移行時に、EBSまたはFSx for NetApp ONTAPの構成をサーバーごとに選定する作業
- **運用効果**: 性能・容量の実績に基づく推奨により、過剰なストレージ割り当てや移行後の性能不足を抑え、設定作業を効率化できます
- **コスト影響**: 移行前に想定コストを確認でき、コスト重視の推奨を選ぶことで過剰プロビジョニングの抑制が期待できます。実際の料金は適用する構成や利用量に応じて変わります

### 技術的な注意点

- **対象サービス**: 推奨対象は Amazon EBS と Amazon FSx for NetApp ONTAP です。FSx for NetApp ONTAPではファイルシステムのレイアウトとサイズも対象です
- **推奨方針**: コスト重視または性能重視を選択します。選択した方針に応じた推奨を確認し、承認してから移行時に適用してください
- **評価データ**: 推奨はサーバーの観測済み性能・容量データに基づきます。データの内容や代表性が推奨結果に影響するため、移行対象の利用状況を確認してください
- **リージョン制限**: AWS Transform for migrations が利用可能なすべてのAWSリージョンで利用できます。対象リージョンはAWS Transformの提供状況に依存します

### 参考情報

## [Marketplace] AWS Revenue Measurement now supports Identity Tagging

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Marketplace
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/revenue-measurement-identity-tagging/

### 概要

AWS Revenue Measurementに、パートナーソリューションが生み出したAWS利用量を識別する「Identity Tagging」が追加されました。リソースごとのタグ付けやコード変更を行わず、ソリューションが使用するIAMユーザーまたはロールへのタグ付けで利用量をパートナー製品に帰属させられます。

### 変更内容・新機能の詳細

パートナーは、ソリューションが利用するAWSアカウント内のIAMユーザーまたはIAMロールにタグを付与します。AWS Revenue Measurementは、そのアイデンティティによって作成されたリソースの利用量を、パートナーの製品に関連付けます。従来のResource Taggingでは、作成・管理する個々のリソースにタグを付ける必要があり、顧客環境ごとにタグ付けを徹底しにくい場合がありました。Identity Taggingでは、個々のリソースやSDK/API呼び出しを変更せずに導入できます。Resource Tagging、User Agent文字列、SaaS Account Taggingも引き続き利用でき、アーキテクチャに応じて方式を選択または併用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS上で顧客向けソリューションを提供し、AWS Revenue Measurementで利用量の帰属を確認するAWSパートナー
- **利用シーン**: ソリューションが使用するIAMロールまたはIAMユーザーを通じて作成されるリソースの利用量を、パートナー製品に関連付ける
- **運用効果**: 個々のリソースへのタグ付けやコード変更を減らし、顧客環境をまたいだ帰属設定を簡素化できる

### 技術的な注意点

- **対象アイデンティティ**: ソリューションが実際に使用するIAMユーザーまたはIAMロールにタグを設定してください
- **帰属範囲**: 記事では、そのアイデンティティによって作成されたリソースの利用量が対象とされています。既存リソースや別のアイデンティティが作成したリソースも対象になるとは限らないため、オンボーディングガイドで条件を確認してください
- **設定要件**: 必要なタグの形式や設定手順、IAM権限はオンボーディングガイドで確認してください。記事には詳細な仕様が記載されていません
- **リージョン**: すべての商用AWSリージョンで一般提供されています
- **コスト**: 追加料金の有無は記事に記載されていません

## [Marketplace] AWS Marketplace now supports buyer approval workflows

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Marketplace
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/marketplace-buyer-approvals/

### 概要

AWS Marketplaceで購入前の承認フローを設定できる「buyer approvals」が一般提供されました。購入金額や商品種別などの条件に応じて、承認先や承認方法を振り分けられます。

### 変更内容・新機能の詳細

購入ポリシーでは、購入金額、商品タイプ、価格、公開オファーかプライベートオファーかなどを条件に、承認が必要かどうかを定義できます。承認リクエストは、AWS Marketplaceコンソール、メールによる承認者のチェーン、またはCoupa・SAP Aribaなどの調達システムに振り分け可能です。メール承認では、調達・財務・法務・クラウドガバナンス担当者がAWSコンソールにサインインせず、メールで商品、価格、契約条件を確認して承認できます。調達システムに振り分けた場合は、既存の承認フローを利用でき、購入ごとに専用の発注書（PO）が作成されるため、支出管理や照合作業に役立ちます。従来の購入可能な商品制限やPO管理に加え、今回の機能により、購入前の承認プロセスも制御できるようになりました。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Marketplaceを利用する企業の調達、財務、法務、クラウドガバナンス担当者、および購入ポリシーを管理する管理者
- **利用シーン**: 高額なソフトウェア契約はCoupaやSAP Ariba、中規模の購入は複数人へのメール承認、少額または従量課金の購入は承認不要とするなど、条件に応じて承認経路を使い分ける
- **運用効果**: 購入前に社内承認を適用し、既存の調達プロセスとの連携や、POを用いた支出追跡・照合を行いやすくなる

### 変更内容・新機能の詳細

Software Partners向けに、次の3つの認定カテゴリーが追加されました。
・Customer Experience – Solution Extensions: 顧客体験のライフサイクル全体でAmazon Connect Customerと連携するソリューションを対象とします。

### 技術的な注意点

- **認定対象**: Software Partnersには新設の3カテゴリー、Services Partnersには既存の2カテゴリーが適用されます
- **申請要件**: Services PartnersはAdvancedまたはPremierティアであること、Software Partnersは承認済みのFoundational Technical Review（FTR）を完了していることが、申請前に必要です

- **コスト**: 認定拡張自体によるサービス料金の変更は記事に記載されていません。各パートナー製品やAmazon Connectの利用料金は個別に確認してください

### 変更内容・新機能の詳細

AWS Continuum for Penetration Testing（旧 AWS Security Agent）が、ペネトレーションテストジョブの一時停止・再開に対応しました。再開時は最後に保存されたチェックポイントから処理を続けるため、クライアント設定エラーなどで失敗した場合でも、ジョブを最初から実行し直す必要がありません。
メンテナンスやデプロイのために実行を中断したり、タスク時間上限に達したジョブの上限を引き上げたり、テスト中に期限切れとなった認証情報を交換したりしてから再開できます。再開前にはネットワークトラフィック設定やVPC構成も更新できますが、対象エンドポイントを含むテスト範囲は変更されません。操作はWebアプリケーション、またはStopPentestJob APIとResumePentestJob APIから行えます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Continuum for Penetration Testingを利用するセキュリティチーム、アプリケーション担当者
- **利用シーン**: デプロイやメンテナンス時の中断、設定修正・認証情報交換後のテスト再開
- **運用効果**: 完了済みの作業や検出結果を引き継げるため、再実行による手戻りを抑え、テストを効率的に継続できます

### 技術的な注意点

- **再開期限**: ジョブ作成から7日以内に再開する必要があります
- **テスト範囲**: 再開前にネットワークトラフィック設定やVPC構成は変更できますが、対象エンドポイントなどのスコープは変更できません
- **API**: 一時停止にはStopPentestJob、再開にはResumePentestJobを使用できます
- **利用可能リージョン**: AWS Continuum for Penetration Testingが提供されているすべてのAWSリージョンで利用できます
- **コスト**: 記事に料金変更の記載はありません。タスク時間上限を引き上げる場合は、利用料金への影響を料金情報で確認してください

## [Security Token Service] AWS STS announces GetScopedCredentials to scope down permissions at runtime

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Security Token Service
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/sts-getscopedcredentials/

### 概要

AWS STS の新しい GetScopedCredentials API により、既存の一時認証情報から、権限や有効期間をさらに制限した一時認証情報を実行時に発行できます。元の呼び出し元のアイデンティティを維持したまま、エージェントやワークロードに必要最小限の認証情報を個別に付与できます。

### 変更内容・新機能の詳細

GetScopedCredentials は、呼び出しに使用した一時認証情報の権限をポリシーで絞り込み、有効期間を短縮した認証情報を取得する API です。権限と有効期間はいずれも元の認証情報の範囲を超えないよう単調に制限されます。そのため、発行された認証情報から元の権限や有効期間を拡大することはできません。取得した認証情報は呼び出し元のアイデンティティを引き継ぎます。API の利用可否は IAM ポリシーで制御され、呼び出しは AWS CloudTrail に記録されます。商用リージョン、AWS GovCloud (US)、AWS European Sovereign Cloud (Germany)、中国リージョンで利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: エージェント、サブエージェント、ワークロードに一時認証情報を付与する開発者・運用者
- **利用シーン**: 既存の一時認証情報を基に、特定タスクに必要な権限だけを持つ認証情報を実行時に発行
- **運用効果**: アイデンティティ管理の仕組みを変更せず、権限と有効期間を限定した認証情報を個別に提供できます
- **監査**: API 呼び出しが CloudTrail に記録されるため、利用状況の追跡に活用できます

### 技術的な注意点

- **権限の制限**: 発行される認証情報の権限は呼び出し元の権限を超えません
- **有効期間**: 発行される認証情報の有効期間は呼び出し元の認証情報を超えません
- **IAM 権限**: GetScopedCredentials API の呼び出しを許可する IAM ポリシーが必要です
- **リージョン**: 商用リージョン、AWS GovCloud (US)、AWS European Sovereign Cloud (Germany)、中国リージョンで利用できます
- **監査**: 呼び出しは AWS CloudTrail に記録されます

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/sts-getscopedcredentials/
- https://docs.aws.amazon.com/STS/latest/APIReference/API_GetScopedCredentials.html

AWS Clean Roomsで、PySparkジョブの実行結果を中間テーブルに書き込み、後続の分析で再利用できるようになりました。複数段階にわたるパートナーとの分析ワークフローを、データを相互に開示・コピーせずに構成しやすくなります。

### 変更内容・新機能の詳細

PySparkジョブの出力先として中間テーブルを利用できます。たとえば、測定ベンダーがPySparkで特徴量エンジニアリングを行い、その結果を後続の機械学習モデルのトレーニングに渡すワークフローを構築できます。記事では、この分析結果を使って価値の高い新規顧客を特定し、広告キャンペーンのオーディエンスターゲティングや入札最適化に役立てる例が紹介されています。AWS Clean Roomsは、各参加者の元データを相互に開示したりコピーしたりせずに、共同分析を行うためのサービスです。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Clean Roomsを利用する企業、データ分析者、測定ベンダー、機械学習チーム
- **利用シーン**: PySparkによる特徴量エンジニアリングの結果を中間テーブルに保存し、後続の分析やモデル学習で再利用
- **運用効果**: 中間結果を次の処理へつなげやすくなり、複雑な複数段階の分析ワークフローを構成しやすくなる
- **データ保護**: パートナー間で元データを開示・コピーせずに共同分析を進められる

### 技術的な注意点

- **リージョン制限**: AWS Clean Roomsの提供リージョンを確認してください。機能の利用可否も対象リージョンで確認する必要があります
- **コスト**: PySparkジョブの実行や中間テーブルの保存に伴う料金が発生する可能性があります。利用前にAWS Clean Roomsの料金情報を確認してください
- **ワークフロー設計**: 中間テーブルを後続処理で再利用する構成では、出力と入力の関連付けや、コラボレーション内のアクセス設定を確認してください

## [Lambda] AWS Lambda now supports customer-managed runtimes, giving platform teams centralized control over runtime contents and updates

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-customer-managed-runtimes/

### 概要

AWS Lambdaで、関数のデプロイとは独立して管理できる「カスタマー管理ランタイム」が一般提供されました。プラットフォームチームが共通コンポーネントや更新を一元管理し、関数を個別に再デプロイせずにランタイムの更新を適用できます。

### 変更内容・新機能の詳細

カスタマー管理ランタイムは、Lambda関数とは別のリソースとして管理されます。ランタイムはAmazon ECR上のOCIコンテナイメージとして構築し、Lambdaのベースイメージを利用する方法と、独自に一から構築する方法があります。関数側はランタイムのエイリアスを設定して利用し、アプリケーションコードは従来どおり.zip形式でデプロイできます。

ランタイムには、承認済みSDK、証明書、セキュリティツール、監視ツールなどの共通コンポーネントを含められます。ランタイムの内容、更新、アクセス権、ライフサイクルをプラットフォームチームが集中管理でき、更新はLambdaが実行環境を再作成する際に関数へ反映されます。そのため、コンポーネント変更のたびに各関数を再デプロイしたり、関数ごとの更新作業を調整したりする必要がありません。更新のスケジュールや段階的な適用、ヘルスメトリクスの確認、ロールバックにも対応します。

ランタイムはリソースベースポリシーを使って、他のAWSアカウントやAWS Organizations内のアカウントと共有できます。AWS CLI、AWS SDK、CloudFormation、AWS CDKから作成・管理できます。従来の「custom runtimes」機能は「bring your own language」に名称変更されました。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数のLambda関数に共通のランタイム、ライブラリ、証明書、セキュリティ・監視コンポーネントを配布・管理するプラットフォームチームおよびアプリケーションチーム
- **利用シーン**: 組織承認済みコンポーネントを共通ランタイムとして配布し、関数ごとの再デプロイを避けながら更新する
- **運用効果**: ランタイム更新を一元管理し、段階的な適用、健全性の確認、迅速なロールバックを行いやすくなる
- **利用可能リージョン**: すべての商用AWSリージョンで一般提供

### 技術的な注意点

- **更新の反映タイミング**: 更新はLambdaが実行環境を再作成する際に反映されるため、既存の実行環境に即時反映されるとは限りません
- **構成**: ランタイムはAmazon ECRのOCIコンテナイメージとして用意し、関数ではランタイムのエイリアスを参照します。関数コードは引き続き.zip形式でデプロイできます
- **共有と権限**: 他アカウントやAWS Organizationsとの共有には、ランタイムのリソースベースポリシーを設定してください
- **コスト**: カスタマー管理ランタイム自体の追加料金はありません。関数には通常のLambda料金、ランタイムイメージには通常のAmazon ECR料金が適用されます
- **既存機能の名称**: 既存のcustom runtimes機能は「bring your own language」に名称変更されています

- https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-customer-managed-runtimes/
