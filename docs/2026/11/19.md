## [Opensearch Service] Amazon OpenSearch Memory is now generally available

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Opensearch Service
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-opensearch-memory-generally-available/

### 概要

Amazon OpenSearch Memoryが一般提供され、AIエージェントにセッションをまたいだ永続メモリを追加できるようになりました。会話履歴を毎回モデルに渡さず、過去のやり取りや判断、ユーザーの好みに関連する情報を検索・再利用できます。

### 変更内容・新機能の詳細

OpenSearch Memoryは、エージェントとのやり取りをイベントとして原文のまま保存し、数秒以内に検索可能にします。その後、保存したイベントから有用な構造化メモリを非同期で導出します。メモリの抽出、埋め込みの生成、インデックス作成、統合、新しい情報に応じた追加・更新・スキップ、検索までのライフサイクルを管理します。検索ではキーワード検索、セマンティック検索、ハイブリッド検索を利用できます。サーバーレス機能のため、クラスターやインスタンスタイプ、インデックスを利用者が用意する必要はなく、抽出と検索の容量は自動的にスケールします。

### 影響範囲・利用シーン

- **対象ユーザー**: Amazon OpenSearch Serviceを利用してAIエージェントを構築・運用する開発者、クラウドエンジニア
- **利用シーン**: 過去の会話、ユーザー設定、以前の判断を次のセッションでも参照するエージェントの構築
- **運用効果**: 会話履歴全体を毎回モデルに送る必要を減らし、メモリの抽出・検索基盤を個別に構築・運用する負担を軽減
- **提供リージョン**: 米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（フランクフルト）、アジアパシフィック（東京）

### 技術的な注意点

- **アクセス制御**: メモリストアごとにIAMでアクセスを制御できます。actorおよびsessionのスコープも設定できます
- **データ保持**: イベントとメモリそれぞれに有効期限を設定できます。要件に応じて保持期間を設計してください
- **検索と反映**: イベントは数秒以内に検索可能になりますが、構造化メモリの導出は非同期で行われます
- **リージョン制限**: 記事公開時点の提供リージョンは米国東部（バージニア北部、オハイオ）、米国西部（オレゴン）、欧州（フランクフルト）、アジアパシフィック（東京）です
- **コスト**: 料金が発生します。利用量や料金体系の詳細は公式料金ページで確認してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-opensearch-memory-generally-available/

## [Glue] Introducing the Apache Spark Optimization Agent for AWS Glue ETL

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Glue
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/apache-spark-aws-glue-etl/

### 概要

AWS Glue ETLに、完了済みのApache Sparkジョブを分析してコストまたはパフォーマンスの改善案を提示する「Apache Spark Optimization Agent」が追加されました。設定変更案に加え、根拠となるテレメトリや推奨理由も確認できます。

### 変更内容・新機能の詳細

AWS Glueコンソールから任意の完了済みジョブ実行を選び、コストまたはパフォーマンスのどちらを優先するか指定すると、エージェントがジョブ設定、ログ、Sparkテレメトリをまとめて分析し、数分以内に具体的な最適化案を返します。分析は決定論的な推奨エンジンによって行われ、並列度不足、結合キーのデータ偏り（skew）、メモリ不足によるディスクへのspill、アイドル状態のExecutor、過剰なキャパシティ確保など、実行時間やコストに影響する要因を調べます。コストと性能がトレードオフになる場合は、選択した目標指標を改善しつつ、もう一方の指標の悪化を定められた範囲内に抑える提案を行います。また、AWS Glueの新しいバージョンへの移行やAWS Gravitonプロセッサの利用といったベストプラクティスも確認します。提案はインフラストラクチャ、Spark設定、コード、データレイアウトの領域別に分類されます。コンソールに加えて、Amazon SageMaker Unified Studio MCP Server経由で利用でき、アクセスはIAMで認証され、AWS CloudTrailに記録されます。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS GlueでApache Spark ETLジョブを開発・運用するデータエンジニア、分析基盤チーム、クラウド運用チーム
- **利用シーン**: 完了済みジョブの設定や実行結果を分析し、コスト削減または処理時間短縮につながる改善案を検討する
- **運用効果**: テレメトリに基づく問題要因と根拠を確認でき、手作業でのログ・メトリクス分析やチューニングの負担を軽減できる
- **利用方法**: AWS Glueコンソール、またはAmazon SageMaker Unified Studio MCP Server経由で利用できる

### 技術的な注意点

- **対応バージョン**: AWS Glue 4.0以降が対象です
- **リージョン制限**: AWS Glueが利用可能なリージョンで提供されますが、AWS GovCloud（US）リージョンおよび中国リージョンは対象外です
- **権限と監査**: アクセスにはIAM認証が必要で、アクセスはAWS CloudTrailに記録されます
- **分析対象**: 完了済みジョブの設定、ログ、Sparkテレメトリを分析します。提示されるのは推奨事項であり、変更を適用する際は内容を確認してください
- **コスト**: 本機能の利用に追加料金はありません

### 参考情報

- https://aws.amazon.com/blogs/big-data/introducing-the-apache-spark-optimization-agent-for-amazon-emr-serverless-and-aws-glue-etl/

## [SageMaker] Amazon SageMaker AI now supports cross-Region inference routing

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: SageMaker
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/sagemaker-cross-region-routing/

### 概要

Amazon SageMaker AI のクロスリージョン推論ルーティングにより、リージョン内の容量不足やエンドポイントの異常時に、別リージョンの正常なエンドポイントへ推論リクエストを振り分けられるようになりました。独自のリージョン間ルーティングやヘルスチェックを構築せずに、推論サービスの可用性を高められます。

### 変更内容・新機能の詳細

推論ルーターを作成し、既存のリアルタイムエンドポイント、非同期エンドポイント、推論コンポーネントを登録して、アプリケーションからルーター宛てにリクエストを送ります。ルーターはまず自身のリージョンにあるエンドポイントを優先し、エラーの増加に応じて、別リージョンにある正常なエンドポイントへ新しいリクエストを切り替えます。ローカルのエンドポイントが回復すると、トラフィックは段階的に戻されます。既存のエンドポイント、モデル、コンテナを変更する必要はありません。クロスアカウントで利用する場合、エンドポイント所有者はエンドポイントポリシーで利用を許可するルーターを制御できます。また、任意のクロスリージョントラフィック上限を設定して、ローカル利用者向けの容量を確保できます。リアルタイム推論の応答には、処理を担当したエンドポイントとルーティング理由が含まれ、ルーターのメトリクスは Amazon CloudWatch で確認できます。

### 影響範囲・利用シーン

- **対象ユーザー**: SageMaker AI でリアルタイム推論または非同期推論を運用する開発者、MLプラットフォーム担当者、SRE/運用チーム
- **利用シーン**: 特定リージョンのアクセラレーテッドインスタンスの容量不足、またはエンドポイント異常時に、別リージョンのエンドポイントへ推論リクエストを振り分ける
- **運用効果**: 独自のリージョン間ルーティング、ヘルスチェック、リトライ処理の開発・保守を抑え、推論アプリケーションの可用性を高められる
- **対応範囲**: リアルタイム推論は商用AWSリージョンの32リージョン、非同期推論は25リージョンで利用可能

### 技術的な注意点

- **ルーティング設定**: 推論ルーターに既存の対象エンドポイントまたは推論コンポーネントを登録し、アプリケーションの送信先をルーターに変更します
- **クロスアカウント制御**: 他アカウントのルーターにエンドポイントを利用させる場合、エンドポイントポリシーで許可を設定します
- **容量保護**: 任意のクロスリージョントラフィック上限を設定し、エンドポイントのローカル利用者向け容量を確保できます
- **監視**: CloudWatch のルーターメトリクスでトラフィックの振り分け先を確認できます。リアルタイム応答には処理したエンドポイントとルーティング理由が示されます
- **リージョン制限**: リアルタイム推論は32リージョン、非同期推論は25リージョンが対象です。利用前に対象リージョンを確認してください
- **コスト**: クロスリージョン推論ルーティング自体の追加料金はありません。リクエストを処理する SageMaker AI エンドポイントの通常料金と、CloudWatch メトリクスの通常料金が発生します

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/sagemaker-cross-region-routing/

## [General] AWS announces ExtendDB 1.0  

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-extenddb-1-0/

### 概要

AWSが、DynamoDB互換のオープンソースアダプター「ExtendDB 1.0」を発表しました。選択したデータベースをバックエンドとして利用でき、DynamoDB向けのアプリケーションコードを大きく変更せずに、オンプレミスや各種クラウド、エッジ環境でワークロードを実行できます。

### 変更内容・新機能の詳細

ExtendDB 1.0は、本番利用向けとして公開された初のリリースです。DynamoDB互換APIを提供し、PostgreSQL、SQLite、Cassandra、MongoDBの4種類をストレージバックエンドとして選択できます。ローカル開発やCI向けには、SQLiteを使ってDynamoDB互換エンドポイントを起動するextenddb-devコンテナイメージと、@extenddb/dev npmパッケージが提供されます。これにより、開発・テストのために外部データベースを別途用意する必要がありません。AWSがメンテナンスし、Apache License 2.0で公開されており、GitHub上で開発されています。

### 影響範囲・利用シーン

- **対象ユーザー**: DynamoDB互換アプリケーションをオンプレミス、プライベート／パブリッククラウド、エッジ環境で運用したい開発者・インフラ担当者
- **利用シーン**: DynamoDB向けアプリケーションを、選択したデータベースをバックエンドとして動作させる
- **開発・テスト効果**: SQLiteベースの開発用エンドポイントにより、ローカル開発やCI環境のセットアップを簡素化できる
- **運用効果**: 実行環境やストレージバックエンドを選択でき、DynamoDB APIを利用するワークロードの配置先に柔軟性を持たせられる

### 技術的な注意点

- **互換性**: 記事ではDynamoDB APIとの互換性が示されていますが、採用前に利用するAPIや機能がExtendDB 1.0でサポートされるか、プロジェクトの仕様で確認してください
- **バックエンド**: PostgreSQL、SQLite、Cassandra、MongoDBで機能、性能、可用性、運用方法が異なるため、ワークロードに応じた検証が必要です
- **本番運用**: ExtendDBとバックエンドのデプロイ、セキュリティ、バックアップ、監視、スケーリングは利用者側で設計・運用する必要があります
- **開発用構成**: extenddb-devコンテナイメージと@extenddb/dev npmパッケージは、SQLiteを使ったローカル開発・CI向けです
- **ライセンスとコスト**: Apache License 2.0で提供されます。利用料金は記事に記載されていませんが、実行環境やバックエンドのインフラ費用が発生する場合があります
- **リージョン制限**: AWSリージョン上のマネージドサービスではなく、各自の環境で実行するソフトウェアとして紹介されています。記事にリージョン制限の記載はありません

## [General] AWS Transform custom now supports cross-account sharing of transformation definitions

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-custom-cross-account-td/

### 概要

AWS Transform customで、変換定義（TD）と関連レッスンをAWS RAM経由で他のAWSアカウント、OU、または組織全体に共有できるようになりました。共有先は静的コピーではなくライブリソースを利用し、既定では所有者が公開した最新バージョンを実行できます。

### 変更内容・新機能の詳細

TDの所有者はAWS RAMで共有範囲を指定し、4種類の管理されたアクセス許可から選択できます。許可の範囲は、既定の実行のみから、レッスンの利用、レッスンの所有者への提供、TDのダウンロードを許可するものまで段階的に設定できます。レッスンが所有者に戻るのは、共有権限で許可され、かつ利用者が提供に同意した場合に限られます。これにより、中央チームやAWS PartnerはTDを一度作成して複数アカウントに展開し、所有権を維持しながら標準化された変換を提供できます。共有はAWS Transform CLIおよびAWS RAMから利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数アカウントを管理するプラットフォームエンジニアリングチーム、AWS Partners、AWS Transform customのTD所有者・利用者
- **利用シーン**: APIやフレームワークのアップグレード、移行、言語変換などの標準化された変換を、AWS Organizations内の複数アカウントへ展開
- **運用効果**: TDを一元管理し、利用者が所有者の最新公開版を既定で利用できるため、静的コピーの配布・更新作業を削減
- **レッスン共有**: 権限と利用者の同意に応じて、変換から得られたレッスンを共有・集約可能

### 技術的な注意点

- **利用リージョン**: 米国東部（バージニア北部）、欧州（フランクフルト）、欧州（ロンドン）、アジアパシフィック（ムンバイ）、アジアパシフィック（ソウル）、アジアパシフィック（シドニー）、アジアパシフィック（東京）、カナダ（中部）で利用可能
- **共有範囲**: AWS RAMを通じてアカウント、OU、またはAWS Organizations全体に共有できます
- **アクセス許可**: 共有先に付与する操作を管理された権限から選択し、レッスンの利用・提供やTDのダウンロードを必要最小限に制限してください
- **バージョン管理**: 共有先は既定で所有者の最新公開版を実行するため、公開後の変更が利用者に影響する可能性があります。運用前に変更管理や検証手順を整備してください
- **レッスンの提供**: レッスンは権限が許可し、利用者がオプトインした場合にのみ所有者へ戻ります
- **料金**: 記事には共有機能自体の追加料金は明記されていません。AWS Transformの利用料金については最新の料金情報を確認してください

## [CloudFront] Amazon CloudFront standard logging now supports CMCD and additional log fields

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-standard-logging-cmcd-fields

### 概要

CloudFrontの標準ログで、これまでリアルタイムログでのみ利用できた追加フィールドとCMCD（Common Media Client Data）フィールドを記録できるようになりました。追加のリアルタイムログ用データストリームを構築せずに、再生状況とCloudFrontの配信情報を照合できます。

### 変更内容・新機能の詳細

標準ログに追加できるフィールドには、リクエストを処理したCloudFrontサーバーのIPアドレス、プライマリディストリビューションとステージングディストリビューションのトラフィックを区別する識別情報、メディア品質信頼度スコアが含まれます。また、動画プレーヤーがリクエストに付加するCMCD情報として、ビットレート、バッファ長、再生セッションIDなども記録できます。標準ログはAmazon S3、Amazon CloudWatch Logs、Amazon Data Firehoseへ配信できます。これにより、視聴者の再生問題をCloudFrontの配信データと関連付け、障害調査を効率化できます。

### 影響範囲・利用シーン

- **対象ユーザー**: CloudFrontで動画配信を行うストリーミングチーム、SRE、運用・分析担当者
- **利用シーン**: 視聴者の再生セッションやCMCD情報とCloudFrontのアクセスログを照合し、再生停止や品質低下の原因を調査
- **運用効果**: リアルタイムログ用の追加データストリームを用意せずに調査に必要な情報を標準ログへ集約でき、トラブルシューティングを迅速化
- **ログ配信先**: Amazon S3、Amazon CloudWatch Logs、Amazon Data Firehose

### 技術的な注意点

- **利用方法**: 標準ログの設定で必要な追加フィールドを選択してください
- **CMCD情報**: CMCDフィールドの記録には、動画プレーヤーが各リクエストでCMCD情報を送信している必要があります
- **提供範囲**: すべてのCloudFrontエッジロケーションで利用できます
- **料金**: CloudFront標準ログの料金が適用されます
- **リアルタイムログ**: 今回の追加フィールドを標準ログで利用するために、別途リアルタイムログのデータストリームを設定する必要はありません

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/cloudfront-standard-logging-cmcd-fields
- https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs.html

## [CloudFront] Amazon CloudFront Announces WebSocket and gRPC Support for Origin Mutual TLS

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: CloudFront
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-cloudfront-origin-mtls-websockets-grpc/

### 概要

CloudFrontが、アプリケーションオリジンとの相互TLS認証（origin mTLS）をWebSocketおよびgRPC通信にも対応させました。CloudFrontからの接続をTLS証明書で認証できるため、共有シークレットやIP許可リストに頼らず、HTTP・WebSocket・gRPCで一貫したオリジン認証を実現できます。

### 変更内容・新機能の詳細

CloudFrontは、AWSリージョン内のアプリケーションオリジンに対するWebSocketおよびgRPC接続で、オリジンとの相互TLS認証を利用できるようになりました。オリジン側がCloudFrontからの接続をクライアント証明書で確認することで、インターネットに公開されたアプリケーションへの未認証リクエストを防ぎやすくなります。対象オリジンには、Application Load BalancerやAPI GatewayなどAWS上のサービスのほか、オンプレミス環境やAWS外でホストされたオリジンも含まれます。従来はWebSocketやgRPCの接続元を識別するために共有シークレットやIP許可リストを使う必要がありましたが、origin mTLSによりHTTPを含む複数の通信方式で証明書ベースの認証に統一できます。

### 影響範囲・利用シーン

- **対象ユーザー**: CloudFront経由でWebSocketまたはgRPCの通信を提供するアプリケーション開発者、セキュリティ担当者、運用チーム
- **利用シーン**: チャット、共同編集、ライブダッシュボードなど、双方向通信やストリーミング通信を行うアプリケーションのオリジン保護
- **運用効果**: 共有シークレットやIP許可リストに依存せず、CloudFrontからオリジンへの接続を証明書で認証できる
- **コスト**: origin mTLSの追加料金はありません

### 技術的な注意点

- **レイテンシ**: cf.fetch()は応答を待って処理を判断するため、呼び出し先APIの応答時間がリクエスト処理時間に影響します

- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/amazon-rds-fast-storage-volume-initialization/

### 概要

Amazon RDSで、ポイントインタイムリカバリ、リードレプリカ作成、Single-AZからMulti-AZへの変換時に行われるストレージボリュームの初期化が高速化されました。初期化中もDBインスタンスは利用でき、進捗を確認できます。

### 変更内容・新機能の詳細

これらの操作ではスナップショットからストレージボリュームを作成し、Amazon S3からデータブロックを読み込みます。従来は、ブロックへのアクセス状況などによって初期化速度が変動し、初期化中にI/Oレイテンシが増加する場合がありました。今回の機能では、インスタンスに接続されたgp3およびio2ストレージボリューム全体で、DBインスタンスあたり最大4 TiB/時の専用帯域を使って初期化します。アカウント内で同時に行われる初期化が利用可能な帯域を超える場合、残りのブロックはベストエフォートで処理されます。機能はデフォルトで有効で、追加設定は不要です。

### 影響範囲・利用シーン

- **対象ユーザー**: RDSでポイントインタイムリカバリ、リードレプリカ作成、Single-AZからMulti-AZへの変換を行う利用者
- **利用シーン**: 復旧やレプリカ作成、可用性構成の変更後に、ストレージの性能が安定するまでの時間を予測しやすくする
- **運用効果**: 初期化中もDBインスタンスを利用でき、初期化状況を確認できる
- **対応エンジン・リージョン**: MariaDB、MySQL、PostgreSQL、Db2、Microsoft SQL Server、Oracle。商用AWSリージョンおよびAWS GovCloud (US) リージョンで利用可能

### 技術的な注意点

- **対象ストレージ**: 初期化速度の上限は、インスタンスに接続されたgp3およびio2ボリューム全体でDBインスタンスあたり最大4 TiB/時です
- **同時実行時の帯域**: アカウント内の同時初期化が利用可能な帯域を超える場合、残りのブロックはベストエフォートで初期化されます
- **進捗確認**: RDSコンソール、DescribeDBInstances API、AWS CLI、AWS SDKでStorageOperationStatusおよびStorageOperationPercentProgressを確認できます
- **有効化**: デフォルトで有効で、利用者による設定変更は不要です
- **コスト**: 追加料金はありません

## [Clean Rooms] AWS Clean Rooms supports writing PySpark job results to intermediate tables

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Clean Rooms
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-clean-rooms-pyspark-intermediate-table

### 概要

AWS Clean Roomsで、PySparkジョブの実行結果を中間テーブルに書き込み、後続の分析で再利用できるようになりました。複数段階にわたるパートナーとの分析ワークフローを、データを相互に開示・コピーせずに構成しやすくなります。

### 変更内容・新機能の詳細

PySparkジョブの出力先として中間テーブルを利用できます。たとえば、測定ベンダーがPySparkで特徴量エンジニアリングを行い、その結果を後続の機械学習モデルのトレーニングに渡すワークフローを構築できます。記事では、この分析結果を使って価値の高い新規顧客を特定し、広告キャンペーンのオーディエンスターゲティングや入札最適化に役立てる例が紹介されています。AWS Clean Roomsは、各参加者の元データを相互に開示したりコピーしたりせずに、共同分析を行うためのサービスです。

### 影響範囲・利用シーン

- **対象ユーザー**: AWS Clean Roomsを利用する企業、データ分析者、測定ベンダー、機械学習チーム
- **利用シーン**: PySparkによる特徴量エンジニアリングの結果を中間テーブルに保存し、後続の分析やモデル学習で再利用
- **運用効果**: 中間結果を次の処理へつなげやすくなり、複雑な複数段階の分析ワークフローを構成しやすくなる
- **データ保護**: パートナー間で元データを開示・コピーせずに共同分析を進められる

### 技術的な注意点

- **リージョン制限**: AWS Clean Roomsの提供リージョンを確認してください。機能の利用可否も対象リージョンで確認する必要があります
- **コスト**: PySparkジョブの実行や中間テーブルの保存に伴う料金が発生する可能性があります。利用前にAWS Clean Roomsの料金情報を確認してください
- **ワークフロー設計**: 中間テーブルを後続処理で再利用する構成では、出力と入力の関連付けや、コラボレーション内のアクセス設定を確認してください

- https://docs.aws.amazon.com/clean-rooms/latest/userguide/what-is.html

## [Lambda] AWS Lambda now supports customer-managed runtimes, giving platform teams centralized control over runtime contents and updates

- **公開日**: 2026-11-19 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-customer-managed-runtimes/

### 概要

AWS Lambdaで、関数のデプロイとは独立して管理できる「カスタマー管理ランタイム」が一般提供されました。プラットフォームチームが共通コンポーネントや更新を一元管理し、関数を個別に再デプロイせずにランタイムの更新を適用できます。

### 変更内容・新機能の詳細

カスタマー管理ランタイムは、Lambda関数とは別のリソースとして管理されます。ランタイムはAmazon ECR上のOCIコンテナイメージとして構築し、Lambdaのベースイメージを利用する方法と、独自に一から構築する方法があります。関数側はランタイムのエイリアスを設定して利用し、アプリケーションコードは従来どおり.zip形式でデプロイできます。

ランタイムには、承認済みSDK、証明書、セキュリティツール、監視ツールなどの共通コンポーネントを含められます。ランタイムの内容、更新、アクセス権、ライフサイクルをプラットフォームチームが集中管理でき、更新はLambdaが実行環境を再作成する際に関数へ反映されます。そのため、コンポーネント変更のたびに各関数を再デプロイしたり、関数ごとの更新作業を調整したりする必要がありません。更新のスケジュールや段階的な適用、ヘルスメトリクスの確認、ロールバックにも対応します。

ランタイムはリソースベースポリシーを使って、他のAWSアカウントやAWS Organizations内のアカウントと共有できます。AWS CLI、AWS SDK、CloudFormation、AWS CDKから作成・管理できます。従来の「custom runtimes」機能は「bring your own language」に名称変更されました。

### 影響範囲・利用シーン

- **対象ユーザー**: 複数のLambda関数に共通のランタイム、ライブラリ、証明書、セキュリティ・監視コンポーネントを配布・管理するプラットフォームチームおよびアプリケーションチーム
- **利用シーン**: 組織承認済みコンポーネントを共通ランタイムとして配布し、関数ごとの再デプロイを避けながら更新する
- **運用効果**: ランタイム更新を一元管理し、段階的な適用、健全性の確認、迅速なロールバックを行いやすくなる
- **利用可能リージョン**: すべての商用AWSリージョンで一般提供

### 技術的な注意点

- **更新の反映タイミング**: 更新はLambdaが実行環境を再作成する際に反映されるため、既存の実行環境に即時反映されるとは限りません
- **構成**: ランタイムはAmazon ECRのOCIコンテナイメージとして用意し、関数ではランタイムのエイリアスを参照します。関数コードは引き続き.zip形式でデプロイできます
- **共有と権限**: 他アカウントやAWS Organizationsとの共有には、ランタイムのリソースベースポリシーを設定してください
- **コスト**: カスタマー管理ランタイム自体の追加料金はありません。関数には通常のLambda料金、ランタイムイメージには通常のAmazon ECR料金が適用されます
- **既存機能の名称**: 既存のcustom runtimes機能は「bring your own language」に名称変更されています

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/11/aws-lambda-customer-managed-runtimes/
- https://docs.aws.amazon.com/lambda/latest/dg/welcome.html
