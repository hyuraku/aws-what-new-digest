## [Corretto] Amazon Corretto September 2026 Patch Updates

- **公開日**: 2026-09-28 (JST)
- **カテゴリ**: Corretto
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-corretto-sept-2026-updates/

### 概要

Amazon Correttoの複数バージョン（Corretto 25.0.4.10.1、21.0.12.11.1、17.0.20.12.1、11.0.32.12.1）に対するパッチが公開され、主に最新のtzdata 2026dが組み込まれました。Correttoは無償のマルチプラットフォームなOpenJDK配布です。

### 変更内容・新機能の詳細

2026年9月25日付で、AmazonはCorrettoの複数LTS/Feature Release版向けパッチを公開しました。対象バージョンはCorretto 25.0.4.10.1、21.0.12.11.1、17.0.20.12.1、11.0.32.12.1で、いずれもダウンロード可能です。本パッチの主な内容はtzdata（タイムゾーンデータベース）を最新版の2026dに更新することです。タイムゾーンの変更は日時計算、スケジューラ、ログのタイムスタンプ解釈などに影響するため、アプリケーションの動作確認が推奨されます。Correttoは複数プラットフォームで提供され、Correttoのホームページやダウンロードページから個別に取得できます。Linux環境ではapt、yum、apk用のCorrettoリポジトリを設定してパッケージ管理経由で更新を適用できます。なお、記事ではCorretto 27を含む各バージョンのダウンロード案内も示されていますが、本パッチで更新が提供されたのは上記の4バージョンです。

### 影響範囲・利用シーン

- **対象ユーザー**: Javaアプリケーションを運用する開発者・SRE/運用チーム（Corretto 11/17/21/25を使用している環境）
- **利用シーンまたは効果**: タイムゾーン変更に依存するバッチ処理、スケジューラ、ログ解析、認証・課金・レポート生成などの正確性向上（tzdata更新により最新の地域別夏時間や法改正が反映される）
- **運用効果**: tzdata更新により時刻ずれや誤スケジュールのリスクを低減できるため、運用トラブルの予防に寄与する
- **導入の注意点**: ランタイム上のJVMプロセスは再起動が必要（JVMは起動時のタイムゾーンデータを参照するため）、影響範囲の確認と段階的ロールアウトを推奨

### 技術的な注意点

- **適用方法**: Corretto公式ダウンロードからバイナリを取得するか、Linuxではapt/yum/apk用のCorrettoリポジトリを設定してパッケージ管理で更新を適用
- **JVM再起動**: tzdata更新は稼働中のJVMに自動反映されないため、JVMプロセスの再起動が必要
- **互換性検証**: アプリケーションの日時処理・テストスイートで事前検証を行ってから本番反映すること
- **ロールアウト**: パッケージ管理（apt/yum/apk）経由での段階的適用やブルー/グリーン展開が推奨される
- **コスト**: Amazon Corretto自体は無償で提供されるためソフトウェア利用料は発生しないが、更新作業に伴う運用コスト（テスト・ダウンタイム）は考慮が必要
- **リージョン制限**: Correttoの配布・ダウンロードに地域制限は通常ない（S3配布のミラー等に依存するが、公開情報上はリージョン制限なし）
- **その他**: 本パッチは記事記載の4バージョンに対する更新であり、Corretto 27はダウンロード可能と案内されているが、この記事で列挙されたパッチ対象には含まれていない点に注意

## [Documentdb] Amazon DocumentDB (with MongoDB compatibility) now supports retryable writes

- **公開日**: 2026-09-28 (JST)
- **カテゴリ**: Documentdb
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-documentdb-retryable-writes/

### 概要

Amazon DocumentDB（MongoDB互換）はエンジンバージョン8.0.2から retryable writes をサポートし、トランジェントなエラー（ネットワーク断やプライマリフェイルオーバー等）発生時にドライバが特定の書き込みを自動的に1回再試行できるようになりました。これにより追加のアプリ側コード変更なしに耐障害性が向上します。

### 変更内容・新機能の詳細

主な変更点：
- サポート開始バージョン: エンジン 8.0.2 以降で retryable writes をサポート。
- 動作: MongoDB 互換ドライバが一部の書き込み操作をトランジェントエラー発生時に自動で一度再試行します。多くの現行ドライバは既定で retryable writes を有効にしています。
- 接続文字列: これまでエラー回避のために connection string に retryWrites=false を設定していたアプリは、DocumentDB 8.0.2 以降ではその設定を外しても問題ありません。
- 対応/非対応操作: retryable writes は単一ドキュメント書き込み等の多くの書き込みコマンドで有効ですが、updateMany と deleteMany、ならびにトランザクションの commit / abort コマンドは retryable の対象外です（これらは自動再試行されません）。
- 利用可能性: インスタンスベース／サーバーレスクラスターの両方で、Amazon DocumentDB 8.0 が提供されている全リージョンで利用可能。
- 旧バージョンの扱い: 8.0.2 未満のエンジンでは retryable writes は未サポートのため、ドライバ側で retryWrites=false を設定しておく必要があります。
参考: ドライバ側はセッションID（lsid）やトランザクション番号等を用いて再試行の整合性を管理するため、ドライバとサーバーの互換性が重要です。

### 影響範囲・利用シーン

- **対象ユーザー**: MongoDB互換アプリケーション開発者、SRE/運用チーム、DocumentDBを利用するバックエンドサービス運用者
- **利用シーン**: ネットワーク断やプライマリフェイルオーバーが起きやすい環境での単一ドキュメント書き込み、短時間のトランジェント障害に対する耐障害性向上
- **運用効果**: アプリ側での再試行ロジックを簡素化でき、トランジェントエラーによる失敗が減少して可用性が向上する。なお updateMany/deleteMany やトランザクションの commit/abort は自動再試行の対象外であるため、これらを使う処理は別途対策が必要

### 技術的な注意点

- **IAM権限**: 特別な追加権限は不要。通常のAmazon DocumentDBアクセス権があれば利用可能です
- **リージョン制限**: Amazon DocumentDB 8.0 が提供されているリージョンで利用可能。8.0 未提供のリージョンでは利用不可です
- **コスト**: retryable writes 自体に追加料金は発生しませんが、再試行により短時間での書き込み/IOが増える可能性があり、結果的にスループットや課金に影響する場合があります
- **エンジンバージョン**: 必須は 8.0.2 以上。8.0.2 未満では retryable writes はサポートされないため、ドライバで retryWrites=false を設定してください
- **ドライバ設定**: 多くの現行 MongoDB 互換ドライバは既定で有効。古いドライバではサポートがないか既定で無効の場合があるため、使用するドライバのバージョンと設定を確認してください
- **非対応操作**: updateMany、deleteMany、およびトランザクションの commit / abort は retryable の対象外です。これらを含む処理はアプリ側で冪等性や再試行制御を実装してください
- **互換性とテスト**: 自動再試行はアプリの副作用（重複挿入等）に影響する可能性があるため、ステージング環境で挙動確認と負荷テストを行ってください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-documentdb-retryable-writes/
- https://docs.aws.amazon.com/documentdb/latest/developerguide/

## [Documentdb] Amazon DocumentDB (with MongoDB compatibility) adds support for 5 MongoDB aggregation stages and change stream capabilities in version 8.0.2

- **公開日**: 2026-09-28 (JST)
- **カテゴリ**: Documentdb
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-documentdb-8-0-2/

### 概要

Amazon DocumentDB (MongoDB互換) がマイナー版 8.0.2 で retryable writes、5つの新しい集約ステージ、change stream の強化、クエリ性能改善、部分インデックスの reIndex サポートを追加しました。MongoDB API 互換性が向上し、移行や高度な分析が容易になります。

### 変更内容・新機能の詳細

主な追加・変更点は以下の通りです。

- Retryable Writes: insert/update/delete の操作が一時的なネットワーク障害やフェイルオーバー時に自動で再試行されるようになり、アプリケーションの耐障害性が向上します（マイナー版 8.0.2 以降）。

- 新しい集約ステージ: $setWindowFields（ウィンドウ関数一式を含む）、$bucketAuto、$facet、$graphLookup、および相関 $lookup をサポート。これにより時系列のウィンドウ集計、自動ビン化、ファセット検索、グラフ/階層クエリ、相関サブクエリ的な結合が可能になり、複雑な分析ワークロードを DB 側で効率的に処理できます。

- Change Stream の強化: $changeStreamSplitLargeEvent ステージにより 16MB 制限を超える大きな変更イベントを分割して配信できるようになりました。また、createCollection と createIndex の操作についても change stream でイベントが発行されるようになり、スキーマやインデックス変更の監視が容易になります。

- クエリ性能改善: クエリプランナーの改善により、find および aggregation に対する index-only スキャン、$expr に対するインデックススキャン、インクリメンタルソート、count / countDocuments() の高速化などが追加され、適切なインデックス設計と組み合わせることで応答性が向上します。

- インデックス管理: 部分インデックス（partial indexes）に対する reIndex コマンドをサポートし、インデックスの再構築運用が可能になりました。

これらの機能は Amazon DocumentDB バージョン 8.0.2 以降で利用可能で、既存の MongoDB ワークロードをアプリケーションコードの大幅な変更なしに移行しやすくすることを目的としています。

### 影響範囲・利用シーン

- **対象ユーザー**: MongoDB から Amazon DocumentDB へ移行を検討している開発者・SRE・データエンジニア
- **利用シーン**: 高度な集約分析（ウィンドウ関数、グラフ探索、ファセット検索）、変更イベント監視（createCollection/createIndex の検知）、フェイルオーバー時の書き込み冗長化（retryable writes）
- **運用効果**: アプリケーション側の変更を最小化して互換性を高めつつ、クエリ応答性と耐障害性を改善できるため、移行コストと運用負荷を低減可能
- **パフォーマンス効果**: index-only スキャンやインクリメンタルソートにより読み取り/集計パフォーマンスが向上し、クエリコスト削減につながる可能性がある
- **監査/監視への影響**: change stream による createCollection/createIndex イベントの追加により、スキーマ変更の追跡や自動化トリガーが容易になる

### 技術的な注意点

- **必要バージョン**: Amazon DocumentDB 8.0.2 以降で利用可能です
- **ドライバ互換性**: retryable writes や一部の MongoDB API はクライアント側ドライバの対応や設定（ドライババージョンやオプション確認）が必要な場合があります。事前に使用するドライバの互換性を確認してください
- **インデックス設計**: index-only スキャンや $expr のインデックス活用は適切なインデックス設計が前提です。性能改善を得るにはインデックスやクエリのプロファイリングが必要です
- **change stream 制限**: 大きなイベントは $changeStreamSplitLargeEvent により分割されますが、アプリケーション側で分割されたフラグメントの結合処理が必要になる場合があります
- **コスト**: 新機能自体で追加料金は発生しませんが、高頻度の変更ストリームや複雑な集約処理は I/O/CPU を増加させ、利用料金に影響する可能性があります
- **リージョン制限**: Amazon DocumentDB が利用可能な全リージョンで 8.0.2 の機能が提供されます（記事時点）。ただし、各リージョンでのロールアウト状況は AWS コンソールまたはリリースノートで確認してください
- **その他制約**: 完全な MongoDB の互換性を保証するものではありません。アプリケーション移行前に互換性リストとリリースノートでサポート状況を確認してください

## [Fsx Netapp Ontap] AWS Backup adds logically air-gapped vault support for Amazon FSx for NetApp ONTAP

- **公開日**: 2026-09-28 (JST)
- **カテゴリ**: Fsx Netapp Ontap
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-backup-air-gapped-vault-fsx-ontap/

### 概要

AWS Backupの「論理的エアギャップ（logically air-gapped）ボールト」がAmazon FSx for NetApp ONTAPのボリュームを保護対象としてサポートされました。これによりFSx ONTAPのバックアップを不変（immutable）で隔離保存し、クロスアカウント／クロスリージョンで直接復元できるようになります。

### 変更内容・新機能の詳細

論理的エアギャップ・ボールトは不変（ロックされた）バックアップを保存するAWS Backupのボールトタイプで、AWS管理キーまたはカスタマー管理のKMSキーで暗号化された状態で隔離されます。今回の更新で、Amazon FSx for NetApp ONTAPのボリュームをこの論理的エアギャップ・ボールトに保存できるようになりました。設定方法は、バックアッププランで対象（primary target）またはコピー先（copy destination）として該当ボールトを指定するだけです。ボールトは同一アカウント内／他アカウント／他リージョンに保存可能で、AWS Resource Access Manager（RAM）を使って復旧やリストア検証のために共有できます。万が一アカウントが侵害された場合でも、Multi-party approval（多者承認）を有効にしてボールトへのアクセスや操作を保護できます。直接復元（direct restore）機能により、共有先アカウントからバックアップを別途コピーすることなく復元ジョブを開始できるため、リカバリ時間（RTO）短縮に寄与します。本サポートは、論理的エアギャップ・ボールトとAmazon FSx for NetApp ONTAPの両方が利用可能なAWSリージョンで提供されます。操作はAWS Backupコンソール、AWS CLI、AWS SDKで行えます。

### 影響範囲・利用シーン

- **対象ユーザー**: データ保護／バックアップ担当者、SRE、DR/BCP担当者、セキュリティ・コンプライアンスチーム
- **利用シーン**: FSx for NetApp ONTAPのバックアップを不変・隔離して保存し、クロスアカウント／クロスリージョンの復旧テストや実運用復旧に利用
- **運用効果**: ランサムウェアなどによるデータ改ざんやアカウント侵害時の二次被害を抑制し、直接復元によりリカバリ時間を短縮。コンプライアンス（不変保持）や災害復旧要件の満足に寄与

### 技術的な注意点

- **IAM権限**: AWS Backup、AWS RAM、KMS（CMK）を操作するための適切なIAM権限が必要。バックアップ作成・復元、ボールト共有、Multi-party approvalの設定権限を確認してください
- **リージョン制限**: 本機能は「論理的エアギャップ・ボールト」と「Amazon FSx for NetApp ONTAP」の両方が利用可能なリージョンで提供されます。詳細なリージョン可用性はドキュメントで確認してください
- **コスト**: 論理的エアギャップ・ボールトの保存、保管期間、不変保持やKMS利用（カスタマー管理キー）の使用料、クロスリージョン転送（コピー）に伴う料金などが発生する可能性があります。直接復元の利用で一部のコピーコストを削減できる場面があります
- **KMS/暗号化**: AWS管理キーまたはカスタマー管理キー（CMK）で暗号化可能。CMKを使う場合はKMSの使用許可とポリシー管理に注意してください
- **不変性/ロック**: ボールト内のバックアップはデフォルトでロックされ不変になります。保持期間やロック設定は削除できない／変更できない場合があるため、ポリシー設計に注意してください
- **共有と復元**: ボールト共有はAWS RAMで行い、共有先で直接復元ジョブを開始できます。ただし共有設定・権限が正しくないと復元できないため事前検証を推奨します
- **Multi-party approval**: アカウント侵害時の安全策として有効。承認プロセスや承認者の管理運用（SOP）を整備してください
- **ツール**: コンソール、AWS CLI、AWS SDKから操作可能。自動化やIaC（CloudFormation/CDK）での対応を検討する場合は対応リソース／APIを確認してください
