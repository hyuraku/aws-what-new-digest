## [Ec2] Amazon EC2 Future-dated Capacity Reservations Now Supports Postponing Start Dates

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/ec2-fcr-postpone-start-date/

### 概要

Amazon EC2のFuture-dated Capacity Reservations（将来指定のキャパシティ予約）で、予約開始日の延期が可能になりました。延期時に新しい開始日・必要なコミット期間を示す見積もりが提示され、承認後に予約が更新されます。

### 変更内容・新機能の詳細

Future-dated Capacity Reservationsは最大120日先まで必要なキャパシティを確保できる機能です。本アップデートにより、配備前であれば予約の開始日を後ろ倒し（postpone）できるようになりました。開始日を延期すると、EC2は新しい開始日とその時点で必要となるコミットメント期間（契約期間）を反映した見積もりを提示します。見積もりを確認・承認すると、当該Future-dated Capacity Reservationの開始日が更新されます。注意点として、開始日をいつ延期するかによってはコミットメント期間が延長される（＝合計のコミット日数が増える）可能性があり、それに伴い料金が変動します。本機能は全てのFuture-dated Capacity Reservation利用者に提供されており、リージョンごとの対応状況はAWS Capabilities by Regionで確認できます。詳細な操作手順やAPI仕様はCapacity Reservationのユーザーガイドを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: インフラ/クラウド運用者、容量計画担当者、SRE
- **利用シーン**: 配備スケジュール変更が発生した場合に、事前確保したキャパシティ開始日を実際のローンチ日に合わせて後ろ倒しする運用
- **運用効果**: 不要に早い開始日にキャパシティが割り当てられることを防ぎ、リソースの無駄やコストのムダを抑制できる
- **コスト影響**: 延期によりコミットメント期間が増えると料金（予約のコミット分）が増加する可能性があるため、見積もりの承認前にコストを確認する必要がある
- **リージョン影響**: 機能はリージョン依存のため、利用前に対応リージョンを確認する必要がある（AWS Capabilities by Region参照）

### 技術的な注意点

- **IAM権限**: 予約の変更を行うために該当するEC2の権限が必要（例: ec2:ModifyCapacityReservation または該当するFuture-dated CR操作を許可）
- **リージョン制限**: 全リージョンで自動的に提供されているわけではありません。利用前にAWS Capabilities by Regionで対応状況を確認してください
- **コスト**: 開始日の延期に伴いコミットメント期間が延びると料金が増える可能性があります。EC2が提示する見積もりを必ず確認・承認してください
- **操作手順/API**: コンソールで開始日延期のワークフロー（見積もりの提示と承認）が提供されます。CLI/SDK/APIでの操作方法についてはCapacity ReservationユーザーガイドとAPIリファレンスを確認してください
- **タイミング制約**: 配備（開始日）前でなければ延期できない点に注意してください。延期可能な期間や頻度はドキュメントで確認する必要があります

## [Rekognition] Amazon Rekognition Face Liveness now returns Feedback Codes

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Rekognition
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/rekognition-liveness-feedback-codes/

### 概要

Amazon Rekognition Face Livenessが、低いライヴネススコアの原因を示すFeedback CodesをGetFaceLivenessSessionResults APIの応答で返すようになりました。これによりエンドユーザーへ具体的な改善アドバイスを提示して再試行を促せます。

### 変更内容・新機能の詳細

GetFaceLivenessSessionResults APIレスポンスにFeedback Codesが含まれるようになりました。各コードは低スコアに寄与した具体的な条件（例：照明不良、顔の一部遮蔽、目が閉じている、低い映像品質など）を識別します。1つのセッションで複数のFeedback Codesが同時に返されるため、ユーザーは複数の問題点をまとめて修正して再試行できます。従来の出力（ライヴネスの信頼度スコア、顔照合用の参照画像、セッション監査画像）は維持され、Feedback Codesはこれらの補助情報として、オンボーディングや再認証のUX改善、アクセシビリティ対応に活用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: ID確認担当者、認証フロー開発者、SRE/運用チーム
- **利用シーン**: 新規ユーザーの本人確認（オンボーディング）、再認証フロー、アクセシビリティ対応でのユーザー誘導
- **運用効果**: ユーザーに具体的な改善点を提示することで再試行成功率が向上し、誤検知によるサポート負荷を低減可能
- **UX改善**: フロントエンドでコードに対応する具体的な案内（例：光源の位置を変える、カメラから顔を離す、目を開けるなど）を表示して離脱率を下げられる
- **分析活用**: 返却されるFeedback Codesを集計すれば、現場の共通問題（照明環境やデバイス品質）を把握して対策やドキュメント改善ができる

### 技術的な注意点

- **API**: Feedback CodesはGetFaceLivenessSessionResults APIのレスポンスに含まれます。実装はAPIドキュメントを参照してください
- **IAM権限**: 少なくともrekognition:GetFaceLivenessSessionResults（およびセッション作成を行う場合はrekognition:StartFaceLivenessSession等）の最小権限を付与してください
- **リージョン制限**: 利用可能リージョンは記事記載の通りです（US East (N. Virginia)、US West (Oregon)、Europe (Ireland)、Asia Pacific (Tokyo, Mumbai, Malaysia, Thailand)、South America (São Paulo)）。対象リージョンでの利用可否を事前に確認してください
- **コスト**: Face Livenessの既存の課金体系が適用されます。Feedback Codes自体に追加料金は明示されていませんが、ライヴネスセッションの呼び出し回数や保存する監査画像の保管コストは影響します
- **データ保護**: セッション監査画像や参照画像を保存する場合は自社のデータ保持・プライバシーポリシーや法規制に従ってください
- **実装注意**: フロントエンドで表示するメッセージは誤解を招かないように設計し、複数コードが返ることを考慮して総合的な改善案を提示してください

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/09/rekognition-liveness-feedback-codes/
- https://docs.aws.amazon.com/rekognition/latest/APIReference/API_GetFaceLivenessSessionResults.html
- https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html

## [Bedrock] Grok 4.7 is now available on Amazon Bedrock 

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-grok-4-7/

### 概要

Amazon BedrockでSpaceXAIのGrok 4.7が利用可能になりました。Grok 4.7はコーディング、エージェント的タスク、ナレッジワーク向けに改善されたフロンティアモデルで、US GeoとGlobalのクロスリージョン推論をサポートします。

### 変更内容・新機能の詳細

Grok 4.7は前バージョン（4.6）を拡張し、以下の点で強化されています：混在ドキュメント（mixed-document）処理の精度向上、リポジトリ規模のコーディングでの計画立案とエラー回復（repo-scale coding with planning and error recovery）、ブラウザ利用エージェントの改善（フォーム自動入力やポータルナビゲーションの信頼性向上）。Amazon Bedrock上ではコンソール操作とサポートされるAPIを通じてプログラム的に利用可能で、推論プロファイル（レイテンシ/スループット設定等）やエンドポイント設定を用いて運用できます。詳細な対応リージョン、エンドポイント、API、機能、推論プロファイル、価格はAmazon Bedrockのドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発者、機械学習エンジニア、SRE、R&Dチーム、ナレッジワーカー
- **利用シーン**: 大規模リポジトリのコード生成・リファクタリング、エージェントによるブラウザ操作（フォーム記入やポータル自動操作）、ドキュメント横断検索や複数ドキュメントをまたぐ問合せ応答
- **運用効果**: より堅牢なコード自動生成とエラー回復により開発生産性向上、ブラウザエージェントの信頼性向上で自動化ワークフローが現実的に実装可能
- **制約・考慮点**: 大型モデルゆえに推論コストとレイテンシが増大する可能性があり、クロスリージョン推論はデータ転送・コンプライアンスの検討が必要

### 技術的な注意点

- **IAM権限**: Bedrockのモデル呼び出し（例: InvokeModelに相当するAPI）やエンドポイント管理に必要なIAM権限を事前に付与してください（詳細はBedrockドキュメントのポリシー例を参照）
- **リージョン制限**: Grok 4.7はUS GeoとGlobalのクロスリージョン推論をサポートしますが、すべてのリージョンでローカルに利用できるわけではありません。利用可能リージョンはドキュメントで確認してください
- **コスト**: 推論料金が発生します。クロスリージョン推論ではリージョン間データ転送コストとレイテンシが追加で発生する点に注意してください
- **性能/レイテンシ**: 大型言語モデルのため推論レイテンシやスループット要件を評価し、必要に応じてバッチ化や非同期処理、推論プロファイル設定を検討してください
- **データ保護・コンプライアンス**: US Geoオプションの利用やクロスリージョン推論によりデータの所在や転送先が変わるため、取り扱うデータ（PII、機密情報など）について社内規定や法規制を確認してください
- **モデル制限**: 高い能力を持つ一方で誤情報（hallucination）やコンテキストの誤解が生じる可能性があります。ファクトチェックやツール（検証用リトリーバルや外部ツール連携）での補強を推奨します
- **API/実装**: コンソールからの操作に加え、Bedrockが提供するAPI/SDKでモデルID（Grok 4.7）を指定して呼び出します。モデルのパラメータ（温度、最大トークン等）や推論プロファイルを実運用に合わせて調整してください

## [Bedrock] Claude Sonnet 5.5 now available on AWS

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/claude-sonnet-5-5-aws/

### 概要

Claude Sonnet 5.5がAWSで利用可能になりました。Sonnet 5からの性能向上により、コーディングとナレッジワークで高速かつ低コストにタスクを処理できます。

### 変更内容・新機能の詳細

Claude Sonnet 5.5はSonnet 5の改良版で、特にコーディング支援とナレッジ作成（1ページ要約、図表、スライド要約、文書編集、スプレッドシート整備など）に強化が入っています。セッション内での継続的な作業（同一会話での機能追加やバグ修正）、出力の要件照合や検証がより安定して行え、ほとんどの作業でタスクあたりのコストが低く、応答速度も向上しています。AWS上では2つのアクセス方法が提供されます。1) Amazon Bedrock経由：Sonnetの機能をAWSインフラ内で利用でき、リージョンごとのデータレジデンシーを維持しつつ、GuardrailsやKnowledge BasesなどのAWS管理機能と統合された単一サービスで利用可能です。2) Claude Platform on AWS経由：Anthropicのネイティブなプラットフォーム体験（同一API、機能、コンソール）をAWSコンソール上で直接利用でき、AWSの課金・認証と統合されます。これにより、既存のSonnet 5ベースの導入は自然な形でSonnet 5.5へ移行できます。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発チーム（ソフトウェアエンジニア、QA）、プロダクトチーム、ドキュメント作成者、データ担当者
- **利用シーン**: コード生成・バグ修正・機能追加の同一セッションでの作業、要件に沿った出力の検証、1ページ要約や図解・スライド作成、ドキュメントやスプレッドシートの自動クリーニング
- **運用効果**: タスクごとのコスト低減と高速化により開発サイクル短縮、人的工数削減、ドキュメント品質向上と共有準備時間の短縮

### 技術的な注意点

- **IAM権限**: BedrockやClaude Platformの利用には適切なIAMロール/ポリシー（Bedrock、SecretsManager、CloudWatch等へのアクセス権）が必要です
- **リージョン制限**: Sonnet 5.5の提供状況はリージョンごとに異なります。利用前に公式のリージョン可用性を確認してください
- **コスト**: 記事では「ほとんどの作業でコスト低下」とありますが、実際の料金は呼び出し回数・トークン消費量・選択したアクセス経路（Bedrock料金、またはプラットフォームの課金体系）によって異なります。見積もり・モニタリングを推奨します
- **データレジデンシー**: Bedrock経由はAWSインフラ内でのデータ処理・レジデンシー制御が可能ですが、Claude PlatformはAnthropicネイティブ体験を提供するためデータフローや保存ポリシーを確認してください
- **API互換性**: BedrockのAPIとAnthropicネイティブAPIには違いがあります。既存の実装を移行する際はAPI呼び出し・パラメータ・応答形式の差分確認が必要です
- **モデル動作**: 強化されているとはいえ、誤情報（ハルシネーション）や仕様逸脱のリスクは残ります。重要な出力は検証プロセス（テストケース、要件チェック）を組み込んで運用してください
- **運用監視**: レイテンシやコストを抑えるために呼び出し頻度の制御、キャッシュ、ロギング（CloudWatch等）を適用することを推奨します
