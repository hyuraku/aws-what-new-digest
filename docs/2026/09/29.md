## [Systems Manager] AWS Systems Manager now supports sharing documents through AWS Resource Access Manager

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Systems Manager
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/systems-manager-sharing-documents-ram/

### 概要

AWS Systems Manager の SSM ドキュメントを AWS Resource Access Manager（AWS RAM）を使って組織単位（組織全体または特定のOU）で共有できるようになりました。これによりアカウントの追加・削除に応じた共有設定の自動更新が可能になります。

### 変更内容・新機能の詳細

主な変更点は、Systems Manager ドキュメント（SSM Documents）を従来の「公開」または「個別アカウントIDの列挙」で共有する方式に加えて、AWS RAM のリソースシェアを使ってAWS Organizations全体または特定のOUに共有できるようになったことです。共有手順は、AWS RAMでリソースシェアを作成し、共有したい SSM ドキュメントを追加し、共有先として組織またはOUを選択するだけです。共有は RAM とリソースベースポリシーで管理されるため、標準的な AWS の認可メカニズムに従ってアクセスが付与されます。組織外のアカウントに共有する場合は、そのアカウントにリソースシェアの招待が届き、招待を受諾した時点でアクセスが有効になります。Systems Manager コンソール、AWS CLI、AWS SDK から操作可能で、Systems Manager が利用可能なすべてのリージョンで利用できます。共有に対する追加料金は発生しません。ドキュメントの所有権やタイプによっては共有制限がある場合があるため、共有前に確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: マルチアカウント環境を管理するクラウドエンジニア、プラットフォーム/ガバナンスチーム、SRE
- **利用シーン**: 共通の運用ドキュメント（例: 標準化された Runbook、構成適用ドキュメント、オートメーション）を組織単位で配布して一括管理・運用する場面
- **運用効果**: アカウントの追加・削除に伴う共有設定の手動更新が不要になり、一貫したドキュメント配布とアクセス管理が容易に（ガバナンスと運用負荷の低減）
- **セキュリティ/承認フロー**: 組織外アカウントへの共有は招待制で承諾が必須のため、ドキュメント所有者と受領側の双方でコントロール可能
- **コスト影響**: ドキュメント共有自体に追加料金は発生しません（ただし、Systems Manager や AWS RAM の利用に伴う通常の料金は継続）

### 技術的な注意点

- **IAM権限**: リソースシェア作成には AWS RAM の操作権限（例: ram:CreateResourceShare, ram:UpdateResourceShare, ram:AssociateResourceShare, ram:DeleteResourceShare）および SSM 側のドキュメント閲覧/管理権限が必要です。組織外で招待を受ける側は ram:AcceptResourceShareInvitation が必要になる点を確認してください。具体的な最小権限は導入前に公式ドキュメントで確認してください。
- **リージョン制限**: Systems Manager が提供されている全リージョンで利用可能と発表されていますが、組織や RAM の特定機能はリージョン/サービス構成に依存する場合があるため、自身のリージョンでの提供状況を確認してください。
- **コスト**: ドキュメント共有に追加課金はありません。ただし、Systems Manager（オートメーションの実行、パラメータストア等）や AWS RAM を利用する際の通常のサービス利用料金は発生します。
- **共有の範囲と制御**: 共有は RAM のリソースシェアとリソースベースポリシーで制御されます。組織内での自動更新（アカウントの追加/削除に追従）を行いますが、AWS 管理ドキュメントなど一部ドキュメントは共有対象外となる可能性があるため、ドキュメントの所有者/タイプを事前に確認してください。
- **外部アカウント対応**: 組織外アカウントへ共有する場合、受信側の明示的承諾（AcceptResourceShareInvitation）が必要です。自動化したい場合は CLI/SDK での招待受諾処理を検討してください。
- **運用上の推奨**: 最小権限の原則に従い、組織単位でのロール分離と監査ログ（CloudTrail）を有効にして誰が共有を作成/変更したかを追跡してください。

## [Datasync] AWS DataSync now supports shared VPCs

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Datasync
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-datasync-shared-vpcs/

### 概要

AWS DataSyncが共有VPC（Shared VPC）をサポートしました。これにより、AWS Resource Access Manager (RAM)で共有されたサブネットを使ってDataSyncエージェントを作成し、中央管理されたVPCエンドポイント経由で複数アカウントからプライベートにデータ転送できます。

### 変更内容・新機能の詳細

従来は各AWSアカウントごとにPrivateLinkのDataSync VPCエンドポイントを作成する必要があり、各エンドポイントがIPアドレスを消費し運用負荷を増やしていました。今回の更新により、VPC所有アカウントが管理する単一のVPCエンドポイントと共有サブネットをAWS RAMで他アカウントと共有し、共有サブネット上でDataSyncエージェントを作成してタスクを実行できるようになりました。これによりIPアドレスの節約とアカウントごとのエンドポイント管理の削減が可能です。単一アカウント内でも、複数サブネットに対して1つのVPCエンドポイントを使えるようになり、以前必要だった「サブネットごとのエンドポイント」要件が緩和されます。Shared VPCサポートは、EnhancedモードおよびBasicモードのエージェントベースのタスク両方で有効です。利用開始はコンソールまたはCreateAgent APIで、AWS RAMで共有されたサブネットを指定してDataSyncエージェントを作成します。サービスはDataSyncが提供されている全リージョン（Secretリージョンを除く）で利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: ネットワークを中央集約している組織、マルチアカウント環境のインフラチーム
- **利用シーン**: 中央VPCの単一PrivateLinkエンドポイント経由で複数アカウントのDataSyncエージェントがプライベートにデータ転送を行うケース（オンプレ←→S3/EFSなど）
- **運用効果**: 各アカウントにエンドポイントを作る必要がなくなり、IPアドレス消費の削減とエンドポイント管理コスト（作成・パッチ・監視）の低下が期待できる
- **セキュリティ効果**: トラフィックが共有VPC内のPrivateLinkで閉域化されるため、インターネット経由を避けた安全なデータ転送が可能
- **コスト効果**: エンドポイント数を減らすことでインターフェースエンドポイントの時間課金・データ処理課金を全体的に減らす可能性がある（ただしエンドポイント料金はVPC所有アカウントに集中する）

### 技術的な注意点

- **IAM権限**: RAMでのリソース共有受諾、DataSyncエージェント作成（CreateAgent）や関連するEC2操作（ネットワークインターフェイスの作成/利用）に関する権限が必要です。受信側アカウントが共有サブネットにENIを作成できる権限を確認してください
- **リージョン制限**: DataSyncが提供されている全リージョンで利用可能。ただしAWS Secret Regionsでは除外されています
- **サポートモード**: EnhancedモードおよびBasicモードのエージェントベースのタスクをサポートします
- **ネットワーク設定**: 共有サブネットのルートテーブル、NACL、セキュリティグループがDataSyncの通信（エージェントとDataSyncサービス間のPrivateLink接続）を許可しているか事前に確認してください。VPC所有者側でのセキュリティグループとエンドポイントポリシー設定が重要です
- **エンドポイント管理**: 中央アカウントのVPCに作成したインターフェースVPCエンドポイントが全ての共有サブネットから利用されるため、エンドポイントの課金および可用性責任はVPC所有アカウントに集中します
- **コスト**: 全体のエンドポイント数は減るが、エンドポイントの時間単価・データ転送料金は引き続き発生します。課金割り当てはオーナーアカウントに偏る可能性があるため請求設計に注意してください
- **運用注意**: サブネット共有はRAMの仕組み（リソース共有の作成と受諾）を伴うため、共有フローとアカウント間の運用手順を整備してください
- **その他制約**: 特に注意点がない場合はありません（上記項目を参照）

## [General] AWS Transfer Family now supports downloading multiple files and folders in web apps 

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/transfer-family-web-apps-download-multiple-files-folders

### 概要

AWS Transfer Family の Web Apps で、複数ファイルやフォルダをまとめてダウンロードできる機能が追加されました。選択したファイル／フォルダを1回の操作で ZIP 形式で取得でき、展開すると元のフォルダ構成が保持されます。

### 変更内容・新機能の詳細

エンドユーザーは Web アプリ上で任意のファイルとフォルダを組み合わせて選択し、アクションメニューの「Download」を選ぶことで一括ダウンロードが可能になりました。ダウンロードは ZIP アーカイブとして配信され、解凍時に元のフォルダ構造が保持されます。Web アプリはダウンロード対象の一覧と各ファイルごとのリアルタイム進捗（成功／失敗ステータス）を表示します。対応ブラウザは Google Chrome、Mozilla Firefox、Microsoft Edge などの Chromium 系ブラウザで、Safari は現時点で未対応（Safari では従来通り単一ファイルのダウンロードのみ）。この機能は Transfer Family Web Apps を提供しているすべての AWS リージョンで利用可能です。利用開始は対象の場所でファイル／フォルダを選択し、アクションメニューから Download を選ぶだけです。

### 影響範囲・利用シーン

- **対象ユーザー**: ファイル転送を Web ブラウザ経由で行うエンドユーザー、SaaS/社内ポータルを構築する開発者や運用担当者
- **利用シーン**: 複数ファイルやディレクトリをまとめて提供・受領するワークフロー（アセット配布、ログ一括取得、データセットのダウンロードなど）
- **運用効果**: ユーザー操作の簡略化と作業時間短縮、フォルダ構成を保ったまま一括で取得できるため二次処理や手動整理の工数削減が期待できる

### 技術的な注意点

- **IAM権限**: Web Apps 経由でファイルにアクセスするユーザーは、基盤となるストレージ（例: S3 や FSx）への適切なアクセス権限が必要です
- **ブラウザ互換性**: 対応ブラウザは Chrome、Firefox、Chromium 系（例: Edge）。Safari は未対応で、Safari では単一ファイルのみダウンロード可能です
- **リージョン制限**: Transfer Family Web Apps を提供しているすべてのリージョンで利用可能です
- **コスト**: 機能自体に追加料金の明記はありませんが、データ転送量やストレージの利用に伴う通常の料金（S3 からのデータ転送等）が発生する可能性があります
- **大容量ファイルの注意**: 大きなデータセットや多数ファイルの一括 ZIP 配信ではブラウザやネットワークのタイムアウト、メモリ制約、失敗が発生する可能性があるため、大量データでの動作は事前に検証してください

### 参考情報

- https://docs.aws.amazon.com/transfer/latest/userguide/transfer-web-apps.html

## [General] Amazon ElastiCache Serverless for Valkey now supports public endpoints

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-elasticache-serverless-public-endpoints/

### 概要

Amazon ElastiCache Serverless for Valkeyがパブリックエンドポイントをサポートしました。これによりVPNや踏み台なしでインターネット経由からキャッシュへ直接接続できます。

### 変更内容・新機能の詳細

ElastiCache Serverless for Valkeyでパブリックエンドポイントが利用可能になり、ラップトップ、サーバーレス関数、AWS外で動くアプリケーションなどから直接キャッシュへ接続できます。VPCの設定や踏み台サーバー、SSHトンネルが不要で、完全マネージドのインターネット公開キャッシュをコンソール、SDK、CLIから1分程度で作成可能です。接続はすべてIAM認証を用いたTLS 1.3で保護され、パスワードの保管や回転は不要です。接続クライアントはValkey GLIDE 2.2以降（IAM組み込みサポート）を推奨します。GLIDEを使わない場合は、ValkeyクライアントとDeveloper Toolkit for ElastiCache（オープンソースのトークン生成／更新ライブラリ）を組み合わせてIAM認証トークンを生成・更新します。パブリックエンドポイントは全ての商用リージョンおよび中国リージョンで利用可能で、追加料金はなく通常のElastiCache Serverless課金が適用されます。Valkey 9.0以降のサーバーレスキャッシュでパブリックエンドポイントを有効にして利用を開始します。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発者、AIツール/エージェント連携開発者、サーバーレス/オンプレアプリ運用者、プロトタイピングを行うチーム
- **利用シーン**: ラップトップや外部サービスからの迅速なプロトタイプ作成、AIコーディングツールやエージェントがキャッシュへ直接アクセスするケース、VPCに到達できないワークロードへのキャッシュ導入
- **運用効果**: インフラ構成（VPN/踏み台）の簡略化によりセットアップ時間を短縮し、開発サイクルを高速化。IAM/TLSによりパスワード管理の負担を削減
- **リスク/注意点**: インターネット公開により攻撃面が増えるためIAMポリシーや監査（CloudTrail等）でアクセス制御とログ監視を強化する必要あり

### 技術的な注意点

- **IAM権限**: 接続に使用するIAMユーザー/ロールに対してElastiCache接続を許可する適切なポリシーと最小権限を付与してください。詳細なAPIアクションは公式ドキュメントを参照
- **クライアント互換性**: Valkey GLIDE 2.2以降を推奨。未対応クライアントはDeveloper Toolkit for ElastiCacheを用いてIAMトークンを生成/更新する必要あり
- **TLS/認証**: すべての接続はTLS 1.3 + IAMベース認証。パスワード管理は不要だが、TLS検証と最新ライブラリ利用を推奨
- **リージョン制限**: 公開は全ての商用リージョンおよび中国リージョンで利用可能（記事時点）。特定リージョンの細かい差異は公式情報で確認を推奨
- **コスト**: パブリックエンドポイント自体の追加料金は無し。標準のElastiCache Serverless料金が適用されるほか、インターネット経由のデータ転送（egress）による料金が発生する可能性あり
- **セキュリティ/コンプライアンス**: VPCを経由しないためセキュリティグループ等のネットワーク制御は使えない想定。機密データや厳格なコンプライアンス要件がある場合は公開エンドポイントの使用を避けるか、IAMポリシー・監査ログ・組織ポリシーで補完してください
- **作成/運用**: Valkey 9.0以降のサーバーレスキャッシュ作成時にパブリックエンドポイントを有効化（Console/SDK/CLI対応）。接続テストは近接リージョンから行い、レイテンシや同時接続制限を確認してください

## [Ec2] Amazon EC2 Future-dated Capacity Reservations Now Supports Postponing Start Dates

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/ec2-fcr-postpone-start-date/

### 概要

Amazon EC2のFuture-dated Capacity Reservations（将来指定のキャパシティ予約）で、予約開始日の延期が可能になりました。延期時に新しい開始日・必要なコミット期間を示す見積もりが提示され、承認後に予約が更新されます。

### 変更内容・新機能の詳細

Future-dated Capacity Reservationsは最大120日先まで必要なキャパシティを確保できる機能です。本アップデートにより、配備前であれば予約の開始日を後ろ倒し（postpone）できるようになりました。開始日を延期すると、EC2は新しい開始日とその時点で必要となるコミットメント期間（契約期間）を反映した見積もりを提示します。見積もりを確認・承認すると、当該Future-dated Capacity Reservationの開始日が更新されます。注意点として、開始日をいつ延期するかによってはコミットメント期間が延長される（＝合計のコミット日数が増える）可能性があり、それに伴い料金が変動します。本機能は全てのFuture-dated Capacity Reservation利用者に提供されており、リージョンごとの対応状況はAWS Capabilities by Regionで確認できます。詳細な操作手順やAPI仕様はCapacity Reservationのユーザーガイドを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: インフラ/クラウド運用者、容量計画担当者、SRE
- **利用シーン**: 配備スケジュール変更が発生した場合に、事前確保したキャパシティ開始日を実際のローンチ日に合わせて後ろ倒しする運用
- **運用効果**: 不要に早い開始日にキャパシティが割り当てられることを防ぎ、リソースの無駄やコストのムダを抑制できる
- **コスト影響**: 延期によりコミットメント期間が増えると料金（予約のコミット分）が増加する可能性があるため、見積もりの承認前にコストを確認する必要がある
- **リージョン影響**: 機能はリージョン依存のため、利用前に対応リージョンを確認する必要がある（AWS Capabilities by Region参照）

### 技術的な注意点

- **IAM権限**: 予約の変更を行うために該当するEC2の権限が必要（例: ec2:ModifyCapacityReservation または該当するFuture-dated CR操作を許可）
- **リージョン制限**: 全リージョンで自動的に提供されているわけではありません。利用前にAWS Capabilities by Regionで対応状況を確認してください
- **コスト**: 開始日の延期に伴いコミットメント期間が延びると料金が増える可能性があります。EC2が提示する見積もりを必ず確認・承認してください
- **操作手順/API**: コンソールで開始日延期のワークフロー（見積もりの提示と承認）が提供されます。CLI/SDK/APIでの操作方法についてはCapacity ReservationユーザーガイドとAPIリファレンスを確認してください
- **タイミング制約**: 配備（開始日）前でなければ延期できない点に注意してください。延期可能な期間や頻度はドキュメントで確認する必要があります

- https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-reservations.html

## [Rekognition] Amazon Rekognition Face Liveness now returns Feedback Codes

- **公開日**: 2026-09-29 (JST)
- **カテゴリ**: Rekognition
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/rekognition-liveness-feedback-codes/

### 概要

Amazon Rekognition Face Livenessが、低いライヴネススコアの原因を示すFeedback CodesをGetFaceLivenessSessionResults APIの応答で返すようになりました。これによりエンドユーザーへ具体的な改善アドバイスを提示して再試行を促せます。

### 変更内容・新機能の詳細
