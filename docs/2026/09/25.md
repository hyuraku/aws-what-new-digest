## [S3] AWS Elastic Disaster Recovery now supports AWS Graviton-based source servers

- **公開日**: 2026-09-25 (JST)
- **カテゴリ**: S3
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/elastic-disaster-recovery-graviton/

### 概要

AWS Elastic Disaster Recovery (AWS DRS) は、Graviton（arm64）ベースのソースサーバーの保護と復旧をサポートするようになりました。arm64 サーバーを自動検出して Graviton インスタンス上へアーキテクチャを維持したまま復旧できます。

### 変更内容・新機能の詳細

AWS DRS はこれまでの x86 ワークロードと同様に、arm64（AWS Graviton ベース）ソースサーバーの継続レプリケーションと復旧をサポートします。DRS はソースサーバーが arm64 であることを自動検出し、復旧時は Graviton（arm64）インスタンス上に復元してアーキテクチャを保持します。追加の設定は不要で、既存のレプリケーション、フェイルオーバー、リカバリーテストのワークフローがそのまま利用できます。なお、本機能は AWS DRS を提供しているすべてのリージョンで利用可能で、機能追加に伴う別料金は発生しません（ただし通常の DRS 使用料や復旧時のインスタンス／ストレージ費用は別途発生します）。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウド/インフラエンジニア、SRE、バックアップ/DR担当者、Graviton（arm64）へ移行しているまたは移行予定のアプリケーション所有者
- **利用シーンまたは効果**: Graviton ベースのプロダクションサーバーに対する障害時復旧（RTO/RPOの短縮）、DR テストの自動化、混在アーキテクチャ環境での一貫した DR 運用
- **運用効果**: x86 と同様の簡易な設定で arm64 サーバーの保護が可能になり、アーキテクチャ別に異なる手順を用意する必要が減ることで運用負荷が低下します

### 技術的な注意点

- **IAM権限**: DRS に必要な IAM ロール／権限（レプリケーション、スナップショット、EC2 作成など）が適切に設定されていることを確認してください
- **リージョン制限**: 本機能は AWS DRS を提供するすべてのリージョンで有効ですが、利用前に対象リージョンで DRS が提供されているか確認してください
- **コスト**: 機能自体に追加料金はありませんが、継続レプリケーションに伴うストレージ（スナップショット/レプリケーションストレージ）、復旧時の Graviton インスタンス利用料、データ転送費用などは通常の料金が発生します
- **OS/アプリ互換性**: 復旧先が arm64 となるため、OS（カーネル/ドライバ）やアプリケーション／バイナリが arm64 をサポートしていることを事前に確認してください。x86 バイナリのままでは動作しません
- **アーキテクチャ変換**: DRS はアーキテクチャ変換（x86 ⇄ arm64 のバイナリ変換）を行いません。arm64 ソースは arm64（Graviton）へ、そのまま復旧されます
- **テスト/検証**: 実運用に導入する前に復旧テスト（災害リハーサル）を実施し、OS レベルやサードパーティソフトウェアの動作確認を行ってください
- **追加設定**: 記事記載の通り自動検出・復旧が行われるため、特別な追加設定は不要ですが、ネットワーク（ENI, サブネット, セキュリティグループ）、IAM、ライセンス条件など周辺設定の確認は必要です

### 参考情報

- https://aws.amazon.com/about-aws/whats-new/2026/09/elastic-disaster-recovery-graviton/
- https://docs.aws.amazon.com/drs/latest/userguide/

## [General] AWS End User Messaging now supports voice calling on WhatsApp

- **公開日**: 2026-09-25 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-end-user-messaging-voice-calling-whatsapp

### 概要

AWS End User Messaging（Social）がWhatsApp内での音声通話をサポートし、チャットスレッドからそのまま双方向の音声通話を発信／受信できるようになりました。ビジネスは既に検証済みのWhatsAppビジネスIDを利用して通話を行えます。

### 変更内容・新機能の詳細

WhatsApp音声通話機能は、同一の検証済みビジネスID（WhatsApp Business登録済み電話番号）を使って、チャットスレッド内で会話の文脈を維持したまま顧客と音声通話を行えるようにする機能です。通話は顧客→ビジネス、ビジネス→顧客の双方で動作し、ビジネス側から発信するには顧客が事前に連絡許可を与えている必要があります。機能の有効化・管理はAWS End User MessagingコンソールまたはAPIから行えます。提供リージョンは、AWS End User Messaging Socialが利用可能な全リージョンに準じます。詳細な設定や運用方法はAWS End User Messaging Socialのユーザーガイドを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: カスタマーサポート、コンタクトセンター、SaaS事業者、Eコマースやフィールドサービス運用チーム
- **利用シーン**: チャット中の技術サポートで素早く音声で問題を確認する、予約確認や決済サポートでの本人確認、セールスのフォローアップで会話を深める場面
- **運用効果**: チャットから別アプリに切り替える必要がなくなるため応答遅延や文脈喪失が低減され、顧客体験と一次対応率が向上する

### 技術的な注意点

- **電話番号登録**: WhatsApp音声通話を有効にするには、登録済みのWhatsAppビジネス電話番号が必要です
- **顧客同意**: ビジネスから顧客へ発信する場合、顧客が連絡許可（opt-in）を与えている必要があります
- **IAM権限**: End User Messagingのコンソール/APIを操作するための適切なIAM権限を付与してください（API呼び出しや電話番号管理権限等）
- **リージョン制限**: 利用可能リージョンはAWS End User Messaging Socialが提供されているリージョンに限定されます。利用前に該当リージョンでの提供状況を確認してください
- **コスト**: 通話機能の利用に伴い、AWS End User MessagingおよびWhatsAppプラットフォームに関連する料金が発生する可能性があります。料金体系と課金ポリシーを事前に確認してください
- **コンプライアンス/保存**: 通話の録音や個人情報の取り扱いは法令・社内ポリシーに準拠して実施してください。通話データの保存やログ取得が必要な場合は実装・設定を確認してください
- **操作方法**: 音声通話はAWS End User MessagingコンソールまたはAPIで有効化・管理します。既存のメッセージング設定と統合して利用します

### 参考情報

- https://docs.aws.amazon.com/end-user-messaging/latest/social/

## [Ses] AWS End User Messaging and Amazon SES now offer AI agent skills for the AWS MCP Server

- **公開日**: 2026-09-25 (JST)
- **カテゴリ**: Ses
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-messaging-ses-ai-skills-mcp-server/

### 概要

AWS End User Messaging と Amazon SES が、AWS MCP Server 向けの「AI エージェント向けスキル」を公開しました。開発者は自然言語でエージェントに指示するだけで、送信者確認やRCSエージェント作成、実運用メール送信などのメッセージング作業を完了できます。

### 変更内容・新機能の詳細

新しい「AIエージェントスキル」は AWS MCP Server 上で公開され、各スキルは送信者の検証、ブランディングされた RCS エージェントの構築、実運用のメール送信などのワークフローを手順化してエージェントに与えます。これらのスキルは Claude Code、Codex、Cursor、Kiro などの一般的な AI コーディングエージェントと統合されます。利用手順の概略は以下の通りです。
- MCP Server を利用するエージェントに接続する（Claude Code/Codex/Cursor では aws-core プラグインによりサーバーとキュレート済みスキル群を一括インストール、Kiro やその他では MCP 設定ファイルに追加）。
- 目的のチャネル（SES, SMS/RCS, WhatsApp など）のスキルを追加する。
- 自然言語でエージェントに指示することで、スキルが検証済みの手順に沿って必要な API 操作や設定手順を実行あるいは案内する（例：送信 ID の検証、RCS カード・ボタンを含むリッチメッセージ送信、初回の本番メール送信など）。
これにより、従来のように複数のドキュメントやコンソール画面を行き来する必要がなくなり、メッセージング関連の初期セットアップや運用タスクを自然言語で完結できるようになります。

### 影響範囲・利用シーン

- **対象ユーザー**: 開発者、SRE、メッセージング担当者（SES/End User Messaging を使うエンジニア）
- **利用シーン**: 送信者確認や初回本番メール送信、RCS/WhatsApp/SMS のエージェント構築とテスト、ブランディング付きリッチメッセージの作成・送信
- **運用効果**: ドキュメント探索やコンソール移動の手間を削減し、セットアップ時間と人的ミスを低減。エンジニアの作業効率が向上し、オンボーディングが短縮される
- **組織的影響**: 自動化可能な手順が標準化されるため、運用の一貫性が増し、SLA 遵守や迅速なトラブルシュートに寄与する

### 技術的な注意点

- **MCP Server 接続**: エージェントに AWS MCP Server を正しく接続する必要があります（Claude Code/Codex/Cursor は aws-core プラグイン、Kiro 等は MCP 設定ファイルへ追加）
- **IAM 権限**: SES（VerifyIdentity, SendEmail 等）や End User Messaging 用 API の実行に必要な IAM 権限を最小権限で付与してください。エージェントに与える認証情報は漏洩リスクに注意
- **ネットワーク/認証**: MCP Server との通信に必要なネットワーク接続と認証情報の管理（TLS、エンドポイントアクセス制御）を確認してください
- **リージョン制限**: RCS/WhatsApp や一部の End User Messaging 機能はリージョンやキャリア制約があります。利用前に対象リージョンでのサポート状況を確認してください
- **コスト**: SES の送信、RCS/WhatsApp のメッセージ送信、携帯事業者の料金が発生します。スキル自体は操作を自動化するだけであり、実行される API コールに対して通常の課金が適用されます
- **監査・ログ**: 自動操作を行うエージェントのアクションは CloudTrail、SES の送信ログ等で監査可能にしておくことを推奨します
- **互換性**: 現在統合確認されているエージェントは Claude Code、Codex、Cursor、Kiro など。その他エージェントは MCP 設定による追加が必要になる可能性があります
- **注意点**: エージェントに AWS リソース操作を委ねるため、テスト環境での検証を十分に行い、意図しない本番操作を防ぐワークフロー（承認フローや手動確認）を設計してください

### 参考情報

- https://docs.aws.amazon.com/ses/latest/DeveloperGuide/

## [Account Billing] AWS Billing and Cost Management now provides billing context for your account through a new API

- **公開日**: 2026-09-25 (JST)
- **カテゴリ**: Account Billing
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-billing-and-cost-management-billing-context-api/

### 概要

AWS Billing and Cost Managementに新しいAPI「ListBillingViewSegments」が追加され、指定した期間におけるアカウントの請求コンテキスト（請求階層上の立ち位置や課金設定）を取得できるようになりました。コストや使用量データではなく、請求に関するメタ情報を期間ごとに分割して返します。

### 変更内容・新機能の詳細

ListBillingViewSegmentsは、指定した日時範囲に対してアカウントの請求コンテキストを返すAPIです。返却される情報には、アカウントが管理アカウント（payer）かメンバーアカウントか、あるいはBilling Groupのプライマリアカウントかといった請求階層上の位置付け、どのアカウントが請求関係を管理しているか、適用されているレート設定（billableまたはpro forma）などが含まれます。重要な点として、このAPIは金額や使用量そのもの（Cost and Usage data）を返さず、あくまで請求コンテキスト（メタデータ）を返します。

また、アカウントの請求関係は期間中に変更されることがあるため、APIは要求した期間を「有効期間のセグメント」に分割して返します。例えば、あるアカウントが当初は単独のpayerであったが後に別の組織のメンバーになり、さらにその新しいpayerがBilling Conductorで請求を管理するようになった場合、3つのセグメント（それぞれの有効期間）を返し、各セグメント毎に有効だったアカウント構成と請求設定を示します。ListBillingViewSegmentsは全ての商用AWSリージョンで利用可能で、追加料金は発生しません。APIは直接HTTP/APIから呼び出すほか、AIエージェント経由の呼び出しもサポートされます。実運用では、Cost ExplorerやCost and Usage Reports、Billing Conductor、AWS Organizationsと組み合わせて使うことで、過去の請求構成に沿った正確な請求レポートや照合、FinOps分析に役立ちます。

### 影響範囲・利用シーン

- **対象ユーザー**: 請求/FinOpsチーム、SRE/運用チーム、クラウド財務担当者、監査担当者
- **利用シーン**: 過去期間の請求構成（payerやBilling Groupの変遷）を把握して請求照合やレポートの基準を決定する／AIエージェントや自動化ツールで請求コンテキストに基づく処理を行う（例: 正しいpayerに紐づけてコスト配賦）
- **運用効果**: 請求関係の変更に応じた正確な履歴取得が可能になり、コストレポートや監査の整合性が向上。請求構成の変化を自動検出してルール適用や通知を行えるため、誤請求や配賦ミスの低減に寄与します

### 技術的な注意点

- **IAM権限**: Billing/Organizations周りの読み取り権限が必要です（BillingとOrganizationsのAPI呼び出しを許可するIAMポリシーまたは相当の管理ポリシーを付与してください）。
- **出力内容の制限**: このAPIは請求コンテキスト（メタデータ）のみを返します。金額や使用量データは含まれないため、コスト金額はCost ExplorerやCost and Usage Reportsなど別APIで取得してください。
- **セグメント化の挙動**: 期間中に請求関係が変わった場合、APIは有効期間ごとのセグメントを返します。期間選択によっては多数のセグメントが返る可能性があるため、その取り扱いに注意してください。
- **リージョン制限**: 全ての商用AWSリージョンで利用可能とされています（ただし特殊なリージョンやローカルリージョンは要確認）。
- **コスト**: ドキュメント上は追加料金なしと明示されていますが、APIの呼び出し頻度やそれに伴う他サービス（例: データ取得のための追加Cost Explorerクエリなど）によるコストは別途発生し得ます。
- **利用方法**: 直接API呼び出しのほかAIエージェント経由の利用も可能ですが、エージェントに付与する権限は最小権限の原則に従って設定してください。
- **整合性と伝搬遅延**: 請求関連の状態変更が反映されるタイミングには内部的な遅延がある可能性があります。過去データの厳密な照合が必要な場合は、変更イベントのログやOrganizations/Billing Conductorの記録と併用してください。

## [General] Amazon EventBridge relaunches event buses for enterprise scale

- **公開日**: 2026-09-25 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/eventbridge-relaunches-custom-event-buses/

### 概要

Amazon EventBridgeがカスタムイベントバスを強化して再提供しました。アカウント間共有、CloudEventsなどのJSONフォーマット対応、組み込み保持、厳密な順序保証、高度な変換・重複排除など、エンタープライズ規模のイベント駆動アーキテクチャ向けの機能を追加しています。

### 変更内容・新機能の詳細

強化された Custom event bus はサーバーレスなイベントブローカーで、アプリケーション、SaaSインテグレーション、AWSサービス間のイベントルーティングをスケールして実現します。主な技術要素は以下の通りです。

- クロスアカウント共有: AWS Resource Access Manager (RAM) を使って1つまたは複数アカウントとイベントバスを共有でき、パブリッシャーは中央のバスへ直接イベントを送信可能になります。
- 新しいイベント公開API: CloudEventsをはじめとする一般的なJSONベースのイベントフォーマットをネイティブに受け入れ、スキーマを変更せずに保持できます。
- 組み込みの保持(Retention): デフォルトで24時間のイベント保持があり、最長1年まで延長可能。アプリケーションエラーからの復旧や新コンポーネントの初期データ投入（ヒドレーション）に利用できます。
- Subscriberリソース: イベントフィルタリングと、250以上のAWSサービスへの配信を行う新しいサブスクライバ抽象を提供します。高度なイベント変換もサポートします。
- 厳密な順序保証と重複排除: 受信順での処理を保証するネイティブサポートが追加され、コンテンツベースの自動重複排除（イベント評価に基づく）も利用可能です。
- 利用方法: AWS Management Console、AWS CLI、AWS SDKs、Serverless Agent skill、AWS CloudFormation から作成・共有が可能です。
- 後方互換性: 既存のカスタムバスは "Custom event bus - classic" に名称変更され、既存APIは変更されていません。
- リージョンと価格: 発表時点で14リージョンで利用可能（米国・欧州・アジア太平洋の指定リージョン）。新価格モデルはイベント数ではなく転送データ量に課金され、スケールに応じてコスト効率が向上する設計です。

### 影響範囲・利用シーン

- **対象ユーザー**: エンタープライズのアーキテクト、クラウドエンジニア、SaaS統合担当者、チーム間でイベントを共有する組織
- **利用シーンまたは効果**: 中央イベントバスを使ったクロスアカウントのイベント集約と配信、CloudEvents互換のイベント受け入れ、過去イベントを用いたリカバリやコンポーネントのヒドレーション
- **運用効果**: 厳密な順序保証と自動重複排除により順序依存ワークフローの信頼性が向上し、24時間〜1年の保持で障害回復やリプレイが容易になる
- **コスト影響**: 新価格はデータ転送量ベースの課金のため、大量イベントを少量データで扱うケースやスケール時に従来のイベントあたり課金より低コストになる可能性がある（利用パターンに依存）
- **リージョン**: 発表時点では指定の14リージョンで公開。その他リージョンは順次対応予定の可能性あり
- **移行/互換性**: 既存バスは "Custom event bus - classic" として残るため、機能を使うには新しい強化バスへ明示的に移行または新規作成が必要になる可能性がある

### 技術的な注意点

- **IAM権限**: RAMによる共有、パブリッシュ（新API）、Subscriber作成、ターゲットサービスへの配信にはそれぞれ適切なEventBridgeおよびRAM/IAMの権限が必要です。PutEvents相当のAPI権限やCloudFormationでのリソース作成権限を事前に確認してください。
- **リージョン制限**: 発表時点で利用可能なのは以下14リージョンのみ: us-east-1, us-east-2, us-west-2, eu-west-1, eu-central-1, eu-north-1, eu-south-1, ap-northeast-1 (東京), ap-southeast-1 (シンガポール), ap-southeast-2 (シドニー), ap-southeast-3 (マレーシア), ap-southeast-4 (タイ), ap-south-1 (ムンバイ), ap-east-1 (香港)。他リージョンは未対応の可能性があります。

- **運用効果**: TLS鍵交換に対する量子耐性を導入することで、将来の量子攻撃リスク低減とセキュリティ体制の強化が可能

Network Security Managerはスケールしてセキュリティポリシーを展開・適用するためのマネージドサービスです。現時点でAWS WAFとAWS Shield Advancedをサポートし、将来的にAWS Network Firewallのサポートが追加される予定です。主な機能は、Internet向けのアセット（例：Application Load Balancer、Amazon CloudFront）に対する常時稼働のセキュリティ導入自動化（always-on deployment automation）、組織単位でのセキュリティポリシーの集中管理、設定ドリフトの自動検出と自動修復です。これにより、複数アカウント・複数リソースにまたがるWAFルールやShield Advancedの保護設定を一貫して適用でき、手動管理の運用負荷を低減します。料金は別途定められており、詳細はPricingページを参照してください。サービスは現在US East (N. Virginia)（us-east-1）で一般提供されています。

### 影響範囲・利用シーン

- **対象ユーザー**: セキュリティチーム、SRE、クラウド運用者、および複数AWSアカウントを管理する組織
- **利用シーン**: インターネット向けのロードバランサ／CDNに対するWAFルールとDDoS防御（Shield Advanced）を組織全体で一括展開・監査する場合
- **運用効果**: ポリシーの一元管理と自動修復により設定ドリフトを低減し、手動ミスによるセキュリティギャップを削減。導入・運用工数と復旧時間（MTTR）の短縮が期待できる

### 技術的な注意点

- **IAM権限**: 導入前に必要な管理権限（Organization管理者、Firewall Manager相当の権限やWAF/Shield管理権限）が必要。権限スコープは導入設計で確認してください
- **リージョン制限**: 現時点で一般提供はUS East (N. Virginia)（us-east-1）のみ。その他リージョンへは順次展開予定（公式アナウンスを確認）
- **コスト**: AWS WAF、Shield Advanced、（将来のNetwork Firewall）それぞれに別途料金が発生する可能性あり。Network Security Manager自体の利用料金が別途設定されているため、総所有コストを評価してください
- **サービス連携**: 現在サポート済みはAWS WAFとAWS Shield Advanced。AWS Network Firewallは追ってサポート予定のため、現時点でNetwork Firewall中心の構成は制約あり
- **注意事項**: 組織単位での適用は既存ポリシーやアカウント構成に影響を与えるため、ステージング／段階的ロールアウトでの検証を推奨。自動修復ルールは誤設定時に意図しない変更を引き起こす可能性があるため十分なテストを行ってください
