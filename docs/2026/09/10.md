## [Govcloud Us] Amazon Connect Customer now lets you set specific capacity limits for different types of Tasks and Emails

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-connect-capacity-limits/

### 概要

Amazon Connect Customerは、タスクおよびメールの各種コンタクトに対して、複雑度や優先度に基づく個別の同時処理上限（キャパシティ）と割り込みルールを設定できるようになりました。これによりチャネル単位だった従来の同時処理設定を細分化できます。

### 変更内容・新機能の詳細

これまで同時処理（concurrency）設定はチャネル単位で一律に適用され、同じチャネル内の全コンタクトが同一の扱いでした。本リリースでは、管理者がTaskおよびEmailコンタクトを「ワークロードタイプ」（複雑性・優先度・業務機能等で分類）に割り当て、それぞれに対して独立した同時処理上限と割り込み（中断）ルールを設定できます。たとえば「低負荷の簡易Taskは最大3件を同時処理」「高負荷の複雑Taskは同時1件に制限」といった動作が可能です。これらの設定はAmazon Connect Customer提供リージョン（AWS商用リージョンおよびAWS GovCloud (US-West) の提供リージョン）で利用可能です。詳細と設定手順はAmazon Connect Customer Administrator Guideを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: コンタクトセンターマネージャー、ワークフォース管理者、運用／SREチーム、CTIインテグレータ
- **利用シーン**: タスクやメールを複雑度や優先度で分類して適切な同時処理数を割り当てることで、応答品質やSLAを維持しつつエージェントの負荷を管理する場面（例: 高集中業務は同時1件、簡易業務は同時複数可）
- **運用効果**: エージェントのオーバーロード低減、優先度に応じた処理の最適化、SLA達成率向上、より正確なキャパシティプランニングが可能になる

### 技術的な注意点

- **IAM権限**: 管理コンソールやAPIで同時処理設定を変更するにはAmazon Connectの管理権限（関連するIAMポリシー）が必要です。事前に適切なIAMロール/ポリシーを確認してください
- **リージョン制限**: AWS商用リージョンおよびAWS GovCloud (US-West) のAmazon Connect Customer提供リージョンで利用可能。利用可否は各リージョンのサービス提供状況を確認してください
- **適用チャネル**: 本機能はTaskおよびEmailチャネルに対して提供されます。他チャネル（例: 音声/チャット）への同様の細分化が可能かはドキュメントで確認してください
- **設定の影響範囲**: 同時処理上限と割り込みルールの変更はルーティングやエージェントのUI/フロー挙動に影響を与える可能性があるため、ステージング環境で十分に検証してから本番適用してください
- **パフォーマンスとコスト**: 機能自体で直接の追加料金が発生するとは明記されていませんが、同時処理の緩和により必要なエージェント数や外部連携リソースが増減し、運用コストに影響する可能性があります
- **監査・ロギング**: 設定変更や割り込み動作の影響を追跡するため、CloudWatchログやAmazon Connectの監査ログ設定を確認・有効化することを推奨します
- **導入手順・テスト**: 実運用前にワークロードタイプの定義（複雑度基準・優先度ルール）を作成し、エージェント側のUXとルーティング挙動を確認してください

### 参考情報

- https://docs.aws.amazon.com/connect/latest/adminguide/
- https://aws.amazon.com/connect/

## [General] AWS Transform for .NET modernization is now generally available via CLI

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-transform-dotnet-cli

### 概要

AWS Transform の .NET モダナイゼーションが CLI からワンライナーで実行できる形で一般提供（GA）になりました。対話実行とパイプライン組込の両方に対応し、既存のWebアプリ、Visual Studio、Kiro Power、MCPエージェントの体験を補完します。

### 変更内容・新機能の詳細

AWS Transform の "AWS-managed transformation for .NET modernization" が AWS Transform custom を通じて CLI で利用可能になりました。単一の一行コマンドで変換をトリガーでき、対話モードまたは自動化されたCI/CDパイプライン内での実行が可能です。提供される変換には、言語バージョンのアップグレード、フレームワークのマイグレーション、パフォーマンス最適化、コードベース解析などが含まれ、AWS 管理の標準変換をそのまま使うか、組織固有の要件に合わせてカスタマイズすることができます。変換ロジックはエンゲージメントからの学習により継続的に改善され、より正確で効率的な結果が期待できます。サービスは以下の8リージョンで利用可能です: US East (N. Virginia)、Asia Pacific (Mumbai, Tokyo, Seoul, Sydney)、Canada (Central)、Europe (Frankfurt, London)。また、.NET モダナイゼーション変換には月間50,000分の無料エージェント時間が含まれます（詳細は料金ページ参照）。

### 影響範囲・利用シーン

- **対象ユーザー**: .NET アプリケーションを保守・近代化するソフトウェアエンジニア、プラットフォーム/クラウドアーキテクト、SRE/運用チーム
- **利用シーンまたは効果**: レガシー .NET Framework から新しい .NET バージョンへのアップグレード、フレームワーク移行（例: .NET Framework → .NET Core/.NET）、パフォーマンス改善、コード品質解析を自動化して大規模なコードベースを短期間で近代化
- **運用効果**: パイプラインに組み込むことで人的作業を削減し、変換の一貫性と再現性が向上。自動化によりマイグレーション作業の速度とスケールが大幅に改善される
- **コスト影響**: 月間50,000無料エージェント分の提供により小規模～中規模の作業はコスト抑制が期待できるが、超過分や追加のカスタム変換に対しては課金が発生する可能性がある
- **リージョン影響**: 現時点で利用可能なリージョンは限定されており（記事記載の8リージョン）、未対応リージョンでは利用できない

### 技術的な注意点

- **IAM権限**: CLI 実行には AWS Transform へのアクセス権（Transform の実行・管理に必要な IAM ポリシー）が必要。S3/CodeCommit/ECR などソース・成果物の読み書き権限も要確認
- **リージョン制限**: サービスは記事記載の8リージョンのみでGA。対象リージョン以外では利用不可（リージョンを跨いだデータ転送やレイテンシに注意）
- **コスト**: .NET モダナイゼーション変換は月間50,000無料エージェント分が含まれるが、超過分や追加のカスタム変換は料金が発生。事前に AWS Transform の料金ページで想定コストを確認してください
- **CLI利用上の注意**: ワンライナーで実行可能だが、対話モードと非対話モード（スクリプト化）の振る舞いを確認し、CI/CD パイプラインに組み込む際はログ・出力先（S3 等）の取り扱いを定義しておくこと
- **互換性/テスト**: 自動変換は高い精度を目指すが、特に大規模または複雑なコードベースでは事前のテスト、ステージング環境での検証、コードレビューが必須
- **エージェント/リソース**: 変換はエージェント（実行時間）を消費する。エージェントのキャパシティや並列実行の挙動、ネットワーク/ストレージ要件を設計に組み込むこと
- **監査/コンプライアンス**: 生成されたコードや変更履歴の保存・監査要件がある場合は、成果物の保存先とアクセス管理を明確にすること

## [General] AWS Lambda now supports 90-minute function timeout on Lambda Managed Instances

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-lambda-90-minute-function/

### 概要

AWS Lambda の Lambda Managed Instances (LMI) で、非同期およびイベントソースマッピング（ESM）呼び出しに対する関数タイムアウトが従来の15分から最大90分に拡張されました。これにより、メディアトランスコーディングや大規模なデータ処理、金融シミュレーション、AI推論など長時間実行が必要なジョブを再設計せずに Lambda 上で実行できます。

### 変更内容・新機能の詳細

今回のアップデートでは、Lambda Managed Instances を利用する非同期呼び出しおよびイベントソースマッピング（ESM）に対して、関数タイムアウトを最大90分まで設定できるようになりました（従来は最大15分）。LMI はインスタンス上で複数の同時リクエストを処理でき、専用のコンピューティング構成や EC2 に準じたコスト効率の恩恵を受けながらインフラ管理なしで実行できるのが特徴です。90分の拡張は Lambda Durable Functions（チェックポイントとリプレイを行う長期実行の仕組み）内の呼び出しにも適用されます。さらに、非同期でトリガーされたマルチステップな Durable 実行はチェックポイントを組み合わせることで最長1年までの実行シナリオをサポートします。タイムアウト設定は AWS コンソール、AWS CLI、Lambda API、IaC ツール群、Agent Toolkit for AWS などから変更可能です。一方で同期呼び出し（同期的な API 呼び出し等）は従来どおり最大15分が上限です。機能は Lambda Managed Instances が提供されているすべてのリージョンで利用可能ですが、実際の利用前に対象リージョンの LMI 提供状況を確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: サーバーレスで長時間実行ワークロードを扱う開発者、SRE、データエンジニア、MLエンジニア
- **利用シーンまたは効果**: メディアトランスコーディング、バッチデータ処理、Monte Carlo 等の金融シミュレーション、AI 推論や大規模前処理など、以前は15分制限のために分割や別サービス化が必要だった処理をそのまま Lambda で実行可能に
- **運用効果**: アーキテクチャの単純化（分割・キュー連携の不要化）、LMI によるコスト効率向上（EC2 型の利点）および Durable Functions 組合せでの回復性強化

### 技術的な注意点

- **IAM権限**: 関数のタイムアウトを変更するには lambda:UpdateFunctionConfiguration 等の権限が必要です。ESM や Durable Functions を構成する場合は追加のリソースアクセス権限を確認してください
- **リージョン制限**: 本機能は Lambda Managed Instances が利用可能なリージョンで提供されます。利用前に対象リージョンで LMI が有効か確認してください
- **コスト**: 実行時間が長くなるほど課金が増加します。LMI は EC2 風のコスト優位性がある場合がありますが、実行時間・メモリ・vCPU 構成に基づく料金影響を事前に評価してください（詳細は Lambda の料金ページ参照）
- **同期呼び出しの制限**: 同期（同期API呼び出し等）は従来どおり最大15分のままです。長時間実行を行う場合は必ず非同期またはESMでの実行を検討してください
- **互換性とトリガー**: 一部トリガーや統合は非同期実行をサポートしない場合があります。使用するイベントソースが非同期/ESM 呼び出しをサポートするか事前に確認してください
- **Durable Functions**: チェックポイントとリプレイを組み合わせることで最長1年のマルチステップ実行が可能ですが、ステート管理やリトライ戦略、エラー処理設計は別途検討が必要です
- **設定方法**: コンソール、AWS CLI、Lambda API、IaC（CloudFormation/CDK/Terraform 等）、Agent Toolkit からタイムアウト値を設定可能です。変更はデプロイ/設定更新の一部として適用されます

## [Lambda] AWS Lambda now supports Graviton5-powered EC2 instances on Lambda Managed Instances 

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-lambda-graviton5-ec2/

### 概要

AWS LambdaのLambda Managed Instancesで、最新のGraviton5搭載EC2インスタンスタイプ（C9g、C9gd、M9g、M9gd）が利用可能になりました。Graviton4と比べて最大25%の計算性能向上が見込まれます。

### 変更内容・新機能の詳細

Lambda Managed Instancesは、EC2のインスタンス上でLambda関数を運用の簡便さを保ったまま実行できるマネージドサービスです。本アップデートにより、C9g、C9gd、M9g、M9gdといったGraviton5（ARMベース）搭載インスタンスを選択できるようになりました。これにより、同等のワークロードで最大25%のコンピュート性能向上が期待できます。利用方法としては、Capacity Provider作成時に希望するGraviton5インスタンスタイプを指定するか、インスタンスタイプをdefaultに設定すると、Lambdaが関数の設定（アーキテクチャ、メモリサイズ、メモリ対vCPU比）に基づいて自動的にGraviton5インスタンスを候補に含めます。Lambda Managed Instancesはインスタンスライフサイクル管理、OS/ランタイムのパッチ適用、内蔵ルーティング、ロードバランシング、設定可能なパラメータに基づくオートスケーリングなどをフルマネージドで提供します。Graviton5サポートは、Lambda Managed Instancesと対象EC2インスタンスが両方利用可能なリージョンで提供されます。

### 影響範囲・利用シーン

- **対象ユーザー**: サーバレスを好むが専用インスタンスやEC2の価格優位性を活かしたい開発者・SRE/運用チーム
- **利用シーン**: CPU集約型バッチ処理、リアルタイムデータ変換、ハイパフォーマンスAPIバックエンドなどのワークロードでの性能向上とコスト最適化
- **運用効果**: Lambdaの運用簡便性を維持しつつ、Graviton5の性能向上で処理時間短縮やスループット向上、EC2料金の恩恵によるコスト削減が期待できる
- **互換性注意点**: ARM（arm64）アーキテクチャ向けにビルドされたランタイムやバイナリが必要なため、x86_64専用のネイティブ依存は再ビルドが必要

### 技術的な注意点

- **IAM権限**: Capacity Providerの作成・管理やLambda Managed Instancesの利用に必要なIAM権限（Capacity Provider作成、EC2関連、Lambdaの管理権限等）を事前に確認・付与してください
- **リージョン制限**: Graviton5インスタンスとLambda Managed Instancesの両方が利用可能なリージョンでのみ有効です。利用前に対象リージョンでの提供状況を確認してください
- **アーキテクチャ互換性**: Graviton5はARM（arm64）ベースです。関数・コンテナイメージ・ネイティブライブラリはarm64向けにビルド／テストする必要があります
- **ネイティブ依存**: ネイティブ拡張やサードパーティライブラリを含むレイヤーやコンテナは、arm64ビルドや代替バージョンの準備が必要です
- **コスト**: Lambda Managed InstancesはEC2の価格体系を活用できますが、Graviton5のインスタンスタイプごとに単価が異なります。性能向上に伴うコスト効率をベンチマークして評価してください
- **運用自動化**: インスタンスのライフサイクル・パッチ適用・オートスケーリングはマネージドだが、スケーリングパラメータやキャパシティ設定は適切に設計してください

## [Quicksight] Amazon Bedrock Managed Knowledge Base adds APIs and console support for debugging document-level access control

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Quicksight
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-knowledge-base-debugging-document-access-control/

### 概要

Amazon Bedrock Managed Knowledge Baseに、ドキュメント単位のアクセス制御(ACL)をデバッグ・監査するための2つのAPI（CheckIngestedDocumentAcl、GetIngestedDocumentAcl）とコンソール機能が追加されました。これにより、アクセスできないドキュメントの原因切り分けが迅速に行えます。

### 変更内容・新機能の詳細

追加されたAPIは以下のとおりです。

- CheckIngestedDocumentAcl: 指定したインジェスト済みドキュメントIDとユーザー（例: メールアドレス）を指定し、そのユーザーが当該ドキュメントへアクセス可能かどうか（true/false など）を確認します。これにより、検索/取得結果にドキュメントが現れない原因がアクセス権によるものかどうかを即座に判定できます。

- GetIngestedDocumentAcl: 指定したドキュメントに紐づくフルACL（許可されたプリンシパルと権限の一覧）を返します。ACLの内容を直接確認することで、誤った許可設定や抜けを監査・修正できます。

コンソール側ではデータソース詳細ページに「Document Access Control」セクションが追加され、ドキュメントIDとユーザー情報を入力してアクセス可否をチェックしたり、ドキュメントIDからフルACLを取得して表示できます。これらはACL対応データソース向けの機能で、管理者が大規模なナレッジベースのアクセス制御を可視化・運用するのに役立ちます。APIは自動化スクリプトやCI/CDパイプラインに組み込めるため、権限変更後の検証や定期監査にも利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: ナレッジベース管理者、セキュリティ/ガバナンス担当、SRE/運用チーム
- **利用シーン**: 検索結果に期待するドキュメントが表示されない際の原因切り分け、ドキュメント単位の権限設定の監査と修正確認
- **運用効果**: サポートケースを開かずに自己解決が可能になり、トラブル対応時間の短縮と誤設定検出の効率化が期待される
- **スケーラビリティ**: APIを使った自動チェックで大量ドキュメントの権限監査や定期検査が容易になる

### 技術的な注意点

- **IAM権限**: API呼び出しには bedrock:CheckIngestedDocumentAcl および bedrock:GetIngestedDocumentAcl に対する許可が必要（マネージドポリシー/カスタムポリシーでの権限付与を確認してください）
- **リージョン制限**: Managed Knowledge Base機能が利用可能なリージョンのみで使用可能。未対応リージョンでは利用不可の可能性あり
- **対象データソース**: ACL対応（ACL-enabled）として設定されたデータソースに対してのみ有効。ACL未設定のデータソースでは意味を持ちません
- **入力要件**: 照会には正確なドキュメントIDと照合するユーザー識別子（例: メールアドレス）が必要
- **ログ/監査**: API呼び出しはCloudTrail等で記録される（一般的なAWS APIの挙動に準拠）。監査ログとして利用可能です
- **コスト**: これら管理API/コンソール操作自体に特別な料金が発生する可能性は低いが、Knowledge BaseやBedrockの利用料、データ転送等の通常コストは発生します
- **運用上の注意**: ACLの変更や検証を行う際は、変更前後の状態を記録し、誤設定による過剰公開を防ぐため最小権限の原則を遵守してください
