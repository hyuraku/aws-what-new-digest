## [General] Amazon CloudWatch now supports network health indicator for TGW inter-Region peering using synthetic monitors

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/cloudwatch-network-monitoring-tgw-support/

### 概要

Amazon CloudWatch の Network Monitoring において、synthetic monitors が AWS Transit Gateway のリージョン間ピアリング経由のパスに対するネットワークヘルス指標（Network Health Indicator, NHI）をサポートするようになりました。これにより、当該経路で発生する性能劣化が AWS 側ネットワークに起因するかを迅速に判定でき、原因切り分け時間が短縮されます。

### 変更内容・新機能の詳細

これまで synthetic monitors の NHI は AWS Direct Connect 経由の経路に対してのみ提供されていましたが、本リリースにより Transit Gateway (TGW) のリージョン間ピアリング経由で宛先がピアリング済みリージョンに到達するパスについても NHI が拡張されました。NHI は、TGW のピアリング接続までの AWS 側ネットワーク経路のヘルスを反映し、その結果は Amazon CloudWatch のメトリクスとして発行されるため、ダッシュボード表示やアラーム設定が可能です。利用にあたっては対象の経路が TGW リージョン間ピアリングを経由することが前提で、NHI はピア接続点（Transit Gateway peering connection）までの AWS ネットワーク区間を評価するものであり、ピア先リージョン内の VPC 内やオンプレミス側の顧客管理区間までは含みません。利用可能な AWS リージョンは提供されているリージョンリストを確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: ネットワーク運用者、SRE、クラウド/アプリケーション開発者
- **利用シーン**: マルチリージョン構成で Transit Gateway のリージョン間ピアリングを利用するアプリケーションのパフォーマンス劣化切り分け、Synthetic monitor を用いた経路監視とアラート運用
- **運用効果**: AWS 側ネットワークが原因かどうかを自動的に示すことで、原因切り分け時間（MTTR）の短縮、ダッシュボードやアラーム連携による迅速な対応が可能

### 技術的な注意点

- **IAM権限**: CloudWatch のメトリクス閲覧・管理権限（例: CloudWatchReadOnlyAccess / CloudWatchFullAccess、必要に応じて synthetic monitor の作成権限）が必要です。サービスリンクドロールや追加の Network Monitoring 用権限を求められる場合があります。
- **リージョン制限**: すべてのリージョンで利用可能ではありません。対応リージョンは公式のリージョンリストを確認してください（記事参照）。
- **コスト**: synthetic monitors の実行、CloudWatch メトリクスの発行・保存、アラーム作成には料金が発生する可能性があります。監視頻度やメトリクス保存期間によってコストが変動します。
- **設定要件**: 対象パスは Transit Gateway のリージョン間ピアリング経由である必要があります。TGW とピアリング接続が正しく構成されていることを事前に確認してください。
- **カバレッジ**: NHI は AWS ネットワーク区間（エンドポイントから TGW ピア接続まで）を評価します。ピア接続先の VPC 内やオンプレミスのネットワーク、あるいはアプリケーション層の問題は NHI の評価対象外です。

## [Elemental Medialive] AWS Elemental Inference now generates contextual metadata from live video in real time

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Elemental Medialive
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/elemental-inference-contextual-metadata/

### 概要

AWS Elemental Inferenceがライブ映像をリアルタイムで解析し、シーン単位のコンテクストメタデータ（IABカテゴリ、GARMブランド適合性、検出オブジェクト/アクション、ショット／シーン記述など）を自動生成できるようになりました。カスタムMLインフラ不要のサーバーレス運用で、広告決定やメディア資産の強化、コンテンツ発見に利用できます。

### 変更内容・新機能の詳細

新機能はライブ映像のエンコード処理と並列にAI解析を行い、次のようなシーンレベルの知見を生成します：IABコンテンツタクソノミーカテゴリ、GARMブランド適合性シグナル、検出されたオブジェクトおよびアクション、ショット／シーンの記述。広告用途では、MediaLiveがElemental InferenceのフィードIDをSCTE-35アドマーカーに埋め込み、各広告枠でMediaTailorがMonetization Functionを通してそのフィードIDに紐づくシーン信号を取得し、広告サーバーが期待するターゲティングパラメータに変換します。これによりカスタム統合を行わずにコンテキストベースのアドディシジョン（コンテクスチュアルディール振り分け、ブランド適合スコア等）が可能になります。メディア管理面では、オブジェクト／アクションの検出やショット／シーン記述によって自動的に構造化メタデータが生成され、アーカイブの強化、編集支援、パーソナライズ推奨が手作業なしに実現できます。機能はAWS Elemental MediaLiveコンソールから利用可能で、Elemental Inferenceが提供されているリージョンで有効です。

### 影響範囲・利用シーン

- **対象ユーザー**: 放送事業者、OTTプラットフォーム、広告テクノロジー（AdOps）チーム、メディア資産管理（MAM）担当者
- **利用シーン**: ライブ番組のコンテキスト広告配信（SCTE-35でのフィードID→MediaTailor経由によるターゲティング）、自動メタデータ生成によるアーカイブ強化と検索性向上、アシスト編集やパーソナライズ推薦の自動化
- **運用効果**: カスタムMLや後処理なしでリアルタイムな文脈理解が得られ、広告収益の最適化（ブランド適合対応、コンテキストターゲティング）や運用コストの削減（手作業によるログ取りやポストプロダクションの工数削減）につながる

### 技術的な注意点

- **IAM権限**: MediaLive、Elemental Inference、MediaTailor、Monetization Functionを連携するための適切なIAMロールとポリシー（各サービスへのアクセス許可）を事前に設定してください
- **SCTE-35要件**: MediaLiveが埋め込むSCTE-35アドマーカーにElemental InferenceのフィードIDを含めるフローが必要です。既存のSCTE-35ワークフローとの整合性を確認してください
- **MediaTailor設定**: MediaTailorのMonetization Functionを実装して、フィードIDに紐づくシーンシグナルを取得・マッピングし、広告サーバーが期待するターゲティングパラメータに変換する設定が必要です
- **リージョン制限**: 本機能は『AWS Elemental Inferenceが利用可能なリージョン』で利用可能です。利用前に対象リージョンでElemental Inferenceの提供状況を確認してください
- **レイテンシ**: 解析はエンコードと並列に行われますが、シーン解析の完了タイミングやネットワーク条件により実際の利用可能タイミングに遅延が生じる可能性があります。特に短い広告ブレークや低遅延要件のワークフローは事前検証が必要です
- **フォーマット／コンテンツ制約**: ライブストリームベースの機能です。入力コーデックや解像度、フレームレートによる解析精度やコスト影響が出る可能性があるため、想定する配信フォーマットでの検証を推奨します
- **コスト**: Elemental Inferenceの解析処理、追加のMediaTailor呼び出しやMonetization Functionの実行などで追加料金が発生します。想定トラフィックでコスト試算を行ってください
- **データ保護／コンプライアンス**: 映像解析に伴うプライバシーやブランドポリシーの考慮が必要です。地域の規制や社内ポリシーに従って利用してください

## [General] AWS Elemental MediaTailor now offers Yield Optimization to automatically fill ad breaks with Amazon Ads demand

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/mediatailor-yield-optimization/

### 概要

AWS Elemental MediaTailorにYield Optimization機能が追加され、ライブ配信のSSAI中に未使用の広告枠をAmazon Adsの需要で自動的にマネタイズできるようになりました。APS（Amazon Publisher Services）Streaming TVプログラム参加出版社向けの機能で、追加インフラ不要・無償で有効化できます。

### 変更内容・新機能の詳細

Yield Optimizationはサーバーサイド広告挿入（SSAI）を行うライブストリーミングで、未充填の広告ブレイクをAmazon Adsの需要で自動的に埋める機能です。広告は視聴者に届く前にストリームに直接ステッチされるため、デバイスに依存せずシームレスに再生されます。主な技術的特徴は以下の通りです：
- 大規模対応：プロリーグの大会などピーク視聴時の大量リクエストに対応する低レイテンシ設計で、広告フィル（fill）率を最大化します。
- ブランドセーフティと制御：カテゴリフィルタリングにより同一広告ブレイク内の競合を回避でき、出版社は価格フロア（最低入札価格）やカテゴリルールを設定して配信制御が可能です。
- 簡単導入：MediaTailorのAPIまたはコンソールから設定可能で、追加のインフラやクライアント側の変更は不要です。
- 可視化とレポート：広告フィル率などのMediaTailorメトリクスはAmazon CloudWatchで監視でき、収益・支払いはAPS Publisherポータルで確認できます。
- 利用条件：本機能はAPS Streaming TVプログラムに参加している出版社専用で、ライブ配信向けのSSAIに適用されます。
- 価格とリージョン：機能自体は有効化費用不要で、MediaTailorが利用可能な全リージョン（記事に列挙された主要リージョンを含む）で提供されます。

### 影響範囲・利用シーン

- **対象ユーザー**: ライブ配信を行う放送局／メディア出版社、OTTサービス、広告収益化を図るプラットフォーム事業者（APS Streaming TV参加が必要）
- **利用シーンまたは効果**: ライブイベントやスポーツ中継で未使用の広告枠を自動的にマネタイズすることで広告フィル率と収益を向上させる（SSAI環境での即時収益化）
- **運用効果**: クライアント側変更不要で導入が容易、CloudWatchおよびAPSポータルで効果測定が可能なため運用負荷を低減しつつ収益化を迅速化できる

### 技術的な注意点

- **APS参加要件**: この機能はAmazon Publisher Services (APS) Streaming TVプログラムに参加している出版社のみ利用可能です
- **対応コンテンツ**: 主にライブストリーミング（SSAI）向けに設計されており、VODへの適用は記事では明示されていません。VODでの利用可否はドキュメントで確認してください
- **IAM権限**: MediaTailorの設定を変更するためのAPI/コンソールアクセス権限（mediatailor関連のIAMポリシー）が必要です。APSポータルへのアクセス権は別途管理されます
- **リージョン制限**: MediaTailorが利用可能な全リージョンで提供されます（例：US East (Ohio/N. Virginia)、US West (Oregon)、東京、ソウル、シンガポール、フランクフルト、ロンドン、パリ、シドニーなど）。ただし、利用前に対象リージョンでAPS連携が有効か確認してください
- **コスト**: 機能の有効化自体に追加料金は発生しませんが、CloudWatchのメトリクスやログ、通常のMediaTailorおよびデータ転送コストは別途発生する可能性があります。また、Amazon Adsとの収益分配はAPSの契約条件に従いますので契約内容を確認してください
- **広告制御設定**: 価格フロアやカテゴリルールは出版社側で設定・管理可能です。ブランドセーフティのためのカテゴリフィルタリングや除外設定を適切に構成してください
- **クライアント影響**: SSAIでサーバー側に広告がステッチされるため、プレイヤーSDKやクライアント側の変更は不要ですが、再生確認やQAは実施してください
- **モニタリング**: 広告フィル率やレスポンス指標はCloudWatchで確認できます。収益レポートはAPS Publisherポータルで確認してください
- **パフォーマンス**: 大規模イベント向けに低遅延設計ですが、具体的なSLAsやスループット要件は導入前に検証してください

## [General] AWS Elemental MediaLive adds support for A/B forensic watermarking

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/medialive-ab-forensic-watermarking/

### 概要

AWS Elemental MediaLiveがA/B方式のフォレンジック・ウォーターマーキングをサポートしました。ライブ映像の不正再配布元を追跡できるよう、同一チャネルで2種類の透過ウォーターマークを付与した同期出力を生成します。

### 変更内容・新機能の詳細

MediaLiveは単一チャネルから同期した2つの出力バリアント（A/B）を生成し、それぞれに視認性のほとんどない（visually transparent）別々のフォレンジックウォーターマークを埋め込みます。これらのウォーターマークは再エンコードや画面キャプチャ後も残存する設計で、下流のパッケージャとCDNが各セッション毎にA/Bバリアントを組み合わせて一意のセッションシーケンスを作成することで、リーク元の特定が可能になります。実装はDASH Industry Forum（DASH-IF）のA/Bウォーターマーキング仕様（ETSI TS 104 002）に準拠しており、標準に準拠したパッケージャやCDNと相互運用できます。設定はMediaLiveコンソールまたはAPIから、Common Media Application Format（CMAF）Ingest出力グループに対して行います。MediaLiveはCMAF Ingest経由でウォーターマーク付きA/BバリアントをAWS Elemental MediaPackageやサードパーティのパッケージャへ配信し、対応するCDN（例：Amazon CloudFront）を用いて下流でのセッション単位のウォーターマーク組み立てを行います。A/Bフォレンジック・ウォーターマーキングは、MediaLiveが利用可能な全リージョンで使用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: ライブ映像を配信するコンテンツホルダー、放送事業者、OTT プロバイダ、セキュリティ/法務チーム
- **利用シーン**: ライブスポーツや有料イベントの不正再配布（スクリーンキャプチャや再エンコードによる流出）を特定して法的措置や配信遮断に繋げるための追跡
- **運用効果**: 流出ソースの特定が可能になり、不正流通の抑止や調査工数の削減につながる。標準準拠のため既存のMediaPackageやCloudFront等のインフラに組み込みやすい

### 技術的な注意点

- **IAM権限**: MediaLiveの設定・CMAF出力作成・MediaPackageへの接続には該当するMediaLive/MediaPackage/APIの実行権限が必要です。事前に最小権限のIAMポリシーを用意してください
- **リージョン制限**: 記事によれば、MediaLiveが利用可能なすべてのリージョンで利用可能とされていますが、実際の利用前に個別リージョンでの提供状況をAWSコンソールで確認してください
- **コスト**: MediaLiveの通常のインスタンス/チャンネル課金、出力ビットレートに伴う帯域・MediaPackage/CloudFront等の下流サービスの料金が発生します。A/Bの同期出力や下流でのセッション別配信によりオリジン帯域やトランスコード負荷が増える可能性があるため請求影響を確認してください
- **互換性**: 本機能はCMAF Ingest出力グループでの利用が前提です。下流のパッケージャとCDNがDASH-IF（ETSI TS 104 002）に準拠したA/Bウォーターマーキングのセッション組み立てをサポートしている必要があります。MediaPackageは対応していますが、サードパーティ製パッケージャやCDNでは事前確認が必要です
- **運用上の留意点**: フォレンジックウォーターマークは検出防止（盗聴・コピー防止）ではなく追跡手段です。テスト環境で再エンコードやキャプチャ条件下でのウォーターマーク残存性を検証し、ログ/セッション情報の保管運用を設計してください
- **CMAF制約**: 設定はCMAF Ingest出力グループに対して行うため、既存ワークフローがCMAFを前提としているか確認してください

## [Elemental Mediatailor] AWS Elemental MediaTailor now supports Low-Latency HLS ad insertion

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Elemental Mediatailor
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-elemental-mediatailor-low-latency-hls-ad-insertion

### 概要

AWS Elemental MediaTailorがLow-Latency HLS（LL-HLS）での広告挿入をサポートしました。これにより、低遅延のライブ配信（スポーツ、ニュース、ベッティング等）で視聴者に期待される短い遅延を維持しつつ広告を挿入できます。

### 変更内容・新機能の詳細

MediaTailorはHLS Interstitialsを用いてLL-HLS広告挿入を実現します。LL-HLSはEXT-X-PART等の部分セグメント（partial segments）を配信し、プレーヤーが次パートが準備されるまでプレイリスト要求をオープンに保持することで低遅延を達成します。従来の広告挿入方法だと各視聴者ごとにマニフェストをステッチする必要がありキャッシュが効きにくかったのに対し、HLS Interstitialsは広告を個別のプレイリストとして参照する方式を採るため、メディアプレイリストをCDNエッジでキャッシュ可能に保てます。結果として、すべての視聴者が同一のキャッシュ可能なプレイリストを受け取り、MediaTailorはマニフェスト要求パス上での広告決定サーバー（ADS）呼び出しを切り離してスケールした低遅延再生を維持できます。実運用ではマルチミリオンビュー規模のライブスポーツで検証済みです。利用想定はライブスポーツ、速報ニュース、ベッティング・ワager、ウォッチパーティ、インタラクティブライブなど、遅延がプロダクト要件となるケースです。また、本機能はMediaTailorが利用可能なすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: ライブ動画配信事業者、OTTプラットフォームのエンジニア、広告配信エンジニア
- **利用シーンまたは効果**: 低遅延を必須とするライブ配信（スポーツ中継、速報、ベッティング、インタラクティブ配信）での広告挿入をスケールして実現
- **運用効果**: マニフェストを共通化してCDNキャッシュを効かせることで高負荷下でも低遅延を維持しつつ一貫した広告配信が可能
- **ビジネス効果**: 大規模同時視聴時でも広告挿入によるユーザー体験悪化を抑え、収益化機会を維持・向上できる

### 技術的な注意点

- **IAM権限**: MediaTailorの設定変更やチャネル/コンフィグ作成に必要なIAM権限（mediatailor:*系）を付与してください。ADSや配信に関わるAWSリソースへの権限も確認が必要です
- **プレーヤー互換性**: クライアント側でLL-HLS（EXT-X-PART等）をサポートするプレーヤーが必要です。全てのデバイス/SDKでサポートされているわけではないため対象端末で事前検証を行ってください

- **視聴者体験**: 既存のHLS/DASH対応プレーヤーでネイティブ再生できるためアプリ改修なしで導入可能
- **コストへの影響**: MediaLiveでの各ソースの常時エンコードコストは発生するが、プリエンコード保存コストや多段のストレージコスト削減により総コスト構造が改善される可能性あり。MediaPackageでのオンデマンド組み立てや出力配信に伴うリクエスト/パッケージング/データ転送コストも考慮が必要

### 技術的な注意点

- **IAM権限**: MediaLiveおよびMediaPackageのリソース作成・操作に必要なIAMポリシーを付与してください（パッケージングや出力設定の変更権限が必要）

- **遅延**: サーバー側でのオンデマンド組み立てにより若干のパッケージング遅延が発生する可能性があります。リアルタイム性が厳しいユースケースは検証を推奨します
- **コスト**: MediaLiveのエンコード料金、MediaPackageのパッケージング/リクエスト/出力（転送）コストが発生します。オンデマンド生成はプリエンコード保存のコストを削減しますが、トラフィック増加によるデータ転送料金に注意してください

### 概要

AWS Storage Gateway の Amazon S3 File Gateway が、AWS PrivateLink（Interface VPC エンドポイント）経由で FIPS 140-3 準拠のエンドポイントをサポートしました。これにより、規制対象ワークロード向けに FIPS 準拠トラフィックをパブリックインターネットを経由させずにプライベートな AWS ネットワーク内で完結できます。

### 変更内容・新機能の詳細

今回の更新により、File Gateway は Storage Gateway サービスおよび Amazon S3 への通信を FIPS 140-3 準拠のインターフェイス VPC エンドポイント（PrivateLink）経由で行えるようになりました。従来は FIPS エンドポイントはパブリックインターネット経由のみの提供でしたが、今後は VPC 内に FIPS インターフェイスエンドポイントを作成して、ゲートウェイのアクティベーション時およびファイル共有（NFS/SMB）設定時に「FIPS VPC エンドポイント」オプションを選択することで、エンドツーエンドで FIPS 準拠のプライベート接続を実現できます。動作条件として、ゲートウェイのソフトウェアバージョンは 2.1.10 以降が必要です。本機能は Storage Gateway の FIPS エンドポイントを提供する下記 8 リージョンで利用可能です：US East (N. Virginia)、US East (Ohio)、US West (N. California)、US West (Oregon)、Canada (Central)、Canada West (Calgary)、AWS GovCloud (US-East)、AWS GovCloud (US-West)。実装手順の概略は、VPC に Storage Gateway と S3 用の FIPS インターフェイスエンドポイントを作成し、ゲートウェイのアクティベーションまたは既存ゲートウェイの設定で FIPS VPC エンドポイントを選択、必要に応じてエンドポイントポリシー・セキュリティグループ・Private DNS を設定する、という流れです。

- **対象ユーザー**: 規制準拠（FIPS 140-3）が必要な企業、セキュアなオンプレミス→S3 ファイルアクセスを求めるエンタープライズ
- **利用シーン**: 規制対応が必要なバックアップ／アーカイブ、医療・金融などのセキュアなファイル共有（NFS/SMB）ワークロード、オンプレミス機器からの安全な S3 連携
- **運用効果**: トラフィックをパブリックインターネットに出さずに FIPS 準拠通信が可能になり、コンプライアンス要件の満たしやすさとネットワークセキュリティの向上が期待できる
- **導入影響**: ネットワーク構成（VPC エンドポイント、セキュリティグループ、Private DNS）とゲートウェイのソフトウェアアップデートが必要

### 技術的な注意点

- **ソフトウェアバージョン**: ゲートウェイはソフトウェア v2.1.10 以上が必要です
- **リージョン制限**: 本機能は下記 8 リージョンで利用可能—US East (N. Virginia), US East (Ohio), US West (N. California), US West (Oregon), Canada (Central), Canada West (Calgary), AWS GovCloud (US-East), AWS GovCloud (US-West)
- **IAM権限**: VPC エンドポイントの作成、エンドポイントポリシー編集、Storage Gateway のアクティベーション設定に必要な権限を持つ IAM ロール/ユーザーが必要です
- **ネットワーク設定**: Interface VPC エンドポイントは ENI を作成するため、適切なサブネット・セキュリティグループ設定、必要に応じて Private DNS の有効化またはカスタム DNS の設定が必要です
- **エンドポイントポリシー**: S3 および Storage Gateway のエンドポイントに対するアクセス制御（エンドポイントポリシー）を適切に設定してください
- **コスト**: Interface VPC エンドポイントの時間課金とデータ処理料金、追加のデータ転送料金が発生する可能性があります。コスト見積りを行ってください
- **運用上の注意**: 既存ゲートウェイを FIPS PrivateLink に切り替える場合は計画的なメンテナンスを推奨します（接続設定変更や再アクティベーションが必要となるケースあり）

- **利用シーン**: データセンターの撤退（データセンター・エグジット）、レイテンシ要件の厳しいアプリケーションの近接展開、データ主権／居住性準拠のためのリージョン移設

## [General] AWS Lambda now supports 90-minute function timeout on Lambda Managed Instances

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-lambda-90-minute-function/

### 概要

AWS Lambda の Lambda Managed Instances (LMI) で、非同期およびイベントソースマッピング（ESM）呼び出しに対する関数タイムアウトが従来の15分から最大90分に拡張されました。これにより、メディアトランスコーディングや大規模なデータ処理、金融シミュレーション、AI推論など長時間実行が必要なジョブを再設計せずに Lambda 上で実行できます。

### 変更内容・新機能の詳細

今回のアップデートでは、Lambda Managed Instances を利用する非同期呼び出しおよびイベントソースマッピング（ESM）に対して、関数タイムアウトを最大90分まで設定できるようになりました（従来は最大15分）。LMI はインスタンス上で複数の同時リクエストを処理でき、専用のコンピューティング構成や EC2 に準じたコスト効率の恩恵を受けながらインフラ管理なしで実行できるのが特徴です。90分の拡張は Lambda Durable Functions（チェックポイントとリプレイを行う長期実行の仕組み）内の呼び出しにも適用されます。さらに、非同期でトリガーされたマルチステップな Durable 実行はチェックポイントを組み合わせることで最長1年までの実行シナリオをサポートします。タイムアウト設定は AWS コンソール、AWS CLI、Lambda API、IaC ツール群、Agent Toolkit for AWS などから変更可能です。一方で同期呼び出し（同期的な API 呼び出し等）は従来どおり最大15分が上限です。機能は Lambda Managed Instances が提供されているすべてのリージョンで利用可能ですが、実際の利用前に対象リージョンの LMI 提供状況を確認してください。

### 影響範囲・利用シーン

- **対象ユーザー**: サーバーレスで長時間実行ワークロードを扱う開発者、SRE、データエンジニア、MLエンジニア
- **利用シーンまたは効果**: メディアトランスコーディング、バッチデータ処理、Monte Carlo 等の金融シミュレーション、AI 推論や大規模前処理など、以前は15分制限のために分割や別サービス化が必要だった処理をそのまま Lambda で実行可能に
- **運用効果**: アーキテクチャの単純化（分割・キュー連携の不要化）、LMI によるコスト効率向上（EC2 型の利点）および Durable Functions 組合せでの回復性強化

### 技術的な注意点

- **IAM権限**: 関数のタイムアウトを変更するには lambda:UpdateFunctionConfiguration 等の権限が必要です。ESM や Durable Functions を構成する場合は追加のリソースアクセス権限を確認してください
- **リージョン制限**: 本機能は Lambda Managed Instances が利用可能なリージョンで提供されます。利用前に対象リージョンで LMI が有効か確認してください
- **コスト**: 実行時間が長くなるほど課金が増加します。LMI は EC2 風のコスト優位性がある場合がありますが、実行時間・メモリ・vCPU 構成に基づく料金影響を事前に評価してください（詳細は Lambda の料金ページ参照）
- **同期呼び出しの制限**: 同期（同期API呼び出し等）は従来どおり最大15分のままです。長時間実行を行う場合は必ず非同期またはESMでの実行を検討してください
- **互換性とトリガー**: 一部トリガーや統合は非同期実行をサポートしない場合があります。使用するイベントソースが非同期/ESM 呼び出しをサポートするか事前に確認してください
- **Durable Functions**: チェックポイントとリプレイを組み合わせることで最長1年のマルチステップ実行が可能ですが、ステート管理やリトライ戦略、エラー処理設計は別途検討が必要です
- **設定方法**: コンソール、AWS CLI、Lambda API、IaC（CloudFormation/CDK/Terraform 等）、Agent Toolkit からタイムアウト値を設定可能です。変更はデプロイ/設定更新の一部として適用されます

## [Lambda] AWS Lambda now supports Graviton5-powered EC2 instances on Lambda Managed Instances

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Lambda
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-lambda-graviton5-ec2/

### 概要

AWS LambdaのLambda Managed Instancesで、最新のGraviton5搭載EC2インスタンスタイプ（C9g、C9gd、M9g、M9gd）が利用可能になりました。Graviton4と比べて最大25%の計算性能向上が見込まれます。

### 変更内容・新機能の詳細

Lambda Managed Instancesは、EC2のインスタンス上でLambda関数を運用の簡便さを保ったまま実行できるマネージドサービスです。本アップデートにより、C9g、C9gd、M9g、M9gdといったGraviton5（ARMベース）搭載インスタンスを選択できるようになりました。これにより、同等のワークロードで最大25%のコンピュート性能向上が期待できます。利用方法としては、Capacity Provider作成時に希望するGraviton5インスタンスタイプを指定するか、インスタンスタイプをdefaultに設定すると、Lambdaが関数の設定（アーキテクチャ、メモリサイズ、メモリ対vCPU比）に基づいて自動的にGraviton5インスタンスを候補に含めます。Lambda Managed Instancesはインスタンスライフサイクル管理、OS/ランタイムのパッチ適用、内蔵ルーティング、ロードバランシング、設定可能なパラメータに基づくオートスケーリングなどをフルマネージドで提供します。Graviton5サポートは、Lambda Managed Instancesと対象EC2インスタンスが両方利用可能なリージョンで提供されます。

### 影響範囲・利用シーン

- **対象ユーザー**: サーバレスを好むが専用インスタンスやEC2の価格優位性を活かしたい開発者・SRE/運用チーム
- **利用シーン**: CPU集約型バッチ処理、リアルタイムデータ変換、ハイパフォーマンスAPIバックエンドなどのワークロードでの性能向上とコスト最適化
- **運用効果**: Lambdaの運用簡便性を維持しつつ、Graviton5の性能向上で処理時間短縮やスループット向上、EC2料金の恩恵によるコスト削減が期待できる
- **互換性注意点**: ARM（arm64）アーキテクチャ向けにビルドされたランタイムやバイナリが必要なため、x86_64専用のネイティブ依存は再ビルドが必要

### 技術的な注意点

- **IAM権限**: Capacity Providerの作成・管理やLambda Managed Instancesの利用に必要なIAM権限（Capacity Provider作成、EC2関連、Lambdaの管理権限等）を事前に確認・付与してください
- **リージョン制限**: Graviton5インスタンスとLambda Managed Instancesの両方が利用可能なリージョンでのみ有効です。利用前に対象リージョンでの提供状況を確認してください
- **アーキテクチャ互換性**: Graviton5はARM（arm64）ベースです。関数・コンテナイメージ・ネイティブライブラリはarm64向けにビルド／テストする必要があります
- **ネイティブ依存**: ネイティブ拡張やサードパーティライブラリを含むレイヤーやコンテナは、arm64ビルドや代替バージョンの準備が必要です
- **コスト**: Lambda Managed InstancesはEC2の価格体系を活用できますが、Graviton5のインスタンスタイプごとに単価が異なります。性能向上に伴うコスト効率をベンチマークして評価してください
- **運用自動化**: インスタンスのライフサイクル・パッチ適用・オートスケーリングはマネージドだが、スケーリングパラメータやキャパシティ設定は適切に設計してください

## [Quicksight] Amazon Bedrock Managed Knowledge Base adds APIs and console support for debugging document-level access control

- **公開日**: 2026-09-10 (JST)
- **カテゴリ**: Quicksight
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-knowledge-base-debugging-document-access-control/

### 概要

Amazon Bedrock Managed Knowledge Baseに、ドキュメント単位のアクセス制御(ACL)をデバッグ・監査するための2つのAPI（CheckIngestedDocumentAcl、GetIngestedDocumentAcl）とコンソール機能が追加されました。これにより、アクセスできないドキュメントの原因切り分けが迅速に行えます。

### 変更内容・新機能の詳細

追加されたAPIは以下のとおりです。

- CheckIngestedDocumentAcl: 指定したインジェスト済みドキュメントIDとユーザー（例: メールアドレス）を指定し、そのユーザーが当該ドキュメントへアクセス可能かどうか（true/false など）を確認します。これにより、検索/取得結果にドキュメントが現れない原因がアクセス権によるものかどうかを即座に判定できます。

- GetIngestedDocumentAcl: 指定したドキュメントに紐づくフルACL（許可されたプリンシパルと権限の一覧）を返します。ACLの内容を直接確認することで、誤った許可設定や抜けを監査・修正できます。

コンソール側ではデータソース詳細ページに「Document Access Control」セクションが追加され、ドキュメントIDとユーザー情報を入力してアクセス可否をチェックしたり、ドキュメントIDからフルACLを取得して表示できます。これらはACL対応データソース向けの機能で、管理者が大規模なナレッジベースのアクセス制御を可視化・運用するのに役立ちます。APIは自動化スクリプトやCI/CDパイプラインに組み込めるため、権限変更後の検証や定期監査にも利用できます。

### 影響範囲・利用シーン

- **対象ユーザー**: ナレッジベース管理者、セキュリティ/ガバナンス担当、SRE/運用チーム
- **利用シーン**: 検索結果に期待するドキュメントが表示されない際の原因切り分け、ドキュメント単位の権限設定の監査と修正確認
- **運用効果**: サポートケースを開かずに自己解決が可能になり、トラブル対応時間の短縮と誤設定検出の効率化が期待される
- **スケーラビリティ**: APIを使った自動チェックで大量ドキュメントの権限監査や定期検査が容易になる

### 技術的な注意点

- **IAM権限**: API呼び出しには bedrock:CheckIngestedDocumentAcl および bedrock:GetIngestedDocumentAcl に対する許可が必要（マネージドポリシー/カスタムポリシーでの権限付与を確認してください）
- **リージョン制限**: Managed Knowledge Base機能が利用可能なリージョンのみで使用可能。未対応リージョンでは利用不可の可能性あり
- **対象データソース**: ACL対応（ACL-enabled）として設定されたデータソースに対してのみ有効。ACL未設定のデータソースでは意味を持ちません
- **入力要件**: 照会には正確なドキュメントIDと照合するユーザー識別子（例: メールアドレス）が必要
- **ログ/監査**: API呼び出しはCloudTrail等で記録される（一般的なAWS APIの挙動に準拠）。監査ログとして利用可能です
- **コスト**: これら管理API/コンソール操作自体に特別な料金が発生する可能性は低いが、Knowledge BaseやBedrockの利用料、データ転送等の通常コストは発生します
- **運用上の注意**: ACLの変更や検証を行う際は、変更前後の状態を記録し、誤設定による過剰公開を防ぐため最小権限の原則を遵守してください
