## [Bedrock]  OpenAI GPT-6 Astra is now generally available on Amazon Bedrock

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Bedrock
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/openai-gpt-6-astra-on-amazon-bedrock/

### 概要

OpenAIの最新大規模モデル「GPT-6 Astra」がAmazon Bedrockで一般提供開始になりました。最大100万トークンのコンテキストを扱い、より高度な推論・判断・ブラウザ操作・プロ品質の生成をビジネスワークフロー向けに提供します。

### 変更内容・新機能の詳細

GPT-6 Astraは深い推論力、組織の文体やテンプレートに合わせた出力整形、ブラウザやコード操作を含む高度なマルチモーダル/ツール使用能力を持つOpenAIの最上位モデルです。Amazon Bedrockの推論エンジン上で稼働し、BedrockのAPI（コンソールまたはプログラム的なInvoke API等）から直接呼び出せます。特徴として最大1,000,000トークンのコンテキストウィンドウをサポートするため、大量文書の一括解析や長文履歴を必要とするエージェント設計に適しています。ChatGPT WorkやCodexはBedrock上のAstraをバックエンドとして利用可能で、OpenAIからは企業向けChatGPTプラグイン（ブラウザ利用拡張）が提供され、一般的な業務アプリケーションとの連携が強化されています。Bedrock側ではスケール、セキュリティ（IAM、VPCエンドポイント、暗号化）、アクセスガバナンス、CloudTrailによる呼び出し監査といった既存のAWSコントロールが利用できます。詳細な対応リージョン、エンドポイント、API仕様、inference profile（性能/コスト設定）、料金はAmazon Bedrockのドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: AI/MLエンジニア、アプリケーション開発者、SRE/運用、セキュリティ・コンプライアンス担当者、業務部門の高度な自動化ニーズを持つユーザー
- **利用シーンまたは効果**: 自律エージェントの構築、大量文書の横断検索・解析、複雑なソフトウェア不具合の調査、競合する入力を比較して判断が必要な業務プロセス、自動化されたプロ品質の文書・設計生成
- **運用効果**: より少ない手動介入で複雑なタスクを自動化できるため工数削減と品質向上が期待できる
- **コスト影響**: 大容量コンテキストと高性能推論はコスト増につながる可能性があるため、inference profileやバッチ化・キャッシュ戦略で最適化が必要
- **導入の留意点**: ChatGPT WorkやCodex連携を含む統合では追加設定（プラグイン管理、API設定、企業ポリシー適用）が必要

### 技術的な注意点

- **IAM権限**: Bedrockのモデル呼び出しやリソース管理には適切なIAMポリシー（例: bedrock:InvokeModel 等）が必要。最小権限原則でロールを設計してください
- **リージョン制限**: 全リージョンで即時提供されるとは限らないため、利用前にBedrockドキュメントで対応リージョンとエンドポイントを確認してください
- **コスト**: 最大コンテキスト長・高スループット推論は課金が高くなる傾向があります。inference profileや並列度、リクエストあたりのトークン長を監視して最適化してください
- **セキュリティ/データ保護**: 機密データを送信する場合はVPCエンドポイント、KMSによる暗号化、CloudTrailログの有効化、データ保持ポリシーを検討してください。出力の機密情報漏洩リスクに対するガードレール（フィルタリング、ポストプロセッシング）を実装すること
- **性能/レイテンシ**: 100万トークン規模の入力はメモリ・計算負荷およびレイテンシを増大させます。バッチ処理、ストリーミングや部分的な文脈投入など設計上の工夫が必要です
- **モデル出力の品質管理**: 高度な推論能力がある一方で誤情報（hallucination）や望ましくない出力が発生する可能性は残るため、検証ループやルールベースのポストチェックを推奨します
- **互換性/統合**: ChatGPT WorkやCodexと連携する場合は各サービス側の設定（プラグイン管理、エンタープライズ設定）を確認してください
- **コンプライアンス**: データ主権や業界規制の要件がある場合は、モデル呼び出しの送信先リージョンやログ保管先を確認し、必要に応じて法務/コンプライアンスチームと調整してください

## [Timestream] Amazon Timestream for InfluxDB 3 now supports custom plugins

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Timestream
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/timestream-influxdb-custom-plugins/

### 概要

Amazon Timestream for InfluxDB 3がカスタムPythonプラグインの実行をサポートしました。管理されたInfluxDB 3（Core/Enterprise）上でリポジトリに置いたプラグインを実行し、データ処理をDB近傍で完結できます。

### 変更内容・新機能の詳細

今回のアップデートにより、ユーザーが管理する公開/プライベートリポジトリに格納したPythonプラグインを、Timestream for InfluxDBの処理エンジンがトリガーに応じて取得・実行できるようになりました。プラグインは既存の処理エンジンがサポートするトリガータイプ上で動作し、データ変換、アラート生成、集約、外部サービスとの連携などのワークロード固有ロジックをデータベース側で実行可能にします。実行環境は管理されたPythonランタイムで、標準ライブラリとAmazonが検証したパッケージ群が含まれており、任意の外部インフラを立てずに処理を移譲できます。導入手順は、DBパラメータグループにプラグインリポジトリを設定しそれをクラスターに適用、influxdb3 CLIまたはHTTP APIでプラグイントリガーを作成する流れです。プライベートリポジトリへは、AWS Secrets Managerに格納したトークンで認証します。機能はAmazon Timestream for InfluxDBが利用可能な全リージョンで提供されています。

### 影響範囲・利用シーン

- **対象ユーザー**: InfluxDB 3 を運用するアプリケーション開発者、データエンジニア、SRE/運用チーム
- **利用シーンまたは効果**: データ受信時のカスタム変換・集約・アラート生成をDB側で実行し、別途ETLパイプラインや外部関数基盤を構築せずに遅延・運用コストを削減
- **運用効果**: ネットワーク往復や外部サービス運用を減らし、処理をデータに近い場所で実行することでレイテンシ削減と運用負荷の軽減が期待できる
- **開発効果**: Pythonで既存の処理ロジックを移植しやすく、デプロイはリポジトリ＋パラメータグループ＋トリガーの組合せで簡素化
- **リージョン影響**: Amazon Timestream for InfluxDB が利用可能な全リージョンで利用可能

### 技術的な注意点

- **IAM権限**: プラグインの操作やリポジトリ参照、Secrets Manager参照などに必要なIAM権限を事前に設定してください（例: SecretsManager:GetSecretValue、Timestream/InfluxDB 管理権限）
- **リージョン制限**: 機能はTimestream for InfluxDB提供リージョンで利用可能ですが、対象リージョンを事前に確認してください
- **コスト**: プラグイン機能自体の明示的な追加料金は記事に記載されていませんが、実行によるクラスターのCPU/メモリ利用増加、Secrets Manager利用料、データ転送などがコストに影響します
- **リポジトリ/認証**: プライベートリポジトリはAWS Secrets Managerに格納したトークンで認証します。リポジトリ設定はDBパラメータグループで管理されます
- **実行環境制約**: 実行は管理されたPython環境（標準ライブラリ＋Amazon検証済みパッケージ）で行われます。ネイティブ拡張(.so/.dll)やOSレベルの追加パッケージ、任意の非検証パッケージが利用できない可能性があるため、依存関係は事前に確認してください
- **デプロイ手順**: 1) DBパラメータグループにプラグインリポジトリを設定 2) そのパラメータグループをクラスターに適用 3) influxdb3 CLIまたはHTTP APIでトリガーを作成（プライベートリポジトリの場合はSecrets Managerのトークンを指定）
- **デバッグ/ログ**: 実行ログやエラーの扱い（CloudWatch連携等）の詳細はドキュメントで確認してください。ローカルでの動作検証と十分なロギング実装を推奨します

## [SageMaker] Amazon SageMaker Feature Store now supports individual feature updates to lower write latency

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: SageMaker
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/08/sgm-feature-store-update-record/

### 概要

Amazon SageMaker Feature Storeがレコード内の個別フィーチャー更新（feature-level writes）に対応しました。これによりレコード全体を書き換えずに特定のフィーチャーだけを更新でき、書き込みレイテンシとコストを低減できます。

### 変更内容・新機能の詳細

新機能では、Feature StoreのランタイムAPIを通じて単一リクエストでレコード内の一つまたは複数のフィーチャーのみを更新できます。従来の「read-modify-write」パターン（レコードを読み出して変更し、全体を再書き込みする処理）を置き換えられるため、必要なフィーチャーだけを書き換え、それ以外は変更せずに残ります。これにより書き込み量とデータ転送が削減され、書き込み遅延が低下します。複数パイプラインが同じFeature Groupへ書き込む場面では、各パイプラインが自分の算出するフィーチャーだけを更新できるため、ストリーミング処理と夜間バッチ処理が同一レコードを独立して更新可能です。高スループットで単一フィーチャーを更新する用途に適しており、データ取り込みパイプラインにマージロジックを組み込む必要がなくなります。なお、この機能はFeature Storeが利用可能な全リージョンで提供されています。

### 影響範囲・利用シーン

- **対象ユーザー**: データサイエンティスト、機械学習エンジニア、データエンジニア、SRE/運用チーム
- **利用シーン**: ストリーミングジョブとバッチジョブが同一レコードの異なるフィーチャーを更新するケース、単一フィーチャーを高頻度で更新するオンライン/バッチ推論パイプライン
- **運用効果**: 書き込みレイテンシの低減、不要なレコード全体の再書き込みの削減によるコスト削減、パイプライン間のマージロジック削減により運用複雑性の低下

### 技術的な注意点

- **IAM権限**: Feature Store Runtimeの書き込みAPI（例: PutRecord 等）に対する適切なIAM権限を付与してください。既存のポリシーを確認し、必要に応じて更新が必要です。
- **リージョン制限**: 本機能はAmazon SageMaker Feature Storeが利用可能なすべてのリージョンで有効です（リージョンに依存する機能や設定がある場合は事前確認を推奨）。
- **SDK/CLI**: 新しい書き込みオプションを利用するには、最新のAWS SDK（boto3等）／AWS CLIにアップデートしておくと確実です。
- **整合性と競合**: 各書き込みはリクエストで指定したフィーチャーのみを更新しますが、同一フィーチャーに対する同時更新の競合解決（最後の書き込みが勝つ、タイムスタンプ管理など）については、ワークフロー設計時に想定して検証してください。
- **コスト**: 個別フィーチャー更新によりデータ量・処理時間が減りコスト削減が見込めますが、APIコール数やストレージ、データ転送の料金は引き続き発生します。負荷パターンに応じて請求影響を評価してください。

## [Govcloud Us] AWS Transform is now available in AWS GovCloud (US-West)

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Govcloud Us
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-transform-govcloud-us-west/

### 概要

AWS Transform が AWS GovCloud (US‑West) リージョンで利用可能になりました。ガバメント機関や規制対象組織が、隔離された環境内で大規模なサーバー移行を計画・実行できるようになります。

### 変更内容・新機能の詳細

AWS Transform は GovCloud (US‑West) にデプロイされ、AWS GovCloud (US) の境界内で動作する環境から大規模なサーバー移行を自動化できるようになりました。サポートされる移行ソースには VMware、ベアメタル、Hyper‑V、データベースワークロードが含まれ、サーバーのレプリケーション（複製）とカットオーバーを自動化して、手作業や人的リスクを低減します。今回のリージョンローンチでは、移行先として AWS GovCloud (US‑East) と AWS GovCloud (US‑West) の両方が選択可能です。一方で、モダナイゼーション（近代化）、カスタム変換、アセスメント機能はこの GovCloud リージョンには含まれておらず、これらの機能は引き続き商用のサポート対象リージョンで提供されます。GovCloud の隔離された運用境界により、連邦機関や防衛関連、その他の規制産業が敏感データや規制対象ワークロードを移行する際のコンプライアンス要件に対応しやすくなります。

### 影響範囲・利用シーン

- **対象ユーザー**: 連邦機関、政府系組織、国防関連企業、HIPAA/FISMA/ITAR 等の規制対象業務を扱う組織
- **利用シーンまたは効果**: GovCloud 内でのサーバー移行自動化（VMware/ベアメタル/Hyper‑V/DB）により、大規模移行プロジェクトの複雑さと手作業を低減
- **運用効果**: レプリケーションとカットオーバーの自動化でダウンタイムと人的ミスを減らし、移行リスクの低減とスピードアップを実現
- **制約**: モダナイゼーションやカスタム変換、評価機能は GovCloud では未提供のため、移行後のアプリケーション近代化や詳細な評価は商用リージョンで行う必要がある

### 技術的な注意点

- **IAM権限**: AWS Transform を使用するために必要な IAM ロール/ポリシー（レプリケーション/EC2作成/ネットワーク設定等）を事前に設定してください
- **リージョン制限**: AWS Transform の GovCloud 展開は GovCloud (US‑West) に限定され、モダナイゼーションやアセスメント機能は商用リージョンのみで提供されます。移行先は GovCloud (US‑East) と GovCloud (US‑West) のみサポート
- **エージェント/アクセス要件**: ソースサーバ（VMware ホストや物理サーバ、Hyper‑V、DB）への管理アクセスや、必要に応じてレプリケーション用エージェントの導入が必要です。ネットワーク経路とファイアウォール設定を確認してください
- **ネットワーク/セキュリティ**: GovCloud の隔離ポリシーに従い、VPC、サブネット、NACL、セキュリティグループの設定と KMS キー管理など暗号化要件を整備する必要があります
- **コスト**: レプリケーション用のインスタンス、データ転送、ストレージ（スナップショット/複製ストレージ）などの追加コストが発生します。見積もりとコスト管理を事前に検討してください
- **互換性**: 一部の移行パスやデータベースの特殊構成は追加作業が必要になる場合があります。商用リージョンでのみ提供される変換ツールや評価ツールに依存するシナリオは別途計画が必要です

## [API Gateway] Amazon API Gateway now supports mutual TLS for backend integrations

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: API Gateway
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-api-gateway-mutual-tls-backend/

### 概要

Amazon API Gateway（REST API）は、バックエンドとのTLSハンドシェイクでクライアント証明書（ACMで管理された証明書）を提示できるようになり、API Gateway→バックエンド間での相互TLS（mTLS）をサポートします。これにより、クライアント→APIおよびAPI→バックエンドの双方で相互認証を適用できます。

### 変更内容・新機能の詳細

従来、API Gatewayは統合先（バックエンド）に対して自身で生成した自己署名証明書のみを提示していました。本リリースにより、AWS Certificate Manager（ACM）で管理される証明書（外部PKIからインポートした証明書、またはAWS Private Certificate Authorityで発行された証明書）をAPI Gatewayのバックエンド統合に使用できるようになりました。
- 動作: API GatewayはTLSハンドシェイク時にACMの証明書を提示し、バックエンドはその証明書を検証して接続元が期待するAPIであることを確認できます。
- 証明書管理: 証明書をACMにインポートするか、ACM PCAで発行可能。ACM内で証明書が再インポート／更新（更新や自動更新）されると、API Gatewayは再デプロイ不要で自動的に更新を伝播します（ダウンタイムなし）。
- 適用範囲: REST APIのバックエンド統合に対する機能で、API Gatewayのコンソール、AWS CLI、CloudFormationから設定可能です。
- セキュリティ領域: 金融、医療、ゼロトラスト／規制対応が必要な環境で、クライアント→API、API→バックエンドの両方における相互TLSを実現できます。

### 影響範囲・利用シーン

- **対象ユーザー**: API設計者、セキュリティエンジニア、SRE、金融/医療など規制環境で運用するシステム担当者
- **利用シーン**: クライアント→APIとAPI→バックエンドの両方向で相互TLSを適用してエンドツーエンドの相互認証を実現するケース（例: バンキングAPI、医療データ連携、ゼロトラストアーキテクチャ）
- **運用効果**: バックエンドが接続元APIの真正性をTLSレイヤで検証できるため、中間者攻撃や不正なサービスからの接続を低減し、セキュリティポスチャ向上およびコンプライアンス対応が容易になる
- **導入障壁**: ACMへの証明書導入（またはPCAの導入）とバックエンド側でのクライアント証明書検証設定が必要になるため、証明書ライフサイクル管理の運用が必要
- **可用性影響**: 証明書更新はAPI Gatewayが自動伝播するため、証明書更新によるダウンタイムは基本的に発生しない

### 技術的な注意点

- **対応APIタイプ**: 現時点ではREST APIのバックエンド統合に対する機能です。HTTP APIやWebSocket APIでのサポート状況は個別確認が必要です
- **ACM所在リージョン**: ACMで管理する証明書はAPI Gatewayが配置されたリージョンのACMで扱う必要があります（リージョン特有の証明書スコープに注意）
- **バックエンド設定**: バックエンド（統合先）はクライアント証明書の検証を行うよう設定する必要があります。CAチェーンをバックエンドの信頼ストアに登録する等の設定が前提です
- **証明書形式**: 証明書はACMでサポートされる形式である必要があります（一般的にはPEM等）。外部PKIからのインポートはACMの手順に従ってください
- **権限/IAM**: API GatewayとACM操作のために適切なIAM権限（apigateway:PATCHなどAPI Gatewayの設定権限、acm:ImportCertificate/DescribeCertificate/GetCertificate/RequestCertificateなど）が必要です
- **CloudFormation/CLI**: コンソールのほかAWS CLIおよびCloudFormationから設定可能です。CloudFormationテンプレートでの設定フィールドはドキュメントで確認してください

## [General] Amazon Bedrock AgentCore Memory now supports direct ingestion to long-term memory

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/agentcore-memory-direct-ingest

### 概要

Amazon Bedrock AgentCore Memoryは、短期メモリイベントを作成せずに直接長期メモリ向けにコンテンツを投入できるIngestData APIを公開しました。これにより長期メモリの抽出パイプラインを短期メモリに依存せずに利用できます。

### 変更内容・新機能の詳細

IngestData APIは会話型ペイロード（USER/ASSISTANTロールを持つメッセージ）およびJSONペイロード（振る舞いイベント、アクティビティログ、システムイベントなど）を受け取り、AgentCoreに設定された長期メモリ抽出戦略へファンアウトして長期メモリレコードを生成します。従来はコンテンツを一旦短期メモリイベントとして保存してから抽出処理を行う必要がありましたが、IngestDataはその中間イベント作成を不要にします。オプションのメタデータもCreateEventと同じ抽出パイプラインに流され、処理後はListMemoryRecordsやRetrieveMemoryRecordsで結果確認が可能です。リアルタイム通知はKinesisでストリーミングでき、抽出失敗はListMemoryExtractionJobs経由でリドライブ（再処理）できます。IngestDataはAgentCore MemoryがサポートされるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: LLMアプリ開発者、データエンジニア、SRE/運用チーム
- **利用シーン**: 会話履歴やアクティビティログを短期イベントに残さず直接長期知識ベースへ取り込みたいケース（カスタム長期記憶、パーソナライズ、検索強化など）
- **運用効果**: 短期メモリの管理不要によりパイプラインが簡素化され、長期メモリ抽出の導入を短期メモリ実装から切り離して進められる
- **導入効果**: 不要な短期イベントの保存を省略でき、短期ストレージやイベント管理の負荷が低減される一方で長期レコードのストレージと抽出処理コストは発生する

### 技術的な注意点

- **IAM権限**: IngestDataおよび関連の読み取り（ListMemoryRecords、RetrieveMemoryRecords、ListMemoryExtractionJobs）とKinesis書き込みの権限が必要です。詳細なAPI権限はドキュメントを確認してください。
- **リージョン制限**: AgentCore Memoryがサポートされるすべてのリージョンで利用可能と明記されていますが、利用前に対象リージョンでAgentCore Memoryが有効か確認してください。
- **コスト**: 長期メモリレコードのストレージ、抽出処理（抽出ジョブ）およびKinesisストリーミングの利用に対する課金が発生します。短期イベント未作成により短期ストレージ費用は削減されますが、トータルコストはワークロードに依存します。
- **ペイロード/データ管理**: 会話型（USER/ASSISTANT）および汎用JSONを受け入れますが、ペイロードサイズ制限やフォーマット要件はドキュメントで確認してください。個人情報や機密データを送信する場合はデータ保護と暗号化方針を遵守してください。
- **可観測性とエラーハンドリング**: 抽出結果はListMemoryRecords/RetrieveMemoryRecordsで確認可能。抽出失敗はListMemoryExtractionJobsで検出・リドライブできます。リアルタイム通知はKinesisを利用するため、ストリームの可用性や遅延も考慮してください。
- **移行/互換性**: 既存のCreateEventベースのフローと並行運用が可能で、必要に応じて短期イベントベースの処理から段階的に切り替えられます。
- **運用上の制限**: APIレート制限やジョブキューの挙動、処理遅延の特性は環境に依存するため、スケールテストを推奨します。

## [General] AWS HealthOmics introduces resource fallback order for WDL workflows 

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/aws-healthomics-resourcefallback-wdl/

### 概要

AWS HealthOmicsがWDLワークフロー向けに「resource fallback」ディレクティブを導入しました。優先するアクセラレータ（GPU/その他）を順序付けし、最終的にCPUにフォールバックする設定が可能になり、アクセラレータ不足での再実行を減らせます。

### 変更内容・新機能の詳細

resource fallbackディレクティブは、WDLタスクごとに優先するアクセラレータの順序付きリストを定義できる機能です。各アクセラレータ（プロファイル）には検索のためのタイムアウトを個別に設定でき、HealthOmicsは指定順にアクセラレータを探索します。指定したアクセラレータが利用できない場合でも、ユーザーがジョブを再提出することなく自動的に次の候補へ移行します。最後の候補としてCPUプロファイルを含めることで、アクセラレータが全て確保できない状況でもインスタンス確保の可能性を高められます。タイムアウトを短く設定すればフォールバックを素早く進められ、長く設定すれば優先アクセラレータを確保できる確率が上がります。機能は以下のリージョンで利用可能です：US East (N. Virginia, Ohio)、US West (Oregon)、Europe (Frankfurt, Ireland, London)、Israel (Tel Aviv)、Asia Pacific (Seoul, Singapore, Tokyo)。詳細はAdvanced Resource Configurationのドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: 研究者、バイオインフォマティクスエンジニア、パイプライン運用者、SRE
- **利用シーンまたは効果**: GPUや専用アクセラレータに依存する解析ジョブで、アクセラレータ不足によるジョブ再提出や長時間待機を減らし、プロダクションワークフローの継続稼働を実現
- **運用効果**: 自動フォールバックにより手動介入とデバッグ時間が削減され、スループットの向上と安定稼働が期待できる

### 技術的な注意点

- **IAM権限**: ワークフロー定義やリソースプロファイルの変更に必要なHealthOmics関連の権限を事前に確認してください（編集/更新権限が必要）
- **リージョン制限**: 本機能は記事で列挙されたリージョンで利用可能です。その他のリージョンでは未対応の可能性があります。各アクセラレータの可用性はリージョン/インスタンスタイプ依存です
- **コスト**: フォールバック先（特にCPU）での実行は処理時間が延びる可能性があり、その分コストが増加します。長いタイムアウトは待機時間を増やし完了までの遅延要因になります
- **ランタイム影響**: 優先アクセラレータを待つ時間はワークフローの総所要時間に影響します。タイムアウトの調整でトレードオフを設計してください
- **互換性**: WDLワークフローで指定して使用する形式となるため、使用中のWDLバージョンとHealthOmicsのリソース設定仕様を確認してください
- **その他運用上の注意**: アクセラレータの在庫やService Quotas、組織の制限（アカウントレベルのインスタンス上限）を考慮し、事前に検証環境で挙動を確認してください
- **HIPAA**: HealthOmicsはHIPAA適格サービスですが、ワークフローの運用にあたっては組織側のコンプライアンス設定を継続して確認してください
