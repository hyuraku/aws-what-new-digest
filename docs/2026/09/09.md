## [Aiml] Amazon Bedrock Managed Knowledge Base now supports Confluence Data Center as a native data source connector

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Aiml
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-bedrock-managed-knowledge-base-confluence-data-center-native-data-source-connector/

### 概要

Amazon Bedrock Managed Knowledge BaseがConfluence Data Centerをネイティブなデータソースコネクタとしてサポートしました。セルフホストのConfluence Data Center上のページやブログ記事を直接クロールしてBedrockのマネージド知識ベースへ取り込めます。

### 変更内容・新機能の詳細

新しいConfluence Data Centerコネクタは、従来必要だったカスタムな取り込みパイプラインを不要にします。ユーザーはConfluenceインスタンスの認証情報を提供するだけで、コネクタがページ／ブログのクロール、メタデータ抽出、インクリメンタル同期（差分取り込み）を自動で実行します。クロールはスペースやコンテンツ種別でフィルタリングでき、必要なコンテンツだけを知識ベースに取り込むことで無駄なデータ蓄積とコストを抑制します。取り込まれたConfluenceの情報は、Bedrock上のRAG（retrieval-augmented generation）エージェントや内部アシスタントの根拠資料として利用でき、エンジニアリングドキュメント、ランブック、チームナレッジの活用を容易にします。

### 影響範囲・利用シーン

- **対象ユーザー**: Confluence Data Centerをセルフホストで運用している企業、社内向けAIアシスタントやRAGシステムを構築する開発チームやナレッジマネジメント担当者
- **利用シーン**: エンジニア向けドキュメント検索、運用ランブックに基づくチャットボット、社内FAQや手順書を根拠にした生成応答
- **運用効果**: カスタムインジェスト開発工数の削減、インクリメンタル同期による再取り込みコスト低減、フィルタで不要データを除外して知識ベースを集約・最適化

### 技術的な注意点

- **IAM権限**: Bedrock Managed Knowledge Baseの作成・更新やコネクタ操作に必要なAWS権限を付与してください（詳細はユーザーガイド参照）。Confluence側の認証情報管理はSecrets Managerなどを利用することを推奨します。
- **リージョン制限**: Bedrock Knowledge Bases自体や本コネクタの提供リージョンは限定される可能性があります。導入前に対象リージョンでのサポート状況を確認してください。
- **コスト**: データ取り込み、ストレージ、検索／リトリーバルの利用料金が発生します。インクリメンタル同期やフィルタを使って取り込むデータ量を制御することでコスト抑制が可能です。
- **ネットワーク／認証**: セルフホストのConfluenceに対してコネクタがアクセスできるネットワーク経路が必要です（パブリックアクセス、VPN、VPC接続、プロキシ経由など）。アクセス許可やIP制限、証明書の設定等を確認してください。
- **データガバナンス**: 取り込むコンテンツに機密情報や個人情報が含まれる場合、アクセス制御や監査、暗号化方針を事前に整備してください。取り込みフィルタと削除ポリシーを活用して不要情報の流入を防止してください。
- **同期挙動**: コネクタはメタデータ抽出とインクリメンタル同期を行いますが、同期間隔や一回のクロールで処理する量の上限など運用上の制約がある可能性があります。大量データ移行時は設計を検討してください。

## [Elastic Block Store] Amazon EBS Volume Clones now supports copying volumes across accounts

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Elastic Block Store
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/ebs-volume-clones-cross-account-copy/

### 概要

Amazon EBS Volume Clonesがアカウント間でのEBSボリュームのコピー（再暗号化）をサポートしました。ターゲットアカウントのAWS KMSキーで再暗号化して異なるAWSアカウントへボリュームを複製できます。

### 変更内容・新機能の詳細

新機能では、ソースアカウントのEBSボリュームをAWS Resource Access Manager (AWS RAM)でターゲットアカウントと共有し、ターゲット側で同じアベイラビリティゾーン内にコピーを作成するワークフローを提供します。コピー作成時にターゲットアカウントのAWS KMSキーを指定して再暗号化できるため、プロダクションと開発でKMSキーを分離した運用（キー分離ポリシー）に対応します。全てのボリュームタイプ（未暗号化、AWS管理暗号、カスタマーマネージドキーで暗号化されたボリュームを含む）でサポートされ、AWS マネジメントコンソール、AWS CLI、AWS SDKから利用可能です。リージョンは、EBS Volume Clonesをサポートするすべてのリージョン（商用リージョン、AWS GovCloud (US)、中国リージョン、対応するローカルゾーン等）で利用できます。実運用では、例として本番データベースのボリュームを分離した開発アカウントに複製して開発・検証用に使う、あるいは本番/非本番で別々のKMSキーを維持する必要のある組織に役立ちます。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウドエンジニア、SRE、開発チームやセキュリティ/コンプライアンス担当者
- **利用シーン**: 本番ボリュームを分離した開発/検証アカウントに安全にコピーして再現環境を作る、あるいは環境ごとにKMSキーを分離してセキュリティ要件を満たす
- **運用効果**: アカウント境界を越えた安全なデータ複製により開発の迅速化とキー管理分離が可能に。手動でのスナップショットエクスポートや複雑なキー共有作業を削減できる

### 技術的な注意点

- **IAM権限**: AWS RAMでの共有受諾（ram:AcceptResourceShareInvitation等）と、ターゲット側でのEBSコピー作成に必要なEC2/EBS権限を事前に付与してください。また、コピー後に指定するターゲットKMSキーを利用するためのkms:Encrypt/kms:GenerateDataKey権限が必要です。
- **KMS権限**: ターゲットアカウントのKMSキーは該当アカウントのIAM主体が利用できるようキー ポリシーおよびIAMポリシーを設定してください。ソースがカスタマーマネージドキーで暗号化されている場合でも本機能で再暗号化されますが、万一のアクセスエラーに備えソース側のKMSポリシーも確認してください。
- **AWS RAM**: まずソースアカウントでボリュームをAWS RAMで共有し、ターゲットアカウントが共有を受諾する必要があります。共有可能なリソースタイプや許可設定を確認してください。
- **アベイラビリティゾーン制約**: コピーは同じアベイラビリティゾーン内で作成されます。ターゲットアカウント側に同一AZでのリソース作成余裕（容量・サブネット等）が必要です。
- **対応ボリューム**: 未暗号化ボリューム、AWS管理キー暗号化、カスタマーマネージドキーで暗号化されたボリュームのいずれもサポートされます。コピー時にターゲットKMSキーで暗号化（あるいは未暗号化のまま）設定可能です。
- **リージョン制限**: EBS Volume Clonesをサポートするリージョンで利用可能です。リージョン未対応の場合は利用できません。
- **コスト**: EBSボリュームのストレージ料金、EBSのコピー/クローンに関連する通常の料金、及びKMSの利用料金が発生する可能性があります。リージョン間コピーでは追加料金や転送コストが別途発生する場合があります（本機能は同リージョン・同AZコピーが前提）。
- **利用方法**: AWS マネジメントコンソール、AWS CLI、AWS SDKで操作可能。手順は「ソースで共有」→「ターゲットで共有受諾」→「ターゲットでコピー作成（KMS指定）」の順です。
- **その他**: コピー後はターゲットアカウント内の通常のEBSボリュームとして扱えます。セキュリティ上の懸念があるデータは事前にマスキングやマスキング自動化を検討してください。

### 参考情報

- https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ebs-volume-clones.html

## [EKS] AWS Private CA EKS add-on and Connector for AD now available in AWS GovCloud (US)

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: EKS
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/private-ca-eks-addon-ad-govcloud/

### 概要

AWS Private CAのKubernetes用コネクタがAmazon EKSのマネージドアドオンとして、またActive Directory用コネクタがAWS GovCloud (US-East/US-West)で利用可能になりました。政府機関向けワークロードで証明書発行・配布・更新の自動化が可能になります。

### 変更内容・新機能の詳細

・EKSアドオン（AWS Private CA Connector for Kubernetes）: EKSコンソール/CLI/APIからの簡易インストールとライフサイクル管理に対応するマネージドアドオンとして提供されます。cert-managerと連携して、AWS Private CAへ証明書要求を行い、Kubernetes Secretへ配布・自動更新を実現します。これによりIngressコントローラのTLS有効化やIstio/Linkerdなどのサービスメッシュ内のサービス間通信の保護が容易になります。
・Active Directoryコネクタ（AWS Private CA Connector for Active Directory）: AWS GovCloudの環境で、Active Directoryに参加しているユーザー/コンピュータ/オブジェクト向けにAWS Private CAを証明機関として自動発行させる機能を提供します。既存のMicrosoft証明書登録インターフェース（自動登録/グループポリシー/テンプレート）と連携し、スマートカード認証、LDAPS、802.1Xなど企業向けユースケースをサポートします。
・セキュリティ: AWS Private CAは秘密鍵をFIPS 140-3 レベル3準拠のHSMで保護します。
・対象リージョン: AWS GovCloud (US-East) および AWS GovCloud (US-West) にて利用可能。

### 影響範囲・利用シーン

- **対象ユーザー**: 政府機関や規制対応が必要な組織のクラウド運用者、セキュリティ／基盤チーム、Kubernetesプラットフォームエンジニア
- **利用シーン**: EKS上のIngressやサービスメッシュでのTLS自動化、Active Directoryに参加するデバイスやユーザーへの自動証明書発行（スマートカード、LDAPS、802.1X等）
- **運用効果**: 証明書の手動管理を削減し、証明書発行・配布・更新の自動化によりダウンタイムや人的ミスを低減。コンプライアンス要件のある環境で一貫した証明書管理が可能

### 技術的な注意点

- **IAM権限**: EKSでのアドオン管理やPrivate CA操作に必要なIAM権限（eks:AssociateAddon/eks:UpdateAddon、acm-pca関連権限など）を事前に確認・付与してください
- **cert-manager要件**: Kubernetes側では互換性のあるcert-managerのインストールと適切なCRD/RBAC設定が必要です。サポートするcert-managerのバージョンを確認してください
- **Active Directory連携**: AD側での自動登録設定（証明書テンプレート、グループポリシー、自動登録権限）や、コネクタがADに接続可能なネットワーク経路（VPN/Direct Connect/同一VPCなど）を確保する必要があります
- **ネットワークとポート**: AD連携や証明書配布に必要なポート（LDAPS等）やファイアウォール設定を確認してください
- **リージョン制限**: 現時点では AWS GovCloud (US-East) および AWS GovCloud (US-West) のみで利用可能です。他リージョンでは未提供の場合があります
- **コスト**: AWS Private CAの管理費用および発行ごとの料金、EKSクラスターやデータ転送等の通常のAWSリソースコストが発生します。アドオン自体に追加料金がかからないケースでも基盤サービスの料金に注意してください

## [Ec2] AWS Systems Manager now diagnoses more issues that cause EC2 instances to be unmanaged

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Ec2
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/systems-manager-diagnoses-ec2-unmanaged/

### 概要

AWS Systems Managerの診断機能が拡張され、これまでのネットワーク接続診断に加えて、EC2インスタンスおよびハイブリッドでアクティベートしたノードがSystems Managerにより“managed”にならない原因を追加で6カテゴリ特定できるようになりました。これにより、未管理状態の原因をより具体的に把握して早期に対処できます。

### 変更内容・新機能の詳細

従来はネットワーク接続に関する診断のみを提供していましたが、今回の拡張で以下の6つのカテゴリを新たに診断できます：IAM権限、SSM Agentのバージョン、インスタンスのステータスチェック（system/instance reachabilityなど）、OS設定（ファイアウォールやサービス状態など）、Default Host Management Configuration（ホスト管理の既定設定）、およびハイブリッドアクティベーション（オンプレミスや他クラウドでのマネージドインスタンス登録）。

診断はSystems Managerの統合コンソールから実行し、各カテゴリごとに特定された問題をレポートします。各診断結果にはステップバイステップの修復手順が付属し、一部の問題についてはコンソール上から直接Automationランブックを実行して自動で修復できます。診断処理自体はSystems Manager Automationランブックとして実行されるため、Automationの通常課金が適用されます。機能はデフォルトで有効になっているすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: クラウド/ハイブリッド環境のインフラ運用者、SRE、セキュリティ/コンプライアンス担当者
- **利用シーンまたは効果**: 未管理（unmanaged）状態のEC2インスタンスやハイブリッドノードの原因特定と迅速な復旧（パッチ適用、Run Command、Session Manager接続、インベントリ収集の再開）
- **運用効果**: 原因が特定しやすくなることで対応時間が短縮され、Fleet全体をより速くSystems Managerで一元管理できるようになる

### 技術的な注意点

- **IAM権限**: 診断とAutomation実行にはSystems ManagerとAutomationを実行するためのIAM権限（ssm:Describe*, ssm:SendCommand, automation:StartAutomationExecution等）および必要に応じたEC2権限が必要です。ターゲットインスタンスのIAMインスタンスプロファイル（例: AmazonSSMManagedInstanceCore）も正しく設定されていることを確認してください。
- **SSM Agent/OS要件**: SSM Agentのバージョン互換性やサービス起動状態、OS設定（ファイアウォール、SELinux等）が診断対象になります。Agentのアップデートや修復はインターネットアクセスまたは必要なエンドポイント（S3やSSMエンドポイント）へのアクセスが必要です。
- **ネットワーク/エンドポイント**: 診断はネットワーク接続問題も引き続き検出します。VPCエンドポイント（Interface Endpoint）利用時はエンドポイント設定、NAT/プロキシやポリシーでのHTTPS(443)アウトバウンド許可を確認してください。
- **ハイブリッドアクティベーション**: ハイブリッド（オンプレ等）ノードはActivation ID/Codeと有効な状態が必要です。Activationの有効期限や登録状態、SSM Agentの接続状態を確認してください。
- **リージョン制限**: 記事によれば「デフォルトで有効なすべてのAWSリージョン」で利用可能です。GovCloudや中国リージョンなどデフォルト設定と異なるリージョンでは挙動や利用可否が異なる場合があるため事前確認を推奨します。
- **コスト**: 診断はAutomationランブックとして実行されるため、AWS Systems Manager Automationの標準の実行課金が発生します（詳細は料金ページを確認してください）。
- **その他**: 一部の自動修復ランブックはインスタンス上での操作（Agentの再起動、設定変更）を伴うため、運用上の影響（サービス中断等）を考慮して実行してください。

## [Aiml] AWS Entity Resolution adds record-level confidence scores for ML matching

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: Aiml
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/entity-resolution-record-confidence/

### 概要

AWS Entity ResolutionがMLベースのマッチングワークフローでレコード単位の信頼度（confidence）スコアを提供開始しました。個々の解決レコードごとにマッチ品質を評価できるため、差別化したしきい値運用でより多くのレコードを安全にアクティベートできます。

### 変更内容・新機能の詳細

これまではマッチグループ単位の信頼度スコアが全レコードに同一で付与されており、ほぼ確実なマッチと境界的なマッチを区別できませんでした。今回の変更により、MLベースのマッチングワークフローでは各レコードに対して個別の信頼度スコアが付与されます。これにより、自動マージに高い信頼度しきい値を使い、より緩いしきい値で追加のレコードをアクティベートするなど、用途ごとに差別化したポリシー運用が可能になります。インクリメンタルMLワークフローを利用している場合は、既存のRecordConfidenceLevel列がレコード単位のスコアを反映するように更新され、スキーマ変更は不要です。レコード単位のスコアは監査可能なエビデンスとして保持され、コンプライアンス対応や説明可能性（explainability）の向上にも寄与します。本機能はAWS Entity Resolutionが利用可能なリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: データエンジニア、CDP/マーケティングチーム、CRM運用者、データガバナンス/コンプライアンス担当者
- **利用シーン**: 顧客レコードの重複解決（同一人物マージ）、アドレス可能オーディエンスの拡大、リード管理、カスタマー360の統合
- **運用効果**: レコードごとのスコアに基づき高信頼レコードは自動マージ、低めのしきい値で追加レコードをアクティベートすることでアクティベーション対象を拡大し、リード変換率や到達率を改善できる
- **監査・説明性**: 各レコードに証拠となる信頼度が残るため、監査対応や外部説明（内部監査・規制対応）が容易になる

### 技術的な注意点

- **適用範囲**: MLベースのマッチングワークフローに対して提供されます（ルールベース/決定的マッチングの挙動については個別に確認してください）
- **スキーマ互換性**: インクリメンタルMLワークフローでは既存のRecordConfidenceLevel列がレコード単位スコアを反映するため、スキーマ変更は不要です
- **IAM権限**: Entity Resolutionのワークフロー実行や結果参照に必要なIAM権限を事前に確認・付与してください（ワークフロー実行・読み取り権限など）
- **リージョン制限**: AWS Entity Resolutionが利用可能な全リージョンで利用可能です。対象リージョンでのサービス提供状況は公式リージョン一覧で確認してください

## [API Gateway] Amazon API Gateway now supports mutual TLS for backend integrations

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: API Gateway
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/amazon-api-gateway-mutual-tls-backend/

### 概要

Amazon API Gateway（REST API）は、バックエンドとのTLSハンドシェイクでクライアント証明書（ACMで管理された証明書）を提示できるようになり、API Gateway→バックエンド間での相互TLS（mTLS）をサポートします。これにより、クライアント→APIおよびAPI→バックエンドの双方で相互認証を適用できます。

### 変更内容・新機能の詳細

従来、API Gatewayは統合先（バックエンド）に対して自身で生成した自己署名証明書のみを提示していました。本リリースにより、AWS Certificate Manager（ACM）で管理される証明書（外部PKIからインポートした証明書、またはAWS Private Certificate Authorityで発行された証明書）をAPI Gatewayのバックエンド統合に使用できるようになりました。
- 動作: API GatewayはTLSハンドシェイク時にACMの証明書を提示し、バックエンドはその証明書を検証して接続元が期待するAPIであることを確認できます。
- 証明書管理: 証明書をACMにインポートするか、ACM PCAで発行可能。ACM内で証明書が再インポート／更新（更新や自動更新）されると、API Gatewayは再デプロイ不要で自動的に更新を伝播します（ダウンタイムなし）。
- 適用範囲: REST APIのバックエンド統合に対する機能で、API Gatewayのコンソール、AWS CLI、CloudFormationから設定可能です。
- セキュリティ領域: 金融、医療、ゼロトラスト／規制対応が必要な環境で、クライアント→API、API→バックエンドの両方における相互TLSを実現できます。

### 影響範囲・利用シーン

- **対象ユーザー**: API設計者、セキュリティエンジニア、SRE、金融/医療など規制環境で運用するシステム担当者
- **利用シーン**: クライアント→APIとAPI→バックエンドの両方向で相互TLSを適用してエンドツーエンドの相互認証を実現するケース（例: バンキングAPI、医療データ連携、ゼロトラストアーキテクチャ）
- **運用効果**: バックエンドが接続元APIの真正性をTLSレイヤで検証できるため、中間者攻撃や不正なサービスからの接続を低減し、セキュリティポスチャ向上およびコンプライアンス対応が容易になる
- **導入障壁**: ACMへの証明書導入（またはPCAの導入）とバックエンド側でのクライアント証明書検証設定が必要になるため、証明書ライフサイクル管理の運用が必要
- **可用性影響**: 証明書更新はAPI Gatewayが自動伝播するため、証明書更新によるダウンタイムは基本的に発生しない

### 技術的な注意点

- **対応APIタイプ**: 現時点ではREST APIのバックエンド統合に対する機能です。HTTP APIやWebSocket APIでのサポート状況は個別確認が必要です
- **ACM所在リージョン**: ACMで管理する証明書はAPI Gatewayが配置されたリージョンのACMで扱う必要があります（リージョン特有の証明書スコープに注意）
- **バックエンド設定**: バックエンド（統合先）はクライアント証明書の検証を行うよう設定する必要があります。CAチェーンをバックエンドの信頼ストアに登録する等の設定が前提です
- **証明書形式**: 証明書はACMでサポートされる形式である必要があります（一般的にはPEM等）。外部PKIからのインポートはACMの手順に従ってください
- **権限/IAM**: API GatewayとACM操作のために適切なIAM権限（apigateway:PATCHなどAPI Gatewayの設定権限、acm:ImportCertificate/DescribeCertificate/GetCertificate/RequestCertificateなど）が必要です
- **CloudFormation/CLI**: コンソールのほかAWS CLIおよびCloudFormationから設定可能です。CloudFormationテンプレートでの設定フィールドはドキュメントで確認してください
- **コスト**: ACMへの証明書インポート自体は追加料金が発生しませんが、AWS Private CAを利用して証明書を発行する場合はPrivate CAの月次/発行コストが発生します。運用コスト（証明書ライフサイクル管理）も考慮してください
- **リージョン制限**: REST APIが利用可能なすべての商用リージョンとAWS GovCloud（US）リージョンで利用可能とアナウンスされていますが、利用前に対象リージョンでのサポート状況を確認してください
- **互換性/暗号套件**: バックエンドとAPI Gateway間のTLSバージョンや暗号スイートの互換性を確認してください。必要に応じてバックエンドのTLS設定を調整する必要があります

## [General] Amazon Bedrock AgentCore Memory now supports direct ingestion to long-term memory

- **公開日**: 2026-09-09 (JST)
- **カテゴリ**: General
- **リンク**: https://aws.amazon.com/about-aws/whats-new/2026/09/agentcore-memory-direct-ingest

### 概要

Amazon Bedrock AgentCore Memoryは、短期メモリイベントを作成せずに直接長期メモリ向けにコンテンツを投入できるIngestData APIを公開しました。これにより長期メモリの抽出パイプラインを短期メモリに依存せずに利用できます。

### 変更内容・新機能の詳細

IngestData APIは会話型ペイロード（USER/ASSISTANTロールを持つメッセージ）およびJSONペイロード（振る舞いイベント、アクティビティログ、システムイベントなど）を受け取り、AgentCoreに設定された長期メモリ抽出戦略へファンアウトして長期メモリレコードを生成します。従来はコンテンツを一旦短期メモリイベントとして保存してから抽出処理を行う必要がありましたが、IngestDataはその中間イベント作成を不要にします。オプションのメタデータもCreateEventと同じ抽出パイプラインに流され、処理後はListMemoryRecordsやRetrieveMemoryRecordsで結果確認が可能です。リアルタイム通知はKinesisでストリーミングでき、抽出失敗はListMemoryExtractionJobs経由でリドライブ（再処理）できます。IngestDataはAgentCore MemoryがサポートされるすべてのAWSリージョンで利用可能です。

### 影響範囲・利用シーン

- **対象ユーザー**: LLMアプリ開発者、データエンジニア、SRE/運用チーム
- **利用シーン**: 会話履歴やアクティビティログを短期イベントに残さず直接長期知識ベースへ取り込みたいケース（カスタム長期記憶、パーソナライズ、検索強化など）
- **運用効果**: 短期メモリの管理不要によりパイプラインが簡素化され、長期メモリ抽出の導入を短期メモリ実装から切り離して進められる
- **導入効果**: 不要な短期イベントの保存を省略でき、短期ストレージやイベント管理の負荷が低減される一方で長期レコードのストレージと抽出処理コストは発生する

### 技術的な注意点

- **IAM権限**: IngestDataおよび関連の読み取り（ListMemoryRecords、RetrieveMemoryRecords、ListMemoryExtractionJobs）とKinesis書き込みの権限が必要です。詳細なAPI権限はドキュメントを確認してください。
- **リージョン制限**: AgentCore Memoryがサポートされるすべてのリージョンで利用可能と明記されていますが、利用前に対象リージョンでAgentCore Memoryが有効か確認してください。
- **コスト**: 長期メモリレコードのストレージ、抽出処理（抽出ジョブ）およびKinesisストリーミングの利用に対する課金が発生します。短期イベント未作成により短期ストレージ費用は削減されますが、トータルコストはワークロードに依存します。
- **ペイロード/データ管理**: 会話型（USER/ASSISTANT）および汎用JSONを受け入れますが、ペイロードサイズ制限やフォーマット要件はドキュメントで確認してください。個人情報や機密データを送信する場合はデータ保護と暗号化方針を遵守してください。
- **可観測性とエラーハンドリング**: 抽出結果はListMemoryRecords/RetrieveMemoryRecordsで確認可能。抽出失敗はListMemoryExtractionJobsで検出・リドライブできます。リアルタイム通知はKinesisを利用するため、ストリームの可用性や遅延も考慮してください。
- **移行/互換性**: 既存のCreateEventベースのフローと並行運用が可能で、必要に応じて短期イベントベースの処理から段階的に切り替えられます。
- **運用上の制限**: APIレート制限やジョブキューの挙動、処理遅延の特性は環境に依存するため、スケールテストを推奨します。

AWS HealthOmicsがWDLワークフロー向けに「resource fallback」ディレクティブを導入しました。優先するアクセラレータ（GPU/その他）を順序付けし、最終的にCPUにフォールバックする設定が可能になり、アクセラレータ不足での再実行を減らせます。

### 変更内容・新機能の詳細

resource fallbackディレクティブは、WDLタスクごとに優先するアクセラレータの順序付きリストを定義できる機能です。各アクセラレータ（プロファイル）には検索のためのタイムアウトを個別に設定でき、HealthOmicsは指定順にアクセラレータを探索します。指定したアクセラレータが利用できない場合でも、ユーザーがジョブを再提出することなく自動的に次の候補へ移行します。最後の候補としてCPUプロファイルを含めることで、アクセラレータが全て確保できない状況でもインスタンス確保の可能性を高められます。タイムアウトを短く設定すればフォールバックを素早く進められ、長く設定すれば優先アクセラレータを確保できる確率が上がります。機能は以下のリージョンで利用可能です：US East (N. Virginia, Ohio)、US West (Oregon)、Europe (Frankfurt, Ireland, London)、Israel (Tel Aviv)、Asia Pacific (Seoul, Singapore, Tokyo)。詳細はAdvanced Resource Configurationのドキュメントを参照してください。

### 影響範囲・利用シーン

- **対象ユーザー**: 研究者、バイオインフォマティクスエンジニア、パイプライン運用者、SRE
- **利用シーンまたは効果**: GPUや専用アクセラレータに依存する解析ジョブで、アクセラレータ不足によるジョブ再提出や長時間待機を減らし、プロダクションワークフローの継続稼働を実現
- **運用効果**: 自動フォールバックにより手動介入とデバッグ時間が削減され、スループットの向上と安定稼働が期待できる

### 技術的な注意点

- **IAM権限**: ワークフロー定義やリソースプロファイルの変更に必要なHealthOmics関連の権限を事前に確認してください（編集/更新権限が必要）
- **リージョン制限**: 本機能は記事で列挙されたリージョンで利用可能です。その他のリージョンでは未対応の可能性があります。各アクセラレータの可用性はリージョン/インスタンスタイプ依存です
- **コスト**: フォールバック先（特にCPU）での実行は処理時間が延びる可能性があり、その分コストが増加します。長いタイムアウトは待機時間を増やし完了までの遅延要因になります
- **ランタイム影響**: 優先アクセラレータを待つ時間はワークフローの総所要時間に影響します。タイムアウトの調整でトレードオフを設計してください
- **互換性**: WDLワークフローで指定して使用する形式となるため、使用中のWDLバージョンとHealthOmicsのリソース設定仕様を確認してください
- **その他運用上の注意**: アクセラレータの在庫やService Quotas、組織の制限（アカウントレベルのインスタンス上限）を考慮し、事前に検証環境で挙動を確認してください
- **HIPAA**: HealthOmicsはHIPAA適格サービスですが、ワークフローの運用にあたっては組織側のコンプライアンス設定を継続して確認してください
